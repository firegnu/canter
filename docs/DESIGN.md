# canter 设计

canter 是用户自己做的 coding agent。本文件记已经定下的事和来由；实现中要改设计，先改这份文档。

调研报告在 `docs/调研/R49-自研agent调研.md`，是从 ranch 仓库（`github.com/firegnu/ranch`）的同名文件原样复制来的（2026-10-23）。报告里的 `docs/任务/…`、`crates/corral/…`、DESIGN §7–§10 等路径指 ranch 仓库；`L`、`W` 编号的出处见报告末尾。报告写完后用户又定了几件事，和报告推荐不同的以本文件为准（见下面「和报告不同的地方」）。

## 用户已定的

2026-10-23，用户在 ranch 主控那里定的。

1. **独立，不和 ranch 这一套绑死**：「这个coding agent不需要和ranch/corral/paddock/cairn等绑定死。这样我随时可以在任何terminal中启动。」canter 仓库里不放任何 ranch 的东西；以后要接 corral，由 corral 去适配 canter 的公开接口。 不和任何终端绑定（10-27 用户：「agent不能和任何terminal绑定」「其他的terminal不能崩，这是底线」）：基本功能只用所有终端都认的写法；针对某个终端的效果（如 P2-52 Ghostty 标签上的进度）只能是额外的，要确认真是那个终端才发，别的终端什么都收不到、照常能用。
2. **一台机器一个常驻服务端、多个客户端**：「我要的是一个服务器，多个客户端。主要的考虑是，我肯定会先做tui，然后对接上corral这一套，但是也可以单独发布桌面app」。循环、工具、权限、会话都在服务端；终端界面、桌面应用、网页、corral 都是客户端。
3. **语言 Rust**：服务端和终端客户端用 Rust。用户：「我接受你的建议Rust」。
4. **模型不自研**：「我是想拥有一个自研的agent。model就算了。」
5. **做到什么程度**：「照着调研文档来，但是初步能达到pi我就很满意了」。架构照报告「冲着 Claude Code、Codex 的标准分」，不留死路；第一个目标是能替掉 pi 干日常的活。
6. **模型和账号**：用户有 ChatGPT Pro 订阅和 DeepSeek 的 BYOK（自己的 API key）。第一期两个都接：
   - ChatGPT Pro：经 OpenAI 的「Sign in with ChatGPT」，走 Responses 接口（报告 §4.4）。
   - DeepSeek：API key，走 Chat Completions 接口。
   - 不用 Claude 订阅：「不要查claude的条款，我不会拿claude订阅来做接入自研的agent的」。
   - **2026-10-24 改：第一期只接 DeepSeek。** 用户：「这样，我觉得第一期先不做订阅的接入。就是BYOK」。BYOK 只接 DeepSeek，不接 OpenAI 的 API key。所以第一期只做 Chat Completions 接口，base_url 和 key 可以配置。ChatGPT Pro 登录和 Responses 接口往后放。模型接入层仍按多家来做，以后加 Responses 不用推翻。
   - 跟着改的：第一期改文件用「整文件写 + 按文字替换」；Codex 的 apply_patch 是给 GPT 用的，等接 OpenAI 时再搬（用户 10-24 选定）。
7. **名字和仓库**：`canter`（马的「慢跑」步法），仓库 `github.com/firegnu/canter`，公开，Apache-2.0。用户：「开源，repo就放在github上」。
8. **协议：结构照 Codex，传输和类型 canter 自己定（报告 §5.7 的 C）**。2026-10-24 在 canter 仓库定的，用户：「好，就用 C，改 DESIGN」。
   - 目标续跑（P2-109，10-29 主控和用户确认）：参考 Codex `rust-v0.163.0` 的 ThreadGoal 和目标更新通知，快照增加可选 `goal`，`session.goal.updated {goal}` 保存并广播完整状态（清除为 null）。字段为 `id/objective/status/budgetUsd/cost/createdAt/updatedAt`，`cost` 沿用 `{usd, unknown}`；状态 `active/paused/complete/blocked/budgetLimited`。`GET/POST/DELETE /v1/sessions/{id}/goal` 查询、设置、清除，`POST .../goal/pause` 和 `.../goal/resume` 暂停、继续；信息接口 features 增加 `goals`。旧客户端忽略新增字段和事件，旧会话没有目标。与 Codex 不同：预算按美元，只有用户能建目标，模型仅有 `get_goal` 和 `update_goal {status: complete|blocked}`；续跑轮提问有五分钟超时。
   - 命令规则（P2-108，10-29 主控确认）：批准决定增加字符串 `acceptWithExecpolicyAmendment`；请求增加可选 `proposedExecpolicyAmendment`（词前缀数组的列表），回答增加可选 `execpolicyAmendment`，服务端校验它与提议完全相同。沿用 Codex `rust-v0.163.0` 的命名与提议→确认结构；canter 保留原来的字符串决定枚举，把 amendment 放在回答顶层，并用二维数组支持组合命令一次写多条。请求另带可选 `sessionPrefixes`，明确本会话放行范围。所有新增字段可省略，旧客户端滤掉未知决定，旧会话仍能打开。
   - 加目录（P2-118，10-29 主控确认）：公开会话设置和创建参数新增可选 `additionalDirectories` 字符串数组，旧存盘缺省为空；PATCH 新增可选 `addDirectories`，由服务端追加、规范化、去重，省略或空数组不改变目录，不提供移除。完整列表随 `session.updated` 存盘和广播。沿用 Codex app-server v2 的会话设置和更新结构；Codex 的 `sandboxPolicy` 在 `type: workspaceWrite` 下带 `writableRoots`，canter 的目录同时用于模型环境、文件引用和批准判断，因而单列这两个字段，不引入沙箱策略或把它们称为沙箱可写根。多客户端并发追加在服务端串行处理，不由客户端读出整表再覆盖。`GET /v1/info.features` 增加 `addDirectories`，终端使用新参数或命令前检查支持情况，避免旧服务端忽略字段后误报成功；旧客户端忽略新字段，照常使用。
   - `canter --add-dir <路径>` 可重复，配合 `-c` / `--resume` 加到打开的会话；会话内 `/add-dir <路径>` 提示结果。相对路径按会话 cwd，`~/` 按会话 HOME；必须是存在的目录，规范化后位于 cwd 或已加目录内则提示已覆盖。目录与会话一起保存，不读取新增目录的 `AGENTS.md`。`/new`、`/handoff`、计划批准选「清空上下文实施」的新会话沿用原会话加进来的目录，由服务端重新校验、规范化；失效的目录提示原因后跳过，仍开新会话，旧服务端不支持时不带目录（P2-122）。打开时的目录列入环境段；中途追加说明到模型历史尾部，保持已发送前缀。`@` 同时扫描新增目录、遵循各目录的 git 忽略规则；cwd 下仍用相对路径，额外目录用绝对路径区分同名文件。
   - `askForExecution` 下 write/edit 在 cwd 和新增目录内直接执行，目录外复用文件修改批准框。比较规范化后的真实路径，解析 `..` 和符号链接，新文件以最近存在的父目录解析；读文件、shell 批准、只读白名单、受保护路径、计划模式、审查轮、`alwaysAsk`、`allowAll` 不变。目录外选择 `acceptForSession` 沿用工具名授权（write/edit 各自独立，与 alwaysAsk 一致），不新增按目录授权规则。状态栏 git、`/diff`、`/review` 仍只看 cwd。本件不是沙箱。
   - 模型重试（P2-110，10-28 主控确认）：参考 Codex `rust-v0.163.0` 的 `ErrorNotification`（`error/willRetry/threadId/turnId`），其 `StreamError` 发 `willRetry: true`、不结束轮。canter 新增 `modelRetry` 项目，复用 `item.started/completed`，沿用 `error`、`willRetry`，会话和轮 ID 由既有事件外层携带；增加 `attempt/maxRetries/delaySeconds`，让客户端显示第几次、多久后再试、为什么。做成项目而非只发错误通知，是为了快照、重开、其它终端和导出都保留重试记录；旧客户端按 Unknown 项目跳过。回答和思考项目新增可选 `status: interrupted`，没有字段的旧存盘按正常完成读；只有断流出错重发而丢弃的半截才标 `status: interrupted`，不进入模型历史。用户按 Esc 打断的一切行为照 main 原样，不受本件影响：已收到的半截回答和思考留在模型历史中，已收到但未执行的工具调用照旧补 interrupted 占位结果；界面、存盘、导出均不额外给这些项目加中断标记（10-28 用户：「不能改现在esc的行为，这个破坏太多了」）。逐项完成的信号和项目 ID 是模型层到核心的内部事件，不进入客户端协议。`/btw`、`/handoff` 共用重试，通过各自私有流显示重试和重发后的内容，照旧不存盘、不广播。
   - 经过：用户先说「协议我觉得做好使用成熟的现有的coding agent使用的协议」，选了 Codex app-server 协议，不用 ACP（「ACP我一直不是很看好」）。10-23 用户又提醒「我们选的 Codex app-server 协议是 OpenAI 自家的协议，不是公共标准，会跟着 Codex 版本一起变」。可选的有两条：A 是以 Codex 某版为底拷一份、自己管；C 是自定 HTTP + SSE（报告 §5.7）。最后定了 C。
   - 传输：客户端用普通 HTTP 请求下命令；服务端用一条 SSE 长连接按顺序推事件，每条带递增序号，断线后从序号接着收（报告 §5.2 的甲，传输学 opencode）。
   - 结构：照 Codex app-server v2，会话 → 一轮 → 一条条项目；批准、提问是服务端等客户端回答的请求；事件分开始、增量、完成。字段名尽量和 Codex 一样。只参考，不拷 Codex 的协议代码；参考的版本写进任务文件。
   - 后台命令（P2-28）：参考 Codex `rust-v0.163.0` 的 commandExecution、后台进程管理和 `/ps`、`/stop`，不提供 PTY 或写 stdin。新增 `backgroundCommand.updated` 事件和快照 `backgroundCommands`（旧存盘默认空），记录会话内从 1 起的 `id`、原卡片 `itemId`、命令、开始/结束时间、运行状态和退出码；原卡片仍用 commandExecution，后台状态按 itemId 关联，工具调用返回不代表进程结束。新增 backgroundCommandAction 项目记录 shell_output / shell_stop。`GET /v1/sessions/{id}/backgroundCommands` 列状态，`GET .../backgroundCommands/{commandId}` 取最后 1 MiB 输出，`POST .../backgroundCommands/{commandId}/stop` 停一条，`POST .../backgroundCommands/stop` 停全部，`POST .../shellBackground {itemId}` 把指定前台命令转后台（过期请求不影响后来的命令）。UI 读取不消耗模型的增量游标；输出只留会话内存中，避免将常驻服务日志无限写入只追加的事件文件。开始、结束事件存盘；服务端重启不恢复进程和日志，残留运行状态恢复为已退出、退出码未知。与 Codex 的进程编号和 write_stdin 不同，canter 用会话内小整数、独立看输出和停止工具。结束事件不发起模型轮，下一次请求之前将完成通知追加到模型历史。
   - P2-28 交叉审查后补充：后台 shell 的 `item.completed` 表示该次工具调用已返回，原 commandExecution 卡片使用 `status: completed`、`exitCode: null`；进程是否还在跑、最终退出码只看按 itemId 关联的 backgroundCommands，终端显示和导出都叠加该状态，旧客户端不会把已返回的调用永久当作进行中。启动失败用失败态，不登记后台编号或发送完成通知。
   - 后台叫醒（P2-101，10-28 主控确认）：新增 `backgroundEvent {id, commandId?, text}` 项目，复用 `turn.started` / `turn.completed` 和 `item.started` / `item.completed`。叫醒轮的 input 为空，没有 userMessage；事件卡片参与快照、重放、导出和回退，旧客户端按 Unknown 跳过。达到叫醒上限的提示同样存为 backgroundEvent，commandId 省略。沿用 Codex app-server v2 的会话→轮→项目结构；后台完成/正则匹配的事件项目及服务端自动开轮是 canter 的扩展，不伪造客户端输入或用户消息。私有 `background_notice` 继续携带 Message::User，增加事件标识和命令编号，以同一标识补记、去重；压缩拼稿标为后台事件，不计作用户原话。
   - 协议类型放单独的 Rust 包，从它生成 JSON Schema 和 TypeScript 类型；agent 核心和协议之间隔一层转换。
   - 理由：A 拷过来、不跟上游以后，同样是 canter 自己维护的协议，和 C 只差传输方式和拷不拷类型代码。传输上 HTTP + SSE 更贴合 canter：一台机器多个客户端，断线能接着收，以后 corral、pony 这类同步程序直接接，curl 就能排错。
   - 代价：离用户原来要的「使用成熟的现有的coding agent使用的协议」远一步，用的是 Codex 的结构，不是它的协议本身；协议包要自己写，估 1,000–1,500 行（报告 §9.1）。
   - **和 Codex app-server v2（`rust-v0.163.0`）不一样的地方**（第 1 件定的，细节见 `docs/任务/P1-1-协议包和存盘.md` 的完成记录和「审查后修改」，以及 `crates/canter-protocol/README.md`）：
     - 命名：`session`、`sessionId` 代替 `thread`、`threadId`；事件名用点号（`session.status`、`turn.started`、`item.delta` 等）。每条事件外层带 `seq`（每个会话从 1 起）、`sessionId`、`timestamp`（Unix 毫秒）；快照带 `lastEventSeq`；命令的回复带 `eventSeq`。
     - 计划和待办（P2-34）：参考 Codex `rust-v0.163.0` 的 `update_plan`，参数为可选 `explanation` 和 `plan: [{step, status}]`，状态用 `pending` / `in_progress` / `completed`，每次整份替换；空步骤或多个进行中步骤返回错误，保留原清单。无需批准，审查轮也能用。canter 新增 `plan` 项目（`id/explanation/plan/status`），复用 `item.started` / `item.completed`，不另发 Codex 的 `turn/plan/updated`：快照已有完整项目，取最后一个成功的计划项目就是当前清单，回退截掉轮后自然恢复先前清单；失败项目不替换它。协议里的 `PlanStepStatus` 用 camelCase（`pending` / `inProgress` / `completed`），与协议其余地方及 Codex v2 的 `TurnPlanStepStatus` 一致；模型工具参数仍用 snake_case（`in_progress`），在工具层转换，避免将工具参数命名带入公开协议。未知项目和状态按 Unknown 跳过。会话设置新增可选 `planEnabled`，仅报告打开时冻结的开关，旧客户端忽略；旧会话省略时按开启处理。`config.json` 的 `plan_enabled` 默认 true，每次新建或从存盘打开会话时读取，已加载会话不变；改开关后新建会话马上生效，已加载会话需重启服务端后再恢复。false 时不提供工具，终端不显示清单，压缩也不附清单。开启时，压缩通过工具层将当前清单转为工具参数形式（snake_case）的 JSON，附在摘要消息的 `[Current plan]` 段里，使模型可原样回传给 `update_plan`；已知步骤的内容和状态含义保持不变，Unknown 状态的步骤跳过；再次压缩拼稿时按摘要消息的位置去掉上一份附带清单，保留摘要正文和用户原话。不改核心提示词或压缩的九个小节，也不把附带清单计作用户原话。工具说明要求三步及以上的任务使用、开始时标进行中，每完成一步立刻调用标完成再开始下一步，不得攒到最后一起更新。10-28 用户长程试用 ink-sample 时，DeepSeek 列了五步、开头标第一步进行中，中间六十来次工具调用不更新、最后才全勾；光靠工具说明约束不住，用户同意「1 和 2 一起做吧」。因此修订原先「不提醒」：不催模型创建清单，只在开关开启且当前清单还有 pending 或 inProgress 步骤时，从上一次成功的 update_plan 起逐个计数其它工具调用（同一回复多个调用分别算），每到第 10 次在该工具结果末尾附一句英文提醒，要求已完成的步骤先用 update_plan 标完成再继续。提醒或成功更新后计数清零；失败的 update_plan 不清零，也不算其它工具调用；没有清单、全部完成或关闭时不计数、不提醒。计数只在会话内存里，服务端重启后从 0 起。提醒只追加到模型历史的工具结果，不修改已经发出的内容，不进入界面事件或导出；压缩拼稿归在工具结果下，不计作用户原话。终端每次成功更新出进度卡片；状态行下面、输入框上面最多五行未完成步骤，进行中优先，超出写 `… and N more`，只有一行空间时在当前步骤后接 ` (+N more)`；给滚动提示和至少一行对话留位，全部完成或空清单收起；导出保留每次清单卡片。
     - 会话设置：新增 `session.updated`，建会话时和每次修改后各写一条，带公开设置：名字、模型、权限模式、工作目录。环境变量不公开，也不存盘（10-24 改，见第 14 条）。

## 按命令放行（P2-108，2026-10-29）

主控确认：只有服务端状态目录的 `rules.json`（默认 `~/.canter`，支持 `CANTER_HOME`），与含凭证的配置分开，写入权限 0600。格式为 `{"rules":[{"pattern":["cargo","test"],"decision":"allow"}]}`，结果为 allow / prompt / forbidden，按词前缀匹配，冲突取 forbidden > prompt > allow，空前缀无效。每次判断重新读取，改文件不用重启；不存在表示无规则，读不了或格式错时所有权限模式的模型 shell 都退回单次询问，每次连续故障在会话内提示一次，恢复后照常。

规则只管模型 shell（含后台），用户 `!`、MCP、网页和改文件批准不变。禁止在三种权限模式都有效，不弹框并向模型说明；allow/prompt 在总是问、只问执行有效，全部允许只看禁止（坏文件仍询问）。prompt 可以覆盖只读白名单，也优先于会话前缀授权；命中 prompt 不提供两种前缀放行。受保护路径、计划模式和审查轮只读限制优先。

组合命令逐段判断，全部被规则、会话前缀或只读白名单放行才不问；一段禁止即拒绝，一段要问即询问。不能确定的变量、替换或语法不能靠 allow 或会话前缀免批准，已识别的字面命令前缀仍用于禁止判断。沿用只读解析机制，白名单本身不扩展。`cd ~` 后直接换行也按家目录计算后续路径；cd 目标以 `~` 开头但未展开时，算判断不了，不自动放行。

批准框显示实际将保存的词前缀，选永久放行则一次保存所有需要批准的段，本次执行并提示文件路径；shell 会话授权也只记这些前缀。前缀取程序加能确定的子命令，无子命令取程序；前置选项等不能确定时不建议。带路径的程序按完整词匹配，不按文件名回退；相对路径程序只提供会话前缀，不提供永久项。过宽的解释器、包装命令等参考 Codex 的 BANNED_PREFIX_SUGGESTIONS，不提供永久或会话前缀放行，包括 uv run、npm/pnpm/yarn exec、pnpm/yarn dlx、rustup run、docker run/exec、kubectl exec，以及 find、sed，具体清单记在任务完成记录。这些自动建议限制不影响用户手写的文件规则。只有文件管理，不做规则界面、项目级规则、通配或沙箱。
