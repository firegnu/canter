标记：「查到」＝读代码或文档得到，带文件和行号（canter 路径省略仓库前缀，Codex 路径以 `codex-rs/` 开头）；「推测」＝没有实测的判断；「未知」＝本轮查不到、要实测或问人的。没有标的方案、写法都是建议。

## 结论

- **总纲走得通。** canter 的协议本来就是 HTTP＋SSE，会话状态全在服务端；加一个 TCP 监听和令牌，任何客户端都能连同一套路由（查到：`crates/canter-server/src/http.rs:302` 只有一个 `router`，监听只在 `crates/canter-server/src/lib.rs:152` 一处）。工作量在「客户端把自己机器上的东西交给服务端」的那几处。
- **真正的同机假设只有三类：**
  1. 客户端交整份环境变量，服务端用它整个替换命令、钩子、LSP 的环境；沙箱保护哪个 HOME、技能和全局 AGENTS.md 从哪读，也都看它（查到，见 1.3）。远程时这份环境是另一台机器的。**安全后果**：沙箱会去保护客户端机器的 `HOME/.ssh` 这类路径，服务端机器真正的 `~/.ssh` 不在保护名单里（查到 `crates/canter-tools/src/sandbox.rs:51-58` 的写法，后果是推论）。
  2. 贴图只交客户端本机路径，服务端去读（查到，见 1.4）。
  3. 终端在客户端机器上直接跑 git、gh、遍历文件：分支、状态栏改动行数、`/diff`、`/review`、`/files`、`@` 补全（查到，见 1.5）。
- **另外两类是「本机管理」，不是协议问题。** 一类是找服务端、自动起、`serve --replace`、`upgrade`、`service install`；另一类是 `canter auth`、`canter mcp`、`skills install`。它们操作的就是服务端机器的状态目录和进程，远程时应在服务端机器上执行。连远程时客户端明确拒绝，提示文字也要改对。
- **推荐写法：** 路径字段（`cwd`、新增目录、`LocalImage`）一律当作服务端机器上的路径，这本来就是现在的语义，只是以前恰好同机。客户端手里的内容直接交内容（图片交字节）。客户端看不到的东西由服务端接口提供（工作区查询）。`env` 改为可选，不交就用服务端的默认会话环境。所有客户端走这一条路。
- **有一处要主控定（见第 6 节第 1 件）：** 有几件事只有「客户端能看到服务端的文件和环境」时才成立：交 `env`、在本机打开服务端路径（链接、`/memory` 编辑器、P2-292 的 HTML）、`/export` 写到哪。我建议把这算成「怎么连」的区别：经 unix socket 连上就是同机，照旧做；远程不做或改成复制。这样本机用法完全不变，也和终端已有的 SSH 规则一致。如果主控认为这算「两套」，本机就得放弃交 `env`、放弃直接打开链接，本机用法会变。
- **传输和认证：** 沿用 HTTP＋SSE，不换 WebSocket。TCP 默认关，只听配置里写明的地址。第一版只允许回环地址和 Tailscale 地址，因为 canter 自己不做 TLS。TCP 上每个请求都要令牌，回环也要；unix socket 照旧不要令牌。令牌按客户端分别发放，服务端只存哈希，撤销后已开的 SSE 流立刻断。要 HTTPS（以后 iOS、网页）时用 `tailscale serve` 在前面套。
- **拆分：** 五件开发加一次试用，顺序是 A1 环境 → B1 监听和令牌 → B2 客户端远程连接 → 试用（Mac 终端连 5090）→ A2 图片交字节 → A3 工作区查询搬到服务端。B1 碰要害，必须交叉审查；A1 也建议交叉审查，因为它决定沙箱保护哪个 HOME。

### 1.6 信任目录、沙箱、批准、`--yolo`

- 查到：全部在服务端判定和执行。信任目录由服务端检查（`crates/canter-server/src/trust.rs:74`、`:83`，DESIGN 418 行）。沙箱在服务端起命令时套（DESIGN 587 行，P2-166/P2-289）。批准是服务端发请求、客户端答复。`--yolo`（`sandboxDisabled`，P2-198）是新建会话时的参数。
- 远程时：机制跨机照样成立，不用改。含义变了：能连上 TCP 端口并带对令牌的人，就能以服务端用户的身份跑任意命令，`--yolo` 时连批准都没有。**令牌等于这台机器的 SSH 登录权限**，第 3 节按这个强度设计。
- 沙箱保护名单受 1.3 的会话 HOME 影响。

## 2. 按总纲给改法

一句话：**路径都是服务端的路径；客户端有的内容交内容；客户端看不到的东西由服务端接口给。** 本机终端也走这条路。

### 2.1 各条怎么改

| 同机假设 | 对所有客户端都成立的写法 | 本机终端用起来 |
|---|---|---|
| 监听、认证（1.1） | 同一个 `router` 挂两个监听：unix socket（文件权限，不要令牌）和可选的 TCP（要令牌）。认证只套在 TCP 那一路上。 | 不变。 |

### 2.2 协议改动和兼容

全部是加字段、加接口，`PROTOCOL_VERSION` 保持 1（查到：`crates/canter-protocol/src/lib.rs:43`），符合「新字段可选、旧接口保留」。

| 改动 | 旧客户端连新服务端 | 新客户端连旧服务端 |
|---|---|---|
| 新建、恢复的 `env` 改为可选 | 旧客户端总会交，行为不变 | 只可能同机（旧服务端没有 TCP），新客户端同机时照旧交 |
| 输入类型 `image`（data URL） | 旧客户端不发 | 旧服务端把它当 `Unknown`，返回 invalid（查到 `http.rs:1227-1233`）。新客户端先看 `/v1/info` 的 `features` 里有没有 `imageData`，没有就提示 `serve --replace`。不在客户端留 `localImage` 的老路，免得出现两套。 |

### 2.3 和 Codex 的对照

- 相同：Codex 的 `thread/start` 没有 `env`，`cwd` 可选（查到 `codex-rs/app-server-protocol/src/protocol/v2/thread.rs:64`、`:83`）。图片可以交 data URL 或 `fileId`，也保留 `LocalImage`（`v2/turn.rs:451-511`），服务端只收 data URL，不去抓 http 图片（`codex-rs/app-server/src/image_url.rs`）。工作区查询由服务端提供：`fuzzyFileSearch`、`gitDiffToRemote`、`review/start`、`fs/readFile`、`fs/readDirectory`、`command/exec`（`codex-rs/app-server-protocol/src/protocol/common.rs:1053`、`:1073`、`:1179`、`:1480`、`:1589`、`:1602`）。Codex 的 CLI 也有「远程服务端上的新任务用这个目录」的参数（`codex-rs/cli/src/main.rs:356`）。canter 的方向和它一致。
- 不同：canter 保留可选的 `env`。理由是 DESIGN 第 14 条，本机终端靠交环境让命令拿到当前 shell 的变量（direnv、`FOO=1 canter` 这种），去掉就是本机用法变了。canter 不做通用的 `command/exec`、`fs/writeFile`，因为没有客户端要用，按需再加。

## 3. 传输和认证

### 3.1 沿用 HTTP＋SSE，不换 WebSocket

- 理由：canter 的协议是普通请求加一条 SSE 事件流，批准也是普通 POST，不需要双向通道。同一个 `router` 挂到 TCP 上就能用，客户端只是把 `reqwest` 的 `.unix_socket(...)`（`client.rs:535-545`）换成普通基地址。断线重连已经支持 `Last-Event-ID`（`http.rs:1698`）。
- Codex 用 WebSocket，是因为它的协议本身是 JSON-RPC 双向消息（查到 `codex-rs/app-server-transport/src/transport/mod.rs:85-88`：`stdio`、`unix`、`ws`、`off`）。canter 没有这个需要。
- 网页客户端：浏览器的 `EventSource` 不能带自定义请求头（Web 标准，本轮没查证），所以网页要用 `fetch` 读流的方式收 SSE，才能带上令牌。这是网页客户端的事，协议不用改。
- 断线：服务端给接进来的 TCP 连接开 keepalive；客户端在 SSE 上设空闲超时，约 3 次心跳（45 秒）收不到就重连（推测这个值够用，试用时看）。

### 3.2 监听：默认关，只听写明的地址

- `config.json` 加 `remote.listen`（地址列表），不写就不开 TCP。不支持 `0.0.0.0`、`::` 这种全部地址。
- 第一版只允许两类地址：回环（给 SSH 隧道和 `tailscale serve` 用）和 Tailscale 地址（`100.64.0.0/10`、`fd7a:115c:a1e0::/48`）。其他地址启动时拒绝，提示「use a Tailscale address or an SSH tunnel; canter does not serve TLS」。理由：令牌是明文 HTTP 头，只有回环或 WireGuard 加密的网里才能这样传。
- 注意：`100.64.0.0/10` 也是运营商 NAT 的地址段。这里的检查只是防手误，不是安全边界，真正的边界是令牌。
- 推测：tailscaled 起来之前绑 Tailscale 地址会失败，手动起不受影响，以后装成服务时要重试。
- `serve --replace` 换进程时，新进程要绑同一个端口。现在的交接顺序能不能保证不冲突，要在 B1 里核实（推测：tokio 在 Unix 上 bind 会设 `SO_REUSEADDR`，但旧进程还在 listen 时照样会冲突）。

### 3.3 令牌：发、存、换、撤

- **发**：在服务端机器上跑 `canter remote token add <客户端名>`，打印一次随机 256 位令牌。不提供协议接口来发令牌，这样漏了一个令牌也造不出新令牌。
- **存（服务端）**：`<CANTER_HOME>/remote-tokens.json`，权限 0600，每个客户端一条 `{name, sha256, created}`，不存明文。比对用常量时间（Codex 也这么做：`codex-rs/websocket-auth/src/lib.rs:8`、`:18`）。
- **存（客户端）**：见第 4 节，`remotes.json` 权限 0600。`canter remote add` 从标准输入读令牌，不放在命令行参数里，以免进 shell 历史和 `ps`。
- **带**：`Authorization: Bearer <令牌>`，每个 TCP 请求都要，回环地址也要。不放在网址里，以免进日志。日志只记客户端名，不记令牌。
- **换**：给同一台客户端加一个新名字的令牌，客户端换上后删旧的。按客户端分开，删一个不影响别的。
- **撤**：`canter remote token remove <名>` 改文件，服务端在下一个请求时发现文件变了就重读（按修改时间缓存），新请求立刻被拒，并且主动关掉这个令牌开着的 SSE 流。Codex 在 WebSocket 建立以后不再检查过期和撤销（查到 `codex-rs/websocket-auth/src/lib.rs:286-287`）。canter 的 SSE 流可能一开几天，所以要主动断。
- **unix socket**：照旧靠目录 0700、socket 0600，不要令牌。
- **和 Codex 对照**：
  - 相同：
    - 非回环地址必须配认证（Codex：`codex-rs/app-server-transport/src/transport/websocket.rs:167`）。
    - 令牌只存哈希，比对用常量时间。
    - unix socket 用 0600（`codex-rs/app-server-transport/src/transport/unix_socket.rs:34`）。
  - 不同：
    - Codex 允许回环 WebSocket 不带认证（`websocket.rs:81` 提示「binds localhost only (use SSH port-forwarding for remote access)」）。canter 的 TCP 一律要令牌，理由是本机已经有受文件权限保护的 unix socket；多用户机器上，回环端口别的用户也能连。
    - Codex 拒绝带 `Origin` 头的请求（`websocket.rs:103-107`）。canter 不拒，理由是 canter 每个请求都要 Bearer 令牌，浏览器跨站请求带不上它；以后网页客户端也可能需要发 `Origin`。canter 也不加 CORS 头。
    - Codex 另有 JWT 签名令牌模式和走 OpenAI 后台的远程控制（配对码、按客户端列出和撤销：`common.rs:1265-1272`）。canter 不需要这些。手机配对码以后再说（见 5.3）。

### 3.4 Tailscale 和 TLS

- 第一版 canter 不做 TLS。Mac 连 5090 走 Tailscale 地址上的明文 HTTP 加令牌，WireGuard 负责加密。
- 以后 iOS、网页要 HTTPS 时（推测：iOS 的 App Transport Security 默认要求 HTTPS），canter 只听回环，前面用 `tailscale serve` 套 HTTPS（ts.net 证书），令牌照样要。推测有两点要试：`tailscale serve` 转 SSE 时会不会攒着不发；证书会进公开的证书透明日志，机器名会被看到。
- 自带 TLS（rustls 加证书文件或自签名证书指纹）要管证书和轮换，只有不用 Tailscale 时才需要，放到以后。
- Codex 对照：Codex 服务端也只监听 `ws://`，不自己做 TLS。它的客户端只在 `wss://` 或回环 `ws://` 上发令牌（查到 `codex-rs/app-server-client/src/lib.rs:1707-1720`；终端 `codex-rs/tui/src/lib.rs:519`）。canter 客户端照这个规则做：令牌只发给 `https://`、回环或 Tailscale 地址，其他 `http://` 地址拒绝。和 Codex 的差别是允许 Tailscale 地址上的明文，理由同上。

## 4. 客户端怎么找服务端

- **本机**：不变。`ensure_server` 照旧读 `server.json`、找 socket、找不到就自动起。不带 `--server` 的 `canter`、`canter exec` 永远连本机。
- **远程列表**：放客户端的 `<CANTER_HOME>/remotes.json`，权限 0600，内容是 `{name, url, token}` 的列表。用 `canter remote add <名> <url>`（令牌从标准输入读）、`canter remote list`、`canter remote remove <名>` 管理。第一版不设「默认远程」，保证本机用法不变。
- **怎么选**：`canter --server <名>`、`canter exec --server <名>`、`canter usage/stats/doctor --server <名>`。连上先请求 `/v1/info`，比对协议版本，版本不一致按 2.1 给远程版本的提示。重连时用 `/v1/info` 的 `instance` 判断是不是同一个服务端。
- **以后的桌面版、iOS、网页**：数据也是 `{name, url, token}`，各自存进自己的安全存储（比如钥匙串）。Tailscale 的机器名就是网址的一部分，不需要另做发现。局域网自动发现（Bonjour）不做，以后要再说。

## 6. 要用户（主控）定的事

### 第 1 件：「客户端能不能直接看到服务端的文件和环境」算不算「怎么连」的区别

- 问题：总纲说「区别只在怎么连和怎么认证」，也说「本机用法不变」。下面几件只有同机时才有意义，要么按连接方式区分，要么本机也放弃：
  - 交 `env`；
  - 在本机直接打开服务端路径（终端里点文件链接、`/memory` 用编辑器打开）；
  - `/export` 的相对路径；
  - 模型用 `open` 打开 HTML（P2-292）。
- 选项：
  - **(a) 算。** 经 unix socket 连上就是同机：照旧交 `env`、直接打开路径。远程不交 `env`，用服务端默认环境；路径只复制。服务端和协议只有一条路（`env` 可选、路径都是服务端路径），差别只在客户端按连接方式决定交不交、开不开。终端已有的 SSH 规则（`links.rs:172-200`，SSH 时链接只复制）就是这个思路。
  - **(b) 不算。** 本机也不交 `env`、也不直接打开路径。本机用法会变：direnv 和 `FOO=1 canter` 这类临时变量失效，点文件链接只复制、不打开，`/memory` 不能直接编辑。
- **建议 (a)。** (b) 和「本机用法不变」直接冲突，换来的统一只体现在客户端的一个判断上。

### 第 2 件：网络安全先只支持 Tailscale＋令牌，还是一开始就自带 TLS

- (a) Tailscale＋令牌：canter 只听回环和 Tailscale 地址，明文 HTTP 加令牌；要 HTTPS 时在前面套 `tailscale serve`。
- (b) 一开始就自带 TLS：canter 自己管证书。
- **建议 (a)。** 用户的两台机器已经适合用 Tailscale（Mac 上有 `/usr/local/bin/tailscale`，查到；5090 上有没有未知）。自带 TLS 要多做证书管理，没有 Tailscale 的场景以后再加。Codex 服务端也不自己做 TLS。

### 第 3 件：第一个拿来验证远程的组合

- **建议照主控提议：Mac 终端连 5090 服务端**，再加一个回环 TCP 的自动化端到端测试，常驻在测试里。
- 前提要用户确认（未知）：
  - 5090 上装没装 Tailscale；
  - 5090 上的 canter 怎么构建和更新；
  - 5090 上跑哪个模型（ChatGPT 见第 4 件）。
- 不建议拿 iOS、网页做第一个，它们还没有仓库。

### 第 4 件：服务端在远端时 GPT 凭证怎么办（和 DESIGN 第 26 条 ① 冲突）

- 现状（查到）：
  - DESIGN 第 26 条 ①：GPT 凭证只放本机 canter 服务端，不放远程或托管环境；登录走官方流程，回调到 `127.0.0.1`。
  - `docs/调研/P2-33-第二个模型方案.md:33`：条款 §1（「local and under the user's control」）和 §2、自托管虚拟机指南之间的说法有歧义。
  - 同一文档 `:67`：查不到公开的设备码登录约定；用 SSH 转发回调端口技术上可行，但官方没写。
- 选项：
  - **(a) 保持第 26 条 ①。** 远程服务端不用 ChatGPT，用 DeepSeek 等按 key 计费的模型。客户端连远程时，`canter auth` 直接拒绝。
  - (b) 在 5090 上登录：用 SSH 把回调端口转回来，或者手动把回调网址贴回去。5090 是用户自己的机器，可以说是「under the user's control」，但要先改第 26 条 ①，并且承担条款歧义。
  - (c) 把 Mac 上的凭证拷到 5090：同 (b)，还多一份凭证副本。
- **建议 (a)**：第一版不碰，远程工作不被它卡住。用户想在 5090 上用 Pro 的话，另开一件先读条款再定。

### 第 5 件：5090 上的服务端怎么常驻

- 现状（查到）：Linux 不支持 `service install`（`crates/canter/src/service.rs`），P2-160 定过不做 systemd。
- 选项：
  - (a) 试用期在 SSH 或 tmux 里手动 `canter serve`；
  - (b) 现在就做用户级 systemd 服务。
- **建议 (a)**，试用顺了再决定要不要推翻 P2-160。

### 第 6 件：远程会话的默认环境从哪来

- 选项：
  - (a) passwd 取 HOME/USER/SHELL，加一次登录 shell 探测（取 PATH 等），再加 `config.json` 覆盖；
  - (b) 只用服务端进程自己的环境：自动起的进程几乎是空的，装成服务的有 plist 里那几个；
  - (c) 只用配置文件写死。
- **建议 (a)**。(b) 在自动起的服务端上 PATH 不全；(c) 每台机器都要手写。登录 shell 探测要设超时，探测失败退回 (b) 加 passwd，并在 `canter doctor` 里显示出来（推测：VS Code 远程开发是这么拿环境的，本轮没查证）。

## 7. 已查证、推测、未知汇总

- **已查证**（带行号的都是）：
  - 只有 unix socket 一个监听；
  - `env`、`cwd` 必填；
  - 会话环境整个替换命令、钩子、LSP 的环境；
  - 沙箱按会话 HOME 定保护名单；
  - 贴图交本机路径、服务端去读；
  - 默认请求体上限 2 MB；
  - 终端在本机跑 git、gh、遍历；
  - GPT 和 MCP 登录回调都绑 `127.0.0.1:0`；
  - `canter mcp` 不连服务端；
  - Codex `rust-v0.169.0` 的传输、认证、图片、工作区接口写法。
- **推测**：
  - 远程时各条的具体表现（没起远程实测）；
  - TCP 半开的检测时长；
  - `serve --replace` 换端口时会不会冲突；
  - `tailscale serve` 转 SSE 的表现；
  - iOS 的 HTTPS 要求；
  - 浏览器 `EventSource` 带不了请求头；
  - VS Code 的环境探测做法；
  - squire 要跟着改一行；
  - 旧客户端忽略新字段。
- **未知**：
  - ChatGPT 有没有设备码登录；
  - 条款对远程凭证的确切口径；
  - 5090 上有没有 Tailscale、时区怎么设；
  - 服务端常驻进程的当前目录（影响相对 `cwd` 的解析）。
