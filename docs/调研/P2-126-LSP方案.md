# P2-126：通用的「改完拿诊断」方案

2026-10-29。设计报告，不是已批准的实现规格。依据本件任务、P2-94 的最新决定、`docs/DESIGN.md` 第 8、14、17 条；canter 阅读和实测基线为 `0855a250ad4985c448bf59c5786e42186642c6ac`。本报告未修改 DESIGN，也未实现产品代码。

## 1. 结论和要用户定的问题

**建议本期做通用框架，第一版推荐 Rust + Python，默认关；成功写文件后自动收诊断，最多同步等 500 ms，晚到的结果在下一次模型请求前追加，不自行叫醒模型。** 第一版接哪些语言仍由用户在实施时定，下面没有把推荐改写成决定。

价值是让模型较早发现局部错误，缩短「写一段、发现错误、修正」的循环。它不能代替项目检查，也没有证据证明能单独解决长任务可靠性问题。大头不是给每个语言写一套工具，而是进程生命周期、文档同步、诊断时效和模型历史的衔接。

| 待定项 | 推荐 | 理由和代价 |
| --- | --- | --- |
| 第一版语言 | Rust（rust-analyzer）+ Python（pyright）；TS/JS 紧接着单列接入件 | 两种不同服务器足以检验框架没有写成 Rust 专用，本次两种都已实测。TS/JS 有前端使用价值，但本机没装对应服务器，本次不能承诺其表现；如果第一批就需要前端，可同批加入，增加约 1–2 人日接入和实测。C/C++ 留到有明确项目及编译数据库时再接。 |
| 默认开关 | 沿用 P2-94，默认关，由用户配置开启 | canter 仓库实测 rust-analyzer 稳定约 2.30 GiB，首次有诊断约 23 秒；装着二进制不等于同意常驻占用资源。 |
| Rust 保存时跑 cargo check 吗 | 内置配置设 `checkOnSave: false`，用户可覆盖为 true | 原生诊断先给局部反馈，最终照旧跑项目检查；开启会反复调编译器。实测 true 的热态语法错误约 0.29–0.34 秒补到 rustc 诊断，但这个数字不能代表完整类型检查。关闭也不等于完全不运行 cargo，见第 2、4 节。 |
| 慢诊断怎么办 | 同步 500 ms；超时后有限等待、追加通知；不主动开新模型轮 | 首次索引超出 500 ms 很正常；不能卡住 write/edit，也不能改写已发送的工具结果。空闲后到达的结果保留到下一次实际请求，不额外消耗模型额度。 |
| shell 同步范围 | 第一版在 write/edit 激活实例后同步 shell 和外部修改；纯 shell 会话不自动起服务器 | canter 已要求用文件工具改代码，先覆盖其后的 fmt/checkout。若用户要求从第一条 shell 改动就自动诊断，需要把监视提前到开启 LSP 的会话创建时；这是实质范围差异，不能藏成实现细节。 |
| 资源和共用 | 10 分钟无有效活动回收；同根目录、同服务器配置、同启动环境才共用；最多 2 个实例，单实例进程树 4 GiB、总计 8 GiB 的 RSS 软阈值 | 这是建议起点，不是实测得出的最优值。资源受限时跳过诊断，文件修改仍成功；大型项目可能需要用户调高。不同 PATH 不共用。 |
| 自动启动的授权范围 | 用户开启 LSP 即明确授权配置中的服务器及其分析辅助进程在普通修改轮运行；计划/审查轮不启动、不主动触发检查 | rust-analyzer 的构建脚本、过程宏会执行项目代码，不能把这件事描述成无副作用的只读查询。只采用内置和用户配置的启动命令，不执行仓库自带的 LSP 启动配置。此边界需随实现写进 DESIGN。 |

预计拆 **5 件，约 12–19 人日**，另留约 2–3 人日主控审查、集成和返修；这是工程判断，不是交付承诺。TS/JS、C/C++ 额外接入另计。推荐顺序和范围见第 7 节。

下文标记：**实测**是本机此次运行结果；**查到**来自代码或公开一手材料；**建议/推测**是待用户采纳的方案。没有真调模型，没有测模型修错率或 token 节省。

两个公开项目克隆在 `/tmp/canter-p2-126-probe/` 下，没有装依赖。pyright 的命令入口在 `/opt/anaconda3/bin/`，为避免包装器在隔离 HOME 下尝试准备运行环境，直接运行它已经安装的 JS；没有安装或升级 pyright、Node 或任何语言服务器，也没有写 Python 测量程序。

测量用一次性 Rust 程序，源码及日志放 `/tmp/canter-p2-126-probe/`。它以前台父进程持有服务器的 stdin/stdout，收 `Content-Length` 分帧的 JSON-RPC，不起 daemon。四组依次运行，彼此不并发。

1. 保存测量文件原字节，在文件末尾追加一个错误。Rust/C 是缺少右值的局部语法错误，Python 是把字符串赋给 `int` 的类型错误。
2. 从 `Command::spawn` **之前**的 `Instant` 起算；发送 `initialize`，等回复后发 `initialized`、配置、`didOpen(version=1)`、`didSave`。处理服务器发来的 `workspace/configuration`、进度注册等请求。初始化回复不算首诊断。
3. 首诊断取目标 URI、追加位置、severity=error 的第一条 `publishDiagnostics`；不是日志、空数组或其它文件的错误。此次四组的首次发布恰好都含目标错误。另记录 `source=rustc` 的到达时间。
4. 收到目标诊断后，进度已结束且采样没有 cargo/rustc 子进程，连续保持 10 秒，再每秒采 1 次 RSS、共 10 次。表中「稳定 RSS」是这 10 次范围；四组恰好各自不变。这里的稳定只是短观察窗，未测数小时增长。
5. 每次热态测量先把追加代码改成正确内容，收到清除目标错误的发布，至少等 3 秒且进度结束，再等 1 秒；随后从写盘前计时，发 `didChange`（递增版本，整文件内容）、`didSave`，等新错误。每组做 3 次。日志确认了错误清除和版本推进，不拿启动时缓存诊断当新结果。
6. RSS 来自 `ps -axo pid=,ppid=,pgid=,rss=,comm=`，单位 KiB。分别统计服务器主进程及其子进程树/原进程组。峰值按约 1 秒采样，不是操作系统记录的绝对峰值；进程树 RSS 之和可能重复计共享页。GiB/MiB 均用 1024 换算。
7. 结束时恢复原字节，发 `didClose`、`shutdown`、`exit`，再按记录的进程组清理残留、等待子进程退出。此次记录的 PID 最后查询均不存在，未按名字杀进程。

追加片段如下（每次都保留文件原文，只替换末尾片段）：

| 语言 | 启动时错误 | 清除时 | 热态修改时错误 |

| Rust | `pub fn p2_126_lsp_probe() { let p2_126_initial = ; }` | `pub fn p2_126_lsp_probe() {}` | `pub fn p2_126_lsp_probe() { let p2_126_changed: u32 = ; }` |

rust-analyzer 两组分别使用此前未有该项目构建产物的 target 目录；默认构建脚本、过程宏、cache priming 保留，没有通过关闭分析能力来压低内存。初始化配置如下，`<target>` 是下节命令的 CARGO_TARGET_DIR 实际展开值：

```json
{
  "checkOnSave": false,
  "cargo": { "targetDir": "<target>" },
  "diagnostics": { "enable": true }
}
```

另一组只把 `checkOnSave` 改成 true 并换独立 target。配置也通过 `workspace/didChangeConfiguration` 和 `workspace/configuration` 回复提供。pyright 设置 `python.analysis.diagnosticMode=openFilesOnly`、`typeCheckingMode=basic`。clangd 未生成编译数据库，日志明确用了 fallback command；关闭后台索引和 clang-tidy，因此只代表该 C 文件的基本诊断。

## 3. 别家和协议：查到了什么

### 3.1 参考产品，修正容易误读的地方

- **Claude Code，查到**：官方配置把启动命令、文件扩展名放进插件 `.lsp.json`，二进制用户自己装；首次编辑匹配文件时启动。编辑后的摘要行可展开看错误和警告。缺二进制后，下次编辑会再试。它证明了「配置接语言 + 自动回诊断」这条产品路径，不证明具体等待预算或内存表现。[官方说明](https://code.claude.com/docs/en/plugins/code-intelligence)
- **Claude Code，查到**：官方排错页承认语言服务器索引导致内存上涨，也提醒 monorepo 中配置错误可能带来误报。不能把所有未解析 import 都归咎于模型。[排错说明](https://code.claude.com/docs/en/plugins/troubleshooting#language-server-doesnt-start)
- **omp v18.13.0，源码查到**：此次只读 `/tmp/p2-64-src/omp`，标签提交 `011ab732fa2d8657203d17f6af80d57809eb24f4`，没有搬代码。`defaults.json` 确有 55 个配置；`settings.ts` 中 lazy/shared 默认 true、diagnosticsOnWrite=true、diagnosticsOnEdit=false、去重=true；Rust 配置关闭 `checkOnSave`。[固定版本配置](https://github.com/can1357/oh-my-pi/blob/v18.13.0/packages/coding-agent/src/lsp/defaults.json)、[设置](https://github.com/can1357/oh-my-pi/blob/v18.13.0/packages/coding-agent/src/lsp/settings.ts)
- **omp 的等待不是简单的「最多 12 秒」**：`diagnostics.ts` 同步预算 500 ms，deferred 等待取 `max(12000, requestTimeout×1000)`，每服务器 pipeline 再加 10 秒宽限。canter 不照搬整套参数，只借用同步返回与晚到注入分开的思路。[诊断实现](https://github.com/can1357/oh-my-pi/blob/v18.13.0/packages/coding-agent/src/lsp/diagnostics.ts)
- **omp 的 shared 也不是已验证的同时共用单实例**：该版本 `settings.ts` 和 `client.ts:58–62` 明写每个连接独占一个服务器，释放后留热给后来连接复用。`client.ts:53–55` 的空闲回收默认禁用，配置 `idleTimeoutMs` 后才有计时。此前 P2-88 的「共用、空闲回收」不能读成默认已经解决并发共享和资源上限。[客户端实现](https://github.com/can1357/oh-my-pi/blob/v18.13.0/packages/coding-agent/src/lsp/client.ts)
- **opencode v2.1.3，查到**：迁移说明确认保留 lsp 配置但不启动服务器、不提供 LSP 工具和诊断，建议使用项目的 lint/typecheck/compiler。该段没有解释删除的工程理由，不能据此声称它是因为内存或效果差才删。[固定版本迁移说明](https://github.com/anomalyco/opencode/blob/v2.1.3/services/www/src/docs/content/migrate-v1.mdx#supported-fields-without-direct-native-equivalents)
- **Codex，已有调研事实**：P2-88 对 `rust-v0.163.0` 的扫描没有找到 LSP 实现；这里不把固定版本观察扩大为今后永远没有，也不以其它产品的取舍代替 canter 用户的决定。

### 3.2 协议直接影响实现的约束

**查到**：LSP 3.17 的诊断推送是按 URI 替换整个列表，空数组用于清除；`version` 可选，不能假定每个服务器都给。客户端要先同步文档，再请求相关信息。文件监视通知和文档 `didChange` 是不同通道，不能只发一个文件变化事件就认为已打开文档的内存内容也更新了。[推送诊断规范](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/language/publishDiagnostics.md)、[文档同步规范](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/textDocument/didChange.md)、[文件监视规范](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/workspace/didChangeWatchedFiles.md)

**建议**：底层以 3.17 能力协商为兼容基线，支持 stdio 推送；服务器声明 `diagnosticProvider` 时支持文档级 `textDocument/diagnostic` 拉取，处理 full/unchanged、resultId、refresh 和取消，不实现全工作区扫描式拉取。首批已测服务器走 push，配置为 pull 的服务器才声明并启用 pull；不因它同时提供 pull 就关闭可能另带 rustc 结果的 push。确需两者并用时明确适配并去重。push 以「服务器实例 + URI」为整表边界，不能按每条诊断的 source 拆开后跨批拼接；pull 再区分 provider identifier。没有声明的能力不乱发请求。不能把「通用」解释成首版覆盖所有 LSP 扩展。[拉取诊断规范](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/language/pullDiagnostics.md)

## 4. 六个问题的推荐

### 4.1 第一版语言，以及以后怎么加

**推荐 Rust + Python**，理由见开头。Rust 对应现有主要项目，Python 验证另一套初始化、配置请求和类型诊断路径。TS/JS 是最值得紧接着接入的配置；C/C++ 要把编译数据库作为明确前提，不能因为本次 fallback 成功就承诺常见工程都开箱即用。clangd 官方说明也指出缺少编译参数会误判 include、宏和语言标准。[clangd 编译参数说明](https://clangd.llvm.org/design/compile-commands)

**建议配置位置和职责**：

- 内置数据放 `crates/canter-tools/src/lsp/servers.json`，随 canter 发布，由开发者维护；不要给每种语言加一个模型工具。
- 用户覆盖放 canter 自己的 `config.json` 的 `lsp` 段，沿用状态目录保护；先只支持内置表 + 用户覆盖，不自动加载仓库里的命令配置，不做插件市场或自动下载安装。
- 每份配置至少包含服务器 id、command/args、扩展名到 languageId 的映射、项目根标记/根选择规则、initializationOptions、可回复 `workspace/configuration` 的 settings。可显式指定 root 和启动环境覆盖，以解决特殊布局。
- command 用 argv 直接启动，按客户端环境 PATH 解析；不经 shell，不用 `npx` 一类可能临时联网安装的启动方式。需要项目本地 bin 时由用户明确配置；诊断状态显示实际解析到的可执行文件，便于发现错版本。
- 配置在服务端启动时读取；改变后通过既有 serve 替换生效。先不加动态重载和一套会话内设置系统。

根目录不是简单找最近 `.git`：Rust crate 要归到所属 Cargo workspace，Python 通常按 pyproject/pyrightconfig，TS/JS 按 tsconfig/jsconfig/package 层级。选根限制在该会话 cwd 或已加目录的授权范围内，规范化实际目录，**不同 worktree 不因同一个 git common-dir 而合并**。无法准确推导时用明确 root 覆盖或报告不支持，不默默把整台机器当项目。

以后接一个遵守已实现诊断、同步能力的 stdio 服务器，通常是开发者加一份数据配置、配置样例和固定回放，加一次已装服务器实测；用户也可先在全局配置添加。**不保证所有语言都只加 JSON**：根目录发现、虚拟环境、编译数据库、私有配置请求或 pull-only 特性可能需要小适配器。新增适配器仍放 LSP 模块，write/edit、模型协议和终端不按语言分支。用户只提供项目所需的环境和二进制，不承担维护 JSON-RPC 的工作。

### 4.2 默认开还是关

**推荐关**，不推翻 P2-94 的默认值。建议 `lsp.enabled` 默认 false；关闭时没有启动、监视、后台注入和额外模型工具，也不往系统提示词插当前诊断。用户开启后，普通修改轮的 write 和 edit 都触发，不能照抄 omp 只默认支持 write 的取舍。

开关和语言配置属于用户明确选择。说明开启会运行服务器，Rust 即便 `checkOnSave=false`，默认构建脚本/过程宏准备仍可能启动 cargo 和项目代码；官方把保存检查与 buildScripts 分成独立配置，本次关闭保存检查也观察到 cargo/rustc 子进程。[rust-analyzer 配置](https://rust-analyzer.github.io/book/configuration.html#rust-analyzer.cargo.buildScripts.enable)

计划/审查轮不因为看文件或收过期诊断启动进程，不主动发保存检查；已经有的缓存可供用户看。不要把启动授权伪装成只读工具权限。此自动运行边界应在主控采纳后更新 DESIGN，再实施。

### 4.3 启停、内存、共用、替换和失败

**启动与回收建议**：首次成功写入匹配文件才懒启动；打开会话、列文件、读取代码不启动。一个进程内只有一条 LSP 客户端连接，由 canter 集中管理文档，几个会话订阅结果；同一个 URI 的版本在实例内全局递增，不让各会话从 1 各写各的。

共用键包含：规范化项目根、服务器 id、解析后的可执行路径和参数、初始化/settings 配置、**完整有效启动环境**。第一版直接比较内存中的环境映射，必要时用仅内存的键索引，绝不写进日志或会话事件。PATH 不同必不共用，即便它们碰巧指向同一个 rust-analyzer，后续 cargo/python/node 仍可能不同；同 PATH 但 HOME、VIRTUAL_ENV、RUSTUP_TOOLCHAIN、CARGO_TARGET_DIR 等不同也不共用。这个选择牺牲一部分命中率，换取清楚的环境语义。二进制升级或项目环境文件变更时，让实例失效重启，不把路径相同当成版本永不变。

| 情况 | 建议行为 |
| --- | --- |
| 空闲 | 最后一次真实同步/诊断请求结束后 10 分钟回收；ping、状态查询、内存采样不续命。pending 有时限，不能让挂起请求无限挡住回收。没有任何会话引用时立即清理。 |
| 内存 | 默认最多 2 个实例；每 5 秒采样原进程组/子进程树 RSS，单个 4 GiB、总计 8 GiB；连续两次越线先回收无活动的，仍超限则停止超限实例/最久未使用的实例并报 resourceLimited。停止后不要被同一待办立刻重新拉起；需要后续用户重试或调整配置。 |
| 资源已经占满 | 有空闲实例则回收；都忙则这次诊断跳过并说明，不能把磁盘写入排在资源队列后无限等。阈值可在用户配置调高，不建议默认按 128 GiB 这台机器放宽到十几 GiB。 |
| 正常停止 | 有界等待 `shutdown` 回复，再发 `exit`；超时用 P2-28 的原进程组清理能力，等待 reap，清空诊断和文档版本，增加实例 generation。 |
| serve --replace | 按既有 draining/最多 60 秒等待活动轮的语义停止接新工作；停完会话后、释放服务端锁前关闭 LSP 管理器和看护资源。新服务端不接管旧 PID/管道，不复用旧诊断缓存，下一次修改按客户端重新交来的环境懒启动。不能使用新服务端自己的 PATH 替代会话 PATH。 |
| 服务端被强杀 | 复用进程组 guardian 的所有权管道，让 owner 消失时清理进程组；仅给 LSP 的 processId 或 kill_on_drop 都不够。脱离原组的进程仍是已有看护边界，不能宣传为系统级沙箱。 |
| 没装/启动失败/initialize 超时 | 修改成功，另报诊断 unavailable，带服务器名和不含环境值的原因；initialize 上限 30 秒，启动到首次可用诊断总预算建议 120 秒，均不延长工具的 500 ms 等待。不把进度安静当作全项目索引完成。缺程序按后续编辑重新解析 PATH；其它启动失败设 60 秒退避。 |
| 崩溃 | 清掉原实例 pending、缓存和旧版本；下次有实际修改再尝试，不为崩溃自行唤醒模型。5 分钟内最多 2 次自动重启尝试，再熔断，用户 `/lsp retry` 或重启服务端后恢复。 |

上述 RSS 是**软阈值**：采样间隔内可能超出，也不是进程物理内存的精确去重总量；没有 macOS/Linux 统一的可靠硬限额可直接冒充这套功能。建议按保守阈值停服务来保护主任务，不做首版跨平台资源沙箱。

`/lsp stop <id>` 的建议语义是暂停本会话对该实例的订阅，直到本会话显式 retry；其它会话还有订阅则进程仍活着，界面解释共用状态。不要让一个会话为了省资源把别人的诊断服务无声停掉。retry 对仍健康的共用实例只重订阅/重新同步；失败实例由管理器集中重建，避免并发重复启动。

### 4.4 shell 改了文件，服务器怎么知道

**推荐运行中的实例配工作区文件监视，并在 shell 完成后做一次有界核对。** 只钩住 write/edit 会漏 `cargo fmt`、`git checkout`、MCP 或编辑器修改；只等 shell 退出会漏后台长命令持续写文件；只看 git diff 会漏未跟踪文件和被 checkout 恢复的文件。

流程建议：

1. 管理器监听项目根内匹配源码及项目配置文件的创建、修改、删除/重命名，约 200 ms 合并一批；支持服务器通过 `client/registerCapability` 注册的监视规则。按实际路径去重，不跟符号链接把观察范围扩到授权目录外或受保护状态目录。
2. 已经 `didOpen` 的文件，重读磁盘、核对内容摘要；内容有变化就递增版本并发 `didChange`，确实落盘且服务器要求时发 `didSave`。不能只发 `workspace/didChangeWatchedFiles`，否则服务器可能继续使用旧的打开文档内容。
3. 未打开的文件按匹配规则发 `didChangeWatchedFiles`。普通 shell 修改了匹配源码时，在限额内临时打开这些文件请求诊断，否则 pyright 的 openFilesOnly 一类服务器未必检查它们；这些文件需要有界保留，建议实例最多 64 个打开文档、超出按最近使用回收，并报告本批未覆盖数。
4. 删除/改名按 close、删除/创建通知处理，移除旧 URI 诊断；Cargo.toml、pyproject、tsconfig、编译数据库等变化通知服务器重载，不能确认它支持重载时使实例失效后重建。`git checkout` 的大批变化不逐个无限等待，先合并失效和重载，再覆盖本轮相关文件。
5. shell 前台返回、后台命令完成时核对实例内已打开/近期修改的文件和根配置，补发漏掉的内容变化；监视器溢出或失败则标记 stale，重建监视和实例，不把旧缓存继续称为最新结果。不要在每个 shell 后递归扫描整个仓库；失去监视时应明确不保证未打开文件的诊断覆盖。

不监听 `.git` 内部对象、target、node_modules 和虚拟环境的大量输出；但显式打开的源码、根配置及服务器要求的必要文件不能只因 gitignore 就无声丢掉。监视注册超出范围或超限时显式降级，不假装支持。没有实例时 watcher 不为了 shell 改动自动启动一套服务器；首版因此明确保证「write/edit 启动后，shell 改动也同步」，不承诺从未使用文件工具的纯 shell 会话自动启用 LSP。

内置 write/edit 的成功钩子直接通知，监视器事件按内容摘要去重；撤销/回退的 `restore_file` 也通知，以新版本表示恢复后的磁盘内容，丢弃回退前的 pending。失败/被拒绝的写入不能发成功修改通知。

### 4.5 诊断怎么给模型、怎么显示

**推荐「快速的附工具结果，晚到的独立追加」，两种交付共用一份诊断批次 id。** write/edit 的成功与 LSP 是否可用分开，已写成功的文件不能因服务器缺失变成失败工具调用。

一次修改的顺序：

```text
write/edit 提交磁盘内容
    → LSP 同步（实例 generation + 文档 version + 内容摘要）
    → 总计最多等 500 ms
        → 已有可用结果：附在尚未提交的工具结果尾部
        → 尚无结果：工具成功返回，状态标为等待诊断
    → 晚到结果：按会话合并 pending
    → 下一次真正请求模型之前校验仍适用，再追加诊断通知
```

500 ms 从修改成功后起算，包含连接/启动等待，不能在锁、initialize 或索引前又藏一段无界等待。建议 late ticket 从该次修改起最多保留 60 秒；期间文件又变则旧 ticket 取消，只追最新版本。超过 60 秒仍没到，标 timeout；之后收到的只能更新有时间标记的缓存，下一次修改再请求，不能突然把很久以前的 ticket 当本轮新错误。服务器启动总上限可比 ticket 长，但不能因此把模型阻塞更久。

**结果范围与去重建议**：

- 第一份有效结果给本会话关注文件的当前错误/警告，明确「基线未知」，不能声称全是模型新引入的。随后按 `(server, URI, severity, code, range, message)` 对比本会话已交付结果，只给新增/变化及已解决数量；行号变化可能重报，首版不做复杂追踪。
- 底层按 3.2 的替换边界保存当前列表，空数组代表该来源清除了该文件诊断；去重是交付层行为，不把历次推送无限合并。A 会话已经看过不能导致 B 会话首次看时被全局去重吞掉。
- 每批先排本次修改文件，再排同项目已关注文件；先 error 后 warning，默认不注入 info/hint。最多 20 条、8 KiB UTF-8 正文，单条信息最多 1 KiB；保留文件、行列、来源、code、总数和省略数。限制同时覆盖 relatedInformation，不随附一大段源码。
- 若新问题比额度多，保留总数和「未展示」标记；只把实际交付的条目计入已读集合，不能将被截断问题误记为模型已经知道。不为了补齐省略内容自动开轮。终端 `/lsp` 可看有界缓存中的当前列表；模型需要完整验证仍跑项目命令，首版不另加任意 LSP 调用工具。
- 只缓存本会话关注范围内的诊断；帧读取、stderr、URI 缓存和 pending 队列都设字节上限，超限显式报告不完整。不能只限制给模型的 8 KiB，却在 canter 内部无限积存整个工作区的推送。
- 不能在连续几次空数组后就写「项目检查通过」。有版本的空数组只说明该来源对该文档版本未报问题；超时/没装/未覆盖都是 unknown，不能转成零错误。

**过期和竞争建议**：版本匹配、实例 generation 匹配且交付前磁盘摘要未变，才能把有版本的结果当作该次修改的诊断。拉取请求记录发出时的版本/摘要；文件变化就取消并忽略旧回复。共享实例每文件串行同步、以磁盘为准，工具成功时保存的内容若已被其它会话覆盖，不发送过时 overlay。

协议允许推送不带 version。收到时机、等 200 ms 安静或比较当前文件摘要都**不能证明**它分析的是最新内容。对此优先用可关联的拉取；只支持无版本推送的服务器，降级为「编辑后收到、版本未确认，可能滞后」的提示，不据此宣告已修复/清零，也不标为本次 edit 引入。已知旧 generation/旧 version 的结果直接丢弃；无版本诊断的固有限制必须保留在产品说明中。

**历史和缓存建议**：

- 工具结果一旦写入历史/发给模型就不再修改。late batch 在核心 runner 下一次建请求之前通过追加通知入历史；不用另一条伪造的 tool result 填回原 toolCallId，不更换历史中的旧诊断文本，不改系统前缀。
- P2-101 的排队、去重、追加存盘可以参考，但它的自动叫醒逻辑不能直接套用。当前请求在流式输出时不插进去；当前轮已结束则等待下一次用户轮或其它本来就会发生的模型请求，不为 LSP 独立开轮。
- 未发送 pending 可以合并、丢弃和重新计算；已发送的诊断是历史事实，修复后追加说明。压缩时把仍相关问题和来源归为工具/诊断信息，不记成用户原话。回退时丢弃被回退修改的 pending，按恢复后的磁盘重新同步，不能让被回退轮的通知重新冒出来。
- 服务端重启后不重放未交付的诊断缓存；已交付的历史卡片照旧可查看，清楚标采集时间。环境及共享键不落盘。这样遵守 DESIGN 第 17 条，只向已发送前缀后追加。

**界面与公开协议建议**：

- 成功修改卡片照旧显示 diff，旁边或随后一行显示「LSP：2 errors，1 warning」「诊断等待中」「诊断不可用」；详情展开显示来源、文件、行列和消息。LSP 故障不把成功的文件卡片染成失败。
- 新增 `diagnostics` 项目，关联可选 `sourceItemId`，含批次 id、来源、文件结果、采集时间、时效标记、截断计数。快速和晚到结果复用它；UI 卡片与私有历史交付状态分别记录，inline 已进工具结果的批次不能又注入一次 notice。
- 有活动轮时把可见批次作为该轮的新项目追加；空闲时只更新 `/lsp` 的当前缓存/状态，等下一真实轮才追加历史卡片，不回写已经完成的旧轮。`/lsp` 展示不是发给模型，不能消耗模型的去重游标。
- 新增查询 `GET /v1/sessions/{id}/languageServers`、会话订阅 stop/retry 操作、`languageServer.updated` 状态事件和可选快照 `languageServers`；只广播状态变化，不把每 5 秒 RSS 采样写成永久事件。`/lsp` 展示服务器、项目、状态、RSS、共享引用数和最近失败；旧客户端忽略未知项目/事件，新客户端用 info feature 检查支持。存盘中的运行态恢复后统一为未运行/待重连，不能沿用旧 PID。
- 字段名只是设计提案。沿用 canter 的 HTTP+SSE 和会话→轮→项目结构；这些 LSP 项目/状态是 canter 的扩展，不声称是 Codex v2 原有接口。正式实现前按 DESIGN 第 8 条记录差异，生成 schema/TS 类型并照顾快照、重放、导出。

### 4.6 和项目检查、提示词的关系

**推荐保留「改完跑检查」原要求，不因 LSP 放宽。** 服务器会受项目配置、打开文件、缓存、条件编译、缺依赖影响，某些类型和 borrow-check 错误还要 rustc；测试、构建、格式化、lint 的意义也不同。

Rust 内置建议关闭保存检查，是避免每个 edit 都额外跑一轮项目命令，不是断言原生诊断够全。若用户覆盖为 true，结果中的 rustc 诊断仍不等于最后一次实际项目检查：检查可能早于最后一处修改，目标/features/env 也未必等于项目要求。不能自动拿 LSP 的空列表替代 cargo check/clippy/test 的退出结果。[保存检查配置](https://rust-analyzer.github.io/book/configuration.html#rust-analyzer.checkOnSave)

首版无需修改全局核心提示词。诊断附带一条固定简短说明「局部/异步诊断，仍按项目要求验证」，只随实际结果追加；工具清单不因服务器有没有装而反复变化。若要改全局工具说明或系统提示词，另按 DESIGN 第 20 条提交用户决定，不能借接 LSP 顺手重写。

## 5. canter 接在哪里

以下是**代码查到的落点 + 建议边界**，不是声称已有 LSP 能力。

| 现有模块和位置 | 可以复用的 | 必须新增/调整的 |
| --- | --- | --- |
| `canter-tools/src/lib.rs` 的 `Action::Change`（约 1147 行） | write/edit 共用准备、批准、原子写入、FileChange 卡片 | 成功写入后的文档同步钩子、结构化诊断批次和有限等待；失败写入无通知 |
| 同文件 `restore_file`（约 614 行） | 回退的受保护路径检查及原子恢复 | 恢复/删除也通知 LSP，取消旧票据 |
| `canter-tools/src/executor.rs:16–55,219–262`、`guardian.rs` | 原进程组、看护所有权管道、终止/kill/reap、启动时 FD 串行规则 | 现有 `CommandHandle` 没有 stdin，`spawn` 固定 `/bin/sh -c`、stdin=null；不能把 shell background 当 LSP 传输。新增 argv + 双向 stdio 的专用启动路径，只抽需要共用的底层看护部分 |
| `canter-tools/src/background.rs` | 生命周期和有界缓冲经验 | 它是按会话管理 shell，包含命令编号、输出游标、monitor；LSP 不登记成 `/ps` 的后台 shell，不复用模型 shell_output 的日志游标 |
| `canter-server/src/http.rs` 的 runtime、`lib.rs:144–171` | 会话环境注入、全服务端 draining 和关闭顺序 | 服务端拥有一份 `Arc<LspService>`，会话拿订阅；关闭时统一停池，接配置、状态 API 和 feature |
| `canter-core/src/runner.rs:223,904–910`、`background.rs:243` | 请求前汇总、工具结果提交、追加私有历史 | 保证 inline 先于 tool_result；late 在下一请求前校验/追加，独立去重、不自动 wake；压缩/回退/重放联动 |
| `canter-protocol`、`canter-tui` | 已有项目事件、Unknown 兼容、展开卡片和导出 | 诊断项目、状态快照/事件、查询和会话订阅操作、展示和 `/lsp` |

**建议模块放法**：先在 `canter-tools::lsp` 中做独立模块，内部管理 transport、配置、实例、文件监视和诊断；向核心暴露「成功文件变更」「订阅诊断批次」「状态」「关闭」这些窄接口。核心负责把结果写进历史，服务端负责持有全局实例池，终端不直接运行服务器。没有必要首版为了一个模块就再起外部守护进程；也不需要把整个 Executor 改成通用进程框架。

现有 MCP 用 `rmcp`，不能因为同属 JSON-RPC 就拿它的 MCP 生命周期/stdio 帧规则当 LSP 客户端。优先沿用现有 Tokio/serde_json/nix 做窄实现，类型和监视器库在实现件再选成熟依赖并固定版本；本设计不升级依赖。

最小通用通信仍要处理 Content-Length 字节长度、UTF-8、请求 id 对应、错误、取消、服务器反向请求、初始化能力和 shutdown。文档同步遵守服务器声明的 Full/Incremental、save.includeText；首版不用高成本最小 diff，Incremental 可发送替换整个旧文档范围的一次编辑，按协商的字符编码计算边界，默认 UTF-16。未知请求回协议错误，不能无声等待。不给服务器 `workspace/applyEdit`、执行命令、自动格式化/重命名的权限，返回明确不支持，避免越过已有 write/edit 批准和回退。

## 6. 取舍和仍未知的事

1. **资源阈值是建议值**。公开的大项目报告中有 12–16 GB、约 830 依赖接近 13 GB 的例子；它们是特定版本/项目的当事人报告，不是 canter 本次数据。此次约 2.30 GiB 也不是每个 Rust 项目的上限。[rust-analyzer 讨论 #20871](https://github.com/rust-lang/rust-analyzer/discussions/20871)、[Rust 论坛原帖](https://users.rust-lang.org/t/rust-analyzer-using-13-gib/133914)
2. **通用实现的主要风险是时效，不是发 JSON**。无版本诊断、异步多批发布、共享文档以及外部修改使「新错误」「已经修好」不能只看接收顺序判断。
3. **不做代码导航、重命名、格式化、任意 LSP request 工具**。这些超出本件「改完拿诊断」，尤其 workspace edit 会引入批准和多文件回退的新边界。
4. **shell 覆盖有限而明确**：运行中实例同步 shell/外部文件变化；从未激活 LSP 的纯 shell 会话第一版不自动起服务。监视失败或超限需显示降级，不用无成本保证的说法。
5. **此次数字不验证实施后的共享/回收策略**。阈值、晚到 60 秒、500 ms 同步预算、打开文件限额均是有依据的起点，仍需实现时用假服务器和已装服务器验证。未获得模型效果数据，不预测「错误减少多少」或「长任务成功率提高多少」。

## 7. 估工作量和分件

以下是**建议分件，不是新增验收要求或已经派出的任务**。每件实施时由主控写结果单、用户看过再派。估计包含作者编写直接相关测试的时间，不按行数推算。

| 顺序 | 件 | 做什么 | 影响模块 | 大小/估计 |
| --- | --- | --- | --- | --- |
| 1 | 通用 LSP 生命周期和配置 | 专用双向 stdio；guardian 接入；initialize/配置反向请求/诊断能力；实例池与环境隔离；默认关、懒启动、重试/资源阈值、关闭和 serve 替换 | tools 底层、server 配置/持有 | 大，3–5 人日 |
| 2 | 文件同步和诊断收集 | write/edit/restore 成功钩子；版本和 generation；监视和 shell 完成核对；push/文档 pull；过期/空结果/缓存；文件限额、取消与退避 | tools LSP、core 的 shell/回退接点 | 大，3–5 人日，依赖 1 |
| 3 | 模型交付和公开协议 | inline 500 ms、late 队列、去重/截断、追加历史；不叫醒；诊断项目/状态/API、旧数据兼容；压缩、回退、导出数据链 | core、protocol、server | 大，3–4 人日，依赖 2 |
| 4 | 终端展示和控制 | 诊断摘要/详情；等待、不可用、版本未确认状态；`/lsp` 查询与订阅 stop/retry；旧服务端 feature 检查；导出显示 | tui、CLI 客户端 | 中，1–2 人日，依赖 3 |
| 5 | 首批语言和集成收口 | 用户定首批后，配置 Rust/Python 的 root、settings、环境；假服务器固定回放覆盖完整链；已装服务器实测；核对共享、失效、替换、资源退出 | 各模块的配置和集成测试、文档 | 中，2–3 人日，依赖 1–4 |

合计 12–19 人日；主控审查/集成返修另留 2–3 人日。接 TS/JS 估再加 1–2 人日；已有正常编译数据库的 C/C++ 配置估 1–2 人日，替用户修复杂构建环境不包括在内。没有必要拆成「每种语言写一套框架」，也不建议以当前一次性驱动的体量估算完整产品工作量。

实现期值得保留的自动验证方向：假服务器慢启动/乱序/崩溃/无版本推送/反向配置请求；两会话同 URI 与不同环境；write/edit/checkout/回退后的 stale 清理；晚到不改前缀、不叫醒、不双投；协议旧快照和终端降级；服务端退出清理进程。这些只是供主控拆任务时选择的风险说明，**本设计任务没有自行运行或补写产品测试**。
