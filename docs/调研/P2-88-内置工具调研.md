## 结论摘要

出处和理由见第 6 节。

| 项 | 建议 | 一句话理由 |
| - | - | - |
| grep / glob 专门工具 | 以后再说；先做两处小改 | 四家里三家默认不给专门搜索工具（Codex 没有；pi 有但默认不开；Claude Code 在 macOS / Linux 上默认不给），canter 的 shell 白名单已经让 `rg`/`grep`/`find`/`ls` 免批准；眼下的毛病是「搜不到」画成红色失败、提示词没说用 `rg`，小改就能解决。 |

| `shell` | `/bin/sh -c` 跑命令，每次新 shell | `command`、`timeoutMs`（默认 120 秒，至多 600 秒） | 给模型 32 KiB，超了留头尾各 16 KiB；客户端 1 MiB [CA2] | 白名单只读命令不问（含 `rg`、`grep`、`find`、`ls`），其余按模式问 |
| `ask_user` | 单题多选 | `question`、`options`（2–4 个） | — | 不走批准 |
| `web_fetch` | GET 一个网址，HTML 转 Markdown | `url` | 30 秒、下载 5 MiB、给模型 32 KiB | `alwaysAsk`、`askForExecution` 都问 |
| MCP 工具 | `mcp__服务__工具` | 服务定义 | 同上 | 按执行权限问 [CA9] |

六个内置工具的说明共 690 词（约 900 token）[CA6]。

### 1.3 看下来的三个现象

1. **搜索专门工具不是共识。** opencode 默认给 `grep`/`glob`；pi 有但默认不开；Codex 从来没有，提示词让模型用 `rg`；Claude Code 有，但在 macOS / Linux / WSL 上默认不给，改让模型在 Bash 里用 `find`、`grep`（跑的是内嵌的 `bfs`、`ugrep`）[CL1]。为什么这么改，文档没写（未知）。
2. **计划 / 待办工具近来多数默认关。** Codex 0.163.0 默认关 `update_plan` 并从提示词里删掉相关说明 [C4]；opencode 放在 `experimental.todo` 后面 [O4]；Claude Code 只在较旧的模型上默认给，文档的理由是「On newer models, Claude keeps track of multi-step work without a written checklist, and the tools' definitions and reminders take up context」[CL1]。
3. **LSP 少有人内置。** 四家里只有 Claude Code 有，而且要用户自己装插件和语言服务器；opencode v2 明确去掉了 [O5]。补充参照里 omp 做得最全 [OMP1]，Gemini CLI 没有 [G1]。

### 2.2 单独做工具和「靠 shell 跑 `rg`」比

| 方面 | 单独做 grep / glob 工具 | 现在靠 shell 跑 `rg` |
| - | - | - |
| 批准 | 可以定成只读风险，任何模式和审查轮都直接跑（推测） | 白名单已覆盖常见写法；带管道、变量、未加引号的通配符时会问 [CA2]。实际差别小（推测） |
| 受保护路径 | 可以在遍历时跳过 canter 状态目录，和 `read` 同一套保护（推测） | 只查起点：起点是状态目录或其上级（比如 `~`）就问 [CA2] |
| 截断 | 按条数截，告诉模型「截了，缩小范围」（pi、opencode 这样做）[PI2][O3] | 按字节留头尾，中间的匹配丢了，模型不知道丢了哪些文件（推测） |
| 搜不到 | 回「No matches」，正常结果 | 退出码 1 画成红色失败 [CA4]；Claude Code 专门把这种退出码 1 当正常 [CL1]，canter 可以照做，不必为此加工具 |
| 工具说明的 token | 每个工具说明约 35–100 词（只数说明文字：pi `grep` 约 100、`find` 约 60、`ls` 约 45；opencode `grep` 约 90、`glob` 约 35）。加 `grep`、`glob` 两个约 130–200 词，连参数定义约 200–350 token，每次请求都带（粗估）；相当于现在 6 个工具说明的两到三成 [CA6] | 不加 |

| 模型更会用哪种 | 没找到公开的对比数据（未知）。Codex 让 GPT 用 `rg`；Claude Code 在 Unix 上默认让 Claude 用 Bash 搜；opencode 默认给专门工具。DeepSeek 用哪种更好，只有真调对比才知道（要用户在场、花钱） | 同左 |
| 界面卡片 | 可以有专门卡片，比如「Search "foo" · 12 matches in 5 files」（推测） | 卡片显示整条命令（P2-65）。Codex 的折中：不加工具，终端解析命令拼「Explored」卡片，但解析代码 2,766 行，注释写着「DO NOT REVIEW THIS CODE BY HAND」[C6] |

### 3.2 起服务器的耗时和内存

本轮按任务没装、没跑语言服务器，下面都是公开数据：

- rust-analyzer：有人在 Zed 项目上报告空闲 12 GB、索引时最高 16 GB，维护者回复说和 salsa 缓存、trait 求解有关，迁移完新求解器后再查 [W1]（2025-10-20）；另一位约 830 个依赖的工作区接近 13 GB，回复说「13gb is quite typical for a workspace that big」[W2]（2025-09-14）。
- Claude Code 文档也承认 rust-analyzer、pyright 会索引整个项目，内存高时建议关掉插件、改用搜索 [CL3]。
- 启动耗时：没找到官方数据（未知）。
- canter 自己的仓库 `Cargo.lock` 有 346 个包 [CA11]，在它上面 rust-analyzer 要多少内存、多久能用，未知。
- rust-analyzer 的 `checkOnSave` 默认开，保存时跑 `cargo check` 拿诊断，和「原生诊断」是两个开关 [W3]；omp 把 `checkOnSave` 关了 [OMP1]。所以要拿到和 `cargo check` 一样全的错误，多半还是要跑 `cargo check`（推测）。

### 3.3 和 canter 的结构合不合（以下都是推测）

合的地方：

- canter 一台机器一个常驻服务端，同一项目的多个会话可以共用一个语言服务器，省掉重复索引。omp 为了共用还要另起守护进程，canter 天然就有这一层。
- 只读查询（定义、引用、诊断）可以算只读风险，审查轮照样能用。

难的地方：

- **环境变量**：服务端在后台起，`PATH` 来自各会话的客户端（DESIGN 第 14 条）[CA9]；两个会话 `PATH` 不同，能不能共用一个服务器要定规矩。rust-analyzer 经 rustup 代理起，还依赖 rustup 的环境。
- **文件同步**：`write`/`edit` 改的文件能通知语言服务器；`shell` 里 `cargo fmt`、`sed -i`、`git checkout` 改的文件要靠监视文件变化才知道。
- **内存**：常驻服务端长期挂着十几 GB 的 rust-analyzer 不合适，要用到才起、空闲就停。`canter serve --replace` 升级后要冷启动重来。
- **重命名**：rename 改的是多个文件，不经 `write`/`edit` 的 diff 和批准，也进不了 P2-23 的文件回退（回退只认内置 write/edit）[CA9]。真做的话，重命名是最后才考虑的。
- **没装、崩了**：照常干活，诊断缺席，工具回错误，和 Claude Code 一样。

大概多大：大件。新的进程管理和 JSON-RPC、文件同步、诊断收集（核心）；工具；协议（诊断怎么显示、`/lsp` 状态）；终端。

### 3.4 不做 LSP 的替代

canter 的系统提示词已经要求改完跑项目的检查（测试、构建、格式化、lint）[CA5]；opencode v2 去掉 LSP 时也是这样建议的 [O5]；Codex 一直没有 LSP。对 Rust 项目，`cargo check` 本来就要跑。
