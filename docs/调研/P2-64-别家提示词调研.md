# P2-64 别家提示词调研

2026-10-27。按 `docs/任务/P2-64-别家提示词调研.md` 做：只查主流 agent 的系统提示词和其他内置提示词写了什么、多长、在一次请求里放在哪一层，以及和 canter 现状的对照。本轮不给推荐方案，不改代码。

调查方法：只读源码、公开文档和本机程序文件；没有运行任何一家 agent，没有抓真实请求，没有调用模型接口。源码里的字数是按空白分词后的词数；token 是按 1 词约 1.3 token 的粗估，只用于比较量级。中文结论里的「事实」都有出处；没有出处的写「推测」或「未知」。

补充：

- Codex 的 `models.json` 模型清单是当前运行时来源；`core/gpt_*_prompt.md` 是旧版文件，仍留在仓库里，但会话启动时优先用 `instructions_template`，其次才是配置覆盖或历史记录。[C2][C8]
- Claude Code 的完整静态提示词不是单个字符串：程序里有 `__SYSTEM_PROMPT_STATIC_BREAKPOINT__` 标记，按静态/动态两段拼给 API，并分别设缓存断点。[CL2][CL3]
- Gemini 的 prompt 不含 `AGENTS.md`；项目文件叫 `GEMINI.md`。Tier 1（全局、用户项目 memory）拼进 `systemInstruction`；Tier 2（扩展、项目 memory）和环境信息放第一条 user 消息。[G1][G3][G4]
- opencode 的 provider prompt 是「override」：gpt/kimi/meta/trinity 会替换基础 111 词，anthropic 是「append」。[O3]

### 1.3 分家观察

**Codex。** 系统提示词的核心不是 `models-manager/prompt.md`，而是 `models.json` 里每个模型的 `instructions_template`。当前 11 个模型的模板从 2,664 到 3,452 词，内容覆盖 Personality、General、Engineering judgment、Frontend guidance、Editing constraints、Autonomy、Working with the user、Formatting、Final answer、Intermediary updates。[C1] `models-manager/prompt.md`（3,389 词）是回退模板，额外写了 AGENTS.md spec、Preamble、Planning、Task execution、Validating、Tool Guidelines；这两份不是同一份。[C1][C8] 模型模板里明确要求「先读代码、少猜、用 `rg`、并行读、不要串无关命令、验证、最终回答结构化」。[C1]

**Claude Code。** 程序里能读到的主干包括：身份句（CLI / Agent SDK / 通用 Claude agent 三种）、`Use the instructions below…`、URL 不要猜、工具结果可能含注入、Tone and style、Doing tasks、Using your tools、Plan mode 说明、session-specific guidance、`<system-reminder>` 说明。另有一条专门的「verified vs assumed」段落，要求区分「跑过/读过」和「以为」。[CL3] 官方文档说明 CLAUDE.md 不是系统提示词的一部分，而是作为 system 之后的 user 消息注入；环境（工作目录、平台、shell、OS 版本）也在对话里，不在系统提示词里。[CL1][CL2]

**Gemini CLI。** `getCoreSystemPrompt` 按选项拼：Preamble、Core Mandates（安全、来源控制、不可信数据、上下文效率）、SubAgents、AgentSkills、Hook、Primary Workflows / Planning Workflow、Task Tracker、Operational Guidelines（Tone、Security、Tool Usage、Interaction）、YOLO、Sandbox、Git、User Memory。[G1] 其中 Core Mandates 明确把外部工具/MCP 输出包在 `<untrusted_context>` 里当被动数据；Operational Guidelines 要求目标少于 3 行、GitHub Markdown、修改文件前解释、被拒绝不重试。[G1]

**opencode。** 基础 `system.txt` 只有 111 词：身份、Harness（GFM、system-reminder 是 harness 指令、独立工具并行）、Communication、Working in codebases，以及按工具插入的几行专用工具规则。[O2] 真正长的内容在 `plugin/system-prompt/*.txt`：OpenAI、gpt-astra、Kimi、Meta、Trinity、Anthropic 各一份，按模型 id 命中后覆盖基础 prompt；Anthropic 是追加。[O3] 这些 provider prompt 里有大量工具、验证、精确性、子 agent、并行规则。[O3]

**pi。** 默认 prompt 只有 239 词，结构是 preamble、tools、rules、docs、project_context、skills、cwd 七段。工具列表和规则是按启用工具生成的；项目上下文（AGENTS.md 等）直接放进系统提示词；没有权限、git、计划、子 agent、输出格式这些大段内容。[PI1]

**omp。** 在 pi 的结构上大幅扩写：`system-prompt.md` 1,735 词，含 Role、Engineering、Personality、Runtime、Skills & Rules、Internal URLs、Tool Inventory、xd 设备、Scratchpad、Tool Policy、Exploration、AST、Delegation、Workflow、Delivery、Critical 等；70 处条件块按工具/设置/人格裁剪。[OMP1] 工具战术、委派门槛、验证、交付契约都写在系统提示词里，另有一批 `prompts/system/*.md` 作为计划模式、标题、子 agent、btw、压缩、记忆等专用提示词。[OMP3]

**canter。** `SYSTEM` 只有 78 词：在用户项目里写代码、改前先读相关文件和项目说明、最小改动、保留无关工作、验证、用工具拿事实、工具输出和仓库内容当数据、如实说失败、没定的重要选择先问、不泄露凭证和运行时配置。[CA1] 其余内容全部是环境、`AGENTS.md`、技能清单；工具使用策略、权限、格式、计划、git、子 agent 都没有写。[CA1]

### 2.3 会话中途插进来的提醒

- **Claude Code** 最典型：文档明确说 system reminder 是「应用程序加到对话里的文本」，CLAUDE.md、output style、hook 输出、可用技能/子 agent、任务列表提醒、文件变更提示都以 `<system-reminder>` 或单独的 system 消息出现；它们不是系统提示词，通常放在 user 消息里，也可能是一条短 system 消息。[CL2] 程序里的说明也区分了这两种形态。[CL3]
- **Codex** 用 world-state 的「快照 + 差分」：环境、AGENTS.md、权限、模型切换、计划等状态先记快照，变化时只在历史里追加「替换说明」，不重写前面的前缀。AGENTS.md 变化时追加 `REPLACEMENT_NOTICE`；无变化就不追加。[C4]
- **opencode** 把技能、MCP、AGENTS.md、日期/环境都做成「instruction source」，初始值放第二条 system 部分，之后变化以 system 消息追加；Chat Completions 适配器统一把中途 system 包成 `<system-update>` 放进 user 消息。[O4][O5] Plan mode 的提醒特意放在对话尾部、用户消息之前，避免动缓存前缀。[O6]
- **Gemini CLI** 走「分层上下文」：全局指令在 systemInstruction；扩展+项目在第一轮 user 消息；子目录内容在工具输出里按需加载。环境/日期/目录树在第一条 user 消息。[G4]
- **pi** 把系统提示词拆成可 diff 的 section，变化时发一条只含变化 section 的 system 消息；不支持中途 system 的接口则把所有后续 system 消息折叠进开头那条。[PI2][PI3]
- **omp** 有整套中途 notice：自动继续、btw、计划模式、MCP、会话状态、工具提醒等，分别在 `prompts/system/` 下。[OMP3] 对 DeepSeek 这类 provider，append-only 模式会冻结 system+tools 前缀，后续只追加消息。[OMP2]
- **canter** 没有中途提醒机制：前缀在打开会话时固定，历史只追加；`/review`、`/btw`、`/handoff` 都是一次性请求，不写回主线历史。[CA1][CA2][CA3][CA4]

## 3. 一次请求里的位置（分层）

下面的图只画模型看到的结构；括号里是出处。不同 provider 的字段名不同，图里用「system / developer / user」表示角色层。

### 3.1 Codex（Responses API）

```text
input[0]  developer: <base instructions>                 [C3]
input[1]  user:      # AGENTS.md instructions …          [C4]
input[..] user:      <environment_context> …             [C5]
input[..] developer: <permissions instructions> …        [C5]
tools:              [exec_command, write_stdin, apply_patch,
                     update_plan, view_image, …]          [C7]
之后:               user / assistant / tool 项；world-state
                     变化时在这里追加差分
```

事实：

- Responses 请求体里没有 `instructions` 字段；基础指令被包成 developer 角色的消息，插在 `input` 最前面。[C3]
- 工具定义在顶层 `tools` 字段，不混在消息里。[C3][C7]
- AGENTS.md 是 user 角色的 fragment，开头是 `# AGENTS.md instructions for <dir>`，结尾 `</INSTRUCTIONS>`；全局、线程、仓库的说明合并成一个快照。[C4]
- 环境是 user 角色 `<environment_context>`；权限是 developer 角色 `<permissions instructions>`。[C5]
- 每个 step 重新渲染 world state，和上一份快照比较，只把变化的部分追加到历史。基础指令是 `Placement::Prefix`，每次请求重新放到开头；AGENTS.md/环境/权限是 `Mergeable`，同角色合并成一条消息。[C4]
- 请求带 `prompt_cache_key`，按线程生成，用于跨请求命中前缀缓存。[C3]

### 3.2 Claude Code（Anthropic Messages）

```text
system:  [静态段] [__SYSTEM_PROMPT_STATIC_BREAKPOINT__] [动态段]
         （两个 text block，各自 cache_control）         [CL2][CL3]
messages[0] user: <system-reminder> 初始上下文
         （claudeMd、userEmail、currentDate、gitStatus、Environment…）[CL1][CL3]
tools:   工具定义（单独字段）
之后:    user / assistant / tool_result；中途提醒以
         独立 system 消息或 <system-reminder> 出现        [CL2]
```

事实：

- 默认有两段系统提示词：静态段和动态段，断点标记在中间；只有直接调 Claude API 或 AWS 上的 Claude Platform 时才拆两段，走 Bedrock/Vertex/Foundry/网关时整段发送。[CL2]
- 环境（cwd、平台、shell、OS 版本）和 CLAUDE.md 都在对话里，不在系统提示词里；官方文档明确说 CLAUDE.md 是 system 之后的 user 消息。[CL1][CL2]
- CLI 有 `--exclude-dynamic-system-prompt-sections`，把 cwd、环境、memory 路径、git 状态从系统提示词移到第一条 user 消息，目的是跨用户/机器复用前缀缓存。[CL3]
- 系统提示词在会话第一次请求时记录，之后复用，直到压缩或新会话才换；中途要改行为，官方建议放进后续 user 消息或 hook 的 `additionalContext`。[CL2]
- 中途提醒可以是一条独立 system 消息，也可以是 user 消息/tool result 里的 `<system-reminder>`；程序里也专门做了「伪 system-reminder」转义，防止用户内容伪造。[CL3]

### 3.3 Gemini CLI（Google GenAI）

```text
systemInstruction: [核心 prompt + Tier 1 memory
                    （全局、用户项目 memory）]              [G1][G2][G3]
contents[0] user:  <session_context>
                   （日期、OS、临时目录、目录树、
                    Tier 2 memory：扩展/项目）              [G4]
tools:             functionDeclarations                    [G5]
之后:              user/model/function 轮次
```

事实：

- 核心 prompt 和 Tier 1 memory（全局、用户项目记忆索引）拼成一条 `systemInstruction`；`renderFinalShell` 把 memory 附在核心 prompt 后面。[G1][G2][G3]
- 环境不是系统提示词的一部分：`getEnvironmentContext` 生成 `<session_context>`，作为第一条 user 消息。[G4]
- 代码注释写明三层：Tier 1 全局放 system instruction；Tier 2 扩展+项目放第一条 user 消息；Tier 3 子目录放工具输出，按需加载。[G4]
- 工具定义单独发送。[G5]
- memory 刷新时（`refreshMemory`、`refreshMcpContext`）会调用 `updateSystemInstructionIfInitialized` / `updateSystemInstruction`，整段 systemInstruction 重算；没有做差分追加。[G2][G3]

### 3.4 opencode（多协议）

```text
system[0]: 基础 prompt（111 词）或 provider prompt      [O2][O3]
system[1]: 初始 instructions 块
           （date、env、AGENTS.md、skills、MCP references…）[O1][O4]
tools:     工具定义
messages:  user / assistant / tool
中途:      instructions 变化 → 新的 system 消息（Chat Completions
           包成 <system-update> 塞进 user）              [O4][O5]
```

事实：

- `baseTranscript` 的 `system` 是数组：第一项是 agent 自己的 system 或基础 prompt，第二项是 `initial` instructions。[O4]
- instructions 的来源按「用户级→项目级→日期/环境」排序，注释说明这是为了让 baseline 可复用。[O1] 日期和环境放在 `core/date`、`core/environment`，初始值就是 system 的第二部分。[O1]
- instructions 变化时，`InstructionState.commit` 把变化渲染成文本事件，后续请求把 `Message.system(update)` 放在历史里；Chat Completions 适配器把中途 system 包成 `<system-update>` 放进 user 消息。[O4][O5]
- Anthropic 适配器支持原生中途 system 的 Claude 版本时发 `role: system`，否则包成 user 文本；Gemini 也包成 user 文本。[O5]
- Plan mode 的提醒放在对话尾部、用户消息之前，明确为了不动缓存前缀。[O6]

### 3.5 pi（多协议）

```text
system:  preamble / <tools> / <rules> / <docs> /
         <project_context> / <skills> / <cwd>          [PI1]
tools:   工具定义（单独字段）
messages: user / assistant / tool
中途:    section diff → 新 system 消息（模型支持时）
         或折叠进开头 system（模型不支持时）           [PI2][PI3]
```

事实：

- `buildSystemPromptSections` 按固定顺序生成 section：preamble、tools、rules、docs、project_context、skills、cwd；项目上下文里的 `AGENTS.md` 用 `<project_instructions path="…">` 包起来。[PI1]
- `_preparePromptAndToolLoadout` 对 section 做 diff，只把变化的 section 作为一条新的 system 消息放进历史。[PI2]
- 模型未声明支持中途 system 时（DeepSeek 的 Chat Completions 默认如此），后续 system 消息会被折叠进开头那条，只保留当前 section 状态。[PI3][PI5]
- Anthropic 的自适应：OAuth token 时先发 Claude Code 身份句，再发自己的 system；普通 token 只发自己的 system。[PI3]
- Chat Completions 根据模型是否推理，选择 `developer` 或 `system` 角色作为指令角色。[PI3]

### 3.6 omp（多协议 + append-only）

```text
systemPrompt[0]: 静态大模板（Role/Engineering/Tool Policy/Workflow…）[OMP1]
systemPrompt[1]: <project-context>
                 （workstation、repo-rules/AGENTS.md、dir-context、
                  workspace-tree、active-repo、append）          [OMP1]
tools:           工具定义
messages:        user / assistant / tool
append-only 模式: system+tools 冻结为 StablePrefix，消息只追加；
                 模型/工具/MCP 变化时才 invalidate                   [OMP2]
```

事实：

- 渲染结果先推静态模板，再推 `project-prompt.md` 生成的 `<project-context>`；注释明确说这样不同目录的会话共享静态前缀，Anthropic 的缓存断点落在 project block 之前。[OMP1]
- `project-prompt.md` 里的环境是 `<workstation>`（OS、架构、模型等），`AGENTS.md` 在 `<repo-rules>`，嵌套说明在 `<dir-context>`，工作区树在 `<workspace-tree>`。[OMP1]
- append-only 模式的注释写明了目标和机制：system prompt + tool specs 只算一次并冻结，消息只增长，除非 `invalidate()`（如 MCP 重连）。[OMP2]
- 该模式对 `deepseek`、ollama、lm-studio、llama.cpp 等 provider 自动开启；模型切换会触发 `invalidateForModelChange`。[OMP2]
- 中途 notice 很多，都是独立的 prompt 文件，按事件追加。[OMP3]

### 3.7 canter（Chat Completions）

```text
messages[0] system: SYSTEM
                    + Working directory / System / Date (UTC)
                    + Global instructions (~/.agents/AGENTS.md)
                    + Project instructions（根目录到 cwd 每层 AGENTS.md）
                    + Available skills（名字、简介、SKILL.md 路径）[CA1]
tools:              [read, write, edit, shell, ask_user, web_fetch, MCP…][CA1]
messages[1..]:      user / assistant / tool
压缩:               同一 prefix + 转写文本 → 生成摘要；
                    新历史 = 最近用户消息 + `[Context summary]` user 消息 [CA2]
/btw、/handoff:     同一 prefix + 历史 + 问题；不写回历史            [CA3]
/review:            TUI 生成一条 user 消息（指令 + 带 untrusted 标记的 diff）[CA4]
```

事实：

- `prefix()` 只返回一条 `Message::System`，把固定段、环境、全局和项目 `AGENTS.md`、技能全部拼进去；工具定义由 `request()` 单独放进 `tools`。[CA1]
- `AGENTS.md` 每份上限 64 KiB；读取顺序是全局，然后从仓库根到工作目录逐层。[CA1]
- 前缀在打开会话时生成，之后不重读；中途改 `AGENTS.md` 要等下一个会话。[CA1]（DESIGN 第 17 条）
- 压缩请求复用同一个 prefix，把历史转写成文本放进 user 消息；压缩后的历史是「保留的最近用户消息 + 一条 `[Context summary]` user 消息」。[CA2]
- `/btw` 直接复用 `context::request()` 的 prefix+history，再追加问题；`/handoff` 在同样基础上追加固定英文交接说明和方向。[CA3]
- `/review` 的指令和 diff 在 TUI 侧拼成一条 user 消息，diff 用 `<<<BEGIN_UNTRUSTED …>>>` / `<<<END_UNTRUSTED …>>>` 包住。[CA4]

- opencode 的 DeepSeek route 是 `OpenAI Chat`，`/chat/completions`；system parts 合并成一条 leading `role: system` 消息，中途 instructions 更新包成 `<system-update>` 放进 user 消息。[O5][O8]
- pi 的 DeepSeek provider 是 `openai-completions`；如果模型没有声明 `supportsMidConvoSystemMessages`，后续 system 消息会被折叠进开头那条 system，等价于改前缀。[PI3][PI5]
- omp 对 `deepseek` 自动开启 append-only context，system+tools 冻结，后面只追加消息；这是几家里面最明确为 DeepSeek 前缀缓存优化的一种做法。[OMP2]
- canter 只有 Chat Completions；所有内容在一条 system 里，历史只追加，和 DeepSeek 的前缀缓存天然兼容，但动态内容（日期、AGENTS.md、技能）全部落在前缀里。[CA1]

### 4.2 层次差别

1. **canter 把动态内容放进同一条最高优先级消息。** Codex 把 AGENTS.md/env 放 user，Claude 把 CLAUDE.md/env 放 user，opencode/pi 把初始 instructions 放第二段 system，omp 把 project-context 放第二块，Gemini 把 Tier 1 memory 放 systemInstruction、Tier 2 memory 和环境放第一条 user；canter 把环境、全部 AGENTS.md、技能都塞进同一条 system。[C4][CL1][O1][PI1][OMP1][G1][G3][CA1]
2. **canter 只有一条 system。** Codex 按角色分 developer/user 多条，Claude 是两段 system + 多条 user，opencode 是两条 system 部分，omp 是两块 systemPrompt。[C3][CL2][O4][OMP1]
3. **canter 没有「记录系统提示词」的概念。** Claude 在第一次请求时记录系统提示词，之后复用，直到压缩或新会话；Codex 每步重算 world-state 但只追加差分；canter 是打开会话时算一次，之后完全不看变化。[CL2][C4][CA1]
4. **canter 的压缩摘要落在历史里，不在前缀里。** 压缩后的新历史是「最近用户消息 + `[Context summary]`」，prefix 不变；Codex/Claude/Gemini/opencode/pi/omp 的压缩结果也都是新历史/新摘要，不重写固定提示词。[CA2][C6][CL3][G1][O6][PI6][OMP5]
5. **canter 的 `/review` 是唯一带不可信标记的路径。** 主线工具输出没有 `<untrusted_context>` 或等价包装；Codex 用权限和 guardian，Gemini 用标签，Claude 用 system-reminder 说明，omp 用 XML 规则。[CA4][C5][G1][CL2][OMP1]

### 4.3 回答用户的问题

**canter 把固定段、环境、`AGENTS.md`、技能拼成一条 system 消息，和别家不一致。**

- 一致的部分：都把固定指令放最高优先级（system 或 developer）；工具定义都单独发；都尽量让请求开头在会话内可复用（Codex/Claude/omp 有明确机制，见 3.8）。[C3][CL2][OMP2][CA1]
- 不一致的部分：
  1. **动态内容的位置**：多数别家把环境、项目指令、权限从固定提示词主体里拆出去（放 user，或第二段/第二块 system）；canter 全塞在同一条 system 里。[C4][CL1][O1][PI1][OMP1][G3][CA1]
  2. **消息条数**：别家通常是多条（固定、项目、权限、环境分别一条或两块），canter 只有一条。[C3][CL2][O4][OMP1]
  3. **变更处理**：别家有差分、快照、重算、冻结等机制；canter 在会话中途完全不处理，等下个会话。[C4][CL2][O4][OMP2][CA1]
  4. **内容覆盖面**：别家的系统提示词普遍包含工具策略、权限、计划、输出格式、安全/注入；canter 只覆盖身份、最小改动、验证、如实报告、先问、不泄露凭证。[C1][CL3][G1][O3][OMP1][CA1]

按「层」比较，canter 和 Gemini 的 Tier 1 最接近（memory 进 system），但 Gemini 把扩展/项目 memory 和环境放第一条 user，且 memory 刷新会重算 systemInstruction；canter 连环境都在同一条 system 里，变更则完全不处理。[G1][G3][G4][CA1]
