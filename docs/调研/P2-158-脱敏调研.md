**结论摘要**

- **事实**：别家没有一家在「发给模型的每一段内容」上做通用密钥格式扫描。Codex 主要靠 shell 沙箱、可配置的 shell 环境变量策略，以及默认关闭的凭证遮蔽；Claude Code 靠 Read/Edit/Bash 权限规则、Bash 沙箱和默认关闭的 `sandbox.credentials`，官方文档明确说没有内置凭证拒绝清单；opencode 只给默认 agent 加了「读 `*.env` / `*.env.*` 要问」这一条，shell 默认放行；pi 核心没有批准和扫描，文档要求用户自己上操作系统沙箱；omp 有最接近本件的可逆占位符替换，但默认关闭，而且只按内容格式、不按文件名。
- **事实**：canter 现在只有很窄的几处防：文件工具拒绝 canter 自己的状态目录和 `config.json`；沙箱打开时再加 `~/.ssh`、`~/.aws`、`~/.gnupg`、状态目录不可读；MCP 结果里替换配置的 `env`/`headers` 值和 OAuth token，`web_search` 结果里替换 DeepSeek key 的回显。项目里的 `.env`、私钥、带令牌的配置，沙箱开或关都能被 `read` 读到；shell、`!`、MCP、`web_fetch`、`web_search`、AGENTS.md、技能、LSP 诊断、压缩摘要都没有通用格式扫描。[K1][K2][K3][K5][K6][K8][K9][K10][K14]
- **事实**：canter 的 DeepSeek key 在 `config.json`，不在会话 shell 的环境变量里；但客户端把启动终端的整个环境原样交给会话，用户自己 export 的 `*KEY*`、`*TOKEN*` 等会进 shell，`env` 一跑就随输出进模型。沙箱关时模型还能在批准后或「全部允许」下 `cat ~/.canter/config.json`。[K9][K19]
- **推测**：最贴合用户「不走 sandbox 也应该脱敏」的做法是「发送边界按格式替换、写回时按映射还原」为主，再加一小份高风险文件名/路径门和环境变量过滤；只按文件名挡不算脱敏，只按格式替换也挡不住无格式密码、拆分/加密和 shell 直接外传。gitleaks 的规则可以用（MIT），但整份 222 条会带来误报和性能开销，建议先取高置信前缀规则，DeepSeek 要自己补。

### 1.2 Codex（`rust-v0.163.0`）

- **事实**：Codex 内置模型工具里没有通用的 `read` 文件工具；读文件主要经 `shell`（以及 `view_image`），扩展或 MCP 可以另外提供 `read_file`，app-server 的 `fs/readFile` 是客户端接口。文件读取的边界主要是沙箱和 shell 环境；没有一份「这些路径不让模型读」的默认清单。[C1][C7][C8]
- **事实**：默认文件系统 profile 是「全盘可读 + 指定根可写」；可写根里的 `.git`、`.agents`、`.codex`、`.aws` 有**写**保护，不是读保护。[C1][C2][C8]
- **事实**：`ShellEnvironmentPolicy` 默认 `inherit = All`、`ignore_default_excludes = true`。也就是说默认**不**按 `*KEY*`、`*SECRET*`、`*TOKEN*` 过滤；只有把 `ignore_default_excludes` 设为 false，才会应用这三条默认排除。另有硬编码的 `NON_INHERITABLE_ENV_VARS`（Codex 自己的执行服务令牌、`NODE_REPL_AUTH_TOKEN`、guardian key、OpenAI 身份令牌文件等），无论用户怎么配都不会传给子进程。[C3][C4]
- **事实**：`credential_masking` 是 `UnderDevelopment`、默认 false 的特性；打开后 shell 快照拿到的凭据是 dummy/占位值，真实值由启用的网络代理在出站请求里替换。它主要覆盖 shell 环境里的凭证，不是对文件内容或工具输出做格式扫描；没有网络代理时还会给出「masking inactive」警告。[C5][C6][C11]
- **事实**：用户可以通过 permission profile 的 `deny` 文件系统项、`shell_environment_policy.exclude` / `include_only` 自行收窄；这些都不是默认。没有看到对模型请求内容的通用脱敏。[C3][C10]
- **未知**：企业托管 profile 的实际默认值、以及 Codex 云会话里的额外代理是否覆盖文件内容，本轮没有查。

### 1.3 Claude Code（官方文档，2026-10-31）

- **事实**：官方 `sandboxing` 页写：Bash 沙箱默认可以读「大部分机器，包括 `~/.ssh` 和 `~/.aws/credentials` 这类凭证文件」；环境变量默认从 Claude Code 继承，包括其中的秘密。`sandbox.credentials`、`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` 可以另外收窄。[A3]
- **事实**：`sandbox.credentials` 页明确写「There is no built-in credential deny list, so only the files and variables you list are restricted」；`sandbox.credentials.files` 的默认是 unset，即默认没有受保护的凭证文件。`deny` 对文件是沙箱内拒读、对环境变量是每条沙箱命令前移除；`mask` 对环境变量给每会话哨兵并由 TLS 终止代理换回，对文件在 Linux/WSL2 给哨兵副本、在 macOS 直接不可读。[A3][A4]
- **事实**：Read 权限规则可以按路径拒绝，例如 `Read(./.env)`、`Read(./.env.*)`、`Read(./secrets/**)`；文档把 `.claudeignore` 说成没有作用，要搬到 Read deny 规则里。这是用户配置，不是默认清单。[A1]
- **事实**：`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` 会从 Bash、hooks、stdio MCP 等子进程环境里去掉「名字或值看起来像凭证」的变量；`GITHUB_TOKEN`、`GH_TOKEN` 和代理设置保留。默认不开启。[A5]
- **事实**：错误报告和 `/feedback` 包会按已知 API key/token 格式脱敏；这只覆盖这些上报通道，不是模型请求。[A6]
- **事实**：auto 模式的分类器会拦「把敏感数据发到外面」这类动作，但那是按命令/动作审查，不是对文件内容或工具输出做格式替换。[A2]
- **未知**：文档没有逐项列出产品内置的 Read 默认 deny；本轮没有静态查看本机二进制，不能断言除文档所述外没有隐藏默认。文档能确认的是 `sandbox.credentials` 没有内置清单。

### 1.4 opencode（`v2.1.3`）

- **事实**：默认 agent 的权限是 `*` allow，外加读 `*.env`、`*.env.*` 为 ask、`*.env.example` 为 allow。`read` 工具在真正读之前调用 `FileAccess.authorizeRead`，按路径资源走权限闸门。[O1][O2][O3]
- **事实**：shell 工具用 `shell` 动作做权限判断，默认规则是 allow；所以 `cat .env`、`grep -r TOKEN .` 这类命令默认不经过 `.env` 的 read 询问。没有按文件内容或输出格式的扫描。[O1][O4]
- **事实**：`session/transfer.ts` 有一套 `[redacted:…]`，但那是分享/传输会话时的整段替换，不用于模型请求。[O5]
- **推测**：如果把默认改为更严格，仍然只保护 read 工具；shell 是另一个入口。

### 1.5 pi（coding-agent `1.4.0`）

- **事实**：文档说 pi 不在每次工具调用前请求批准，安全应交给操作系统用户、容器、虚拟机或沙箱；`read` 直接读文件，`bash` 用 `getShellEnv()` 继承环境。[P1][P2][P3]
- **事实**：仓库里的 `protected-paths` 示例只挡 `write`/`edit` 到 `.env`、`.git/`、`node_modules/`；`permission-gate` 示例用几条正则挡危险命令；还有基于 sandbox-runtime 的 `sandbox` 示例。这些都要用户自己装。[P4]
- **事实**：核心只有 `/bug` 报告里的 URL/JSON 脱敏，没有模型边界扫描。[P5]
- **未知**：用户实际安装的扩展和配置本轮没有查。

### 1.6 omp（coding-agent `18.14.0`）

- **事实**：`secrets.enabled` 默认 false；打开后从三类来源取秘密：全局/项目 `.omp/secrets.yml`、进程环境里名字匹配 `KEY|SECRET|TOKEN|PASSWORD|PASS|AUTH|CREDENTIAL|PRIVATE|OAUTH` 且值至少 8 字节的变量、连接 URL 里的密码；再加 `patterns.ts` 里的内置厂商格式（GitHub/GitLab、OpenAI/Anthropic 前缀、AWS、Google、Slack、npm、Stripe、SendGrid、HuggingFace、JWT、PEM 私钥等）。[M1][M2][M3]
- **事实**：请求 provider 前遍历消息文本，把命中的秘密换成按安装密钥生成的占位符；模型返回的工具参数在真正执行前用反向映射还原；助手文本和压缩/分支摘要在本地显示时再还原。占位符只有本 obfuscator 生成、且带每安装 HMAC 键的才能反向，注释明确说这是为了防止模型凭空合成占位符。`replace` 模式则换成固定串、不可逆。[M4][M6][M7]
- **事实**：这套是内容/格式驱动，没有按文件名的清单；没被配置、也不匹配内置格式的密码不会命中。默认关闭，所以默认 pi/omp 的模型请求不会脱敏。[M1]
- **事实**：omp 依赖的 pi-ai 还有一层不可逆的 `[*_token_redacted]` 格式替换，同样默认关闭；注释说明不可逆占位符会让 edit 的 `old_string` 对不上磁盘原文，所以 omp 把同样的形状改走可逆 obfuscator。[M5]
- **推测**：omp 的做法证明了「发请求前替换 + 写回前还原」可行，但也暴露了风险：还原发生在所有工具参数上，模型把占位符挪到别的文件/变量时它不会阻止。

### 1.7 共性

- **事实**：别家的默认都很窄。Codex 保护的是写入元数据和 shell 环境；Claude Code 明确没有内置凭证文件拒绝清单；opencode 只有 `.env` 的读询问；pi 核心没有；omp 的内容替换默认关。
- **事实**：有「替换」能力的三家，都是把真实值留在本机、只在特定边界换：Codex/Claude Code 是环境变量哨兵 + 网络代理换回，omp 是消息占位符 + 工具参数还原。没有一家把 gitleaks 这类完整格式清单拿来扫所有模型输入。
- **推测**：canter 如果要做，机会点在「所有发往模型的文本只有一个拼装处」；代价是误报会直接改变模型看到的代码，必须处理写回和显示，不能只做字符串替换。

## 2. canter 里密钥能从哪些入口流到模型

**总事实**：工具结果的文字原样进入模型历史，再原样拼进请求；中间没有格式扫描。`Tools::execute` 产出 `ToolOutput.text`，`runner` 调 `state.tool_result`，`tool_result` 直接 `Message::ToolResult { text }`；`context::request` 把 `prefix` 和 `history` 克隆后发给模型。[K5][K6]

| `read`（文本） | 文件原文加行号，最多 2000 行 / 64 KiB | 只拒 canter 状态目录和 `config.json`；无格式扫描 | 再拒 `~/.ssh`、`~/.aws`、`~/.gnupg`、状态目录；`.env` 仍可读 | 只拒状态目录；`.ssh` 等可读 | [K1][K2][K4] |
| `read`（图片） | 原图字节作为图片给模型 | 无；图片里的文字/二维码不经过文本扫描 | 图片在允许路径内才可读 | 同左，无凭证目录限制 | [K4][K18] |

| `@` 引用文件 | **只把路径写进消息**；模型随后用 `read` 读 | 同 `read` | 同 `read` | 同 `read` | [K16] |

| LSP 诊断 | 诊断 message/source 等拼进文件修改结果或后续说明 | 无扫描；LSP 进程还拿到完整会话环境 | 无影响（LSP 不套沙箱） | 无影响 | [K14] |
| 压缩摘要 | 先把完整历史（含工具结果、工具参数）拼成 transcript 再请求摘要；摘要替换历史 | 无扫描；摘要请求和摘要本身都可能带密钥 | 无影响 | 无影响 | [K7] |
| 会话存盘 / 日志 / 导出 | `events.jsonl` 0600、目录 0700，原文；`/export` 原文写文件 | 无内容日志；没有模型边界扫描；未来遥测（P2-116）要用同一套 | 无影响 | 无影响 | [K15][K16] |
| 用户输入 / `ask_user` 回答 / 图片 | 用户原话和图片直接进历史 | 不扫（用户自己给的内容） | 无影响 | 无影响 | [K5] |
| 模型错误 / 重试 | 错误文字；`ApiKey` 的 Debug 不打印 key | 只保护 canter 自己的凭证对象；工具/文件内容不在错误路径 | 无影响 | 无影响 | [K17] |

### 2.1 shell 环境变量（重点）

- **事实**：终端启动 canter 时，`Context::current()` 把 `std::env::vars_os()` 里能转成 UTF-8 的全部变量放进 `Context.env`；新建会话和每次 resume 都把它交给服务端。核心把它作为私有 `LocalExecutor.environment`，shell 启动时 `env_clear().envs(&environment)`。[K9][K19]
- **事实**：`config.json` 里的 `api_key` 只用于 canter 自己的模型/搜索请求，服务端不会把它合并进会话环境；核心 README 也写明不读服务端进程环境。所以「canter 自己的 DeepSeek key 在不在 shell 环境里」的答案是：默认不在，除非用户自己在启动终端里 export 了同名或别的 `*KEY*`/`*TOKEN*`。[K6][K9]
- **事实**：模型在 shell 里跑 `env`、`printenv`、`set`，或 `ps auxe` 这类命令，输出会进入模型；没有按变量名/值过滤。[K18]
- **事实**：MCP stdio 子进程只拿 8 个基础变量（`HOME`、`PATH`、`USER`、`LOGNAME`、`SHELL`、`TMPDIR`、`LANG`、`LC_ALL`）加用户配置的 `env`，不是会话环境；LSP 子进程拿完整会话环境。[K10][K14]
- **事实**：沙箱打开时，shell 仍然继承同一份环境变量；沙箱限制的是文件/网络，不改变环境内容。
- **推测**：如果只做「文件名挡」，`env` 这条完全挡不住；按变量名过滤（像 Claude Code 的 scrub）或按值格式替换，是两条不同的路。

### 2.2 文件工具和沙箱的区别

- **事实**：`protected_paths` 只有服务端状态目录和 `config.json`；文件工具对这两处一律拒绝，沙箱开关都一样。[K1][K4]
- **事实**：沙箱打开时，`resolve_sandbox_read` 把 `~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.canter`、`CANTER_HOME` 和状态目录列为不可读；文件工具和模型 shell 都受这条边界。[K2][K3]
- **事实**：`.env`、`*.pem`、项目里的 `config/*.json` 不在不可读清单里；沙箱开或关都能 `read`。沙箱开时 shell 也能 `cat` 项目里的 `.env`（项目目录可读）。
- **事实**：`read` 的图片路径同样只走这些检查；图片里的密钥不会被文本扫描发现。[K4]
- **推测**：沙箱关时，模型在「总是问」下点一次批准、或在「全部允许」下，就能读 `.ssh`；沙箱开时这条被挡住，但项目 `.env` 仍然漏。

### 2.3 shell 里的 grep/glob

- **事实**：内置工具只有 read、write、edit、shell、shell_output、shell_stop、monitor、ask_user、web_fetch、web_search、update_plan、submit_plan、MCP 两件；没有 grep、glob。[K4]
- **事实**：模型要找代码通常用 shell 的 `rg`/`grep`/`find`；输出走 shell 的 32 KiB 头尾截断，不经过任何格式扫描。计划模式/审查轮的只读白名单会限制能跑哪些命令，但不是内容脱敏。[K20]
- **推测**：只要 `.env` 在项目里，`rg -uu TOKEN .` 或 `grep -r .env` 就可能把内容带进模型；文件名门要挡 shell 就得分析命令目标，而这条按 P2-143 的经验并不可靠。

### 2.4 用户 `!` 命令

- **事实**：`!` 走 `spawn_user`，直接 `launch(..., sandboxed=false, None)`；即使沙箱开着也不套墙。输出上限和 shell 一样，最后作为用户消息追加到模型历史。[K2][K8]
- **推测**：用户自己跑 `!env`、`!cat .env` 时，内容会进模型；这是「用户主动给」的入口，是否要脱敏要用户定。若做发送边界扫描，这条也会被覆盖。

### 2.5 MCP

- **事实**：MCP 服务配置的 `env`/`headers` 值（≥8 字节，stdio 服务跳过 8 个基础变量名）和 OAuth `access_token`/`refresh_token` 会进每个服务的 `secrets` 列表；`Server::public()` 在结果文本、结构化 JSON、服务名/工具名/说明里替换这些值。值按长度降序替换，避免短值先替换掉长值的一部分。[K10]
- **事实**：MCP 工具结果里的任意其它密钥、文件内容、文件路径不在这套替换里；模型传的 MCP 参数也不扫。[K10]
- **事实**：MCP 图片是原始字节，交给模型看；文本扫描不覆盖。[K10]
- **推测**：MCP 服务本身可能返回从 `.env` 读到的内容，或者模型把参数里的秘密传给服务；发送边界扫描能覆盖前者（如果格式可认），不能覆盖服务内部行为。

### 2.6 `web_fetch` / `web_search`

- **事实**：`web_fetch` 只接受 http/https，拒绝 URL 里的用户名/密码，不跟随跨主机重定向；页面内容原样进模型（HTML 转 Markdown），没有内容扫描。[K12]
- **事实**：`web_search` 只把 DeepSeek 的 API key 在结果字段中的回显替换；查询原文、结果标题/URL/summary 的其他内容不扫。工具说明虽然要求「不要把密钥、代码、个人信息放进查询」，但这是提示词约束，不是检查。[K11]
- **推测**：模型可以把秘密拼进 URL 查询串或搜索查询发出去；发送边界扫描如果只替换消息文本里的密钥，URL 会被改坏，是否要拦/问是另一个决定。`web_search` 的结果来自外部，也可能包含别人的密钥。

### 2.7 AGENTS.md、技能、LSP、压缩

- **事实**：AGENTS.md 是核心直接 `File::open` 读的，每份最多 64 KiB，原文进固定前缀；`~/.canter/AGENTS.md` 虽然会被 `read` 工具拒绝，但核心拼前缀时直接读，所以 read 工具的保护挡不住它。[K6]
- **事实**：技能的列表只带名字、说明、路径；点名使用时 `skill_invocation` 读 SKILL.md 全文，原文进模型。[K13]
- **事实**：LSP 诊断的 message/source 等拼进文件修改结果或后续说明；LSP 子进程拿到完整会话环境，stderr 不转发到日志。[K14]
- **事实**：压缩先把完整历史（含工具结果和工具参数）拼成 transcript，再用单独请求摘要；摘要和保留的用户原话替换历史。摘要请求本身也会把原始密钥发给模型。[K7]
- **推测**：只在工具出口做脱敏不够，压缩、btw、handoff 都从历史重新拼请求；要做就在所有「发请求」的公共出口做，或者在做历史的入口做统一替换。

### 2.8 存盘、日志、导出

- **事实**：会话目录 0700、`events.jsonl` 和副本 0600；事件里是工具结果、模型输出、压缩请求的原文。本轮没有找到把工具内容写进服务端日志的代码；MCP 断开只打经过 `public()` 的服务名。[K15][K10]
- **事实**：`/export` 把会话原文写成 Markdown，新文件、不覆盖；没有额外脱敏。[K16]
- **事实**：P2-116 遥测还没做；任务背景已经要求遥测和 eval 不能带出密钥。
- **推测**：本地存盘保留原文有利于审计和恢复，但导出/遥测/分享会重新变成出口；如果只做「发请求前替换」，本地文件仍是明文，需要另定导出/遥测策略。

### 2.9 沙箱开/关的差别（汇总）

| 入口 | 沙箱开 | 沙箱关 |
| --- | --- | --- |
| `read`/`write`/`edit` | 多挡 `~/.ssh`、`~/.aws`、`~/.gnupg`、状态目录；`.env` 照读 | 只挡状态目录；`.ssh` 等可读 |
| 模型 `shell` | OS 墙：读写范围、凭证目录、网络按权限档 | 无 OS 墙，只有批准/命令规则 |

## 3. 按格式认密钥

### 3.1 gitleaks 能不能用

- **事实**：gitleaks 是 MIT；最新标签 `v8.30.1`，clone 的提交日期 2026-10-23；HEAD 是一次 dependabot 合并，仓库仍在发布版本。[G0][G1]
- **事实**：默认配置 `config/gitleaks.toml` 有 222 条 `[[rules]]`；其中 221 条有 `keywords`，130 条有 `entropy`，1 条有 `secretGroup`，5 条有 `path`，13 个 per-rule `[[rules.allowlists]]`，2 条有 `regexTarget`；没有 `[[rules.required]]` 复合规则。[G2][G3]
- **事实**：规则字段是 `id`、`description`、`regex`、`path`、`entropy`、`secretGroup`、`keywords`、`allowlists`；allowlist 支持 path、regex、stopwords、commits、`match`/`line` 目标。对 canter 有意义的是 regex、entropy、secretGroup、keywords、regex/stopword allowlist；path/commits 主要用于仓库扫描，模型输出里没有可靠路径时用不上。[G3]
- **事实**：Go 的 `regexp` 是 RE2 语义；本轮在规则里没有找到 lookaround、反向引用等 Rust `regex` 不支持的构造。Rust `regex` 也是线性时间、无 lookaround/backref，scoped flag（如 `(?i:...)`）、`\b`、`\x60` 等都有对应；**未知**：本轮没有实际用 Rust `regex` 编译全部 222 条，不能保证每条都一次通过。
- **事实**：gitleaks 扫描前先把文本转小写，用所有规则的 keywords 建 Aho-Corasick 预筛，只有命中 keyword 的规则才跑正则；如果规则没有 keyword 就总会跑。默认还会做 base64/hex/percent/unicode 解码，最多递归 5 层（`--max-decode-depth` 默认 5）。[G4][G5]
- **事实**：`generic-api-key` 是最宽的一条：匹配 `access/auth/api/credential/creds/key/password/secret/token` 附近的 `=`/`:` 等，值长度 10–150（或 12 字节以上的 base64 形状），要求 Shannon 熵 ≥ 3.5，并带一份很长的 stopwords 和 match allowlist。它是误报的主要来源。[G6]
- **事实**：gitleaks 默认规则里有 `anthropic-api-key`、`openai-api-key`、`aws-access-token`、`jwt`、`private-key` 等，但**没有 DeepSeek 规则**；DeepSeek key 只能靠通用规则或自定规则命中。[G2][G8]
- **事实**：其他清单：`detect-secrets` 是 Apache-2.0；`trufflehog` 是 AGPL-3.0。两者本轮只核对了许可证，没有评估规则数量和误报；trufflehog 的 detector 设计通常会在线验证凭证（会请求服务商），这也会带来网络和许可两方面的额外约束。[G7]

### 3.2 怎么搬进 Rust

- **推测**：规则来源可以二选一：
   - 运行时解析 gitleaks TOML：加 `serde` + `toml` + `regex` + `aho-corasick`；保留 `keywords`、`entropy`、`secretGroup`、allowlist 的 regex/stopwords。启动时编译一次，规则文件放在 canter 仓库或用户配置里。优点是用户能用现成 gitleaks 规则；缺点是启动解析和编译成本、规则格式要长期跟。
   - 生成 Rust 静态表：把选中的规则转成 `const` 数组（regex 源串、flags、keywords、entropy、allowlist），不依赖 TOML 解析。优点是启动快、依赖少；缺点是更新规则要改代码。
- **事实**：`regex` crate 的 `Regex` 不支持反向引用和 lookaround，和 Go RE2 基本对得上；编译失败要按规则报错并跳过，不能让一条坏规则拖垮启动。
- **事实**：需要自己实现 Shannon 熵（对 `secretGroup` 或整个 match）和 keyword 预筛；`aho-corasick` crate 可以直接做多 keyword 匹配。
- **推测**：allowlist 只需实现 regex 和 stopwords；`path`/`commits` 在「扫描模型文本」场景没有路径/提交可言，可以忽略或只用于 `read` 文件路径。
- **推测**：解码 pass 是可选增强：实现 base64/hex/percent 解码会明显增加代码和 CPU；第一版可以不做，或只对工具结果做一次解码，不对全量历史做 5 层。
- **事实**：如果复制 gitleaks 规则或代码，按 MIT 在 `THIRD-PARTY-NOTICES.md` 写项目、版本、原文件；规则文本也算受版权保护的数据。

### 3.3 误报和漏报（估计，不是实测）

- **推测**：高置信的厂商前缀规则（`ghp_`、`glpat-`、`sk-ant-`、`AKIA`、`AIza`、`xox[baprs]-`、`-----BEGIN … PRIVATE KEY-----`、JWT 三段式）误报很低；它们要求固定前缀和长度/字符集，正常代码和哈希/UUID 一般不会命中。
- **事实/推测**：`generic-api-key` 会命中「变量名像密钥、值有足够熵」的普通代码。例如测试里的假 key、示例配置、长 base64、某些 UUID/哈希，只要附近出现 `token`/`secret`/`password`/`key` 等词，就可能被当成秘密；gitleaks 用 stopwords 和 allowlist 压，但不能保证没有。[G6]
- **推测**：base64/hex 解码会把「编码后的密钥」也扫出来，同时也会把普通压缩数据、图片 base64、测试夹具解出更多随机文本，增加误报和 CPU。
- **推测**（按规则形状推，不是实测）：
  - 测试里的假 key：带厂商前缀的（`sk_test_…`、`AKIA…`、`ghp_…`）会被高置信规则命中，模型看到的代码会变成占位符；这是「宁可误伤」的代价，测试夹具可以用 allowlist 排除。
  - 40/64 位十六进制哈希：一般不会被前缀规则命中；如果同一行有 `token=`/`secret=` 之类关键字且熵够，`generic-api-key` 可能命中，概率中等。
  - UUID：单独出现一般不会；`password = "<uuid>"`、`secret: "<uuid>"` 这类带关键字写法可能被 `generic-api-key` 命中，概率中等偏低。
  - 普通 base64 数据：只有 `generic-api-key` 或解码 pass 可能命中；长 base64 且靠近关键字的误报概率偏高。
  - 正常函数名、短变量、短路径：基本不命中，因为高置信规则要求前缀/长度/字符集，通用规则要求值 ≥10 字符和熵。
- **事实/推测**：漏报包括：没有固定格式的密码/口令；长度短于规则下限的值；拆成多段、运行时拼接的密钥；加密/压缩后的密钥；图片/音频/二进制里的信息；自定义服务商的 token；低熵密钥；`.env` 里 `KEY=value` 但值不满足通用规则的情况。DeepSeek key 需要单独补规则。base64 编码的密钥有机会被 gitleaks 的 decode pass 命中，但拆开拼接、加密、压缩不能保证。
- **未知**：在 canter 实际会看到的正常 Rust/TypeScript/Python 代码上，误报率是多少；本轮没有跑大规模样本，也没有用真实仓库做统计。能确定的是：如果启用 `generic-api-key` 且不按文件类型/测试夹具调 allowlist，测试代码和示例配置会先出问题。

### 3.4 性能代价（有依据的估计）

- **事实**：gitleaks 的主要优化是 keyword 预筛：先用 Aho-Corasick 扫一遍小写文本，只对命中 keyword 的规则跑正则；所以不是 222 条正则都完整扫全文。[G4]
- **推测**：在 Rust 里，64 KiB 的单次工具结果（`read` 上限）用 keyword 预筛 + 少量正则，量级应在亚毫秒到几毫秒；一次请求的历史可能到几百 KiB（长会话/压缩前），量级可能到十几到几十毫秒。相对模型请求通常几百毫秒到几秒，这个开销可以接受，但要在请求边界只做一次，不能对每个流式增量做。
- **推测**：如果每个请求都把完整历史重新扫一遍，长会话会线性变慢；更稳的是在内容进入历史时（工具结果、用户输入、MCP、网页、指令文件）做一次替换并保存占位符，或者在请求拼装时只扫新增/未扫过的消息。两种都要保证占位符稳定，否则会破坏 prompt cache。
- **推测**：base64/hex 5 层解码的成本可能是正则本身的数倍；第一版可以只对「短且像编码块」的片段解码，或把解码做成可选。
- **推测**：222 条 `regex::Regex` 的编译内存可能到几 MB 到几十 MB 量级（取决于是否用 lazy DFA）；启动时编译一次可接受，但不要把编译放到每次请求。

## 4. 替换带来的问题

### 4.1 会发生什么

**推测**：

- 模型读到的是 `DB_PASSWORD=[canter:secret:…]`；它改 `.env` 时如果整文件重写，很可能把占位符原样写回。若不做还原，真实文件里就留下占位符，服务起不来；若做还原，文件保住真实值。
- 模型可能把占位符挪到别的变量、别的文件、README、日志或 shell 命令里；还原会把这些位置写成真实密钥，造成扩散。
- 模型可能只看到占位符，无法判断值的长度/格式/是否为空，做校验类修改（比如生成连接串、比较哈希）会出错。
- **事实/推测**：占位符如果可以被模型/网页内容凭空写出，反向映射就可能把真实密钥注入到模型指定的位置；必须只还原「本会话真实生成过」的占位符，最好带每安装 HMAC。
- **推测**：批准框显示的是替换前还是替换后的内容，影响用户判断：显示占位符，用户看不出值；显示真实值，终端/日志里又出现密钥。

### 4.2 别家怎么处理

- **事实**：omp 在模型返回后、工具执行前对工具参数做 `deobfuscateToolArguments`，所以 edit 的 `old_string` 和 write 的内容里的占位符会还原成真实字节；助手文本在本地显示时也还原。它的占位符带每安装密钥，注释明确说防止模型合成。它没有按文件限制还原范围。[M4][M6][M7]
- **事实**：omp 注释提到不可逆的 `[*_token_redacted]` 会让 edit 的 `old_string` 对不上磁盘原文，所以它宁可走可逆占位符。[M5]
- **事实**：Codex/Claude Code 的 `mask` 是「环境变量给哨兵、代理在出站请求换回」，不是文件内容替换；Claude Code 在 macOS 上对文件 `mask` 直接等于拒读，避免文件内容出现哨兵。[C5][A3]
- **未知**：Codex 的 credential broker 对文件内容是否有类似处理；本轮没有看到文件内容进入这条链。

### 4.3 可选办法和风险

| 办法 | 做法 | 风险 | 对日常改 `.env` 的影响 |
| --- | --- | --- | --- |
| 拒绝含占位符的写入 | 发现 write/edit 内容里有已知占位符就报错，让模型重新读/问用户 | 最安全，不会扩散；但模型经常整文件重写，会频繁失败；模型可能改用 shell 绕过 | 大；除非改成按行编辑 |
| 写入时换回原值 | omp 式：只还原已知占位符，再执行 write/edit | 保留真实值、`.env` 可改；但占位符被挪到别的文件/变量会扩散；需防伪造；edit 的 oldText 要先还原才能匹配 | 小 |
| 按文件保留原值/合并 | 只允许改非秘密行，秘密行保持原样；或写回时把原秘密行合并回去 | 需要解析文件格式（dotenv、JSON、YAML），每种格式都要做；对格式不熟的文件会误判 | 中 |
| 写入前问用户 | 任何含占位符的写入都弹批准框，显示真实 diff | 安全、可控；但打断多，长任务体验差 | 中 |
| 不替换，只挡读 | 见 §5 做法 A | 不改变内容，编辑正常；但批准后真实值进模型，等于没脱敏 | 小 |

### 4.4 建议（待定）

**推测**：如果做替换，建议：

1. 占位符用不可猜的格式（每安装密钥的 HMAC + 可读标签），只还原本会话真实生成过的；模型新写的同形字符串不还原。
2. 只在 `write`/`edit` 的文件内容上还原，不在 shell 命令、MCP 参数、web URL 上还原；shell 里的占位符直接报错或让模型改用文件工具。这样可以避免把密钥写进命令行/进程表/远端请求。
3. 还原范围尽量绑定来源文件：某个占位符是在读 A 文件时生成的，就只在写 A 文件时还原；至少对「新文件」和「其它文件」拒绝还原，减少扩散。代价是模型跨文件复制密钥的活做不了，需要用户手动做。
4. 批准框和 diff 显示真实值还是占位符要用户定；如果显示真实值，注意终端回滚和日志；如果显示占位符，用户无法核对值。
5. 还原后再做原有的路径/沙箱/批准检查，不能因为「是占位符」跳过写入边界。
6. 给模型的工具说明写清楚：占位符只代表本机真实值，不要改写、不要复制到其它文件；需要真实值时让用户处理。

## 5. 建议

### 5.1 可选做法

**做法 A：只按文件名/路径挡**

- 默认清单可以包含：`.env`、`.env.*`（`.env.example` 可放行）、`*.pem`、`*.key`、`*.p12`、`id_rsa`、`id_ed25519`、`~/.ssh`、`~/.aws`、`~/.gnupg`、`~/.config/gh/hosts.yml`、`~/.netrc`、`~/.npmrc`、`~/.cargo/credentials.toml`、`~/.docker/config.json`、`~/.git-credentials`、`~/.kube/config`、canter 状态目录。
- 挡得住：模型直接 `read` 这些文件；如果 shell 命令也做路径分析，能挡一部分 `cat`/`sed`。
- 挡不住：批准后仍会发给模型；shell 绕过（`cp`、`grep`、变量、脚本、解释器）；`.env` 之外的自定义配置文件；环境变量 dump；MCP/web/AGENTS/LSP/压缩；改名的文件。
- 对日常改 `.env`：批准后能正常改，但一旦批准就泄露真实值；不算「脱敏」。
- 要改的地方：`protected_paths` 增加默认清单/用户清单（文件工具）；shell 的路径分析（另一个难题）；沙箱的不可读清单可复用但不应依赖沙箱开关。
- 和沙箱：沙箱已经把 `~/.ssh` 等挡住；文件名门主要补 `.env` 和沙箱关的情况。

**做法 B：只在发给模型前按格式替换**

- 在请求拼装处（普通轮、btw、handoff、压缩摘要）和工具/输入进入历史处，用一份格式规则把命中的值换成占位符；`write`/`edit` 执行前还原；环境变量按名字/值规则单独处理。
- 挡得住：文件内容、shell 输出、`env`、MCP 结果、网页、AGENTS.md、技能、LSP、压缩；只要格式可认，路径无关。
- 挡不住：无格式密码、短值、拆分/加密、图片/二进制、shell 直接外传（模型不需要看到内容也能 `curl` 带出去）、服务端内部行为。
- 对日常改 `.env`：读到的值变占位符，写回时还原；体验取决于 §4 的还原策略和误报。
- 要改的地方：一个统一的请求脱敏层、规则加载/编译、占位符映射、write/edit 还原、压缩/btw/handoff 覆盖、工具说明；配置。
- 和沙箱：独立；沙箱挡住「模型能读什么」，替换挡住「读到了也看不到真值」。两者互补。

**做法 C：A + B + 环境变量过滤（推荐）**

- B 作为主层，A 只做一小份高风险文件名的兜底，环境变量按名字/值规则过滤（可以并入 B）。
- 理由：用户要的是「不走 sandbox 也脱敏」，B 是唯一真正让模型看不到真值的层；A 对无法识别的整文件（例如任意密码文件）和多层路径有兜底价值；环境变量过滤解决 `env`/`printenv` 这条最常见的泄露。
- 代价：比单做 A 复杂；误报会改变模型看到的代码；占位符写回要小心；性能要控制。
- 对日常改 `.env`：如果按推荐把 `.env` 设为「允许读、值替换」，读到的值变占位符，write/edit 时还原，普通修改和新增变量可以正常做；如果 `.env` 也被文件门设为拒绝，就要用户先放行，体验差。
- 建议的取舍：第一版只上高置信规则（厂商前缀、PEM、JWT、AWS/Google/Slack/GitHub/GitLab/Stripe/npm/HuggingFace/SendGrid/Anthropic/OpenAI 等），加上 DeepSeek 自定规则和「环境变量名像密钥且值 ≥8 字节」；`generic-api-key` 先不放，或只作为用户可开选项。gitleaks 全量 222 条作为可选规则包，不默认开。

**做法 D：只过滤 shell 环境变量**

- 像 Claude Code 的 `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`：按名字或值去掉 `*KEY*`、`*TOKEN*`、`*SECRET*`、`*PASSWORD*` 等，或换成占位符。
- 挡住 `env`/`printenv`/日志里的环境变量；不挡文件内容、MCP/web/AGENTS/压缩。
- 成本低、误报低；可以作为 B 的一部分，不适合单独用。

### 5.2 推荐

**推测**：推荐 **C**，其中 B 是核心，A 是窄兜底，D 并入 B。理由：

- 只做 A 不满足「脱敏」：用户批准一次、或 shell 绕过，内容还是发给模型服务商。
- 只做 B 会漏掉「无法识别格式的整文件」和「命令直接外传」；A 至少让明显的凭证文件需要用户明确放行。
- 沙箱能挡 `~/.ssh` 等目录，但挡不住项目 `.env`、AGENTS.md、MCP、网页、压缩；发送边界替换是沙箱之外唯一覆盖所有入口的层。
- omp 已经验证了可逆占位符 + 工具参数还原这条路；canter 可以借用思路，但要把还原范围收得更窄（文件、来源文件），避免扩散。

### 5.3 和沙箱怎么配合

- **事实/推测**：沙箱是「模型能碰到什么」的边界，替换是「碰到后能看到什么」的边界。两者不能互相替代：沙箱开时 `.env` 仍可读；沙箱关时 `~/.ssh` 可读；MCP/web/AGENTS 不在沙箱里。
- 文件名门不应该只在沙箱打开时生效；它应该是文件工具/shell 的独立默认，沙箱开关不改变「哪些文件算凭证」的规则。
- 替换层不应该依赖沙箱；它在沙箱开/关、`!`、MCP、web、压缩下都要工作。
- 如果以后做「按域名代理」或凭证代理（Codex/Claude Code 的 mask 思路），替换层可以保留为最终兜底；代理能挡网络外传，但挡不住模型看到文件内容。

### 5.4 默认清单放哪、用户怎么加删

**事实**：canter 现在的配置只有机器级 `~/.canter/config.json`（以及 `rules.json`），没有项目级配置；`config.json` 受文件工具和沙箱保护。[K1]
**推测**：

- 内置默认清单（格式规则、文件名/路径、环境变量名模式）放代码常量，跟版本走；用户不应为了基本保护去写配置。
- 用户增删放 `config.json` 的新段（例如 `redaction`），与 MCP、沙箱、`rules.json` 分开；不要把格式规则塞进 `rules.json`（那是命令放行）。
- 如果以后有项目级配置，再允许项目 `.canter` 覆盖/追加；第一版先机器级，避免多一个配置层。
- 用户要能看到当前生效的清单和命中记录；`/permissions` 已有先例，但本件不要求现在做界面。

### 5.5 推荐的第一版边界（供拍板，不是任务书）

- 覆盖所有「发往模型」的文本：普通轮、btw、handoff、压缩摘要请求、工具结果、用户输入、MCP、web、AGENTS/技能、LSP。
- 默认高置信格式 + 环境变量名/值 + DeepSeek 自定；`generic-api-key` 默认关。
- 文件名门只挡明显凭证文件；`.env` 允许读但内容替换（这样能改非秘密行）。
- 占位符写回：只对 write/edit、只对已知占位符、尽量限定来源文件；shell 不还原。
- 本地存盘保留原文；导出/遥测以后默认走同一脱敏器（或至少询问）。
- 先不做：base64/hex 多层解码、代理注入、图片 OCR、跨文件秘密复制。

## 6. 要用户拍板的事

1. **选哪条路**：A 只按文件名挡、B 只按格式替换、C 两样都做（推荐）、D 只过滤环境变量。推荐 C；如果只想先做一件，选 B。
2. **默认文件清单和行为**：哪些文件默认拒绝、哪些默认询问、哪些读后替换？推荐：`~/.ssh`、`~/.aws`、`~/.gnupg`、状态目录默认拒读；`.env`/`.env.*` 默认允许读但值替换；私钥/凭证文件默认拒读，用户可放行。`.env.example` 是否放行？
3. **占位符写回**：还原（推荐，omp 式）还是拒绝含占位符的写入？还原是否只限来源文件、是否只在 write/edit（推荐是）？批准框显示真实值还是占位符？
4. **本地存盘/导出/遥测**：会话文件保留原文（推荐，0600）还是也替换？`/export` 默认原文还是脱敏？P2-116 遥测必须用同一套，是否现在就定？
5. **规则范围**：先用高置信子集 + DeepSeek 自定（推荐），还是直接上 gitleaks 全量 222 条？`generic-api-key` 默认开不开？是否允许用户加载 gitleaks TOML？
6. **项目级配置**：第一版只做机器级 `config.json`（推荐），还是同时做项目 `.canter` 的追加/覆盖？
7. **覆盖范围**：第一版是否把 MCP、web、AGENTS、技能、LSP、压缩全部纳入？推荐全部纳入同一个发送边界；如果只想先覆盖 read/shell，要明确 `env`、MCP、压缩仍然漏。

## 7. 本轮没做 / 未知

- 没有跑 canter 测试（任务不要求），没有改代码/配置/DESIGN。
- 没有读用户真实的 `~/.canter/config.json`、`.env`、`~/.ssh` 或任何真实凭证；报告里没有真实密钥/令牌/环境变量值。
- 没有构造输入绕过 canter 或别家的检查；没有调用模型；没有运行其他 agent。
- 未知：Claude Code 未公开的默认 Read deny、产品内嵌 runtime 版本；Codex 企业托管 profile 的具体默认；canter 真实代码库上的误报率和扫描耗时；omp 在超大历史/并发会话下的实际表现。这些需要实现或用户试用时再测。
