## 1. Codex 怎么做

### 1.1 OS 边界与配置生成

**事实**：macOS 用固定路径 `/usr/bin/sandbox-exec`，把基础 SBPL、文件读写范围、网络规则和必要的平台许可拼成 profile，以 `-p <profile> -D<参数>=<路径> -- <命令>` 启动。基础规则 `deny default`，再允许 fork/exec、同沙箱进程间信号及必要系统操作；子进程继承限制。读写路径不是从命令文本里猜出来的，而是把权限策略转换成 OS 规则。[C1]

**事实**：Linux 0.163.0 默认是 **bubblewrap + seccomp**，不是「只用 Landlock」。根文件系统只读挂载，可写根叠加可写挂载，保护子路径重新只读；建立 user/PID namespace，受限联网使用 network namespace，代理模式额外搭桥通到受管代理。seccomp 限制系统调用。Landlock 留作旧路径；该版对受限文件系统策略拒绝旧 Landlock 路径，README 说明原因涉及无法隔离 app-server 的 Unix socket。优先使用 cwd 外 PATH 上的 bwrap，缺少时用捆绑版本。[C2]

### 1.2 模式、可写目录与网络

下表是源码仍支持的 `SandboxPolicy` / `sandbox_mode` 语义；更细的 permission profile 可另外限制读取，不能把旧模式表当作所有配置的全集。[C3][C4]

| 模式（事实） | 文件范围 | 网络 |
| --- | --- | --- |
| `read-only` | 默认全盘可读，没有普通可写根；运行必需的设备例外另由平台规则处理 | 默认关闭，可单独配置。[C1][C3] |
| `workspace-write` | 默认全盘可读；cwd、`writable_roots`，以及未排除的 `/tmp`、`TMPDIR` 可写 | 默认关闭；普通 `network_access=true` 是放开网络，不自动变成域名白名单。[C3][C5] |
| `danger-full-access` | 不由这层沙箱限制读写 | 不限制。[C3] |
| `external-sandbox` | 假定外层负责隔离，本层视为全盘访问 | 携带外部网络状态；这个名字本身不会创建隔离环境。[C3] |

**事实**：额外目录最终进入 writable roots；`exclude_slash_tmp`、`exclude_tmpdir_env_var` 默认 false。可写根内的 `.git`、`.agents`、`.codex`、`.aws` 有默认写保护；旧策略对已存在的 `.git` 目录或指针文件都保护，指针的 gitdir 目标也只读。cwd 下 `.codex` 即便尚未创建也保护。更细策略还使用受保护元数据名字规则。[C3][C4]

**推测**：在默认 workspace-write 下，`git add`、`git commit` 往往会因为需要写索引、对象或 refs 被挡；worktree 的 Git 元数据可能在工作目录外，不能只看眼前的 `.git` 文件。[C4][T3]

**事实**：0.163.0 的 macOS 网络规则支持只接通指定本机代理端口和指定 Unix socket；当要求受管网络却没有可用代理时，不悄悄放开。当前官方文档另说明 `network_proxy` 为域名策略提供代理执行，但开域名规则不等于打开网络，也不等于自动打开代理。这是与简单网络开关不同的能力。[C5][W1]

### 1.3 沙箱里到底哪些免批准

这里补清 P2-88 §7 的未知：**免批准不只限于「已知只读命令」**。以没有额外强制审查的 0.163.0 普通 shell 路径为准：[C6][C7]

| 条件（事实） | 首次执行决定 |
| --- | --- |
| `on-request`，受限沙箱，未命中危险命令判断、没有显式 ask/deny 规则、不请求扩大权限 | 不问，先在沙箱里执行；包括写项目文件、跑脚本、编译等命令。无需先证明整条命令只读。[C6:770–837] |
| `on-request`，显式请求 `require_escalated` 或其它沙箱权限扩大 | 进入批准流程；规则仍参与决定。[C6:337–460,820–835][C8] |
| `never` | 通常直接在现有边界内尝试；需批准的规则/危险命令可直接拒绝。`never` 不是全盘权限，也不是失败后自动放开。[C6:394–460,793–818] |
| `UnlessTrusted`（源码枚举） | 没有显式 execpolicy allow 的命令要批准。[C6:815–818] |
| `Granular` | 将沙箱、命令规则等批准类别分别控制；不允许询问的类别不能靠弹框放开。[C6:216–242,840–852][C7] |
| 命令每个解析段都被显式 execpolicy allow 命中 | 产生 `Skip { bypass_sandbox: true }`；允许完全出沙箱的策略下，首次就可不套。这比「只免一次确认」更强。[C6:440–454][C7:249–294] |

**事实**：有 denied-read 限制时，Codex 不允许直接去掉执行这些限制的沙箱；显式批准可走扩大其它权限、保留拒读的沙箱路径，单纯 allow 规则不能这样扩大。`strict_auto_review` 还会额外审查原本 Skip 的请求，所以不能把上表说成「任何部署都必然不问」。[C7:249–309][C9:169–224]

**版本提醒**：当日官方文档说显式 `approval_policy="untrusted"` 已退出支持，项目的 `trust_level="untrusted"` 仍可派生严格批准。报告因此保留源码名 `UnlessTrusted`，不向用户推荐复制旧 `untrusted` 配置。[W1]

### 1.4 被挡、询问、重跑的完整链条

1. **事实**：执行返回 stdout/stderr、退出码等；`is_likely_sandbox_denied` 对非零结果检查拒绝关键词和部分平台信号，注释明说不是确定性判断。`Permission denied` 也可能来自普通文件权限，不能保证识别所有拒绝。[C10]
2. **事实**：普通 `on-request` 的失败**不会自动切到无沙箱再跑**，失败输出返回模型。模型若认为需要，另发带 `sandbox_permissions="require_escalated"`、`justification` 的调用；经批准后，普通可出沙箱策略会在该次执行使用 `BypassSandboxFirstAttempt`。`never` 不走失败后的出沙箱批准。[C8][C7:249–294,344–351][C9:394–473]
3. **事实**：`UnlessTrusted`、允许相关询问的 granular 等路径，可以在识别拒绝后组织重试批准，带拒绝原因；已批准过的命令在部分路径不会再问一次，严格自动审查另算。允许完全出沙箱时，第二次尝试选 `SandboxType::None`，然后重新运行命令。[C9:474–565]
4. **事实**：受管网络拒绝是单独分支，可带主机信息并走网络批准；denied-read 存在时要保留沙箱。不能把所有「允许」都解释成整条命令获得无限制权限。[C7:284–320][C9:412–538]

**推测**：命令失败前可能已改过部分文件，整条重跑有重复副作用。canter 不宜仅凭错误文字自动重跑，更不能把任意非零退出当作沙箱拒绝。该结论只来自上述流程阅读，没有做欺骗错误识别的试验。

## 2. Claude Code 怎么做

### 2.1 产品与开源 runtime 分开看

**事实（公开文档）**：`/sandbox` 可启用本机 shell 沙箱；默认关闭。它覆盖命令及子进程，文件工具、WebFetch、MCP、hooks 等另走自身权限。`!` 用户命令通常也在沙箱外，有严格后台会话等例外。未查本机配置，不能判断用户当前是否启用。[A1「What runs outside」「Get started」]

**事实（公开源码）**：sandbox-runtime 独立提供动态 Seatbelt profile，macOS 最终调用 `/usr/bin/sandbox-exec -p ...`；Linux 使用 bubblewrap。它可以显式包住 MCP 服务，但不代表 Claude Code 默认替每个 MCP 包了沙箱。该库标为 research preview，0.0.81 要 Node `>=22.12.0`；Rust canter 若直接依赖它，会增加运行时和发布依赖。[S0][S1][S2]

| 限制项（事实） | runtime 的做法 | Claude Code 的产品边界 |
| --- | --- | --- |
| 文件读 | 通常全盘可读；`denyRead` 禁止指定路径，`allowRead` 可重开较窄区域；窄拒绝仍需保留。[S2][S3] | 默认不能据此认为 `~/.ssh` 等凭证已被隔离；文件工具权限需要另配。[A1] |
| 文件写 | 有写策略时按 `allowWrite` 放行，`denyWrite` 保留保护；未提供写策略的 library 调用可全写，调用方必须正确给策略。[S3:980–1018] | cwd、add-dir、临时目录可写；配置、hooks 等有保护。[A1][A2] |
| 网络 | OS 挡直接连接，只接代理端口；HTTP/HTTPS 和 SOCKS 代理按主机/端口过滤。拒绝优先，无匹配时调用询问回调；没有回调或回调出错则拒绝。[S3:1255–1343][S4:745–837] | 不是对所有工具的统一防火墙。[A1] |
| 本机 IPC | 可按 Unix socket 路径放行；全放开是额外选项。[S3:1285–1315] | 是否允许 Docker、SSH agent 等需另外考虑，域名 allow 不授予这些能力。[S1「Unix Socket Configuration」] |
| 失败信息 | macOS 可收集带命令标记的系统拒绝日志；网络过滤直接返回拒绝原因。[S3:1623–1704][S4] | 由上层选择询问、拒绝或申请不套沙箱；runtime 本身不决定 canter 应如何批准。[A1，推测：对 canter 的边界] |

### 2.2 自动批准、排除与失败

**事实**：Auto-allow 让沙箱内 Bash 通常免问；Regular permissions 仍照普通权限流程。deny、针对内容的 ask、部分命令形式等有例外。`excludedCommands` 让匹配命令在沙箱外执行，仍受普通权限规则支配；当日设置参考的默认值为 unset，即没有排除命令，且组合命令须满足整条调用的适用条件。[A3]

**事实**：失败后模型可请求 `dangerouslyDisableSandbox`；是否再问取决于权限模式和 allow/ask 规则，不能笼统说「出沙箱一定问」。`allowUnsandboxedCommands=false` 关掉这类重试；沙箱不可用还需 `failIfUnavailable` 才不会降为无沙箱运行。[A1「The unsandboxed retry escape hatch」][A3]

**事实**：工具批准与 OS 隔离是不同层，但启用沙箱时，Read/Edit 的相关路径规则和 `WebFetch(domain:...)` 规则会合并进最终沙箱配置：Edit allow 扩大子进程可写范围，Read/Edit deny 限制子进程路径。反向并不成立：仅设置沙箱的 `denyRead` 不限制内置 Read，`allowedDomains` 也不限制 WebFetch。[A2「How permissions interact with sandboxing」][A1「Permission rules」「What runs outside」]

**未知**：本机 Claude Code 的默认排除命令、实际内嵌 runtime 版本、是否已有个人域名/路径例外。本轮没有接触程序或真实配置，不补猜测清单。文档里 Docker 等兼容性示例，不等于所有版本都默认排除了它们。

## 3. 这台 macOS 能不能用

### 3.1 可用与支持承诺是两件事

**事实**：本机有 `/usr/bin/sandbox-exec`，`man sandbox-exec` 的 NAME 和 DESCRIPTION 都标注 DEPRECATED，建议应用采用 App Sandbox。[M1]

**事实**：Apple DTS 在官方论坛说明自定义 sandbox profile 语言不面向第三方提供支持，这是弃用原因；提到 App Sandbox、虚拟机和不同机制的 EndpointSecurity。它没有给出通用命令行 profile 的直接替代。该回复是 2020 年的历史依据，不能据此推定 Apple 在 Darwin 27 新增了什么保证。[W2]

**未知**：Apple 何时删除 `sandbox-exec`、未来系统是否维持现有 SBPL 行为；本轮未找到承诺。**建议（推测）**：第一版可以用它，但沙箱创建失败应明确停止模型命令，不能自动当作无沙箱成功；后端可更换的余地留在后续实现设计，不在此定义接口。

### 3.2 本轮最小实测与耗时

**实测 [M1]**：在 `/tmp` 下自建独占目录，里面只有 `allowed`、`outside`、空 `home` 和自己的探针文件；命令环境先清空，再设隔离 HOME/TMPDIR 和系统 PATH。用 Rust 标准库 `Command::output` 与 `Instant` 测量，没有 Python、外部依赖、联网或系统设置变更。探针编译输出也在 `/tmp/p2-104-src`。

规则如下（`<probe>` 为规范化后的 `/private/tmp/p2-104-probe-<pid>`，不是用户目录；这是**可用性探针，不是生产策略**）：

```scheme
(version 1)
(deny default)
(allow process-exec process-fork)
(allow sysctl-read)
(allow file-read*)
(allow file-write* (subpath "<probe>/allowed") (literal "/dev/null"))
```

运行形态为 `/usr/bin/sandbox-exec -p <上述规则> /bin/sh -c <命令>`，写文件用固定的 `printf probe > "$1"`，路径通过独立参数传入。[M1]

| 实测动作 | 结果 | 单次用时 |
| --- | --- | --- |
| 第一次套沙箱运行 `/usr/bin/true` | 退出 0 | 12.386 ms |
| 写 `allowed/result` | 退出 0，内容为 `probe` | 8.937 ms |
| 写 `outside/result` | 退出 1，`Operation not permitted`，文件不存在 | 8.422 ms |

然后各预热 3 次，顺序交替跑 30 组「直接 `/bin/sh -c /usr/bin/true`」和「加 sandbox-exec 的相同命令」。计时包含创建、profile 编译、shell/true 执行、收输出和等待退出；不含 Rust 编译。P95 用 nearest-rank，第 29 个样本。[M1]

| 30 次统计（毫秒，实测 [M1]） | 最小 | 中位数 | P95 | 最大 | 平均 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 直接 shell + true | 3.520 | 4.119 | 4.956 | 5.072 | 4.128 |
| sandbox-exec + shell + true | 8.014 | 8.881 | 10.324 | 10.429 | 8.979 |
| 每组耗时之差 | 4.030 | 4.893 | 5.674 | 6.060 | 4.851 |

**结论限度**：本机这份小规则可用，起一次简单沙箱命令约 9 ms、额外约 5 ms。没测完整 Codex/Claude profile、路径数量扩大、代理启动、cargo/npm、真实工程或网络拒绝；这些性能与兼容性仍是未知。没有把它当安全审计或逃逸测试。自建运行夹具已删除；没有额外扩展验收测试。[M1]

## 4. canter 要套哪些入口

| 入口 | canter 现状与别家依据 | 建议及第一版范围 |
| --- | --- | --- |
| 模型 `shell` | `LocalExecutor::spawn` 直接 `/bin/sh -c`；Codex 和 Claude Code 可在启动子进程时套 OS 沙箱。[K2][C1][S3] | **第一版套**，覆盖所有模型命令，包括白名单免问命令。批准不改变已选 OS 边界。 |

| 用户 `!`、`!cmd &` | canter 独立命令轮，不请求模型、不经 gate；Codex user shell 明确用 Disabled/None 且不继承网络代理；Claude Code 通常也例外。[K4][C11][A1] | **建议保留用户手动全权限入口**，界面明确写用户命令、未沙箱；模型不能借普通工具调用选择这个来源。是否连 `!` 也套，见 §7。 |
| 内置 `read/write/edit` | canter 在服务端读写，`spawn_blocking` 是线程，不是被 shell 沙箱包住的子进程；P2-118 增加 write/edit 的目录外批准。[K2][K5] | **第一版继续用应用层边界**，不迁出整个文件执行器。读保护须同时覆盖 read 及准备 diff 的读取。若要让所有权限档都守相同可写范围，还需用户同意扩展 P2-118，见 §6。 |
| 别家的文件工具 | Claude Code 文件工具在 shell 沙箱外；Codex 0.163.0 的 `apply_patch` 携带 filesystem sandbox context，并可走沙箱文件 helper。[A1][C12] | **不照搬“所有文件工具都管不到”这个结论**：只包 shell 管不到 canter 当前文件工具，但移到受限 helper 后可做到。这是后续更强隔离的一件，不是第一版前提。 |
| stdio MCP | canter 在服务端启动时创建全局 Registry，按配置直接起 MCP 进程；工具批准发生在后续调用时。Codex 本轮查到的本地 launcher 直接起进程，executor launcher 也传 `sandbox: None`；Claude Code 公开文档说 MCP 不在 Bash 沙箱内。[K6][C13][A1] | **应单独隔离，但第一版后补**；不能给一个全局进程套上任意会话的 cwd/add-dir。先保留现有 MCP 审批，明确它在命令沙箱外；不能因 shell 自动批准而一并免问。用 MCP 的会话不能声称“全部工具都在墙里”。 |
| HTTP MCP | canter 用服务端 reqwest 和配置请求头联网；本机 shell 沙箱不控制远端服务做什么。[K6] | **不属于子进程沙箱**；保留可信服务器配置与工具批准。未来统一网络规则也只约束本机发出的连接，不隔离远端操作。 |
| `web_fetch` | canter 服务端 reqwest 固定 `no_proxy`；同主机和端口才跟跳转，私网/本机不另挡。Claude Code WebFetch 另走权限；Codex 托管 web search 不受命令网络代理控制。[K7][A1][W1] | **第一版保留单独批准边界**，不因为 shell 沙箱而免问。将来按域名联网要显式覆盖它，不能只设 `HTTP_PROXY` 就宣布完成；不在本轮改抓取检查。 |
| 临时脚本（P2-91） | 当前靠 write + shell，没有专门临时目录。两家 OS 机制约束后代进程，不根据脚本语言分类。[K8][C1][S1] | **第一版与普通 shell 同样套**；会话独占临时目录写脚本和中间结果，执行得到的权限仍是会话范围。临时目录不是“只能处理目录内数据”的代码解释器；若要仅处理附带数据，需要另定更小范围。 |

**补充边界（事实与推测分开）**：canter 自己还要读配置/技能和指令、写会话历史/撤销文件、调模型；终端有 `/review` 的 git/gh、statusline 自定义命令、外部编辑器、链接打开及图片剪贴板等操作。[K9] 这些是用户或宿主触发的入口。**建议（推测）**第一版不把整个常驻服务端/终端放进某个会话的沙箱，也不顺带改这些产品行为；明确它们属于可信宿主。否则多会话的凭证、存盘和工作目录会互相牵制。两家其它宿主入口是否逐一有额外隔离，本轮没有完整审计，记为**未知**。

**推测**：这里的隔离也不等于进程资源配额或回滚。canter 已有的看护进程、超时、进程组清理必须保留；Seatbelt 本身不能替项目提供 CPU/内存配额、命令撤销或保证所有后代都回收。现有 README 明说换到其它进程组的后代可能不在清理范围，不能把“套了墙”写成已经修复这个问题。[K3]

## 5. 范围、敏感读取、网络与常用命令

### 5.1 推荐边界

以下全部是**建议（推测）**。列出的事实只用于解释取舍，不代表用户已接受。

| 项目 | 第一版建议 | 依据与代价 |
| --- | --- | --- |
| 可写项目范围 | cwd + P2-118 add-dir；按规范化后的实际路径处理，不因命令 `cd` 改变信任范围 | P2-118 已定跨仓库用途与规范化要求；两家的命令沙箱按路径范围实施。[K5][C3][S3] |
| 临时目录 | 系统临时目录下每会话独占一份，给子进程作为 TMPDIR；不放进受保护的 `~/.canter` 内，不开放整个 `/tmp` | Codex 默认临时范围较宽；runtime 会设置 TMPDIR。会话专用范围更窄，硬编码 `/tmp` 的工具可能需适配；这是有意的兼容性取舍。[C3][S5][K8] |
| `.git` | **第一版全部只读**，含 worktree 指针指向的实际元数据；需要 Git 写操作时申请一次范围明确的元数据写授权，继续保留配置/hooks 保护 | Codex 保守保护全 `.git`；Claude Code 文档允许一般 Git 元数据写而保护 hooks/config。前者简单但 `add/commit` 会停一次；更宽的自动策略可后补。[C4][A1「Filesystem isolation」「Protected paths」][T3] |
| 工作目录外普通文件 | 默认 shell 可读不可写；写入通过 add-dir 或单次指定范围授权，不能只靠「允许这条命令」获得任意目录 | 对应 cwd/add-dir 意图，也使执行审批与路径授权含义分开。[K5][C7] |
| `~/.canter` 及实际状态/配置路径 | 模型命令和文件工具均拒绝读写；连接 canter 自己的控制 socket 也拒绝 | 现有文件工具已保护，shell 尚未保护；Unix socket 在状态目录，文件读写权限并不等价于 socket 连接权限。Codex 也另保护自己的 daemon 通道。[K2][K6][C1:1058–1064] |
| `~/.ssh` 等凭证 | 最少拒绝读写 `.ssh`、`.aws`、`.gnupg` 和用户明确列出的凭证路径；通过同一策略约束 shell 与内置文件读取 | 两家传统默认全盘可读不满足这层目标；SRT 的 denyRead、Codex 细粒度拒读可作参考。代价是 SSH 签名/私有依赖等可能需用户手动执行，或由用户明确调整凭证策略，不能用普通命令批准解除硬拒绝。仅列常见目录不能宣称找到了全部秘密。[C3][C7][S2][K2] |
| 环境中的秘密 | 给模型子进程的环境只带必要运行变量，凭证显式提供；不能以 `env_clear()` 已调用为依据说没有秘密 | canter 随后装回完整会话环境；路径规则不抹掉已经继承的环境值。SRT 另有 unset/mask 处理，说明两者是不同边界。[K2:209–215][S3:1580–1602] |
| 本机 IPC、开发端口 | 默认不开放任意 Unix socket/本机服务；Unix socket 单独限制，开发端口随 §5.2 的 IP 联网授权放开，始终排除 canter 控制 socket | 开放 Docker socket、SSH agent 或宿主 RPC 是另一种能力，不能与「可写一个缓存目录」混为一谈。[C1][C5][S3] |

**推测**：所有范围扩大都应是用户授权，模型不能通过修改仓库里的配置自行加目录、放开联网或改权限。后续策略需覆盖路径别名、链接及实际目标，拒绝规则不能被宽的 add-dir 抹掉；本轮只据源码指出需要这些边界，没有构造绕过用例。[C1][C4][S3][K5]

### 5.2 网络三种方案

| 方案 | 事实依据 | 对 canter 的取舍（推测） |
| --- | --- | --- |
| 全关 | 两家均能用 OS 规则阻止直连；不影响沙箱外的模型服务连接。[C5][S3][W1] | 默认最清楚；新依赖下载、fetch、外部服务测试会失败。不能因此自动移到沙箱外。 |
| 全开 | Codex 普通网络开关、SRT 未要求网络限制时可全开。[C5][S3:1255–1258] | 兼容性好；任何可读资料都可能通过命令出站，不能称为域名保护。**不推荐作为默认**。 |
| 按域名代理 | 两家都有 OS 直连限制配合代理，单设环境变量不够。[C5][S3][S4] | 能把某主机授权与每条命令审批分开，适合长程；要处理代理感知、域名/端口、DNS/私网、重定向和本机服务等，明显扩大第一版。 |

**推荐（推测）**：第一版默认全关；用户可为**一条命令及它的子进程存活期间**批准 IP 网络访问，保留文件限制、敏感拒读与 canter 控制 socket 禁止。这是本次命令的广泛联网授权，**包括本机和内网 IP，不是批准一个网址，也不是仅允许公网**。首版没有域名代理时，不把批准文案写成「仅访问 npmjs.org」。Unix socket 仍单独受限。带网络授权的后台任务也持续持有该授权直到退出，不能用工具调用已经返回来声称授权结束。此方案的实际网络规则兼容性未实测，记为未知。[C5][S3][K3]

**建议（推测）**：按域名代理放到下一件；不用在 canter 首版引入 Node runtime、凭证替换或 TLS 中间人。遇到需要真正全权限的操作，首版让用户用 `!` 手动完成；不提供模型自动无沙箱重试。若用户认为依赖下载提示仍太多，§7 可选第一版直接做代理。

### 5.3 git、cargo、npm 会坏在哪里

以下是**据资料推测的兼容性影响，未运行这些命令验证**。

| 命令/场景 | 预期影响 | 别家已有做法与 canter 建议 |
| --- | --- | --- |
| `git status/diff/log` | 大多只需读；索引刷新、签名、外部过滤器或隐式联网仍可能碰限制 | canter 的只读白名单已经检查部分 Git 配置；保留它。不要给名字为 git 的全部调用免隔离。[K1][K10] |
| `git add/commit/checkout`、worktree | 写 `.git` 时被挡；gitdir/commondir 可以在另一个目录；hooks、签名也可能要求额外能力 | Codex 默认保护全元数据；Claude Code 容许常见元数据写、保护 hooks/config。首版采用前者加显式范围授权。不要为一个 worktree 自动放开主仓库及所有兄弟目录。[C4][A1][T3] |
| `cargo build/test` | 依赖缓存默认在 `~/.cargo`，编译结果或锁文件需写；缺依赖还要联网 | Cargo 支持另设 CARGO_HOME，里面同时有 config、credentials、bin、registry 等；不能把整个真实 `.cargo` 作为普通缓存全写。建议会话专用缓存，可明确复用可信缓存，凭证和工具链保持保护；新缓存有重新下载成本。[T1][C3] |
| canter 自己的构建 | CLAUDE.md 要求 `CARGO_TARGET_DIR` 指到 worktree 外的 `.target/<分支>` | 这一个编译子目录也要由用户加入可写范围，不能只允许 cwd 后声称本项目构建无感。[K11] |
| `npm install/ci/test` | `node_modules` 在项目内可写；Posix 默认缓存 `~/.npm` 在项目外，下载需要网络 | npm 支持改 cache；runtime 默认便利路径只含 `.npm/_logs`，不等于整个缓存都可写。建议会话缓存；包的安装/测试脚本及后代始终在同一沙箱内。[T2][S5][S1] |
| git HTTPS / SSH、数据库客户端 | 代理变量可能只被部分工具采纳；SSH 还依赖密钥/agent；只许可域名并不让忽略代理的程序自动连通 | SRT 提供 HTTP/SOCKS 路由；未接代理的工具需适配，不能一失败就永久排除整类命令。首版由明确的单次能力授权处理，确实不兼容才让用户手动跑。[S1][S3][A1「Network isolation」] |

**事实边界**：Codex writable roots 和 Claude Code `allowWrite` 都能增加工具所需目录；没有查到两家承诺自动、安全地处理所有 cargo/npm 缓存。**未知**：本机各工具、已装依赖、私有 registry、签名设置的兼容性；本轮不读真实配置，不能替用户断言。[C3][A3]

## 6. 和 canter 现有规矩怎么接

### 6.1 已定规矩与新提案不能混用

**事实**：当前 gate 的会话授权优先于普通三档判断；shell 的「本会话允许」等于这一会话所有 shell。`alwaysAsk` 问非读取工具，`askForExecution` 问执行类，`allowAll` 不问；白名单 shell 有免问例外。计划和审查的拒绝先于这些授权。[K1]

**事实**：P2-118 已定的是 **Ask for execution 下**目录外 write/edit 要批准，且明确 `allowAll`、受保护路径等不变。因此**仅完成 P2-118 + shell 沙箱，仍不能说 allowAll 的内置文件工具只能改项目内文件**。这不是实现缺陷的指控，而是任务要求的边界；它的最终会话授权粒度本分支尚无完成记录，未知，需以 P2-118 落地结果为准。[K5]

**建议（推测，须用户同意）**：沙箱与批准作为两层。沙箱开启时，让内置 read/write/edit 也服从同一敏感拒读和可写范围；write/edit 仍用 P2-118 的规范化路径判断而不是迁进新子进程。`allowAll` 仅免问当前范围内的工具，越界失败；询问档允许申请一次指定文件/目录授权。此项**扩展了 P2-118 原来不变的 allowAll 语义及 read 范围**，不能悄悄纳入已经批准的需求。

### 6.2 推荐的批准矩阵

下表全部为**待用户批准的推测方案**，适用于沙箱已成功启用且 §6.1 的范围统一被接受之后；关闭沙箱沿用原行为。依据是现有三档含义、两家沙箱内自动执行机制及 P2-118 的目录边界。[K1][K5][C6][A3]

| 操作 | `alwaysAsk` | `askForExecution`（推荐长程档） | `allowAll` |
| --- | --- | --- | --- |
| 普通 read | 沿用免问，但敏感拒读仍挡 | 同左 | 同左 |
| 范围内 write/edit | 沿用原批准/会话授权 | 免问 | 免问 |
| 范围内模型 shell / 临时脚本 / 后台启动 | 白名单免问，其余照原批准/会话授权 | **沙箱内免问**，P2-108 的显式 ask/deny 如有则保留 | 免问，仍在沙箱内 |
| 普通目录外写、临时联网、Git 元数据写授权 | 必须明确展示扩大的范围 | 同左 | 默认失败，不把“全部允许”变成自动扩大范围 |
| 敏感拒读、控制 socket、计划/审查硬拒绝 | 不被普通批准解除 | 同左 | 同左 |
| MCP、`web_fetch` | 沿用各自批准；明示未受命令沙箱隔离 | 沿用各自批准，不因 shell 免问而免问 | 保留原不问语义，**所以仍有沙箱外副作用** |

**建议（推测）**：错误反馈分清「明确被策略拒绝」「看起来像权限失败」「沙箱启动失败」，保留原退出码/输出；未知错误不自动提权。批准授权范围扩大后，由新的明确调用重新执行，提示前一次可能已产生部分副作用。已有 `AcceptForSession(shell)` 或 P2-108 allow 不能解除 OS 沙箱、敏感路径或网络限制。[K1][C7][C9][C10]

### 6.3 只读白名单、计划和审查

**事实**：白名单源码开头明确说只是批准启发式，不是沙箱；字面路径检查不追踪所有程序内行为。计划模式禁止 write/edit、非白名单 shell、MCP、update_plan，允许 `web_fetch` 沿用原批准；审查轮拒绝 `web_fetch`。后台读取、停止和 monitor 已有各自规则。[K1][K7][K10]

**建议（推测）**：保留白名单用于 `alwaysAsk`、沙箱关闭和只读场景；即使白名单免问也套 OS 限制。计划/审查中新启动的 shell 采用项目只读范围，只允许必要的私有临时写入，不开放普通构建缓存，不能用普通审批或 P2-108 放宽。不能因为 `web_fetch` 叫 fetch 就把审查轮的禁令去掉。

**事实与未知**：已经运行的后台命令不会因为进入计划模式而重新启动；当前系统也没有为它重新套 OS 沙箱的路径。[K3] **建议（推测）**首版保持这个生命周期，提示已有写任务仍在运行；「计划/审查只读」只保证本轮新动作，不声称整台机器或所有既有命令突然只读。若用户要切模式时自动停所有写任务，需要另行批准。

**建议（推测）**：P2-108 首版只决定命令要不要问；不要复制 Codex 显式 allow 同时出沙箱的语义。临时脚本内容可以变，批准 `rustc`、解释器或脚本前缀不代表批准它访问一切。P2-91 的临时目录和提示词说明可随沙箱方案提出，但提示词变更仍要用户定；本轮不写新的提示词。[C6][C7][K8][K11]

## 7. 推荐范围、工作量和要用户定的问题

### 7.1 第一版做什么，以后做什么

**推荐（推测）**：canter 自己用 Rust 管理 macOS Seatbelt 启动，不把 sandbox-runtime 当运行依赖；参考两家的权限边界与异常处理，不复制整套 agent。已验证本机基本可用，独立 Node 运行时和 research preview 依赖对这个 Rust 项目不是最小方案。原生方案仍有维护 SBPL 和处理系统版本差异的成本。[K11][S0][C1][M1][W2]

第一版包含以下结果，均为**待定建议**：

- 模型前后台 shell 和临时脚本默认套墙，沙箱不可用就停止该命令；cwd/add-dir/会话临时目录为普通可写范围，保护敏感路径和控制 socket。[K2][K3][K5][C1][S3]
- `Ask for execution` 的墙内命令免问，越界要有明确范围授权；保留 `Always ask`，`Allow all` 不等于取消沙箱。文件工具用应用层检查保持边界，是否扩展其现有语义由下面第 3 题决定。[K1][K5][C6]
- 网络默认关，单条命令可明确批准广泛联网；`.git` 默认只读，需要写时单次批准限定元数据范围。先提供会话临时/缓存位置，避免顺手开放真实 HOME。[C3][C4][T1][T2]
- 显示实际隔离范围、阻止原因、授权范围和在外执行的入口；后台进程沿用启动时的权限。保留用户 `!`，MCP/`web_fetch` 独立批准。[K3][K4][K6][K7]

**以后再做（推测）**：域名代理及与 `web_fetch` 的统一出站规则、按 MCP 服务划定隔离范围、把文件工具移到受限 helper、更多开发工具兼容性、可重复的凭证委托。它们各自有独立边界，不能用一个 shell 启动前缀冒充已经做完。[C12][C13][S1][K6][K7]

**平台留余地（一句建议，推测）**：让权限含义与 macOS 实现分开，Linux 以后接 bubblewrap/seccomp、Windows 以后选对应系统隔离机制；本轮不展开。[C2][S1]

### 7.2 大概多大一件

下面是**工作量推测**，不是排期承诺；没有写接口字段、拆模块或规定代码行数。

| 层 | 要产生的结果 | 量级依据 |
| --- | --- | --- |
| 工具/执行 | 前后台统一进入沙箱；路径与敏感读取约束；临时目录/缓存；保留看护和取消；拒绝反馈 | 改动最重。现有 shell 启动点集中，但文件操作在同进程、前后台共享生命周期。[K2][K3] |
| 核心 | 区分普通批准与范围扩大；结合会话目录、三档权限、计划/审查；已有后台权限不变 | 中到大；现有工具会话授权不能直接代表新的范围授权。[K1][K4][K5] |
| 协议/存盘/服务端 | 客户端能知道真实启用状态与范围，恢复、多客户端一致，旧客户端不误报安全状态 | 中等；现有 HTTP+SSE 和会话设置可提供基础，但需用户定方案后再设计。[K11，DESIGN 第 8 条] |
| 终端 | 启用状态、范围查看、一次授权文案、未沙箱用户命令提示、失败说明 | 中等；直接关系用户是否知道批准的是联网、写目录还是完全不套。[K1][K4] |

**推测结论**：不是加一个 `sandbox-exec` 前缀的小件；按上述首版范围大约是 **3～4 件中到大的开发/审查工作**。若把按域名网络、MCP 和文件 helper 一并纳入，会变成更大的一组任务。最大未知是实际工程和工具链兼容性，不是本机简单命令多出的约 5 ms。[M1][C1][S3][K2][K6]

### 7.3 可直接交给用户的选择

以下每题的推荐都是**推测/取舍**；都未写入 DESIGN，也未实施。用户可回复编号和选项。

1. **第一版采用哪种沙箱，默认开不开？**
   - **A（推荐）**：macOS 原生 Seatbelt，模型命令默认开启；起不来就明确失败。
   - B：同一方案，但默认关闭、按会话手动开。
   - C：先做容器/虚拟机等更完整环境，再开放自动执行。
   - 依据：本机可用、额外耗时低；Apple 已弃用，未来维护仍有不确定性。A 最快提供实际边界，C 的环境与部署工作明显更大。[M1][W2][C1]

2. **沙箱内命令怎么少问，P2-108 的 allow 是否同时出沙箱？**
   - **A（推荐）**：`Ask for execution` 墙内免问；`Always ask` 保留现有询问；`Allow all` 也守墙。P2-108 allow 只免确认，不移除沙箱。
   - B：三档批准规则全保留，沙箱只兜底，少问主要等 P2-108。
   - C：命令 allow 也能授权在沙箱外执行。
   - 依据：A 直接服务长程任务；C 类似 Codex 的某些显式 allow 行为，授权含义更大。A 会修改现有 `Ask for execution` 的部分行为，需用户同意。[K1][C6][C7]

3. **read/write/edit 是否跟 shell 一起守相同路径边界？**
   - **A（推荐）**：沙箱开启时统一；加入敏感拒读，`allowAll` 的内置修改也不能直接越界。普通外部路径在询问档可获单次授权，敏感硬拒绝不由普通批准解除。
   - B：只采用 P2-118 已定规则；read 和 `allowAll` 继续原样，清楚标明只隔离 shell。
   - C：第一版就把文件工具迁到 OS 沙箱 helper。
   - 依据：B 对当前需求改动少，但无法保证全部文件工具的边界；A 是应用层一致性，仍不等于 C 的 OS 文件隔离。A 明确超出 P2-118 已批准语义。[K2][K5][C12]

4. **第一版怎样联网？**
   - **A（推荐）**：默认全关；需要时单条命令批准 IP 网络，保留文件和控制 socket 限制。该授权包括内网/本机 IP，界面明说。
   - B：第一版就做按域名代理；新主机单独授权并在会话内记住。
   - C：默认全开，只限制文件。
   - 依据：A 范围较小、边界清楚但下载仍可能打断；B 更适合频繁联网的长任务，开发量更大；C 不能防止可读资料经命令发送出去。[C5][S3][S4]

5. **`.git` 写入怎么处理？**
   - **A（推荐首版）**：默认全只读；`add/commit` 等需单次指定元数据写授权，保留 config/hooks 保护；worktree 真实元数据范围展示清楚。
   - B：常见索引/对象/refs 默认可写，仅保护 config/hooks 等，尽量不打断提交。
   - C：`.git` 完全与普通项目文件一样可写。
   - 依据：A 更接近 Codex 的默认边界但批准较多；B 更接近 Claude Code 的兼容性方向，需处理共享 gitdir，不能承诺兄弟 worktree 元数据彼此隔离；C 可能修改以后会被宿主运行的配置/hooks。[C4][A1][T3]

6. **临时脚本和工具缓存放哪里？**
   - **A（推荐）**：每会话独占系统临时目录，缓存另定可写位置；不默认开放整个 `/tmp`、真实 `.cargo`/`.npm`。普通脚本仍按会话沙箱执行，提示词如何说明留到实现任务确认。
   - B：放开系统临时目录和真实常用缓存，优先兼容现有命令。
   - C：第一版不提供临时/缓存位置，遇到问题都手动加目录。
   - 依据：A 避免混进凭证、工具二进制和其它会话，但可能重新下载；B 的真实缓存内不只有可丢弃数据；C 对 P2-91 的便利性帮助有限。[K8][T1][T2][S5]

7. **用户的 `!` 命令要不要套？**
   - **A（推荐）**：保留用户手动全权限，包括手动后台；清楚标识未沙箱，模型不能选择这个入口。
   - B：也套相同沙箱，用户需要自行在普通终端执行不兼容命令。
   - 依据：A 延续 P2-26/P2-28 与 Codex user shell 的分工；B 统一性更强，但改变用户直接执行的使用方式。[K4][C11]

8. **第一版是否接受 MCP / `web_fetch` 尚在 shell 沙箱外？**
   - **A（推荐）**：接受并明确标识，保留各自批准；首版不把它们加入沙箱内免问集合，之后各开一件。
   - B：沙箱会话先禁用这两类工具，直到完成各自隔离。
   - C：一并做完才交付第一版。
   - 依据：全局 MCP 不能直接套每会话范围，`web_fetch` 是进程内直连；A 尽快覆盖最宽的任意命令入口，但有明确覆盖缺口，特别是 `allowAll` 会不问地使用这些工具。[K6][K7][C13]

**交主控的状态**：完成本轮报告不需要主控另做技术决定。上述 8 题是报告的交付内容，需要用户选择后才可开实现任务；不是要求现在修改 P2-118。拆实现任务时再核对 P2-118 最终落地和会话授权粒度，本轮未进入那份 worktree。
