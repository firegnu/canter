**结论摘要**

- 别家（事实）：内置判断都很窄。Codex 只认「带 `-f` 的 `rm`」；Claude Code 只认「`rm`/`rmdir` 删到关键路径」，另有 auto 档的分类器模型；omp 有一份「致命命令」正则表；opencode、pi 核心里没有。「全部放行」档里，Codex 直接拒绝，Claude Code 仍弹框、两分钟没人答就拒绝，omp、opencode、pi 不管。没有一家对 `git reset --hard` 这类「丢未提交改动」的命令做硬判断（Claude Code 只在 auto 档的分类器里拦）。
- canter（事实）：「全部允许」下只看 `rules.json` 的禁止规则，其余一律直接跑，没有任何内置危险判断；禁止规则只按词前缀比，除了 HANDOFF 记的四种写法，还认不出带路径的程序、子命令前的全局选项、选项换顺序、控制结构里的命令、括号和 `${…}` 之后的整段等。「总是问」「只问执行」下，危险命令一般会问，但被放行规则或会话前缀盖住的会直接跑：10-29 装的 `git push` 放行规则会连 `git push --force` 一起放过。
- 推荐（推测）：**内置一份窄的危险判断（方案 A）+ 沙箱 P2-123（方案 C）组合**。危险判断管沙箱管不到的「工作目录里难挽回的删除、git 丢改动、改远端历史和发布」，命中后在「总是问」「只问执行」下强制弹框且不能被放行规则免掉，在「全部允许」下直接拒绝并告诉模型；匹配器的改进同时拿来补禁止规则的漏。清单多宽、「全部允许」下拒绝还是弹框，要用户定（§4.5）。

## 1. 别家怎么防

### 1.2 Codex（`rust-v0.163.0`）

- **事实**：内置危险判断在 `is_dangerous_command.rs`。POSIX 下只有一条：程序是 `rm`（按文件名认，`/bin/rm` 也算）且带强制选项（`--` 之前任一短选项组含 `f`，或 `--force`）。会看穿 `sudo`、`env`（跳过变量赋值和 `-i`）、`trap` 的动作，以及 `bash -lc` 脚本里的字面命令，包括 `if`、`for` 体和命令替换里的；包装嵌套超过 8 层直接当危险。没有 git、chmod、dd 之类的条目（Windows 另有一份 PowerShell/cmd 清单，和本机无关）。[C1:34,49–81,123–151,196–205,233–290]
- **事实**：它自己的测试列出认不出的写法：`cmd=rm; $cmd -rf …`、`echo 'rm -rf …'`（后者本来就不是删除）。不带 `-f` 的 `rm -r` 也不算危险。[C1:293–306]
- **事实**：内置判断只在**这段命令没有命中任何用户规则时**才跑。用户规则写在 `~/.codex/rules/*.rules`，`prefix_rule` 按词前缀匹配，每个位置可写多个备选，结果是 allow / prompt / forbidden。所以用户写了 `allow ["rm"]`，`rm -rf` 就不再算危险；一条命令每段都被 allow 命中时，还会直接出沙箱跑。[C3:305–331][C3R:5–9][C2:440–458]
- **事实**：命中后，`on-request`、`untrusted`、`granular` 档强制再问，`danger-full-access` 下也问；「以后不问」提议的是这一整条命令，不是前缀。`never` 档直接拒绝，告诉模型 `rm -f style commands are not permitted. Use a safer approach`。[C2:793–806,1110–1118][C6:2071–2114,2121–2172]
- **事实**：`--dangerously-bypass-approvals-and-sandbox`（yolo）等于 `never` + `danger-full-access`，所以 yolo 下带 `-f` 的 `rm` 被拒绝。用户 forbidden 规则所有档都拒绝；用户 prompt 规则在 `never` 下也变成拒绝。[C5][C2:216–224,395–436]
- **事实**：所有模型 shell 都经 `unified_exec` 调用这套判断。[C4:1507–1532]
- **事实**：另有软约束：提示词要求「除非用户要求或批准，绝不用 `git reset --hard`、`git checkout --` 这类破坏性命令」。[C7:19] 还有可选的 `approvals_reviewer = "auto_review"`，由另一个模型代用户审批准请求；它具体审什么本轮没看，**未知**。[C8]

### 1.3 Claude Code（官方文档，2026-10-30）

- **事实**：权限档有 default（界面叫 Manual）、acceptEdits、plan、auto、dontAsk、bypassPermissions；终端里 v2.1.283 起默认是 auto。[A1#permission-modes][A2#which-mode-a-session-starts-in]
- **事实**：规则按 deny → ask → allow 判，先命中的算。文档原话：deny 规则「在所有档都拦，包括 bypassPermissions」；allow 规则在 bypassPermissions 下没用；ask 规则和下面的关键路径删除属于「没有哪一档会自动放行」的动作，bypassPermissions 也弹框。[A1#manage-permissions][A2「Available modes」][A2#actions-no-mode-auto-approves]
- **事实**：Bash 规则匹配命令原文（`*` 通配）。先按 `&&`、`||`、`;`、`|`、`|&`、`&`、换行拆段；deny 和 ask 还看子 shell、命令替换、`for` 循环体里的命令。匹配前剥掉 `timeout`、`time`、`nice`、`nohup`、`stdbuf`、`command`、`builtin`、`noglob` 和不带选项的 `xargs`；deny 和 ask 能越过任何前置变量赋值。认不出 `/bin/rm`、`bash -c '…'`、`git -C . push`、`git 'push'`；文档明说 deny 规则「不是围着这个程序的安全边界」，要硬约束得用沙箱或 PreToolUse hook。[A1#compound-commands][A1#process-wrappers][A1#bash-rule-limits]
- **事实**：内置「关键路径删除」检查：`rm` 或 `rmdir` 的目标是根、根下一级目录、家目录、工作目录及其上级、加进来的目录下的通配，或者变量、命令替换做目标（变量为空就成了删根），以及「shell 读法可能和解析结果不同、排除不了危险 rm」的命令。allow 规则和 hook 都放不了。Manual、acceptEdits、plan 下弹框；auto 和 bypassPermissions 在终端里弹框带两分钟倒计时，到时拒绝并告诉模型，一个会话里连续三次没人答就直接拒绝；不在终端（VS Code 面板、桌面应用、`-p`）时直接拒绝。只有设环境变量 `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1` 才能在 bypassPermissions 下关掉。文档也说这个检查会漏，不能代替沙箱，而且只管 `rm`/`rmdir`，别的命令照样能删。[A2#critical-paths][A2#which-paths-are-critical][A2#critical-path-removals-in-each-permission-mode][A2#time-limits-and-denials-in-auto-and-bypasspermissions-modes][A2#turn-off-the-critical-path-removal-prompt-in-bypasspermissions-mode]
- **事实**：受保护路径（`.git`、`.claude`、`.vscode`、`.gitconfig`、`.zshrc` 等 shell 配置）的写入，Manual、acceptEdits 下弹框且 allow 规则放不了，bypassPermissions 下放行。[A2#protected-paths]
- **事实**：auto 档由另一个分类器模型审每个动作，默认拦：`curl | bash`、把敏感数据发到外面、生产部署和迁移、云存储批量删除、force push、`git reset --hard`、`git checkout -- .`、`git restore .`、`git clean -fd`、`git stash drop`/`clear`、`terraform destroy` 等、不可逆地毁掉会话开始前就有的文件；连续拦 3 次或累计 20 次就退回弹框。进 auto 时会丢掉 `Bash(*)` 这类等于任意执行的宽放行规则。[A2#eliminate-prompts-with-auto-mode][A2#how-the-classifier-evaluates-actions]

### 1.4 opencode（`v2.1.3`）

- **事实**：没有内置危险命令清单。在 `packages/core/src` 里搜 dangerous、`rm -rf`，只找到 opencode 自己删目录用的一处。[O7]
- **事实**：shell 工具先把命令解析成段，每段原文作为一个资源去匹配 `shell` 权限；规则用 `*`、`?` 通配，最后一条命中的生效，都不命中就问；deny 在合并已保存的放行之前先判。[O2][O3:74–84,152–175,222–236][O5:68–103]
- **事实**：默认 agent 的权限是 `"*": allow`（只有读 `.env` 要问），所以默认所有 shell 命令直接跑；文档也写「大多数权限默认 allow」。[O1][O5:172–191]
- **事实**：`--auto`（隐藏别名 `--yolo`、`--dangerously-skip-permissions`）下，终端对每个询问自动答「这次允许」；用户写的 deny 照样拦。[O4][O5:22–38][O6]
- **未知**：文档说 `external_directory` 默认问、`.env` 默认拒绝，而 2.1.3 代码里的默认规则是 `*` allow、`.env` 问；运行时以哪个为准，本轮没运行、没查清。和本题关系不大。

### 1.5 pi（coding-agent `1.4.0`）

- **事实**：核心没有批准环节。文档说 pi「不会在每次工具调用前请求批准」，安全要靠操作系统用户、容器、虚拟机或沙箱隔离，看对话记录不算安全边界；bash 工具代码里没有批准逻辑。[P1:3,7,13–17][P5]
- **事实**：示例扩展 `permission-gate.ts`（要用户自己装）用三条正则（`rm -rf`/`rm --recursive`、`sudo`、`chmod`/`chown … 777`）匹配整条命令原文，命中弹框，没有界面时直接拦。同目录还有 `protected-paths`、基于 sandbox-runtime 的 `sandbox`、每轮用 `git stash` 留检查点的 `git-checkpoint` 等示例。[P2][P3:21–26][P4]
- **事实**：pi 没有权限档位，相当于一直「全部放行」。[P1:3]

### 1.6 omp（coding-agent `18.14.0`）

- **事实**：批准档有 always-ask、always-ask-cached、write、yolo，默认 yolo；`--auto-approve` 强制 yolo。[M1][M2:44,97–113]
- **事实**：bash 工具内置一份「致命」正则表：对绝对路径做递归或强制 `rm`、`--no-preserve-root`、任何 `sudo rm`、对 `/` 下的 `chmod -R`/`chown -R`、fork 炸弹、写 `/dev/sd*`、`mkfs`、`dd of=/dev/…`、`shred /dev/…`、`cryptsetup`、写 `/etc/passwd|shadow|sudoers`、`curl`/`wget` 管道给 shell 及 `bash <(curl …)`、`eval $(curl …)`、`kill -9 1`、`shutdown`/`reboot`/`halt`、`init 0`、`nc -e`。注释说故意收紧，只收「自动化里几乎不会正当出现」的。没有 git 条目；`rm -rf ./src`、`rm -rf ~` 这类目标不以 `/` 开头的不算。[M3:181–234]
- **事实**：命中后返回「强制」标记：非 yolo 档一律弹框，用户设了 `bash: allow` 或 `bash.patterns` 里 `*` allow 也盖不过；只有用户的 deny 规则能直接拦。[M3:546–589][M2:462–471][M4:585–628]
- **事实**：yolo 档忽略这个标记，照常放行（测试名就叫 `ignores override-based prompts in yolo mode`）；用户写的 `bash.patterns` deny/prompt 和 `bash: deny`/`prompt` 在 yolo 下仍有效。[M2:422–460][M4:85–101]

### 1.7 共性

- **事实**（汇总上文）：内置判断都只拦很窄的一类，都看不到脚本、解释器、构建工具里面；Claude Code 文档明说规则不是安全边界、要配沙箱，pi 文档把安全完全交给隔离。
- **事实**：没有一家对 `git reset --hard`、`git checkout -- .`、`git clean` 这类「丢未提交改动」的命令做硬判断：Codex、omp 没有条目；Claude Code 只在 auto 档的分类器里拦；Codex 和 canter 都只在提示词里写。
- **事实**：「全部放行」档有三种态度：直接拒绝（Codex `never`）；照样弹框、限时后拒绝（Claude Code bypassPermissions）；不管（omp yolo、opencode auto、pi）。
- **推测**：rm 的两种窄法打扰差别很大。Codex 管所有带 `-f` 的 `rm`，日常的 `rm -rf target/tmp` 也会问；Claude Code、omp 只管删到关键位置的，项目里删构建目录不打扰，但删项目里的 `src` 也不管。

## 2. canter 现在怎样

### 2.1 判断顺序

以下是**事实**（读代码）。模型 shell 的前台和后台走同一条判断。[K10:198]

1. 审查轮和计划模式先硬挡：只读白名单以外的 shell 直接拒绝、不弹框；白名单放过的，再走一遍下面的普通判断，所以禁止规则在计划、审查里也有效。[K5:1019–1059][K1:138–181]
2. 普通判断 `PermissionGate::evaluate`：
   1. 读 `rules.json`；读不了或格式错，三档都问一次（不给前缀选项）。[K1:267–269]
   2. 把命令拆成段，解析不了时保留已认出的字面段；任一段的词前缀命中 forbidden，就拒绝、不弹框，模型收到 `Command forbidden by rules.json`。[K1:270–280][K3:653–705]
   3. 「全部允许」到这里直接执行。[K1:281–283]
   4. 任一段命中 prompt 就问。[K1:284–288]
   5. 整条在只读白名单内，或者能完整解析且每段都被 allow 规则、会话前缀或白名单盖住，直接执行。[K1:289–300][K3:90–99]
   6. 其余的问；能解析时附「本会话这个前缀都放行」「以后这个前缀都不问」两项。[K1:301–337]
3. 回答「允许」时再查一次禁止规则。[K1:201–210]

「总是问」和「只问执行」对 shell 没有区别，代码只单独判「全部允许」。[K1:281]

### 2.2 三种模式下危险命令会不会问、会不会跑

| 情形 | 总是问 / 只问执行 | 全部允许 |
| --- | --- | --- |
| 命中禁止规则（认得出的写法） | 拒绝，不弹框 | 拒绝，不弹框 |
| 禁止规则认不出的写法（§2.4） | 一般会问；**这段如果被更短的放行规则或会话前缀盖住，就直接跑** | **直接跑** |
| 命中要问规则 | 问 | **直接跑**（这一档不看要问规则） |
| 被放行规则或会话前缀盖住，比如已装的 `git push` 盖住 `git push --force` | **直接跑** | 直接跑 |
| 其它危险命令（`rm -rf …`、`git reset --hard`、`dd …`），没写规则 | 问 | **直接跑** |
| `rules.json` 读不了 | 问 | 问 |
| 计划模式、审查轮 | 只读白名单以外一律拒绝 | 同左 |
| 用户自己敲的 `!` 命令 | 不经任何判断，直接跑（按设计） | 同左 |

依据：上表各行都可以从 §2.1 的步骤推出；`!` 命令不调用权限判断见 [K6]，DESIGN 写明规则不管 `!`。[K10:217] 「全部允许只看禁止」也是 DESIGN 定的。[K10:217]

### 2.3 现有各道防线

| 防线 | 管什么 | 挡得住 | 挡不住 |
| --- | --- | --- | --- |
| `rules.json` 禁止规则 | 模型 shell，三档和计划、审查都管 [K1:270–280][K5:1044–1059] | 用户写过的、能认出的字面写法；组合命令里任一段命中都拒绝；引号和反斜杠会先解码，`'rm' -rf`、`git "push"` 能认出 [K13:296–333] | §2.4 那些写法；用户没写的；「全部允许」下模型自己用 shell 改 `rules.json`（§2.5） |
| 要问规则 | 只在「总是问」「只问执行」下有效 [K1:281–288] | 写了的前缀强制弹框，压过白名单和会话前缀 | 「全部允许」完全不看；认不出的写法同禁止规则 |
| 放行规则、会话前缀 | 不是防线，是免问 | — | 前缀以后的任何参数都放过：`git push` 盖住 `--force`、`--delete`、`--mirror` |
| 只读白名单 | 只放不挡；计划、审查里当硬边界 [K3:116–388] | 免问的只有列目录、看文件、搜索、`git status/diff/log/show` 这类，不含删改；`find` 只认不带 `-delete`、`-exec` 的，`sed` 只认只读的 | 已知边界见 DESIGN：不是沙箱，符号链接、程序内部行为挡不全 [K10:98] |
| 受保护路径（`~/.canter` 和 `config.json`） | 只管 read/write/edit 工具 [K4:130–143][K7] | 模型用文件工具读写状态目录 | shell：只在白名单判断里「写出了受保护路径就问」，「全部允许」下 shell 随便改 [K10:97] |
| 计划模式、审查轮 | 新启动的模型 shell 只允许白名单 [K1:138–181][K10:94,191] | 所有删改类命令 | 进入前已在跑的后台命令照常跑 [K14 §6.3]；计划模式下 `web_fetch` 照普通批准，「全部允许」直接抓 [K10:191] |
| `!` 命令 | 不管（用户自己敲的） | — | 按设计不防 |
| 提示词 | 核心提示词要求不跑 `git reset --hard`、`git checkout --`、`git restore`、`git clean`、`git stash`、`git push --force`、`rm -rf`，除非用户明确要求 [K9] | 模型听话时 | 只是要求，模型不听、或被读到的内容误导时不管用 |
| 回退（P2-23） | 只备份 write/edit 工具改的文件 [K10:90] | 内置文件工具的改动 | shell 改、删的文件退不回；`!` 命令轮也只退对话 [K10:56] |

### 2.4 禁止规则认不出的写法

HANDOFF「命令规则（P2-108）」记了四种：`X=1 cargo publish`、`timeout 600 cargo publish`、`bash -c "…"`、括号包着的；并说「总是问」「只问执行」下照旧问，「全部允许」下会直接执行。[K11:135] 读代码核对，**这四种都属实**，另补六种；以下全是**事实**（读代码推出，没有运行）。

禁止规则的比较方式：每段的词列表必须以规则的词前缀开头，逐词完全相同。[K2:49–55]

| # | 写法 | 例子 | 为什么认不出 |
| --- | --- | --- | --- |
| 1 | 前置变量赋值（HANDOFF 已记） | `X=1 cargo publish` | 这段第一个词是 `X=1`；扫描器只把它判为「解析失败」，词列表照原样拿去比 [K3:663–666] |
| 2 | 包装命令（HANDOFF 已记） | `timeout 600 cargo publish`；同类还有 `sudo`、`env`、`nice`、`nohup`、`time`、`command`、`exec`、`xargs rm -rf`、`find … -exec rm` | 第一个词是包装名，不剥 |
| 3 | 另起 shell 或解释器（HANDOFF 已记） | `bash -c "cargo publish"`、`sh -c`、`eval "…"`、`python3 -c "…"` | 引号里整段是一个词，不往里看 |
| 4 | 括号、花括号、反引号（HANDOFF 已记，补全范围） | `(cargo publish)`、`{ rm -rf x; }`；**同一条命令里在它们后面的所有段也丢**：`echo "$(date)"; cargo publish`、`cd ${DIR}; rm -rf build` | 扫描器遇到 `$`、`(`、`{`、`` ` `` 就停 [K3:755–757,828–833]；后续靠按 `; & \| 换行` 重新切段补救，但原文里只要有 `(`、`)`、`{`、`}`、`` ` `` 就整条放弃补救 [K3:695–703,708–710]。`$(…)`、`${…}` 都带括号，所以很常见。括号**前面**已认出的段照样查 |
| 5 | 带路径的程序 | `/usr/bin/git push --force`、`/bin/rm -rf x` | 按完整词比，不退到文件名，这是 DESIGN 定的 [K10:221][K13:330] |
| 6 | 子命令前的全局选项 | `git -C ../repo push --force`、`git -c k=v push`、`cargo +nightly publish` | 第二个词对不上 |
| 7 | 选项换顺序或换拼法 | 规则 `["rm","-rf"]` 认不出 `rm -fr`、`rm -r -f`、`rm -Rf`、`rm --recursive --force`；规则 `["git","push","--force"]` 认不出 `git push -f`、`git push origin main --force`、`git push origin +main` | 词前缀只认固定顺序的字面词 |
| 8 | 控制结构里的命令 | `if …; then cargo publish; fi`、`for f in a b; do rm -rf "$f"; done`、`! cmd` | 拆出来的段以 `then`、`do`、`else`、`!` 开头；扫描器只把这些关键字当「解析失败」，不剥掉 [K3:663–683] |
| 9 | 命令名来自变量 | `cmd=rm; $cmd -rf x`、`$RM -rf x` | 变量不展开（Codex 也认不出这种 [C1:293–306]） |
| 10 | 脚本、构建工具和包管理器里面 | `./clean.sh`、`make clean`、`npm run clean`、`cargo xtask …`、git hooks | 只看命令行，看不到被执行的内容；任何按命令文本判断的办法都管不到 |

**补全 HANDOFF 的说法**：「总是问」「只问执行」下「照旧问」**不总成立**。第 1、4、8、9 种让整条解析失败，放行规则和会话前缀用不上，确实会问 [K1:296–297]；但第 5、6、7 种能完整解析，如果这一段同时被一条更短的放行规则或会话前缀盖住，就不问直接跑 [K1:289–299][K3:94–97]。最现实的组合：禁止 `git push --force`、放行 `git push`，于是 `git push -f` 在三档都直接跑。第 2、3 种（不含 `$` 等符号时）也能完整解析，要看包装名或解释器有没有放行：`timeout`、`sudo`、`env`、`nice`、`nohup`、`time`、`command`、`exec`、`xargs`、`bash`、`sh`、`eval`、`python3` 等都不会出现在一键放行的前缀里 [K2:60–112]，除非用户手写，否则会问。

**附带**：heredoc 的正文会被当成命令行去比。`cat <<EOF > notes.md` 后面正文里有一行 `rm -rf old`，如果有 `["rm","-rf"]` 禁止规则，整条会被拒绝（误拦，偏保守方向）。[K3:695–703]

### 2.5 其它防不住的地方

- **「全部允许」下没法要求「这个也得问我」**（事实）：要问规则在这一档完全不看，用户只能写禁止。[K1:281–288][K10:217] 对比：Claude Code 的 ask 规则在 auto 和 bypassPermissions 下仍弹框，omp 的用户 prompt 在 yolo 下仍有效，Codex 的 prompt 规则在 `never` 下变成拒绝（§1）。
- **已装的 `git push` 放行规则放过 force push**（事实，按记录推演）：10-29 装版时用户定放行 `git push`（「和codex、claude code保持一致」），写进了 `~/.canter/rules.json`。[K11:19][K12:142–144] 按前缀比，`git push --force`、`git push -f`、`git push origin +main`、`git push --delete …`、`git push --mirror` 都被盖住，三档都不问。本轮没有读用户真实的 `rules.json`，用户之后可能已经用 `/permissions` 改过。
- **一键放行能放开危险的变体**（事实）：批准框给的前缀里，`git reset`、`git checkout`、`git restore`、`git clean`、`git stash`、`git branch` 都能「本会话放行」和「以后都不问」（取程序加子命令）；`mv`、`cp`、`make` 给单词前缀。[K2:114–174] 用户为 `git checkout feature-x` 点过一次「以后都不问」，之后 `git checkout -- .` 就不问；为 `cp a b` 点过，之后任何覆盖式 `cp`、`mv` 都不问。`rm`、`find`、`sed`、解释器和包装命令不给这两项，永远问。[K2:62–112]
- **批准框不提示危险**（事实）：批准请求里没有「原因」字段，终端不知道这条为什么值得注意，`git push --force` 和 `git push` 长得一样。[K8] Codex 的批准请求带 `reason`。[C2:407–436]
- **模型能在「全部允许」下改掉自己的禁止规则**（读代码推断，没试）：`rules.json` 在状态目录里，但受保护路径只对 read/write/edit 工具生效；「全部允许」下 shell 命令只要没命中禁止就跑，所以写入或删除 `~/.canter/rules.json` 的 shell 命令会直接执行，而规则每次判断都重读，立即生效。[K4:130–143][K7][K10:97,215] 同理能删 `~/.canter/sessions`、停掉服务端。
- **shell 改的文件回退不了**（事实）：P2-23 只给 write/edit 做备份。[K10:90]
- **命令带着完整的会话环境**（事实）：模型 shell 先清空环境再装回整份会话环境，令牌一类也在里面，外发类命令能直接用。[K4:218–223][K14 §5.1]
- **超出本件范围，只记一笔**（事实）：「全部允许」下 write/edit 能改受保护路径以外的任何文件（比如 `~/.zshrc`、`.git/hooks/*`），MCP 工具和 `web_fetch` 直接执行。[K1:342–348][K10:30,92,93]

## 3. 哪些算危险

只列常见的、对用户有实际代价的，不定 canter 要不要全管。「后果」是这些命令的公开行为（事实，有文档的标了出处）；「为什么难挽回」里没标出处的是**推测**。

| 类别 | 常见写法 | 后果 | 为什么难挽回 |
| --- | --- | --- | --- |
| 删文件和目录 | `rm -rf <目录>`；`rm -rf "$DIR"/*`（变量为空就成了 `/*`）；`find … -delete`、`find … -exec rm`；`git clean -fdx`；`rsync --delete`；`cp`、`mv` 覆盖已有文件；`> file`、`truncate` 清空文件 | 文件直接消失或被盖掉。`git clean` 删的是不在版本控制里的文件，`-d` 进未跟踪目录，`-x` 连 `.gitignore` 里的也删 [G2] | 命令行删除不进废纸篓；没提交过的文件 git 里没有副本（`.env`、本地数据库、手写的笔记正好是这类）；canter 回退只恢复 write/edit 改的文件 [K10:90] |
| git 丢本地改动 | `git reset --hard`；`git checkout -- <路径>`、`git checkout .`、`git checkout -f`；`git restore <路径>`；`git stash drop`、`git stash clear`；`git branch -D`；`git worktree remove --force` | 未提交的改动、没合并的分支没了。`reset --hard` 用提交里的版本覆盖工作区，不在提交里的已跟踪文件被删 [G1] | 没 `git add` 过的改动从没进过对象库，没有副本；reflog 只记提交过的东西；`git add` 过的、丢掉的 stash 可能还能用 `git fsck` 捞，要懂行且赶在垃圾回收之前 |
| 改远端、共享状态和发布 | `git push --force`、`-f`、`origin +main`；`git push --delete`、`--mirror`；`gh repo delete`、`gh release delete`、`gh pr merge`；`cargo publish`、`npm publish`；`terraform destroy`、`kubectl delete`、`aws s3 rm --recursive` | 别人看得到、依赖着的历史被改写或删除；包公开发布；线上资源被删 | 被覆盖的提交如果是别人推的，本机可能没有，远端的 reflog 碰不到；crates.io 发布基本是永久的，版本不能覆盖、代码不能删，yank 也不删代码，泄露的密钥只能立刻换 [W1]；npm 72 小时后撤销要同时满足没人依赖、上周下载少于 300、只有一个维护人，撤了的版本号也永远不能再用 [W2]；云资源删了一般没有回收站 |
| 改系统、配置和权限 | `sudo …`；`chmod -R`、`chown -R`（尤其对家目录或 `/`）；改 `~/.zshrc`、`~/.ssh/*`（含 `authorized_keys`）、`~/.gitconfig`；`git config --global`；`crontab -r`；`launchctl`、`defaults write`；全局安装（`npm i -g`、`brew install/uninstall`、`pip install --break-system-packages`）；`curl … \| sh` | 影响项目以外、之后所有程序；`authorized_keys` 加一行就是后门；`curl \| sh` 跑来路不明的代码 | 原来的权限位和配置没有备份，改完不知道原样是什么；`crontab -r` 一次删掉整张表；`sudo` 越过所有文件权限 |
| 磁盘和进程 | `dd of=/dev/disk…`、`diskutil eraseDisk`、`mkfs`；`kill -9 -1`、`pkill -f <模式>`、`killall`；`shutdown`、`reboot`；写满磁盘；`docker system prune -a --volumes`、`docker volume rm` | 整盘数据没了；用户别的程序被杀，没保存的东西丢了；canter 服务端自己被杀，这台机器上所有会话的进行中轮都断（一台机器一个服务端 [K10:12]）。本项目 CLAUDE.md 专门禁止 `pkill -f canter` 这类按名字批量杀进程 | 进程内存里的状态无法恢复；整盘擦除基本无法恢复 |
| 把数据发出去 | `curl -d @文件`、`curl -T`；`scp`、`rsync` 到别的机器；`nc`；`git remote add … && git push`；`gh gist create`、`gh issue create --body-file`；`npm publish` 把 `.env` 打进包；`env`、`printenv`、`cat ~/.ssh/id_*` 把秘密打进输出 | 代码、凭证、个人数据到了别处；命令输出会发给模型服务商 | 发出去收不回，只能换凭证（cargo 文档对误传的密钥也这么说 [W1]）；canter 的模型 shell 带着会话完整环境，令牌直接可用 [K4:218–223] |

## 4. 建议

三种做法加一个组合。下面「挡得住、挡不住、打扰、改哪里、工作量」都是**推测**，依据是 §1、§2 的事实。

### 4.1 方案 A：内置一份危险判断，所有模式都管

- **做法**：在服务端代码里内置一份窄清单（不放进 `rules.json`：用户在 `/permissions` 里删不掉，模型改文件也去不掉），配上比词前缀聪明的匹配：剥前置变量赋值和常见包装、按文件名认带路径的程序、选项不论顺序、认出控制结构关键字后面的命令、看 `sh -c` 引号里的字面命令。命中后：
  - 「总是问」「只问执行」：强制弹框，不给「本会话放行」「以后都不问」，放行规则和会话前缀不能免（同 Claude Code、omp 的做法）。
  - 「全部允许」：二选一，要用户定（§4.5）。一是直接拒绝并告诉模型原因，用户要做就自己用 `!` 跑或切档（同 Codex `never`）；二是照样弹框，没人答时限时拒绝（同 Claude Code bypassPermissions）。
  - 计划模式、审查轮：不变，本来就只放白名单。
- **挡得住**：清单里命令的常见写法，包括「全部允许」下现在完全不管的那些、已装 `git push` 放行规则下的 force push。
- **挡不住**：脚本、解释器、`make`、`npm run` 里面；变量拼出来的命令名；清单以外的；`$(…)`、`${…}` 之后的段——除非把「解析不了」也当危险，那样会多问很多（Claude Code 只对 rm 这么做）。
- **打扰**：「总是问」「只问执行」下，只在原来会被规则或会话前缀免掉的危险命令上多一次框；原来就会问的只是框上多一句提示、少两个选项。「全部允许」下每次命中要么被拒、要么等人。清单宽窄决定打扰多少：像 Codex 那样管所有带 `-f` 的 `rm`，长任务里清构建目录会频繁被拦；像 Claude Code 那样只管删到关键路径，几乎不打扰，但项目里的 `rm -rf src` 不管。
- **改哪里**：`crates/canter-tools/src/permission.rs` 的 `evaluate`（在禁止判断之后、「全部允许」提前返回之前加一步，命中时不附前缀选项）和 `resolve_with_prefixes`（拒绝对这类命令的会话放行和永久放行）；`readonly.rs` 的扫描或一个新模块（共用拆段结果）；`rules.rs` 的前缀建议不给这类前缀；协议的批准请求可选加一个原因字段（参考 Codex 的 `reason`），终端批准框显示出来；DESIGN「按命令放行」一节和权限模式段；`crates/canter-tools/tests` 下补测试。
- **工作量**：只改工具层判断、不加原因字段的话，大约一件中等的活；加原因字段要连带协议和终端。
- **和 P2-123 怎么配合**：两层互不替代。沙箱管「目录外的读写和联网」，这份判断管「目录内难挽回的操作」。沙箱开了以后「沙箱内免问」的路径也要先过这份判断（Codex 就是危险判断先于沙箱免问 [C2:793–806]）。沙箱默认断网时 push、publish、外发多半已被挡住，清单里远端类的条目就成了第二道。

### 4.2 方案 B：不内置清单，加强用户规则

- **做法**：要问规则在「全部允许」下也生效（同 Claude Code 的 ask 规则）；匹配器做 A 里那些改进，同时补上禁止规则的漏；可选让规则支持「某位置多个备选」或「某个选项出现在任意位置」（参考 Codex 的备选写法、Claude Code 的 `*`）；给一份示例清单让用户自己抄进 `rules.json`，不自动写。
- **挡得住**：用户写了的，以及修好匹配后的常见变体。
- **挡不住**：用户没写的——默认没有保护；不扩格式的话，词前缀表达不了「带 `-f` 的任何 `git push`」；脚本类同 A。用户在「全部允许」下仍可能被模型改掉规则文件（§2.5）。
- **打扰**：完全由用户控制。
- **改哪里**：`permission.rs:281–288` 的判断次序；`readonly.rs` 扫描；`rules.rs` 匹配，扩格式还要改协议的 `CommandRule`、`/permissions` 的显示和 P2-156 的删除；DESIGN 里「全部允许只看禁止」要改。
- **工作量**：不扩格式约一件中等的活，扩格式再加协议和终端。
- **和 P2-123 怎么配合**：同 A。

### 4.3 方案 C：全部交给沙箱 P2-123

- **做法**：不加命令判断，等 P2-123；「全部允许」下命令也在沙箱里跑。
- **挡得住**：工作目录和加进来的目录以外的删改（`rm -rf ~`、改 `~/.zshrc`、改 `~/.canter`）；默认断网时的 push、publish、外发；`.git` 只读时需要写 `.git` 的命令（P2-104 第一版建议 `.git` 全部只读 [K14 §5.1]，`git reset --hard` 要先写索引锁，多半会在动工作区之前失败，没验证）。
- **挡不住**：工作目录里的 `rm -rf src`、`git clean -fdx`、`git checkout -- .`（是否要写 `.git` 没验证）；用户为某条命令批准了联网后，同一条里的 `--force`；沙箱关掉或起不来时；MCP、`web_fetch`；能不能杀沙箱外的进程，**未知**。
- **打扰**：不加命令框；沙箱本身带来的联网、`.git` 授权框另算。
- **改哪里**：现在什么都不改；P2-123 本身估计 3～4 件中到大的活 [K14 §7.2]。
- **代价**：P2-123 落地之前，「全部允许」下直接执行这个洞一直在。

### 4.4 推荐：A（窄版）+ C

理由（推测）：

1. 「全部允许」下直接执行是现在最大的洞。沙箱要 3～4 件才落地，A 的窄版改动集中在 `canter-tools` 的权限判断，能先补上。
2. 沙箱管不到工作目录里的删除和 git 丢改动，而长任务里最常见的事故正是这类；Claude Code、Codex 有沙箱也都另留了 rm 判断（事实，§1）。
3. B 默认不保护，要用户自己写、自己维护，词前缀对选项顺序也无能为力。B 的「匹配器改进」应该并进 A，用同一套拆段和剥包装同时补禁止规则的漏；「全部允许下要问规则也生效」可以作为 A 的附加项，让用户自己再加。
4. 建议单开一件，不并进 P2-123：它不依赖沙箱，沙箱关掉或起不来时也要有用；也比沙箱小，能先上。

窄版清单的起点（建议，范围要用户定）：

- `rm`、`rmdir` 递归或强制删除，且目标是关键路径：`/`、根下一级目录、家目录、工作目录及其上级、加进来的目录及其上级、变量或命令替换做目标（参考 Claude Code）。
- 丢未提交改动的 git 命令：`reset --hard`、`checkout -- <路径>` / `checkout .` / `checkout -f`、`restore`（改工作区的）、`clean -f`、`stash drop` / `stash clear`。
- 改远端历史或删远端：`push --force` / `-f` / `+refspec` / `--delete` / `--mirror`。
- 发布：`cargo publish`、`npm publish`。

其余几类（`sudo`、`chmod -R`、`dd`/`mkfs`、`curl | sh`、`kill`/`pkill`、外发）以后按需要加，或者主要交给沙箱。

「全部允许」命中时，倾向**直接拒绝并告诉模型原因**：用现有的「禁止」路径就能做，不用新协议；长任务没人看时不会卡住，模型可以先做别的；用户要做就自己 `!` 跑。限时弹框体验更好，但要给批准请求加截止时间，是协议改动。

**不推荐现在做的**：用另一个模型来判断危险（Claude Code 的 auto 分类器、Codex 的 `auto_review`）。每个命令多一次模型调用，DeepSeek 要花钱、会变慢，结果不稳定，测试也得靠假服务端回放；可以等 A 和沙箱都有了再看。

### 4.5 要用户定的

1. 选哪种：A、B、C，还是推荐的 A + C；单开一件还是并进 P2-123。
2. 清单多宽：rm 只管关键路径，还是所有 `rm -rf`；git 管哪几条；远端和发布要不要；`sudo`、`chmod -R`、`kill` 这些要不要第一版就管。
3. 「全部允许」下命中：直接拒绝，还是弹框、没人答时限时拒绝。
4. 用户的放行规则能不能盖过内置判断（Codex 能，Claude Code 不能，omp 只有 deny 能）；要不要留一个总开关关掉内置判断（Claude Code 是启动时的环境变量）。
5. 已装的 `git push` 放行规则：内置判断落地后，`git push --force` 这类仍会单独问或拒绝，普通 `git push` 照旧免问——是否接受。
6. 要不要让要问规则在「全部允许」下也生效（B 的一部分，可以和 A 一起做）。
7. 模型用 shell 改 `~/.canter`（包括 `rules.json`）要不要单独挡：P2-104 建议在沙箱里拒绝 [K14 §5.1]；命令文本判断只能挡写出了路径的那部分，挡不全。
