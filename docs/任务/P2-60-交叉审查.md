### 具体意见

1. **必须改：直接关掉终端（关窗口、关标签页、SSH 断线）时，正在跑的状态栏命令和它起的子进程停不掉。**
   - 位置：`crates/canter-tui/src/statusline.rs:177`（`process_group(0)`）、`:230`（`ProcessGroup` 的 `Drop`）；`crates/canter-tui/src/run.rs:349` 主循环和 `crates/canter/src/main.rs` 都不收信号。
   - 问题：命令放进了自己的进程组，停它的 killpg 只在 canter 自己的析构里执行。关终端时 SIGHUP 只到 canter 所在的进程组（前台作业，或会话首进程），canter 按默认动作直接死掉，析构不跑；状态栏命令的进程组既不是前台组、也不是 shell 的作业，收不到 SIGHUP。1 秒上限没人执行了，命令和子进程一直跑到自己结束。
   - 实测（已查证）：本提交的 debug 版 canter，在独立 socket 的 tmux 里跑，`statusLine` 脚本是 `sleep 30 & wait`，等脚本起来后：
     - Ctrl+D 正常退出：0.5 秒内 canter 和 `sleep` 都没了，正常退出这条路没问题。
     - `tmux kill-server`（pty 挂断，等于关掉终端）：canter 立刻没了；`sleep` 的进程组号是 sh 的 pid，和 canter 的组不同，0.5 秒、2.5 秒时都还活着，超过了 1 秒上限，最后由我按记下的 pid 停掉。
     - 真实的终端模拟器关标签页、SSH 断线走的是同一套 SIGHUP 机制。这一点是推测，没在 Terminal / iTerm 里实测。
   - 影响：留下的进程活多久，取决于脚本自己。正常的状态栏脚本几毫秒就结束；卡住的（等网络、等锁）会一直留着。回答输出期间每 0.3 秒跑一次，关终端时正好撞上一个在跑的命令，概率不低。
   - 改法：终端界面收到 SIGHUP（顺带 SIGTERM）时走正常退出路径。比如在 `run_on` 的 `select!` 里加一支 `tokio::signal::unix` 的信号，按退出处理，让 `App` 照常释放、`ProcessGroup` 照常 killpg；或者至少在收到信号时先 killpg 当前在跑的组再退出。终端已经没了，之后写 stdout 会失败（比如退出时 `println!` 打的 `To resume:`），别让它 panic 掉清理。补一条能复现的检查：向终端进程发 SIGHUP 后，状态栏命令起的子进程不在了。

2. **建议改：同一行很长的输出没有上限，读的时候吃内存；成功后每一帧都复制、量一遍，界面空闲时也一直占满一个核。**
   - 位置：`statusline.rs:204`（保留输出只数换行，不限字节）；`:152`–`:154`（`rows()` 每帧 `clone` 整行，再交给 `text::truncate`，它先算整行宽度）。
   - 问题：1 秒内读到的同一行全留在内存里。命令按时成功退出时，这一大行存进 `output` 长期保留；之后每次重画（空闲时也是每 100 ms 一次）都要复制并逐字算宽度。
   - 实测（debug 版，环境同第 1 条）：基线是短输出，canter 常驻内存 23 MB，空闲 CPU 约 3%。
     - 脚本输出 30 MB 不带换行的 `a`：成功显示，之后空闲时 CPU 一直 100%，内存 113 MB，要等下一次成功输出才换掉。
     - 输出 200 MB：1 秒没读完，按超时处理（显示 `statusline error`），内存涨到 142 MB 后没回落。
     - release 版读得更快，1 秒能收进来的更多，每帧开销更小。这部分是推测，没测 release。
   - 改法：读的时候每行（或总共）只留有限的字节，比如几 KiB，多出来的照旧读掉、丢弃；存的时候就截好，`rows()` 不要每帧复制整行。补一条大输出的检查。

3. **建议改：状态栏命令能绕过过滤，直接往终端写转义序列。**
   - 位置：`statusline.rs:177`。
   - 问题：命令只换了进程组，控制终端还在。脚本或它调用的程序打开 `/dev/tty` 写的东西不经过 `lines()` 的过滤，直接进终端。比如 git 走 https 缺凭证时，会往 `/dev/tty` 写 `Username for ...:`，这串字就画进了全屏界面中间（之后它读 tty 会被 SIGTTIN 停住，1 秒后被杀）。
   - 实测（已查证）：脚本 `printf '\033]0;TTYTITLE\007TTYTEXT' > /dev/tty`。用 tmux `pipe-pane` 抓 canter 所在 pty 的原始输出，这串改窗口标题的 OSC 和后面的文字原样在里面。
   - 改法：照 `crates/canter-server/src/discovery.rs:145` 起服务端的做法，在 `pre_exec` 里 `setsid()`。新会话没有控制终端，`/dev/tty` 打不开；它同时是新的进程组，killpg 照旧能用。要拿它**换掉** `process_group(0)`，不能两个都用：std 先做 setpgid，进程已经是组长，再 setsid 会失败。setsid 解决不了第 1 条。

4. **可以不改：sh 已经被收掉之后才 killpg，理论上可能打到别的进程组。**
   - 位置：`statusline.rs:213`、`:222`。
   - 问题：成功、退出码非 0、没有输出这几条路上，`try_join!` 里的 `child.wait()` 先把 sh 收掉，然后才 `drop(group)` 发 killpg。组里还有活着的子进程时组号不会被复用，killpg 正好清掉它们。组里已经没人时，这个号空出来了，理论上可能在这一小段时间里被一个新的进程组长拿到。超时、换会话、正常退出这几条路上，sh 还没被收，没有这个问题。
   - 判断：要在微秒到毫秒级的窗口里把 pid 用完一圈（macOS 上限 99999）才会撞上，实际碰不到。`canter-tools/src/executor.rs` 的 `LocalProcess` 也是先 wait、再在 `Drop` 里 killpg，和现有做法一致。要彻底，就得在收 sh 之前发 killpg，代价是要另外处理「sh 关了标准输出、还没退出」的情况，不值得。

5. **可以不改：双向文字控制符不是 canter 自己去掉的，靠的是 ratatui。**
   - 位置：`statusline.rs:271` 只去 `is_control()`（Unicode 的 Cc）。U+202A–202E、U+2066–2069、U+200E/200F、U+061C 属于 Cf，会进 `Span`。
