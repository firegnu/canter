### 重点 1～5 的查证结果

1. **不用 GPT 时一切不变（已查证）**：core 里唯一的行为改动是 `telemetry::stream` 不再按用途/轮次清 `replay`；Chat Completions 适配器本来就忽略 `replay`（P2-204），别家的历史里也不会有 `replay`，所以发出去的字节、prompt 拼接、压缩（触发、提示词、带回文件和待办）都不受影响；`context.rs` 的估算没改，`context_estimates_do_not_count_private_replay_payloads` 过。`ReplayRejected` 事件只有 `responses.rs` 会发，别家不会写 `replay_rejected` 历史。`stream` 开头新加的锁：三处调用方（`runner::model_response`、`compaction`、`btw::answer`，后者覆盖建议、`/btw`、交接）在调用前都已经通过 `charge_goal()` 和 `model_context()` 锁过 state，所以没有新的锁顺序，对别家只是多一次无竞争的加锁。逐字节固定样例 `chat_completions_renders_exact_bytes_*`、`legacy_requests_keep_the_same_bytes_*`、`fork_preserves_request_bytes_*` 未改断言、照样过。
2. **并发（已查证，没有死锁）**：没有调用方在持有 state 锁时调用或轮询这个流。流内收到 `ReplayRejected` 时去拿锁，我专门查了「调用方在 `select!` 里走了别的分支、流内的取锁排在队里不被轮询、调用方又去锁 state」这种卡死（futurelock）：runner、压缩、btw 三处的另一个分支只有取消（runner 还有 `pending` 非空才开的定时器；被拒发生在本次请求还没任何输出时，`pending` 一定是空的），取消后都是先 `drop(stream)`（压缩是直接 `return`）再锁 state，所以不会卡住。写 `replay_rejected` 失败时流返回 `ErrorKind::Other` 并结束、不再重发，内存里的被拒集合也不更新；日志写不进去时结束这次请求是合理的。
3. **各路径规则（已查证）**：`Replay::belongs_to` 要求模型相同且账号标识相同，没有账号标识的旧 replay 一律不带；换模型、换账号、旧 replay、重开、prefix 压缩、建议/`/btw`/交接都有测试。子 agent 和 fork 走同一个 `wire::request_body` 判断，没有另立规则。辅助请求没有单独的模型配置（查了没有 suggestion/small model 一类的设置），发给的就是会话模型。transcript 压缩只有 system + 一条 user 文字稿，没有助手消息，自然不带 replay。prefix 压缩超窗口（`ContextLength`）时照旧退到 transcript。账号绑定按轮（`model_scope`）走，跨轮重新取当前注册记录，所以换账号后下一轮就不带。
4. **被拒收（已查证，有一处边界见建议 1）**：只认 `error.code == "invalid_encrypted_content"`（HTTP 错误体和 SSE `error`/`response.failed` 都走 `error::classified`）；`allow_replay` 置 false 后同一请求不会再触发，所以只重发一次；`observed` 为真（已有输出或用量）时不重发。被拒的轮次标识先落盘、更新内存、清掉 `history` 里对应 replay，再发第二次请求；重开时 `restore` 汇总全部 `replay_rejected` 再清 history；fork 把这条历史当普通条目复制。replay 没有 scope 时：`replay_scopes` 给空串，`reject_replay` 过滤掉空串、什么也不记，于是之后每次请求都会先被拒一次再重发。但 runner 写历史前一定 `with_scope(turn_id)`，P2-204 起存的 replay 也都有 scope，正常路径到不了这种情况。
5. **隐私和兼容（已查证）**：日志只有一行固定英文；`ModelError` 不带上游原文；`Replay` 的 Debug 是 `Replay([PRIVATE])`；`ReplayRejected` 只带轮次标识。账号标识是以本机 host ID（UUID v4）为键、对本地注册记录 ID（`uuid::new_v4()`，不是 ChatGPT 的 subject/账号 id）做 HMAC-SHA256，推不出原文；测试断言会话文件里没有账号原文 id。旧版读新存盘：`HistoryEntry` 有 `#[serde(other)] Unknown`，`replay_rejected` 会被忽略；`Replay::Responses` 新加的 `account` 字段旧版不认识也会忽略（没有 `deny_unknown_fields`），旧版本来就只在当前轮回传，不会误发。

### 意见

1. **建议改**｜`crates/canter-core/src/fork.rs:99-143`｜fork 在两种情况下会丢掉 `replay_rejected`：从一个还没结束的轮 fork（遇到这一轮的 `TurnBoundary` 就 `break`，这一轮里记下的被拒条目不复制），以及源会话里有 rewind/retract（`history.truncate` 会把截断点之后记下的被拒条目一起删掉，而被拒的往往是更早、仍保留的轮）。后果是新 fork 出来的会话第一次请求会再被同一批密文拒一次、自动重发后重新记下，不会失败，只多一次请求，和 DESIGN「fork 都只用普通内容」不完全一致。改法：fork 时像 `Context` 一样单独收集所有 `ReplayRejected` 条目，不受截断和 `break` 影响，最后统一放进新会话历史；补一个 fork 前已被拒、fork 后第一次请求不带密文的测试（现在没有 fork 相关的被拒测试）。
2. **建议改**｜`crates/canter-model/src/responses.rs:163-169`｜`observed` 在 SSE 终止事件带用量时也会被置真（`sse::usage(&event["response"])` 返回 Some 就 `*observed = true`）。如果上游是用 `response.failed` 并附带非空 `usage` 来报 `invalid_encrypted_content`，就不会去掉密文重发，用户会直接看到 "ChatGPT rejected encrypted history"，而且不记 `replay_rejected`，之后每轮都会再被拒。上游到底是 HTTP 400 还是 `response.failed`、带不带 usage，**我没查证（未知）**；测试只覆盖了 HTTP 400。改法：被拒判断只看「是否已有模型输出」（`sse::has_output`），不把终止事件上的用量算作输出；或者等用户真调看 server.log 再定。
3. **建议改**｜`crates/canter-model/tests/streaming.rs` `responses_replay_metadata_never_changes_chat_completions_bytes`｜这项测试只比较了两次带 replay 的请求彼此相同，没有和「不带 replay」的同一请求比，证明不了「replay 不改变 Chat Completions 字节」。结论本身成立（适配器忽略 replay，现有逐字节固定样例都过），只是这项测试是空转的。改法：再发一次 `replay: None` 的同一请求，断言字节相同。
4. **可以不改**｜`crates/canter-core/src/session.rs:478-507`、`telemetry.rs:86-100`｜被拒标识以轮次为粒度。如果在一轮的工具循环中途被拒，当前轮 id 也会进被拒集合，这一轮之后新产生的、本来有效的 replay 也会被当成被拒而只发普通内容，直到这一轮结束。只影响那一轮剩下的缓存命中，不出错；中途被拒本身也不太可能。
5. **可以不改**｜`crates/canter-model/src/responses/wire.rs` `replay_scopes`｜没有 scope 的 replay 被拒后记不下来（见上面第 4 点），正常路径到不了；要稳妥可以在 core 里对没有 scope 的被拒 replay 直接清掉内存里的那份。
6. **可以不改**｜`crates/canter-server/src/model_auth.rs:93-98`｜账号标识跟着本地注册记录走：同一个 ChatGPT 账号退出后重新登录会生成新的记录 id，算「不同账号」，之前的 replay 只发普通文字。方向是保守的，不会被拒，只是少命中一次缓存。
