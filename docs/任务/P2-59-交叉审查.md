### 五个重点的结论

1. **撤回和模型第一次输出的竞态（已查证）**：`interrupt_inner`（session.rs:651-668）和 `accept_model_output`（session.rs:984-992）都在会话锁里读写 `model_started` / `retracted`，结果只能是二选一。回答、思考、工具调用（runner.rs:335、344、352）和压缩摘要（compaction.rs:257-289）四条路径，在第一次非空输出时都先过这把锁；输了的一路在往 `content` / `pending` 放任何东西之前就 break，不写 Assistant 消息，也不发 item 事件。只有服务方在第一段输出之前就发 usage 时，才会记一条 `session.usage`（推测；DeepSeek 在末尾发，碰不到；就算碰到，记的也是真实花费，可以接受）。
2. **模型历史和恢复（已查证，崩溃这一项实测）**：`TurnBoundary` 在每一轮加用户消息之前记；`Retract` 截到这一轮的边界，截不到之前的消息。插话、压缩请求行都在边界之后，恢复时 `CompactionRequest` 行被忽略。之后再压缩，用的是截过的 history / user_messages。P2-23 回退到撤回轮之前或之后的轮，边界下标都对（手推）。崩溃在「记了 Retract、还没写 `turn.retracted`」之间：探针 4 先撤回，丢掉 Session，删掉事件文件末尾的 `turn.retracted`、`session.status` 两行，再 open。结果补发了一次 `turn.retracted`；快照只剩前一轮，状态空闲，队列为空；下一次请求里有前一轮的问答和新消息，没有撤回的消息、排队的消息和「server stopped」说明。顺序对：先 restore 截历史，再补发事件，再处理没跑完的轮。
3. **插话（已查证，读代码）**：终端只发 queue，自己不插话。别的客户端的插话，如果撤回时还在 `state.steers`，`discard_queue` 照 `interrupted` 移出，发起终端放回输入框；如果已经并进这一轮（只在开轮到第一次 `consume_steering` 之间，或模型空回复后再进循环时才会有），模型历史随边界截掉，终端经 `Steered/Merged` 那一支（retract.rs:134-147）把它挂到这一轮上，也回到发起终端。不会出现「既不发给模型、也不回输入框」。
4. **终端恢复输入框**：回复和事件乱序、在途发送晚回、旁观终端只移除，这几种都对（读代码，开发方的测试也覆盖了）。问题见建议改 1-5。旧客户端：探针 5 用一个不认识的事件替代 `turn.retracted`，这一轮在它那里一直是 `inProgress`，后面的轮照常显示（见可以不改 6）。
5. **不带 `retract` 的普通打断（已查证）**：服务端只多了 `as_mut`，回复 JSON 和原来一样（开发方的测试断言了 `{"eventSeq":…}`）；runner 普通收尾路径没动；普通轮只是在第一次输出时多拿一次锁。现有测试里加的 `retract: None` 都是机械改动，没有放宽断言。注意：终端的 Esc 现在一律带 `retract: true`（按设计），所以在终端上，「模型开口前的普通打断」不再有。

   - 问题：在空闲时问的 `/btw`，回答挂在下一轮提问之前（`at.turn == end && !at.prompt`）。按第 1 条的新规则它被保留，但 `active_btw` 仍被清掉，之后的 btw 事件都被丢掉（`btw_event` 只认 `active_btw`）。这条回答停在半截，永远不会结束，Esc 也停不了它。它没结束，`extend_history` 就停在它这里（app.rs:2183），之后的对话每一帧都在活动区重排，直到这个终端重开。改之前这条回答是整条被删掉。探针：旁观终端先问 `/btw` 并收到 `PARTIAL`，另一个终端发消息再撤回，之后的 ` REST` 和 `Completed` 都没显示；Esc 返回 None；还能再开一个 `/btw`。发起终端碰不到，因为它第一次 Esc 先停掉 btw。
   - 改法：`retain` 之后只在 btw 那条被删掉时才清：`if self.active_btw.is_some_and(|id| id >= self.notices.len()) { self.active_btw = None; }`（删掉的是尾巴，保留的下标不变）；加一条 TestBackend 测试。
