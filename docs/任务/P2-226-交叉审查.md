### 重点逐条

1. 权限：只有一条路。`read()` 经 `self.executor.open_file`（`resolve_path` 里做状态目录拒读、沙箱读检查）打开，同一个流读开头 12 字节认 `%PDF-`，再 `take(50 MiB + 1)` 读进内存；文字转换和转图都只把这份字节经 stdin 交给子进程，worker 参数只有两个行号，`pdftoppm` 参数只有页码（u32）和 `-`，没有路径。`page` 不改 path，读权限规则（`PermissionGate` 按 path 判）和状态目录拒读对它同样生效，测试 `pdf_text_and_images_obey_file_rules_and_protected_state_paths` 覆盖了带不带 `page` 两种。`page` 用在非 PDF 上是在 `open_file` 之后才报错，不会先于检查泄露信息。
2. 不卡住、不留进程：`process::spawn` 起独立进程组 + kill_on_drop + guardian；`run` 里超时、取消、出错都先 `killpg` 再 `wait`；外层 `execute` 的 biased select 在取消时直接丢掉 read future，`LocalProcess::drop` 杀进程组，tokio 回收孤儿；服务端退出由 guardian 杀组。stdin 写和 stdout 读并发（`try_join!`），不会互相堵。输出上限：文字 worker 回传限 50 MiB（实际只回一个 64 KiB 窗口），转图 stdout `take(8 MiB + 1)`，超了立即返回错误并杀进程，`ToolImage::new` 再查一次 8 MiB。坏文件、加密文件：库报错时 worker 回 JSON 错误；库 panic 或栈溢出只死 worker，服务端得到「conversion failed」，只这次 read 失败。
3. worker 入口：canter 只有一个可执行文件，`canter serve`、自动拉起、服务安装都跑同一个 `canter`，`current_exe` 指向它。`main` 第一行按第一个参数严格等于 `--internal-pdf-worker` 分派，早于 `parse` 和读配置；`canter -- --internal-pdf-worker` 不会进；用户手打这个参数也只是等 stdin、吐一行 JSON 错误，无害。升级后旧服务端还在跑（`replace_server` 失败的情况）会起新版 worker；回退到没有这个入口的旧版时，旧版 `parse` 把它当 `unknown option` 报错退出，服务端得到「invalid output」，只这次 read 失败，不会误进对话或别的命令。
4. 看图能力：`runner.rs` 里 `shared.state.lock().await` 是语句内的临时守卫，`let accepts_images = …;` 结束就释放，执行工具时不持锁；紧挨着的上一句 `checkpoint_file` 和 match 守卫里 `goal_summary` 已在同一位置取同一把锁，没有新增等待关系，不会死锁。判断用的 `settings.model` 和 `context::request` 构造请求时的 `request.model` 是同一个值，和 `images.rs` 的判断一致。不能看图时在 `self.pdf.extract`/`render` 之前就返回说明，不起任何子进程（测试 `pdf_page_image_without_image_support_does_not_start_a_converter`）。生产上 `Tools::execute` 只有 runner 一处调用，已改成 `execute_with_images`。
5. 请求前缀：见上面快照核对；另有 `pdf_support_keeps_plain_text_read_requests_unchanged` 断言读普通文字时第二个请求只追加两条消息。

### 意见

1. **建议改** · `crates/canter-tools/src/pdf.rs` `run`（`crate::process::spawn` 直接起进程）
   - 问题：会话开了沙箱时，shell 里跑的命令在沙箱里，但 read 起的 `pdftoppm`（C 写的 poppler，解析模型可指定的任意 PDF）和文字 worker 都在沙箱外、以服务端权限运行。权限检查本身没被绕过（子进程拿不到路径），但恶意 PDF 打穿 poppler 时得到的是不受沙箱限制的进程。
   - 改法：沙箱开着时，两个转换进程套一个最严的沙箱配置（不可写、不联网、只读系统库和程序本身），或者至少 `pdftoppm` 这样做。属于纵深防御，记 HANDOFF 即可。
2. **建议改** · `crates/canter-tools/src/pdf.rs` `Converter::default`（`renderer: "pdftoppm"`）
   - 问题：`pdftoppm` 按服务端进程自己的 PATH 找，不是会话环境（`LocalExecutor` 里那份 env）的 PATH。服务端由 launchd 或别的 PATH 不含 `/opt/homebrew/bin` 的环境拉起时，装了 poppler 也会告诉模型「brew install poppler」。服务安装时存了终端 PATH，常见用法碰不到。
   - 改法：用会话环境的 PATH 解析 `pdftoppm`（和 shell 一致），找不到再报安装提示。
3. **建议改** · `crates/canter-tools/src/pdf.rs` `render`（`-r 150 -scale-to 2400`）
   - 问题：照片多的页面在最长边 2400 像素下 PNG 可能超过 8 MiB，现在直接报「exceeds the 8 MiB limit」，这一页模型就完全看不了。
   - 改法：超限时降一档（比如 `-scale-to 1600`、再 1200）重试一次，仍超再报错。
4. **可以不改** · `crates/canter-tools/src/lib.rs` `read()` 的 `page` 分支
   - 要页面图时先跑一遍完整文字转换只为拿 `page_count`，最坏要 30 + 30 秒；库解析不了而 poppler 能解析的 PDF 也就要不到图。可以让 `pdftoppm` 自己判断页码越界，或换个轻量的页数读取。
5. **可以不改** · OCR 提示文字 `Pages with no extractable text (OCR needed)`
   - 完成记录里说库对文字很少的页也会报需要 OCR，这句话对这类页不准；扫描件页数多时每次读取末尾都带一长串页码。可以改成 `Pages that may need OCR`，连续页写成区间。
6. **可以不改** · 文字 worker 回传格式
   - 服务端和 worker 之间是没有版本号的 JSON；升级没替换掉服务端时，新旧版格式一旦不同，read PDF 会一直报「invalid output」，直到服务端换掉。现在格式简单，出错也只影响这次读取。
7. **可以不改** · `crates/canter-tools/src/lib.rs` read 出错分类
   - 新加的 `ErrorKind::TimedOut → ToolOutcome::TimedOut` 对所有 read 生效，不只 PDF。本地文件读几乎不会出这个错误类型，影响可以忽略。

### 对完成记录「拿主意的地方」逐条表态

- 文字解析放进同一可执行文件的内部 worker 入口、早于 CLI 配置和服务端运行时：同意。库在本进程里停不下来，子进程是唯一能真正杀掉的办法；顺带把库的 panic、栈溢出、内存暴涨都隔在服务端外面。
- 只经 stdin 收已获准的字节，完整文字留在 worker 内分页、只回本次窗口、不写磁盘缓存：同意。服务端不承接整篇展开后的文字，也满足「不缓存到磁盘」。
- 转图也经 stdin 用同一份字节，不重新打开原路径：同意，这是第 5 条权限要求的正确做法。
- 文字转换和转图各 30 秒：同意。注意要页面图时两步串行，最坏 60 秒（见意见 4）。
- 复用进程组、kill-on-drop、guardian，超时和取消都杀组，正常出错路径等回收：同意，读过代码，几条路都能停掉。
- 150 DPI、`-scale-to 2400`、输出流 8 MiB 立即停：同意，能看清正文；超限没有降档重试（见意见 3）。
- 最小改动加 CLI 内部 worker 分派，core 在调用时传入看图能力，不改协议：同意。工具定义不随模型变，没动请求前缀；判断和请求用的是同一个模型。
- 保留库报告的 OCR 页码（含文字很少的页），扫描页测试用合成空页：同意；提示措辞可以再准一点（见意见 5）。
