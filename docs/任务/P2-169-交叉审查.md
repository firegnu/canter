### 意见

1. **建议改**：私有遥测文件出错会拖垮整个会话。
   - 位置：`crates/canter-store/src/lib.rs:377`（`append_private_telemetry`），`crates/canter-core/src/journal.rs:192`（`flush_private_telemetry`）。
   - 问题：第一次写时，用 `read_jsonl::<ModelRequestTelemetry>` 把已有内容逐行解析一遍。只要有一行完整但解析不了（比如以后改了字段类型的版本写的，或被手工改过），就会返回错误，同时把 `write_failed` 和 `journal.failed` 都置上。之后主会话的事件全部写不进去，要重开才好，重开后再用一次 btw 又会坏。这一版自己写的记录能原样读回，所以现在不会触发；但一份附属的遥测文件能让主会话停止写入。

2. **建议改**：派生出来的新会话不带标签。
   - 位置：`crates/canter-tui/src/run.rs:1332`（计划批准时选 Clear context），`:1401`（`new_session`，`/new` 和 `/handoff` 都走这里）。

3. **建议改**：新客户端连旧的常驻服务端时，`--tag` 会被悄悄丢掉。
   - 位置：`crates/canter-server/src/http.rs:281`（features 列表），`crates/canter-tui/src/run.rs` 新建会话处。
   - 问题：旧服务端的 `SessionCreateParams` 不拒绝未知字段，带标签的会话照样建出来，但没有标签。客户端只显示一行版本不一致的提示。常驻服务端要等用户在场才重启，所以升级后客户端新、服务端旧是常见情况。
   - 改法：照 `addDirectories` 的做法，info 的 features 加一项 `"tags"`；带标签新建会话前先检查，服务端不支持就报错，提示 `canter serve --replace`。
4. **建议改**：`telemetry.modelRequest` 没记这次请求的结局。

   - 问题：正常完成、出错、被用户取消的请求，`durationMs` 混在一起。P2-170 做用时统计时，只能靠轮的状态和事件顺序去猜哪一次是被取消的。

  - `/btw` `/handoff`：私有隔离的各项测试都过；私有写失败也不会再影响原会话。

### 意见

1. **可以不改**：带标签的会话多了 info 请求。
   - 位置：`crates/canter-tui/src/run.rs` 的 `require_tags`。
   - 说明：带标签启动，或从带标签的会话 `/new`、`/handoff`、选 Clear context 时，客户端会多发一次 `GET /v1/info`；服务端处理这个请求要把所有会话的 `events.jsonl` 重放一遍（`Store::list`）。要是同时还有附加目录，一次创建会发两三次。这和现有 `addDirectories` 的检查是同一个做法，只影响新建会话那一下的等待，不影响 agent 跑请求和工具。以后要优化，可以在一次创建里只取一次 features。
2. **可以不改**：两种自动压缩分不开。
   - 位置：`crates/canter-core/src/runner.rs` 的 context-length 分支。
   - 说明：「占用超过阈值」和「服务商报上下文超长」引起的压缩都记成 `trigger=auto`；后一种的 `triggerOccupancyTokens` 可能低于阈值，而阈值本身没有记下来。DESIGN 已写明这一口径。以后要区分，可以给枚举加一个值，旧的读取端会把它读成 unknown，不会坏。
