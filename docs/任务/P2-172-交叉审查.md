### 必须改 1：MCP 的「停机不再等」连配置热加载退役也生效了，平时行为变了

- 位置：`crates/canter-tools/src/mcp.rs:509-541`（连接任务），`mcp.rs:315`（`Registry::shutdown` 取消的是同一个 `stop`），`crates/canter-server/src/reload.rs:56-67`、`reload.rs:304`、`reload.rs:317`（运行中改配置，去掉或换掉 MCP 服务时，`ServiceSlot::retire` 调 `service.shutdown()`）。
- 问题（已查证）：新代码把「`stop` 被取消」当成停机，取消后不再等 `waiting`（传输收尾），在途的工具列表刷新也立刻放弃。但 `stop` 不只在停机时取消：服务端运行中热加载退役一个 MCP，也是 `Registry::shutdown` 取消它。于是平时的退役也变了：stdio 服务端不再先收到 stdin 关闭、有最多 3 秒自己退出（rmcp 3.7.0 `TokioChildProcess::graceful_shutdown`），而是马上被整组 SIGKILL；HTTP 服务端的会话删除不再等；退役时在途的刷新被截断；首次列工具失败后起的关闭任务也会被截断。用户授权的是停机时听取消，平时行为不变。
- 实测：草稿副本里给 `mcp_stdio.rs` 加「stdin 读到结束就写一个标记文件」，加一条测试：起服务端、配一个 stdio MCP，把 `mcp_servers` 改空等热加载生效（`fixture.applied`），等进程消失后检查标记。分支版本 5/5 失败（没读到 stdin 结束就被杀）；只把 `mcp.rs` 换回 main 的版本，4/4 通过。分支已有的 `mcp_removal_keeps_...`、`changed_mcp_waits_...` 只看进程有没有消失，查不出来。
- 改法：停机和退役分开取消。退役照 main 的做法：`service_stop.cancel()` 后等 `waiting`，在途刷新等它完成或超时。只有服务端停机（`LiveConfig::shutdown`，会话全关完之后）才让连接任务不再等传输收尾和刷新，比如给 `Registry` 多传一个只在这时取消的令牌，在等退役 worker 之前取消，这样停机时卡在退役里的清理也会被截断。不能用 `stop_reloading()` 那个令牌，它在 60 秒等轮之前就取消了，会在轮还在用 MCP 时把它关掉。加回归：热加载移除 stdio MCP 时，进程先读到 stdin 结束再退出；`shutdown_cancels_a_stalled_mcp_tool_list_refresh` 继续通过。

- 平时退役和 main 一致。逐分支对照 main 的 `connect()`：只有 `stop` 被取消（`ServiceSlot::retire` → `Registry::shutdown`）时，初始列工具中途退役仍是 `service.close()` 等完；首次列工具失败后的关闭任务仍等 `close()`；主循环退役仍是 `service_stop.cancel()` 后等 `waiting`；在途刷新只听 `shutdown`，不听 `stop`，退役时照 main 等刷新完成或原超时；刷新失败时仍是先取消、等收尾、再发 `disconnected`。两条新测试实测覆盖了「读到 EOF 再退出」和「等在途刷新」。
- 停机照样截断：`LiveConfig::shutdown` 只在 `lib.rs:199`（会话全部 `close_for_shutdown` 完之后）和启动中途收到信号时调用，先取消 `self.shutdown` 再等退役 worker 和逐个关服务，所以卡在退役清理或刷新里的连接会马上收手。`shutdown` 是 `startup_stop` 的子令牌，和 `stop_reloading()` 取消的 `LiveConfig.stop` 分开，所以 60 秒等轮期间 MCP 不会被关；`replacement_drain_keeps_mcp_available_to_the_active_turn` 实测排空中已接受的轮还能调 MCP。`Registry::connect` 只有 `reload.rs` 两处调用，都传了这个令牌。
- 附带的变化：停机开始时还在连接中的新 MCP（热加载换上来、还没就绪的那份），初始列工具时被 `stop_reloading` 取消后，会等 `service.close()`，最多等到最终停机令牌取消。main 这里是无限期等 `close()`，现在有了上限，没有会话在用它，不算问题。

### 必须改 2：已解决（已查证）

- `discovery.rs:133` 改成 `UPGRADE_GRACE + 45` = 105 秒，新进程等锁仍 90 秒（`lifecycle.rs:141`），等轮仍 60 秒。DESIGN 第 11 条、钩子一节、服务端 README 都已同步，和用户定的一致。

### 97.45 秒的账（已查证，另有一条推测已排除）

- 加法对：`0.2 + 60 + 2.05 + 2.05 + 10 + 6 + 5 + 0.1 = 85.4`，`85.4 + 10 + 0.05 + 2 = 97.45`，在 105 秒内。
- 逐项核对过：LSP 的 3 秒确实在会话全关之后，按服务依次关（`reload.rs:359-363`）；一个服务里正在初始化的语言服务器也听停止（initialize 请求带 `self.stop`），每个服务 3 秒的上限成立。被取消的轮里，MCP、web_fetch、web_search、钩子都听取消。改文件后的 LSP 诊断等待固定 0.5 秒、不听取消，但和前台 shell 的 2.05 秒是同一个轮里并行的工具，不叠加。新进程拿锁后到发布登记之间只有本地 I/O 和并行的 MCP 初始化；`discover` 的就绪探测上限 2 秒（`discovery.rs:39`、`discovery.rs:52`）。
- 没列、但在余量里的：父命令开始计时到新进程开始等锁之间（读登记、拿 startup.lock、起子进程、子进程初始化）是本地操作，不到 1 秒，从 15 秒段剩的 2.95 秒里出。`draining.write()` 没有上限，DESIGN 已如实写明。
- HTTP 那 5 秒的情况和账上写的不一样，见建议改 2：真遇上时父命令不是等着，而是直接失败。这是原有问题，不是这次引入的。

### 建议改 2（原有问题，和本件无关）：旧服务端停止接受连接到退出之间，父命令的探测会让 `--replace` 直接失败

- 位置：`crates/canter-server/src/lib.rs:157-213`（停机收尾），`crates/canter-server/src/discovery.rs:43-65`（探测），`discovery.rs:192`（父命令每 50 ms 一次 `discover(home).await?`）。
- 问题：旧服务端在停机收尾结束、`stopped.cancel()` 之后，axum 停止接受新连接并丢掉监听（axum 0.8.9 `serve/mod.rs:287-297`）。但 `server.json` 和服务端锁要到 `drop(lease)` 才释放，中间还要等 HTTP 收尾（最多 5 秒）。父命令在这段时间探测旧登记，连接被拒；`server_running` 仍为真，于是 `discover` 返回错误。父命令 `?` 直接退出，丢掉 `kill_on_drop` 的子进程，刚等到锁的新服务端被杀；旧的随后退出，机器上没有服务端。
- 实测（已查证）：用本分支的 `canter` 二进制、`mktemp` 建的隔离 HOME 和 CANTER_HOME（socket 路径太长不能放草稿目录，用完已删）。先起一个服务端，用 `nc -U` 发一个 Content-Length 100 但只给 1 字节体的 POST 挂着，再跑 `canter serve --replace`：不到 1 秒就退出码 1，报 `cannot connect to the registered server; it was not replaced`，几秒后旧服务端退出，没有 `server.json`。同样步骤不挂请求时，替换 0 秒成功。没有挂着的请求时窗口只有毫秒级，现有 `replace_detaches_a_ready_server_with_and_without_an_existing_server` 重复跑 20/20 通过，平时很少撞上。
- 是否原有：main 的 `lib.rs` 停机顺序和 `discovery.rs` 的探测逻辑和本分支相同（`git diff main e99e5e4` 只差期限常量），由代码推出是原有问题。`.target/main` 里现成的二进制停在 P2-125 之前（`14ec7da`），没在 main 二进制上复现。
- 改法（另开一件）：替换中，探测失败但锁还被旧实例占着时当作「还没换好」，继续等到期限，不报错退出；或者旧服务端在停止接受连接前先删掉自己的登记。DESIGN 和 README 里「HTTP 最多再等 5 秒」那一段，到时一并改准。

### 对返工取舍的表态

- 退役和最终停机用两个令牌，最终停机令牌不跟 `stop_reloading()`：同意，这正是上次的改法，测试也覆盖到了。
- 最终停机令牌挂在启动取消令牌下面，启动中途收到信号也走快速清理：同意。
- `LiveConfig::shutdown` 先取消、再等 worker：同意，否则卡在退役里的 HTTP 删除会拖住停机。
- 父命令 105 秒、等锁 90 秒、等轮 60 秒：同意，和用户定的一致；15 秒启动段剩 2.95 秒，自定义更长的 MCP 启动超时仍会超时，DESIGN 已写明这是原有边界。
- 没有给 draining 加上限、没有重排 LSP 清理：同意，不在本件范围。
