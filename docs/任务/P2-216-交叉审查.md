### 主控点名的两处

- **`session.rs` 换模型时把 `runtime.options` 换成 `next_options()`**
  - 和运行中冻结的配置不冲突：`update_inner` 开头已经规定，有进行中的一轮或私答时不许换模型，返回 `Conflict`，所以只会在空闲时换，不会改动正在跑的那一轮。
  - 和 `apply_configuration` 不冲突：换完后 `runtime.revision` 还是旧的，下一轮 `acquire` 拿到的版本号只要不同，就整套重新应用，覆盖这次换上的 options；版本号相同，说明这次换上的就是同一份配置。
  - 不用 ChatGPT 时行为不变：
    - 没有配置来源（非热重载路径、测试）时，`next_options()` 就是 `runtime.options.clone()`，完全一样。
    - 有 `LiveConfig`、没有 GPT 这一家时，`apply_versioned` 原样返回 options。顶层会话的 `runtime.options` 本来就来自同一份 `version.options`；唯一被单独改写的 `sandbox`，打开时由 `set_sandbox_disabled` 设成配置里的值，两边也一样。
    - 所以 Chat Completions 会话换模型后，请求、prompt、压缩线和 main 一致。只有一处不同：等着生效的热重载会在换模型这一刻提前生效窗口和档位，下一轮本来就会生效，结果相同。
- **`reload.rs` 用合成的版本号代替 `version.revision`**
  - 别处只拿这个数比较「和上次是不是同一个」：core 的 `apply_configuration`，`agents.rs` 交给子会话的 `runtime.revision`，`http.rs` 的 `configure_session`。没有地方拿它和 `version.revision` 本身比，也没有地方按大小比较。
  - 合成办法：记下上次的（配置版本，目录版本），对不上就把计数加 1。同一个计数只对应一对值；并发时同一对值可能拿到两个计数，最多多重新应用一次，不会漏掉。
  - MCP/LSP 没就绪时照旧返回 `None`，`acquire` 照旧等到就绪、并且 `version` 还是当前那份才返回。热重载下一轮生效、运行中一轮冻结的边界不变。
  - 没登录 ChatGPT 时目录版本一直是 0，初始的 (0,0) 对应计数 0，热重载后依次是 1、2…，和原来的 `version.revision` 一一对应。

### 建议改

1. **子会话换模型会把继承来的沙箱值换成配置里的值**（这次改动带来的，触发面很窄）
   - 位置：`crates/canter-core/src/session.rs:1832`（`runtime.options = next_options`）。
   - 问题：子会话（`snapshot.parent` 有值）的 `runtime.options.sandbox` 不来自配置，而是打开时从存盘的 `sandbox_enabled` 或父会话继承的。`apply_configuration` 专门为子会话保留这个值（`configuration.rs:223`），这次换模型的新代码没有保留。用 PATCH 给子会话换模型、而它继承的沙箱又和当前配置不同时，下一轮重新应用会按配置的值改建沙箱执行器；`open_agent` 再派生孙会话时，传下去的也是配置的值。服务端没禁止对子会话 PATCH 模型，但目前 TUI 和 agent 工具都不会这么做，所以只记建议改。
   - 改法：换模型时保留原来的 `sandbox`，例如 `let sandbox = runtime.options.sandbox; runtime.options = next_options; runtime.options.sandbox = sandbox;`，和 `apply_configuration` 一致。
