### 必须改

1. **必须改：已有仓库的 Git 锁可以被「把上级目录挪走再重建」绕过**（重点 2；越权）
   - 位置：`crates/canter-tools/src/sandbox_linux.rs` 166–175 行（Git 保护路径逐个文件 `--ro-bind`）、282–325 行 `find_git`。
   - 问题：Linux 只把 `config`、`config.worktree`、`hooks`、`commondir`、`gitdir` 这几个条目本身挂成只读，它们的上级目录可写且本身不是挂载点。Linux 的 rename 只在源或目标「本身」是挂载点时报 EBUSY；挪走上级目录时，挂载跟着原目录走，原路径空了出来。所以墙里可以把 `.git/worktrees/<id>` 改名，再在原位置新建一个带伪造 `commondir`（指向一份写了 `core.fsmonitor` 或 `core.hooksPath` 的 config）的目录；用户在墙外对那个 linked worktree 跑 git 时就会执行墙里写的东西。`.git/modules/<子模块>`、cwd 下嵌套仓库的 `.git`（以及嵌套仓库所在的目录）同理。cwd 自己的主仓库没事，因为 `.git` 本身被 `--bind` 成了挂载点、不能改名。macOS 用 `protect_ancestors`（对每个保护路径的所有上级 `deny file-write-unlink`）加 `worktrees/*`、`modules/*` 的正则堵住了这条路；Codex 在 `sandboxing/src/bwrap.rs` 249–268 行也专门写了「a protected file can still be replaced by renaming a writable parent directory」，并把整个 `.git` 挂成只读。用户定的「锁住已有的、新建的下一条再锁」，被这条路变成了「已有的也能在本条里换成新的」。
   - 改法（交主控定）：照 macOS 的 `protect_ancestors`，把每个 Git 保护路径从可写根往下到它之间的每一级目录都 `--bind d d` 绑到自己身上（按深度排序，内容照样可写，只是成了挂载点，改名和删除都会 EBUSY），等于 Linux 版的「上级不能删、不能改名」。凭证目录不受影响（tmpfs 跟着目录走，挪走后内容仍然看不到），但 cwd 是 HOME 上级（比如 `/home`）时 HOME 本身能被挪走重建，同一个改法一并覆盖。修完写一条普通回归检查（改名 `.git/worktrees/<id>`、`.git/modules/<x>`、嵌套 `.git` 失败、保护内容不变），要不要写由主控定。

2. **必须改：`find_git` 碰到读不了的子目录、走的时候消失的目录、坏的 `.git` 指针，整条命令起不来**（重点 3；正常使用时命令跑不起来）
   - 位置：`sandbox_linux.rs` 282–325 行（`fs::read_dir(directory)?`、`entry?`、`file_type()?`、`canonicalize()?`、`git_metadata(...)?`），288–292 行。
   - 问题：每条命令启动前把 cwd、新增目录、`writePaths` 整棵树走一遍，任何一个错误都让命令失败。5090 实测：项目里有一个 `chmod 000` 的子目录（模拟 docker-compose 把 `./pgdata` 绑给 postgres，属主 999、权限 700），关沙箱 `printf ran` 正常，开沙箱每条命令都是 `Could not start sandbox: Permission denied (os error 13)`。正常项目里会碰到：docker-compose 绑出来的数据库目录、`sudo` 编译留下的 root 目录、`.git` 指针指向已被 prune 的 worktree（`git_metadata` 报错）；后台 `cargo build`、vite、next 正在改 `target`、`node_modules/.vite`、`.next` 时，列出的子目录在 `read_dir` 前被删或改名会偶发 ENOENT。另外 `writePaths` 是单个文件时（288–292 行）会走它的整个上级目录，比如批准 `~/.bashrc` 就要走整个 HOME（主控量过 14 秒），也更容易碰到读不了的目录。
   - 改成跳过会不会让墙里改到已有仓库：属主不是当前用户、当前用户进不去的目录（上面 docker 那种），墙里没有任何 capability，进不去也改不了权限，跳过是安全的；走的时候消失的目录跳过也安全（没了就没有要锁的，重新出现的算新建）；坏的或悬空的 `.git` 指针 git 自己也不会用，跳过安全。**属主是当前用户但读不了**的目录不能直接跳过：墙里可以 `chmod` 回来再改里面仓库的 config。
   - 改法（交主控定）：NotFound 跳过；读不了且属主不是自己的目录跳过；坏指针跳过；属主是自己但读不了的目录维持失败，或者把整个目录只读挂上（更严）；`writePaths` 是文件时不走上级目录，只按 `check_request` 已有的判断处理这个文件。

3. **必须改：沙箱启动器 bwrap 从会话的 PATH 里找，只排除了 cwd 里的**（重点 1；悄悄不隔离）
   - 位置：`sandbox_linux.rs` 21–45 行 `bwrap()`；`probe()` 用的是服务端自己的 `std::env::vars()`。
   - 问题：bwrap 本身在墙外运行。PATH 里排在系统 bwrap 前面的目录，只要有一个能被墙里的命令写到（P2-118 新增目录，或批准过的 `writePaths`；Ubuntu 的 `~/.profile` 会把 `~/.local/bin` 放在 PATH 最前，`pip install --user`、`uv tool install` 这类会申请写 `~/.local`），墙里就能放一个 `bwrap` 进去，之后每条「沙箱开着」的命令都由它在墙外执行，界面上看不出任何变化。排除 cwd 的比较也用的是没规范化的 cwd 和规范化后的可执行文件路径，经过符号链接时会漏。macOS 用固定的 `/usr/bin/sandbox-exec`，没有这个问题；Codex 的查找（`sandboxing/src/bwrap.rs` 245–268 行）会跳过所有可写根里的、以及上级目录可被修改的候选。现有测试 `failed_namespace_setup_preserves_the_reason_and_explains_opt_out` 用 PATH 里的假 bwrap，正好说明 PATH 里第一个 `bwrap` 会被直接执行。doctor 和命令用的 PATH 不同，也会出现 doctor 报正常、命令却起不来（或反过来）。
   - 改法：只从固定的系统目录找（`/usr/bin`、`/bin`、`/usr/local/bin` 之类），或者要求可执行文件和它的各级上级目录属主是 root、组和其他人不可写；doctor 和命令用同一个办法。上面那条测试改成用仅测试可用的注入点给假启动器。这是「更严」，按主控给开发的规矩可以直接做。

### 建议改

4. **建议改：seccomp 连 netlink 也挡，node 的 `os.networkInterfaces()` 在沙箱里一律报错**（重点 4）
   - 位置：`sandbox_linux.rs` 469–487 行。
   - 问题：5090 实测：关沙箱正常；开沙箱不联网和 Allow all（联网）两种都报 `SystemError [ERR_SYSTEM_ERROR]: uv_interface_addresses returned Unknown system error 1`。`getent hosts localhost` 联网时正常（glibc 自己退回），git、cargo、npm 的正常用法没发现受影响。会受影响的是启动时打印局域网地址的开发服务器（create-react-app 的 `npm start`、webpack-dev-server、`next dev` 的 Network 那行都调 `os.networkInterfaces()`）。macOS 上同样的调用能用。
   - 改法：放行 `socket(AF_NETLINK, *, NETLINK_ROUTE)`（再比一下 args[2] == 0）。不联网时在新网络命名空间里只看到 lo；联网时只能读，改路由要宿主网络命名空间的 CAP_NET_ADMIN，墙里没有。

5. **建议改：缺失的 `~/.cargo`、`~/.npm` 的占位建成了空文件**
   - 位置：`sandbox_linux.rs` 562–571 行。
   - 问题：cwd 是 HOME（或新增目录包含 HOME）而用户还没有 `~/.cargo` / `~/.npm` 时，命令运行期间墙外会出现一个叫 `~/.npm` 的空文件；这时用户在墙外第一次跑 npm、rustup 会报 Not a directory。只有 `Mount::Empty` 和名字是 `hooks` 的才建目录。
   - 改法：只读的原缓存根也建目录占位。

6. **建议改：每条命令都整棵树走一遍，大目录很慢**（重点 3）
   - 位置：`sandbox_linux.rs` 125–133 行。
   - 问题：cwd 是 HOME 时每条命令多 14 秒左右（主控的代理数字）；新增目录和 `writePaths` 在 cwd 里面时同一棵树走两遍。
   - 改法：至少去掉重复的根；要不要缓存（比如按目录 mtime）或限制范围交主控定。跳过 `node_modules`、`target` 这类目录会让里面的已有仓库不锁，和「锁住已有的」冲突，不建议这么省。

7. **建议改：输出里出现 `bwrap:` 就当成沙箱没起来**
   - 位置：`crates/canter-tools/src/shell.rs` 398–418 行（`mentions_denial` 里的 `setup_failed`）。
   - 问题：命令自己的输出里有 `bwrap:`（比如在 canter 仓库里 `grep -rn "bwrap:"`），末尾会被加上「Linux sandbox could not start. Install bubblewrap…」，误导模型。
   - 改法：只认命令没起来时 bwrap 自己的报错，比如用 bwrap 的 `--json-status-fd` / `--info-fd` 判断子进程有没有启动，或者只看 stderr 第一行且退出码是 1。

8. **建议改：cwd、新增目录或批准的写路径正好是 `/tmp`（或 `XDG_RUNTIME_DIR`）时，批准的写权限被悄悄换成空的只读目录**
   - 位置：`sandbox_linux.rs` 141–143 行（`Mount::Empty` 覆盖同一路径的 `Mount::Write`）。
   - 问题：更严，不越权，但用户批准了写 `/tmp`，命令却报 Read-only file system，看不出原因。
   - 改法：在 `check_request` 里对这几个路径明确拒绝并说明（照「不存在的 writePaths」的做法），或者对 cwd 给出启动错误。

9. **建议改：HOME 里常见的几个 socket 仍能连**（重点 1）
   - 位置：`sandbox_linux.rs` 47–66 行 `socket_roots`。
   - 问题：用户接受了「不常见位置的 socket 仍能连」。但 Docker Desktop for Linux 的 `~/.docker/desktop/docker.sock`（Docker 的 socket 等于能把 `~/.ssh` 挂进容器读）、1Password 的 `~/.1password/agent.sock` 在这些用户那里是常见位置；macOS 上 Seatbelt 连不上它们。
   - 改法：把 `~/.docker/desktop`、`~/.docker/run`、`~/.1password` 一并盖住（只盖目录，不碰 `~/.docker/config.json`）。属于「更严」；算不算「常见位置」请主控或用户定。

### 可以不改

10. **可以不改：占位文件对墙外 git 的影响**（重点 2）
    - 5090 实测：命令运行时墙外看到 `.git/commondir`（内容 `.`）、空的 `.git/gitdir`、`.git/config.worktree`；墙外 `git status`、`git worktree add/list/prune`、`git gc`、在新 worktree 里 `git status` 都正常，命令结束后占位清掉。唯一变化是 `git rev-parse --git-common-dir` 从 `.git` 变成绝对路径，拿它和 `--git-dir` 比字符串来判断「是不是 linked worktree」的工具会短暂判错；后台命令（比如开发服务器）在运行期间一直留着这些占位。引用计数在 `TARGETS` 锁里加减，清理只删 inode 和内容都没变的文件、只删空目录，没看到会删掉别人的文件；只有 bwrap 失败、`create_dir` 碰到墙外同时新建（EEXIST）时命令会失败，窗口很小。

11. **可以不改：`PR_SET_NO_NEW_PRIVS` 加在 bwrap 上**（重点 4）
