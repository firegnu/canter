### 4. 用量映射与两个百分比

**已查证**：`responses.rs:125` 从终态 response 读 usage；`responses/sse.rs:338` 把 `input_tokens_details.cached_tokens` 映射为 cache_read_tokens，miss 为 input 减 cached；reasoning_tokens 是 output 子集。临时第四轮预设 input 合计 17,100、cached 合计 4,050、output 270（其中 reasoning 180），最终 Turn.usage 恰为这些数，没有把 reasoning 再加到 output，没有重复统计 SSE done/completed。

- 每轮行：`canter-tui/src/cells.rs:563`，本轮所有计入请求的 `sum(cached)/sum(input)`，四舍五入到整数百分比，不是逐请求百分比的平均。
- 状态栏：`app.rs:6190`、`statusline.rs:46`，累计值是会话累计 `total.cached/total.input`，`last` 是最近一次已记录请求的 `last.cached/last.input`。两者四舍五入，不只看当前模型；换 DeepSeek 后累计仍含早先 GPT 用量。
- 缺整个 usage 时模型层不发 Usage，计数保留原值，界面也可能继续显示旧 last；有 usage 却缺 cached_tokens 时适配器保留 None，但 `runner.rs:812` 的 `unwrap_or(0)` 把未知变成 0。额外夹具证实输入仍累计 17,100、cached 变成 0。**这是真实的展示局限，现场是否缺字段不知道。**

当前映射也未保留 cache_write_tokens；它表示写缓存而非本次命中，不能加到缓存命中分子。这不使上述 cached/input 公式算错，但后续诊断应同时采集 read/write 字段，避免把写缓存和读缓存混为一谈（[官方 usage 口径](https://developers.openai.com/api/docs/guides/prompt-caching#monitor-cache-performance)）。

**辅助请求的影响已用假服务端证实**：`suggestions.rs:69` 在轮后追加建议问题，经 `btw::answer` 发请求；`telemetry.rs:86` 对 Suggestion/Btw/Handoff 清掉全部 replay；`btw.rs:270` 以 `in_turn=false` 记账。`runner.rs:805` 把它计入会话 total 并替换 last，但保留 context_tokens，不加到原 Turn.usage（`reducer.rs:398` 同样如此）。专门测试输出：

```text

last=100/1200 (8%), context=1130 unchanged; first_changed_item=2
```

因此自动建议、顺口问、handoff **可能拉低或拉高状态栏累计/last，却不能解释本轮行的 5%**；压缩请求以 `in_turn=true` 记账（`compaction.rs:611`），会影响本轮行。子 agent 有自己的用量，不直接并进父会话的这两个比值（额外子会话汇总另算）。自动标题是 `canter-tui/src/run.rs:1009` 截首条输入，开局示例是本地 git，均不调模型。

### 对第 6 条候选和三次真调方案的影响

- **稳定键/路由身份：略加分，仍是待测候选。** 新增的是 pi **公开 SIWC** 的可比实现，已经不只有 Codex backend 的旁证；但它同时发键和 session-id，没有无键对照或命中率。保留后续键 A/B，头另作变量，不把两者和 replay 改动混在首次三请求里。
