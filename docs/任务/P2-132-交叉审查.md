### 重点看的四项

1. **不留进程**（已查证）：所有路径最后都由 `transport.rs:265-287` 的看护任务收尾：领导进程退出、读写出错或被要求停时，先对整组 `killpg`，再 reap。所以崩溃、超内存、空闲回收、可执行文件变了这几种情况，rust-analyzer 起的 cargo 这类同组子进程都会被清掉。
   - 正常关：shutdown → exit，总共等 3 秒，超时杀整组（`transport.rs:334-346`）。
   - 起到一半被停：initialize 用的是实例的停止令牌，会立刻取消并杀掉进程（`service.rs:154-173`）。进程还在 `spawn_blocking` 里没起完的，起完后也走这条。
   - 服务端停止和 `--replace`：关完会话之后、`stopped.cancel()` 和放锁之前调 `lsp.shutdown()`（`lib.rs:191`）；启动期收到信号也会关（`lib.rs:103`）。
   - 强杀：靠 guardian 清理，服务端测试按 PID 验证了语言服务器和它的子进程都已退出。
   - shell 抽层：`LocalProcess` 原样搬进 `process.rs`；启动锁的范围（建管道、挂 guardian、fork/exec、释放临时 FD）和原来一样；`Executor` 接口没变；回归测试全过。
2. **并发**（读代码查证）：查找同键实例和新建实例都在池锁里，两个请求同时来只会起一个。旧实例退役时，要等它 `done` 才建新的，所以同一个键不会同时有两份。池锁里没有 await。锁的顺序固定为「池 → 实例 reason → 状态（读）」和「池 → last_used」，没有反向。起进程和 `ps` 都在 blocking 线程上做。有一处罕见时机见建议改第 2 条。
3. **授权边界**（已查证）：

   - 命令按 argv 直接起，用会话环境的 PATH 解析，`env_clear` 之后只给会话环境。
   - 环境、settings、stderr 和服务器错误原文都不进错误和日志；`Key`、`FileContext` 和配置类型都没有派生 Debug。
   - `lsp.enabled` 关着时 `servers` 为空，`for_file` 直接返回 None，也不起采样任务。

### 意见

1. **建议改**：`crates/canter-tools/src/lsp/service.rs:485-511`（内存超限的处理）
   - 问题（已查证，读代码）：只要单个或合计连续两次超限，循环条件 `entry.active == 0 || …` 就会把**所有**空闲实例都停掉，并且全部记进 `blocked`（ResourceLimited，要显式 retry 才能再起）。方案 4.3 写的是「先回收无活动的，仍超限再停超限的并报 resourceLimited」，有两处对不上：
     - 单个实例超限时，停掉别的空闲实例并不能让它降下来，却把无关的实例一起锁住了。例子：rust-analyzer 进程树超过 4 GiB（方案实测稳定 2.4 GiB，开保存检查时峰值接近 3 GiB，cargo 并行编译时会更高），同时开着的一个空闲 pyright 也会被锁住。
     - 合计超限时，停掉一个空闲实例后已经降到线下了，后面的空闲实例还是会被停、被锁。
     - `/lsp retry` 要到 P2-135 才有，在那之前被锁住的实例只能靠重启服务端恢复。
   - 改法：
     - 单个超限时，只停、只锁超限的那一个。
     - 合计超限时，按现在的顺序一个个停，降到线下就不再停。
     - 为腾内存停掉的空闲实例按普通回收处理：不进 `blocked`，下次修改时再起。
     - 只有超限的实例，以及腾完空闲实例后仍超限才停掉的忙实例，才进 `blocked`。

2. **建议改**：`service.rs:437-457`（采样任务判断回收），以及 `service.rs:547-566` 和 `263-270`（取得实例、开始请求）
   - 问题（读代码推出，没复现；只在罕见时机出现）：采样任务在池锁外读 `users == 0` 或「`active == 0` 且空闲到期」，然后才调 `stop`。如果在读完和 stop 之间，正好有新会话用 `for_file` 拿到这个实例（加 users 是在池锁里做的），或者正好有请求开始，这一次就会拿到一个正在停的实例，返回 `LSP instance has no subscribers` 或 `reclaimed after inactivity` 错误。不会留下进程，也不会起两份；下次修改时会重新起。
   - 改法（二选一）：
     - 把「users 为 0 就停」的判断和 `stop` 一起放进池锁里做。`for_file` 加 users 也在池锁里，这样两者就不会交错。
     - 或者：`for_file` 第二段循环碰到因回收而停的实例（reason 不是 ResourceLimited）时，回到第一段，等它 `done` 再起新的，而不是把回收原因当错误返回。

3. **建议改**：`crates/canter-tools/src/lsp/transport.rs:166-188`（写线程）
   - 问题（已查证，临时测试）：要发出的一条消息超过 16 MiB（或序列化失败）时，写线程直接返回错误，看护任务随即把整个语言服务器连同进程组杀掉。
     - 调用方拿到的错误是 `LSP server exited or closed its transport`（Unavailable）。实例层没有记原因，会把这次当成「崩溃」，占掉自动重起的 2 次额度。
     - 临时测试的结果：发一条 `MAX_FRAME + 1` 字节的请求后，连接关闭、进程退出，下一条小请求也失败。
     - 写入卡住 3 秒（服务器暂时不读 stdin）也会同样被杀、按崩溃计。
     - 现在还没有调用方发大消息；P2-133 同步整篇文档时，碰到大文件就会触发。
   - 改法：
     - 在 `Connection::send` 入队之前检查大小，超限时只让这一条返回 Protocol 错误（英文原因，比如 `LSP message too large`），连接保持不动。
     - 3 秒写超时可以先保留：建议等 P2-133 实测时看看大文件的 didOpen/didChange 会不会触发，再决定要不要放宽。

4. **可以不改**：`service.rs:57-63`（共用键包含完整环境），相关的是 `crates/canter/src/lib.rs:167`
   - 事实（已查证）：客户端交给服务端的是终端的全部环境变量。不同终端窗口的 `TERM_SESSION_ID`、`TMUX_PANE`、`SHLVL` 等几乎总是不同，所以开在不同终端里的两个会话，即使是同一个仓库，也不会共用实例：会起两个 rust-analyzer（各约 2.4 GiB），再来第三个项目就要挤掉空闲的那个。
   - 这是方案 4.3 写明的取舍（牺牲命中率，换来清楚的环境语义），任务文件也这么要求，不用改。建议 P2-136 实测和写 DESIGN 时补一句：实际上只有同一个终端里开的会话之间才会共用实例。

5. **可以不改**：`service.rs:520-674`（`for_file` 的取消语义），这条是给 P2-133 的提醒
   - 事实（读代码）：调用方取消 `for_file` 时，租约随之释放；如果没有别的订阅，实例会立刻按「没有订阅」停掉，这次启动作废。这种停有原因，不记失败，也不退避。
   - 所以 P2-133 不能用工具那 500 ms 的等待去取消 `for_file`，否则启动慢的服务器每次修改都会起到一半就被停。应该在后台任务里取实例，按会话持有 `Instance`（文档里也写了：保留 Instance 就是保留订阅）。

6. **可以不改**：`crates/canter-tools/src/lsp/config.rs:18-27`（`ServerConfig`）和 `config.rs:75-83`（`validate` 里拦临时安装入口的那段）
   - 字段名拼错（比如写成 `rootMarkers`）不会报错，而是静默继承内置值。等内置表有内容（P2-136）以后，用户可能以为自己覆盖了，其实没有。
   - 临时安装入口只拦了 npm 一系（npx/pnpx/bunx，以及 npm/pnpm/yarn/bun 的 exec/x/dlx），没拦 `uvx`、`pipx run` 这类 Python 的入口。
   - 用户配置是用户自己写的，开了就等于同意运行，这两处只是防手误。P2-136 加内置项时可以顺手加上 `deny_unknown_fields`，并补上 Python 的这几个入口。
