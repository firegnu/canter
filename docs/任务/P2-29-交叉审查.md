### 重点逐条

1. **单实例**：保证。服务端拿到的仍是 `server.lock` 的独占锁；新代码只有在共享锁也拿不到（有人持独占锁，也就是真有服务端）时才走拒绝，检查者和别的启动者只会持共享锁，不会让人被拒。临时测试：服务端在跑、8 个线程不停检查，再起 1000 次全被拒，报 `a server is already running`；3 个启动者同时起、8 个线程不停检查，500 轮每轮恰好一个拿到锁，没有两个都拿到、也没有都被拒。
2. **重试循环没上限**：正常用不会一直转。检查者只在打开文件到关掉之间持共享锁（微秒级），终端断线重连每 500 ms 才查一次（`canter-tui/src/run.rs:48`）。临时测试里 8 个线程不停检查时启动等待 p99 0.2 ms；16 核机器上再压 24 个 `yes`，最长 27 ms。但有进程一直持着共享锁（比如检查到一半被 SIGSTOP、被调试器停住）时，启动会一直空转：临时测试 3 秒内没返回，进程 CPU 时间涨了 2.97 秒，即占满一个核。见下面第 1 条。
3. **`serve --replace`**：对。`WouldBlock if replace` 现在只在真有旧服务端时进入；以前检查撞上会让 `--replace` 在没有服务端时误入这个分支（报「旧服务端还没启动完」，或对残留登记写 `replace.json`），现在不会（临时测试：没服务端、8 个线程检查，`--replace` 1000 次都直接起来）。等旧服务端退出那段只试独占锁，检查者挡住只是 100 ms 后再试，仍在 75 秒期限内；临时测试旧服务端在跑、8 个线程检查，20 次接手都成功，用时 105–526 ms（含负载下）。已有 `sigterm_interrupts_upgrade_draining`、`sigint_interrupts_upgrade_draining` 通过。
4. **锁的语义**：对得上。Rust 1.96 标准库在 macOS（`target_vendor = "apple"`）和 Linux 上，`try_lock` / `try_lock_shared` / `unlock` 都是 `flock(LOCK_EX/LOCK_SH | LOCK_NB)` / `LOCK_UN`。`flock` 的锁属于打开的文件描述：同一进程里分别 `open` 的 fd 之间照样互斥，所以单元测试用多线程能代表多进程；每次检查都新开 fd，`Lease` 自己一个 fd，循环里先 `unlock` 再试独占，没有在同一个 fd 上做共享转独占。fd 都带 `O_CLOEXEC`，子进程 exec 后不会带走锁。别处没有对 `server.lock` 拿独占锁做检查：只有 `Lease::acquire`（占有和 `--replace` 等待）拿独占锁；`startup.lock`、`replace.lock`、事件文件的锁是别的文件；测试 `discovery.rs:120` 只是写空文件。
5. **回归测试**：在原代码上确实因为这个原因失败。我把产品代码临时退回 main、只留新测试，连跑 3 次都在 0.00 秒失败，报 `a server is already running; to upgrade, run canter serve --replace`（已恢复）。修完后不会因为机器忙变成偶发：测试里拿独占锁的只有主线程自己（一次一个、用完就放），共享锁不可能拿不到，所以 `acquire` 不可能报已有服务端，最坏是变慢；测试也没有计时断言。负载下（24 个 `yes`）连跑 20 次全过，0.20–0.41 秒。

### 意见

1. **建议改**｜`crates/canter-server/src/lifecycle.rs:105-120`（`Lease::acquire` 的重试循环）
   - 问题：没有上限，且用 `yield_now` 空转。只要有进程一直持着 `server.lock` 的共享锁，`canter serve` 就一直占满一个核不返回；`--replace` 也卡在这里，到不了后面 75 秒的期限。经 `ensure_server` 起的话，客户端 15 秒后报「timed out waiting for the server to start; check server.log」，日志里什么都没有，后台留下一个空转的 `canter serve`（独立 session）；用户再开一次就再多一个。不会出两个服务端：持锁的进程一放，空转的里只有一个拿到独占锁，其余被拒后退出。以前这种情况是马上报 `already running` 退出，现在是空转，所以算变差，但只在异常时出现，不在「必须改」的范围。
   - 改法：给循环一个短期限（比如 2–5 秒），重试之间睡 1 ms 左右，不用 `yield_now` 空转（正常撞上时检查者微秒级就放，多等 1 ms 无所谓）。到期返回一条单独的错误，比如「the server lock is held by another process; try again」，不要报 `already running`（那正是这次要去掉的误报）。这样 `ensure_server` 看到子进程退出、锁空闲，会马上把这句话带给用户，也不留后台进程。配一条测试：另开 fd 持共享锁，`acquire` 到期返回这条错误；放掉后能正常拿到。
2. **可以不改**｜`crates/canter-server/src/lifecycle.rs:108` 的注释
   - 问题：「Only discovery probes hold shared locks」不全，同时启动的别的服务端在自己的循环里也会短暂持共享锁（临时测试里 3 个启动者互相挡过）。行为没错，只是注释不准。
   - 改法：改成「检查者和正在抢锁的启动者只持共享锁；共享锁拿得到说明没有服务端」之类。
3. **可以不改**｜升级过渡期（不改代码）
   - 问题：`cargo install` 换版本后，开着的旧版终端还是旧代码，断线重连时仍短暂拿独占锁检查。没有服务端、旧终端在重连时，新起的普通 `canter serve` 撞上仍会被误拒（就是这次修的毛病）。`--replace` 不受影响（等待那段只是重试）。旧终端重开后就没有了。
   - 改法：不用改代码；主控觉得有必要，可在 HANDOFF「已知没修的问题」记一句。
