## 要做的

### 1. 每轮结束后生成建议（服务端）

- 一轮正常结束（模型回完、没有工具调用在等）后，服务端在后台生成一条建议。
- 请求照 `/btw` 的办法：同一个模型、同一个思考档位、同样的固定前缀、历史和工具定义，末尾只加一条固定的英文说明，要模型只回用户下一句可能要说的话（一句、短、和用户用的语言一致，没有明显的下一步就回空）。模型返回工具调用不执行；回空、只有工具调用、太长（比如超过一行或 200 个字符）都当没有建议。
- 不存盘、不进模型历史、不改 ctx。用量照 btw 的办法记入会话花费（`session.btwUsage` 或同样含义的事件），遥测按 btw/handoff 的私有请求记，`purpose` 加 `suggestion`。
- 这些情况不生成：
  - 这一轮出错、被 Esc 打断、因花费上限停下；
  - 计划模式下；
  - 还有等批准、等回答（`ask_user`、计划批准）的；
  - 有排队的输入，或者目标续跑、后台叫醒会接着开下一轮；
  - 子 agent 的子会话（主会话照出）；
  - `canter exec` 非交互的轮；
  - 配置关了；
  - 连续 20 条建议都没被用：之后每 4 轮才生成一次，用了一次就恢复每轮都出。计数按会话放在内存里，不存盘。
- 生成时用户发了新输入、开始 `/btw`、`/handoff`、压缩、`/review`，或者会话关闭：取消生成（断开请求，不再记账以外的事），不挡这些操作。
- 生成好以后发一个新事件（比如 `session.promptSuggestion { turnId, text }`）给这个会话所有连着的客户端；不存盘、不重放，后连上的终端看不到。旧客户端按 Unknown 跳过。少出的时候，第一次少出发一条提示，终端显示 `Showing fewer prompt suggestions · use one to bring them back`。
- 用户发输入时，客户端可带可选的 `fromSuggestion: true`，表示这条是用 Tab / → 放进来的建议（放进来以后改过也算用了），服务端据此清零「连续没用」的计数。

### 2. 会话刚打开时的 git 示例（服务端）

- 会话还没有任何对话、工作目录在 git 仓库里时，服务端从最近的提交里挑最近改得多的文件，按固定的英文模板拼一句示例（比如 `explain how <path> works`、`add tests for <path>`），随会话打开的快照或一个事件发给客户端。不调模型、不花钱。
- 不在 git 仓库、没有提交、git 出错时不给，不报错。挑文件用 git 命令读，不改仓库；跳过已删除的文件。
- 配置关了也不给。

### 3. 终端显示和按键

- 输入框空着、没有轮在跑、没有批准框、补全列表、提问框时，把建议（或开局示例）用灰字显示在输入框里。
- Tab 或 → 把灰字放进输入框，光标在末尾，可以改；再按 Enter 发出。灰字显示时只按 Enter 不发。
- 打任何字、粘贴、Esc、开始下一轮：灰字消失，这条建议不再出现。
- 新的一轮开始时清掉旧建议；收到的建议对应的不是最新一轮就不显示。
- 现有按键不变：轮在跑时 Tab 插队（P2-97）、`/` 和 `@` 补全列表里的 Tab、有字时 → 移动光标都照旧。
- 界面文字用英文。

### 3.5 不影响正常流程

用户：「这个功能不能能影响正常的流程（因为这个而造成性能问题）」。具体是：

- 一轮结束：结束事件先发出去，再开始生成；生成等模型时不占会话的锁、登记表的锁，不挡别的会话。
- 下一条输入：生成中用户发的输入立刻被接受，主线请求马上发出，不等建议请求结束或取消完成；取消在后台收尾。
- `/btw`、`/handoff`、压缩、`/review`、关会话、删会话：同上，不等建议。
- 同一个会话同时最多一个建议请求；新的一轮开始前，旧的一定已经取消。
- 打开会话：不等 git 示例。git 示例在后台算，好了再发；只读最近有限的几十条提交，git 有超时（比如 2 秒），超时就不给。
- 终端：灰字只是输入框里多画一行，不加额外的刷新和轮询。
- 遥测、用量记账照 btw 的私有请求走，不进主线的写盘批次。
