### 具体意见

1. **必须改：批准命令的清洗会隐藏实际执行的内容。**
   - **位置**：`crates/canter-tui/src/approval.rs:195–205`，同类调用还在 `:231–232`；所用函数为 `crates/canter-tui/src/text.rs:46–66`。
   - **问题**：批准框复用了用于显示进度输出的 `sanitize`。它遇到独立 CR 会删掉这一行前面全部字符，遇到转义序列还会丢弃内容。这会让批准所见与真正执行的命令不同。实测假模型返回 `printf review-proof > approval-proof.txt #\recho safe`（这里 `\r` 指一个真实 CR 字符）：批准框只显示 `echo safe`，不显示写文件的前缀；按 Enter 后，真实 shell 却在隔离工作目录写出了 `approval-proof.txt`，内容是 `review-proof`。服务端批准参数保留了完整原命令，问题发生在客户端展示。
   - **改法**：批准内容使用保留信息的转义显示，把 CR、ESC 等控制字符显式画成 `\r`、`\x1b` 等可见文本，不能执行回车覆盖语义或吞掉字符。命令、cwd、实际路径和 diff 都应按这个原则检查；普通工具输出的进度清洗可保留。用这个无害写文件例子验证批准框能够看到实际命令前缀。

2. **必须改：尚未重画时，旧画面的批准按键会回答新请求。**
   - **位置**：`crates/canter-tui/src/run.rs:240–257`；`crates/canter-tui/src/app.rs:210–218、468–512`。
   - **问题**：主循环先归并收到的服务端事件，再清空按键队列，中间没有重画；`handle_key` 却直接从最新快照选择 `open_approval()`。另一终端答掉请求 A、模型紧接着发出请求 B 时，当前终端仍显示 A，排队中的 Enter/数字键却会批准 B。`alreadyResolved` 不能保护这里，因为发出去的是 B 的有效请求号。用真实服务端的连续事件，在 TestBackend 按主循环相同的“归并事件 → 处理按键，尚未重画”顺序复现：画面仍是 `printf A > first-proof.txt`，Enter 生成的却是对 `printf B > second-proof.txt` 的 Resolve；服务端返回 `alreadyResolved: false`，并确实执行了 B。输入框切换为批准框时也有同类误触路径。
   - **改法**：批准键必须绑定到最后实际显示的请求号，而不能临时改绑到快照里的下一请求。已显示请求失效时丢弃该键，或只对旧请求作晚答处理；新请求先显示，再接受属于它的按键，不能把切换前已经排队的键直接消费到新请求。对 Esc 也保留“已显示的目标轮”边界，避免事件批处理切到新轮后打断未显示的新轮。补上请求 A 被别人解决、请求 B 到达、旧按键排队这一复现。

3. **必须改：旁观终端会自动撤销其他客户端的关闭操作。**
   - **位置**：`crates/canter-tui/src/run.rs:489–546`，尤其 `reconnect` 无条件调用 `resume`；关联行为见 `crates/canter-server/src/http.rs:359–380`。
   - **问题**：显式 DELETE 会话会结束该会话的 SSE，客户端把它一概当成需恢复的断线，约 500 ms 后 resume。实测保持一个 TUI 旁观，另一 HTTP 客户端 DELETE：快照先为 `Closed`（seq 3），随后无人操作的旁观 TUI 把它恢复为 `Idle`（seq 4）；前后服务端登记完全相同，没有重启服务端，也不需要额外制造断网。因此完成记录所说的“被删掉的会话也会被重新打开”不是可接受的重连副作用，而是直接违背关闭意图。
   - **改法**：区分服务端重启所需的环境恢复与用户显式关闭；显式关闭后的会话保持关闭，只有用户主动 `--resume`/选择接着聊才重新打开。不能仅因 SSE 结束就无条件 resume，也不能简单禁止恢复所有 `closed` 快照，因为服务端正常退出也会写 closed。结合服务端 instance 和明确的关闭语义处理；若现有协议不足以可靠区分，先交主控决定必要的服务端/协议调整。回归验证必须保留“服务端重启仍自动恢复”，同时确认“同一实例上的显式关闭不被旁观者撤销”。

4. **建议改：数字 2 会绕过会话级授权的完整说明。**
   - **位置**：`crates/canter-tui/src/approval.rs:114–123`；`crates/canter-tui/src/app.rs:502–511`。
   - **问题**：完整说明仅在高亮 `AcceptForSession` 时显示，但默认高亮第 1 项，按数字 2 会立即发出回答并关框。实测默认画面未显示“之后把权限模式改回每次问仍有效”，按 2 已生成 `AcceptForSession`。走数字快捷键的用户看不到原任务要求强调的授权范围。
   - **改法**：将“shell 会话内所有命令都放行，改回每次问仍有效”作为选择前即可见的说明；保留线框要求的数字直接作答，不让提示依赖先用方向键选中第 2 项。

5. **建议改：小窗口会截掉批准选项，但仍接受对应按键。**
   - **位置**：`crates/canter-tui/src/approval.rs:125–132`；`crates/canter-tui/src/app.rs:365–400、742–780`。
   - **问题**：给正文保留至少 3 行后，选项、说明和边框可能使总高度超过窗口，最后由终端直接裁切。用 80×10 TestBackend 和普通短 shell 命令复现，第 4 项“拒绝并停下”不可见。正文的 PgUp/PgDn 不能滚出被裁掉的选项；选中第 2 项增加说明后可用空间更少。与完成记录已注明的限制一致。
