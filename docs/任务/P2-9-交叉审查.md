### 要害逐项核对（没发现问题）

- 不污染主线：btw 只克隆 `context::request()` 的结果，不调 `state.message`，不碰 `measured_context`、`active`、`steers`、`queue`；图片提示由 `prepare_request` 返回后丢掉，错误只走私有流。两条 http 测试逐字比较了 btw 请求、问后主线下一次请求、模型历史文件和事件文件，工具没执行。
- 消息序列：只看最后一条助手消息够用。插话只在每次发请求前 `consume_steering` 时进历史，打断时的「补齐工具结果 + 插入打断说明」在 `run()` 里一次持锁做完，所以未收齐结果的工具组只可能是最后一组，后面不会跟用户消息；`truncate(index)` 把这组调用连同已有结果一起去掉。wire 层 `normalize_tool_pairs` 另外还会补缺失结果，多一层保险。主线还在出第一段回复或跑第一组工具时问 btw，末尾是两条连续的用户消息；主线打断后再输入本来就会这样发，不是新出现的序列。
- 锁和并发：btw 只在拼请求、读图片路径、记账、清 `state.btw` 时短暂持锁，模型流不持锁；主线不看 `state.btw`。关会话时先设 `closing` 再取消并等 btw，`available()` 挡住之后的新 btw；`serve --replace` 设 draining 的写锁要等 btw 处理函数的读锁放开，之后关所有已载入会话，btw 随之取消；断开响应流会立刻取消（断开测试 5 秒内入账，比 15 秒心跳短）。终端切会话、退出时 abort 本地任务，新的 `App` 不带旧 btw。
- 记账：`session.btwUsage` 的 total/cost 接在快照累计上，下一条 `session.usage` 再从快照往上加，不重复；Ledger 计入会话合计、按模型和按天的明细，不计入 `turn_costs`/`lastTurnCost`；`active.turn.usage` 不变；ctx 和窗口沿用快照值。取消前收到的用量照记。
- 协议兼容：`EventPayload` 有 `#[serde(other)] Unknown`，旧客户端把新事件解成 Unknown，reducer 忽略；旧会话没有新事件，照常读。DESIGN 第 8 条写了和 Codex 的不同。

### 建议改

1. 建议改：`crates/canter-core/src/context.rs:315`（`/context` 报告的 `context_tokens`），根源在 `runner.rs` `record_usage` 的 btw 分支。
   - 问题：会话里还没有主线请求时先问 btw，快照 `tokenUsage` 变成 `contextTokens: 0`、`modelContextWindow: null`。状态栏因为窗口为空不显示 ctx，没问题；但 `/context` 读到 `Some(0)`，终端显示「Context  ctx 0% 0/…(last request)」，原来是「Context  no request yet」。这和 DESIGN P2-8「可空的 contextTokens（沿用最近普通请求的模型实测值）」以及本件「ctx 保持原值」不一致。
   - 改法：报告里只在 `model_context_window.is_some()` 时取 `context_tokens`（btw 只在主线已有用量时才带窗口）。加一条 http 测试：新会话先 btw，再 `GET context`，`contextTokens` 仍为 null。
2. 建议改：`crates/canter-tui/src/app.rs:449`（`key_on` 开头的 btw Esc）。
   - 问题：btw 在答时，Esc 排在选择框（`/model`、`/think` 等）和 `/` 命令列表之前处理。用户按 Esc 想关列表，结果停了 btw，列表还开着；命令列表那段原有注释写明 Esc「Closes only the list」。
   - 改法：有选择框或命令列表时，Esc 照旧只关它们，不停 btw。批准框里的 Esc 本来就是打断主线，btw 仍应排在批准框前面。
3. 建议改：`crates/canter-tui/src/app.rs:449`，对照 `Shown`（`app.rs:185`）和 `interrupt_seen`。
   - 问题：其它按键都按「按键那一帧画面上显示的内容」处理，btw 这条只看当前状态。主循环先排空消息再处理按键，btw 恰好在两帧之间答完时，用户看着「btw 在答」按下的 Esc 会落到 `interrupt_seen(shown.turn)`，把主线打断。主线答完后迟到的 Esc 什么也不做，btw 答完后迟到的 Esc 却会打断主线（停轮、取消工具），代价不对称。
   - 改法：`Shown` 记下这一帧有没有在答的 btw；画面上有 btw 在答时，Esc 只作用于 btw，已答完就什么也不做，不落到主线。可以再仿照 `guard_until`，在 btw 结束后留一小段保护时间。加一条 slash.rs 测试：画一帧（btw 在答）→ `btw_event(Completed)` → Esc，断言不返回 `Interrupt`。
4. 建议改：`crates/canter-tui/src/app.rs:742`（`btw_event` 里的 `self.history.width = 0`）。
   - 问题：btw 块已经并进历史缓存时（主线空闲时问 btw，这是常见情况），每次更新都清空整段历史缓存，下一帧把所有已完成的轮重新渲染 markdown、重新折行，耗时和会话长度成正比。release 实测（每轮一段约 25 行的 markdown 回答）：50/200/800 轮时，btw 流式每帧 0.9/3.1/12.5 ms，主线流式每帧约 0.07 ms。工具输出、diff 多的长会话会更重。现在还不卡，但白白多花。
   - 改法（二选一）：btw 没答完时不并进历史缓存，让 `extend_history` 遇到没答完的 btw 就停下，它和其后的内容留在实时区每帧画，答完再并入；或者记住 btw 块在 `history.rows` 里的起始行，只截断、重排这之后的部分。
