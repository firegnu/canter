### 五个重点的结论

1. **新旧版本互读**（已查证）
   - 旧版程序读新会话不会坏：main 上的 `Item` 有 `#[serde(other)] Unknown`，`plan` 读成 Unknown；reducer 只处理带 id 的项目（`reducer.rs` 里 ItemStarted/ItemCompleted 的 `if let Some(id) = item.id()`），Unknown 直接跳过，本件没改 reducer；`SessionSettings` 没有 `deny_unknown_fields`，`planEnabled` 被忽略；模型历史没加新条目种类。旧版恢复时把带 `update_plan` 调用的历史发给模型、工具列表里却没有它，见「未知」。
   - 新版读旧会话照常：dev 的 `legacy_session_without_a_plan_opens_and_compacts_without_inventing_one` 覆盖。
   - 重开时追加的 `session.updated` 没有新的副作用：`open_inner` 本来每次都在最后追加一条 `session.status idle`（`session.rs:420`），reducer 对每条事件都更新 `updated_at`，会话列表按 `updated_at` 倒排（`canter-store/src/lib.rs:158`），所以重开本来就会把会话顶到最前，多一条不改变排序。会话列表和 `GET` 读快照不打开会话，不写；只有 resume 写。`usage.rs` 只从 `session.updated` 取模型名，不受影响；终端对 `session.updated` 没有单独的提示。PATCH 从快照复制设置，`planEnabled` 不会被冲掉。
2. **压缩**（已查证，有两处边角：建议改 1、2）
   - 重启后清单还在：恢复用 `Compaction.messages`（含 `[Current plan]`），见 `context.rs` 的 `restore`。
   - 不当成用户原话保留：`user_messages` / `user_inputs` 取 `messages[..len-1]`，不含摘要消息；`ContextCompaction` 项目和 `HistoryEntry::Compaction.summary` 存的都是不带清单的纯摘要。
   - 预算：`context::estimate(&summary_message)` 已把清单算进去。
   - 压缩后回退：压缩会 `clear_boundaries()`，回退只能到压缩之后的轮（`rewind_boundary` 报 "predates the latest compaction"），截断点在摘要消息之后。快照从剩下的轮推出当前清单，模型看到的是「摘要里的清单 + 之后的 update_plan 调用」，最后一份和快照一致。
   - 清单清空（`[]`）后压缩：临时测试 C 得到 `[Current plan]\n[]`，意思是已清空，可以接受。没有清单时不加这一段，dev 测试覆盖。
   - `/handoff` 用的是完整请求（`btw.rs` 调 `context::request`），压缩后的摘要消息连同清单作为上下文进去，这是该有的；清单没有被当作用户原话逐字保留，但有建议改 2 的问题。
3. **当前清单怎么推出**（已查证，没发现错）
   - 校验失败、参数解析失败：`tool_error` 产生 `failed`、`plan: []` 的项目；`current_plan()` 只认 `completed`，不替换。
   - 被打断：`permission()` 返回 None 时项目置 `failed`，模型收到 "Interrupted; not run"。
   - 服务端重启：`open_inner` 把进行中的 Plan 项目置 `failed`，`complete_missing_tools` 给模型补「No result」。
   - 被拒：`update_plan` 在所有权限模式和审查轮都直接放行，没有被拒的路径。关掉开关后模型还调用，`Tools::find` 返回 None，runner 回 "Unknown tool" 并发警告，不产生 Plan 项目。
   - 撤回（retract）只发生在模型开始输出之前，撤回的轮里不会有 Plan 项目。
   - 回退跨过清单更新：dev 测试覆盖退到第二份之前、第一份之前、压缩之后的轮。
4. **工具列表**（已查证，没发现错）：`Tool::ALL` 里 `update_plan` 排在 `web_fetch` 之后、MCP 之前。`find` 只在开关关掉时对 `update_plan` 返回 None，其他内置工具和 MCP 工具的顺序、名字都不变（mcp 测试的顺序断言已跟着改）。MCP 工具名都是 `mcp__服务__工具`，不会和 `update_plan` 撞名。`prepare_named` 直接用 `Tool::from_name`，但 runner 先过 `find` 才会走到它，关掉时进不去。核心提示词的金样文件 `core_deepseek.txt` 没变，确认核心没加句子。
5. **终端**（已查证，有一处：建议改 3）

   - 补全列表优先：列表占满时 `plan_room` 为 0，清单不显示。
   - 批准框、提问框：`box_height = height - 3 - INFO_ROWS`，本意是给状态行、提示行和一行对话留位，清单仍能再占 1 行。临时测试 D：没有清单时，对话区剩 1 行加提示行；有清单时对话区 0 行，清单那一行只写「还有 2 步」，一个步骤都没显示。

### 意见

**建议改 1：关掉开关后，压缩仍然附上清单**
- 位置：`crates/canter-core/src/compaction.rs:159`（取清单）、`:378`（附上）。
- 问题：`current_plan()` 不看开关。会话以前用过清单，之后以 `plan_enabled: false` 重开，再压缩，摘要消息里仍然带 `[Current plan]`，而工具列表里已经没有 `update_plan` 了。临时测试 A 实测 `has_tool=false has_plan=true`。模型看到一份有进行中步骤的清单，却没有工具去勾，可能去调用不存在的工具（回 Unknown tool 并发警告）；界面上又不显示这份清单。这和 DESIGN 第 8 条「false 时不提供工具，终端不显示清单」的意思不一致。
- 改法：取清单时加上 `state.journal.snapshot.settings.plan_enabled != Some(false)`（或者看 `shared.options.plan_enabled`），关掉时不附；补一条测试。

**建议改 2：再次压缩时，上一份清单的 JSON 以「User:」身份进了压缩稿**
- 位置：`compaction.rs:167`，拼 transcript 时 `Message::User { text } => "\nUser: {text}\n"`。
- 问题：上一次的摘要消息本来就以 `User: [Context summary]…` 进入下一次压缩稿（P2-57 起就这样），现在它后面还跟着 `[Current plan]` 和 JSON。临时测试 B 抓到的第二次压缩请求就是这样。压缩模型可能把这段写进「User's words」，也白占一些 token；而新的 `[Current plan]` 压完后会重新附上，旧的那份没有用。
- 改法：拼 transcript 时遇到 `summary_index` 那条消息，去掉 `\n\n[Current plan]\n` 之后的部分。只改拼稿，不动存盘的摘要消息和九个小节。

**建议改 3：矮窗口加上大批准框或提问框时，清单把对话区挤没；只剩一行时只写「还有 N 步」**
- 位置：`crates/canter-tui/src/app.rs:3255`（`plan_room` 用 `2 + INFO_ROWS`）；`crates/canter-tui/src/plan.rs:99-101`（`limit - 1`）。
- 问题：(a) `plan_room` 没给提示行留位。批准框撑满、又往回翻时，对话区变成 0 行（临时测试 D）；点提示行能回到底部，不会卡住，但这时看不到对话。(b) 只剩 1 行、没做完的步骤有 2 步或以上时，`shown = 0`，只显示「还有 2 步」，看不出正在做哪一步。
- 改法：(a) `plan_room` 改成 `height.saturating_sub(3 + INFO_ROWS + bottom.height())`，和 `box_height` 的留位一致；(b) `limit == 1` 时显示进行中的那一步，后面加「（还有 N 步）」，或者 `limit >= 2` 时才用溢出行。两处各补一条 TestBackend 断言。

**建议改 4：文档没跟上**
- 位置：`crates/canter-protocol/README.md`（MCP、webFetch 都有一节，`plan` 项目、`PlanStep`、`settings.planEnabled` 没写）；`crates/canter-tui/README.md`（没写常驻清单放在哪、最多 5 行、做完收起、关掉后隐藏）；`crates/canter-core/README.md:85`（`compaction` 条目的 messages 里多了 `[Current plan]`）。
- 改法：各补一两句，内容照 DESIGN 第 8 条那段。

**建议改 5：README 说「重新打开会话时读取」，实际上多数情况要等服务端重启**
- 位置：`crates/canter-server/README.md:64-66`。
- 问题：终端退出时不关会话（客户端代码里没有 DELETE 调用），会话一直留在服务端内存里。之后 `/resume` 同一个会话并不会重新打开它，开关也就不生效，要等服务端重启或别的客户端关掉它才会重读。README 写的「已打开的会话保持原工具列表」技术上没错，但用户容易以为 `/resume` 一下就换了。

### 必须改 1 的三点

1. **压缩附的清单用工具参数写法**：修好了。`serialize_plan` 把 `Pending` / `InProgress` / `Completed` 转成 `pending` / `in_progress` / `completed`，压缩用它生成 `[Current plan]`；`plans_replace_persist…` 断言两次压缩后的附带清单都等于工具参数形式的 `INITIAL`。
2. **模型原样发回能成功**：修好了。新的端到端测试让假模型从摘要消息里把清单原样抄进 `update_plan`，断言工具回 `Plan updated`、轮里有一个成功的 Plan 项目、当前清单和压缩前一致。
3. **Unknown 步骤**：直接跳过，不输出 `"unknown"`，所以模型抄回来不会因为它被拒；全是 Unknown 时输出 `[]`。单元测试 `plan_serialization_uses_tool_statuses_and_skips_unknown_steps` 覆盖了混有未知状态和空清单两种情况。这一版的工具产生不了 Unknown 步骤，只有以后的版本才会出现；跳过以后，模型下一次整份替换时这一步会丢掉，可以接受。终端和导出也一样跳过 Unknown 步骤，三处一致。

### 意见

**可以不改 1**：`serialize_plan` 用 `json!` 生成每一步，项目里的 serde_json 没开 `preserve_order`（`cargo tree -e features -i serde_json` 只有 alloc/default/raw_value/std），所以对象的键按字母排序，附带清单实际写成 `{"status":"in_progress","step":"Implement"}`，`status` 在前，和工具说明里 `step`、`status` 的顺序相反。模型发回时 JSON 键的顺序不影响解析，端到端测试也证明能用；想和工具说明的顺序一样，可以改用一个只有 `step`、`status` 两个字段的 `#[derive(Serialize)]` 小结构。
