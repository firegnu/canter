### 必须改

**1. 必须改｜run 的 worktree 放在 eval 状态目录里，canter 的读写改文件工具会全部拒绝（跑出来的结果不可信）**

- 位置：`eval/src/prepare.rs` 里 `let worktree = run_dir.join("worktree")`，`run_dir` 来自 `eval/src/paths.rs` 的 `Home::run_dir` = `<eval home>/runs/<轮次>/<次>`；README「目录」一节和 DESIGN 新加那一节写的也是这个布局。
- 问题（已查证，读代码）：canter 服务端把自己的 `CANTER_HOME` 整个当作受保护路径：`crates/canter-server/src/http.rs:224` `protected_paths: vec![self.home.clone(), self.home.join("config.json")]`。`crates/canter-tools/src/executor.rs` 的 `resolve_with_memory` / `check_protected` 对 `path.starts_with(protected)` 的路径一律返回 `this file is private to canter`（只放行两层记忆目录），`read_file`、`write_file` 都走这条。canter 自己的测试 `crates/canter-tools/tests/files.rs:162-187` 断言了 Read / Write / Edit 状态目录里的文件都失败。eval 服务端的 `CANTER_HOME` 就是 eval 状态目录，worktree 在它下面，所以模型对 `TODO.md`、`src/*.ts` 的每一次 read / write / edit 都会失败。
- 后果（推测，没真跑）：模型要么卡住，要么全改用 shell（`--yolo` 关了沙箱，shell 还能写），行为和日常完全不同；用时、请求、工具失败、`read` 次数都没法和日常或以后各轮比。eval 的测试用的是假服务端，所以没测出来。
- 改法：worktree 放到 eval 状态目录外面一个 eval 专用的根下，比如 `local.json` 加 `worktrees`（绝对路径），缺省 `~/.canter-eval-worktrees`；`prepare` 拒绝落在 eval 状态目录里面、或落在 canter 自己状态目录里面的根；`clean` 删之前确认 `state.worktree` 在这个根下面，不在就不删。加测试：准备出的 worktree 路径不以 `home.root` 开头。README 的目录布局和 DESIGN 那一节一并改。

**2. 必须改｜`stop` 只看 PID 活着就发 SIGTERM，`server.json` 过时的时候会停错进程**

- 位置：`eval/src/server.rs` 的 `stop`：`kill(pid, None)` 只确认这个 PID 有进程，然后 SIGTERM。
- 问题（已查证）：canter 正常退出时 `Lease::drop` 会删 `server.json`（`crates/canter-server/src/lifecycle.rs` 末尾的 `impl Drop for Lease`），但崩溃或被 SIGKILL 时不删，文件里的 `pid` 就过时了；PID 被系统回收给别的进程后，`canter-eval stop` 会停掉那个进程。eval 自己的测试 `stop_signals_only_the_pid_in_server_json` 正好说明了这点：`server.json` 里写的是一个普通 `sleep` 进程，它照样被 SIGTERM。canter 自己防 PID 回收的办法是 `Registration.instance`（注释写的是「Distinguishes a new daemon even if the OS reuses a PID」）加 `server.lock` 文件锁（`lifecycle.rs` 的 `server_running`：`try_lock_shared` 返回 WouldBlock 才算服务端在跑）。一轮要跑好几个小时，中间还有大量 `npm test`、`tsc` 子进程，PID 回收的概率不高，但这正是「PID 已经不是 canter 时会误停」。
- 改法：发信号前照 `server_running` 的做法探 `<eval home>/server.lock`：拿得到共享锁（没有服务端拿着锁），就报「server.json 已过时，没停任何进程」后退出；锁被占着才发 SIGTERM。愿意的话再经 socket 确认 `instance` 和 `server.json` 一致。测试改两条：锁被占着时停的是那个 PID；`server.json` 指向一个活着、但没拿锁的进程时不发信号、报错。

### 建议改

**3. 建议改｜eval 状态目录只拦「等于 canter 自己的状态目录」，没拦它的上级目录**（`eval/src/paths.rs` 的 `refuse_daily_state`）

`--eval-home ~` 或 `CANTER_EVAL_HOME=$HOME` 这种写错能通过检查：`prepare` 会清空 `~/memory/*` 和 `~/projects/*/memory/*`，把带 key 的配置写成 `~/config.json`，run 目录建在 `~/runs`。用户的 `~/.canter` 碰不到，但碰得到 eval 状态目录以外的东西。改法：也拒绝 `$HOME` 本身，拒绝 canter 状态目录的上级目录和它里面的目录；或者第一次用时写一个标记文件，以后清目录前先认这个标记。

**4. 建议改｜只拷模型那一段，日常配置里顶层的 `prices` 没带过去**（`eval/src/config.rs`）

canter 的价格表 = 内置价格 + 顶层 `prices` + 各模型自己的 `price`（`crates/canter-server/src/config.rs` 的 `options()`）。内置价格只有 `deepseek-flash` 和 `deepseek-v4-pro`。用户的配置是不是在顶层给 `opencode-go/deepseek-v4.1-flash` 定了价，**不知道**（按规矩没读 `~/.canter`）。要是定了，eval 里每次的花费都会是 `?`。改法：顶层 `prices` 里有 `<家>/<模型>` 这个键，就一起拷过去。

**5. 建议改｜源模型的 `supported_reasoning_efforts` 里没有题目要的档位时，工具会自己补进去**（`eval/src/config.rs` 的 `set_reasoning`）

源模型写了支持哪些档位、但没有 `high` 时，工具把 `high` 加进列表，canter 就会对接入方发一个这家可能不认的档位。等于工具替这一家改了模型能力，和「只拷那一段」不一致。改法：列表里有就设默认档位，没有就报错。源模型没写列表时，canter 的缺省是 `[none, low, high, max]`（`canter-protocol/src/types.rs:52`），照现在补缺省的做法不影响。

**6. 建议改｜`prepare` 中途失败会留下一个半截的 run，按提示的办法清不掉**（`eval/src/prepare.rs`）

run 目录建好、配置写好、记忆清掉之后，worktree 或 setup 失败的话 `state.json` 还没写，`canter-eval clean` 读不到它就报错；而 `prepare` 的报错让人「用 `canter-eval clean` 删掉」。另外 `clean` 只删 worktree，不删 run 目录，同一个 run 名清完以后也不能再 `prepare`。改法：`prepare` 失败时把自己建的 worktree 和 run 目录撤掉；或者至少把提示改成「换一个 run 名，或手动删掉 run 目录」。

### 可以不改

**7. 可以不改｜判分第 5 条只认写在一行里的提示**

在 `src/*.ts` 里按行找 `Remove "` 和 `"? [y/N]`。11-07 那次的写法 `Remove "${name}"? [y/N] ` 能过；字符串跨行拼，或者在双引号字符串里写成 `\"` 会判不过。按 P2-81 的原意够用。

**8. 可以不改｜`steer` 的 HTTP 20 秒超时**

服务端已经收下了，但回包超过 20 秒的话，工具会报错退出、不记 `steers.json`；重开时这一句会再发一次。实际上 input 接口是入队就返回，很难碰到。

### 四个重点的结论

1. **key 和本机数据**：没发现会漏。`config.json` 用 0600 写在 0700 目录里（`paths::write_private`）。`config::write` 先把源文件解析成通用 `Value`，报错只会是 JSON 语法错（行列号）或缺哪家、哪个模型（只带路径和名字），不会带值。`prepare` 打印的摘要里没有配置内容，测试也断言了。`result.json` 和 `checks.json` 只在 eval 状态目录里。结果表（`report.rs` 的 `render`）只写轮次、题、次、数字、没过的检查 id、记录项、会话 ID、模型名、canter 版本、时段，不写 `output_tail`，也不写路径。`long.toml` 只有仓库名和提交哈希。README 里的路径是 `/Users/you/...` 这类占位。
2. **删东西、停进程的范围**：清记忆只动 `<eval home>/memory/*` 和 `<eval home>/projects/*/memory/*`，和 canter 的布局一致（`crates/canter-tools/src/memory.rs:235-239`）。`projects/*` 那一层用 `file_type`（不跟软链接）；`remove_dir_all` 也不跟软链接。canter 自己的状态目录会先规范化路径再比较，拦得住（上级目录拦不住，见第 3 条）。`clean` 用的是 `git worktree remove`，git 不会删主工作区。`CANTER_HOME=<eval> canter serve --replace` 只换那个状态目录里的服务端：`discovery.rs` 的 `start_server` 先 `env_clear` 再设 `CANTER_HOME`，登录服务只覆盖 PATH 和 HOME，socket 和登记文件都在那个状态目录里。`stop` 有第 2 条的问题。
3. **一次跑干不干净、能不能重复**：配置里只有一家一个模型；压缩线写进模型的 `auto_compact_tokens`；思考档位写进 `default_reasoning_effort`，终端开新会话时不带档位（`canter-tui/src/run.rs:551` 是 `reasoning_effort: None`），用的就是服务端这个缺省。记忆每次准备时清空。worktree 是从 `8e19ca8` 检出的 detached 工作区，`node_modules` 拷进去，`dist` 删掉。插话数的是 `BASE..HEAD` 里主题以 `ritual: ` 开头的提交，数到 N 才发，发过的记进 `steers.json`，重开不重发；会话 ID 读的是 `--session-file` 写的 `sessionId`（`canter-tui/src/session_file.rs:76`）。会话正好空闲时插话会开一轮新的，不会被拒（`canter-core/src/session.rs` 里 `state.active` 为空那条路）。**但是**有第 1 条，按现在的布局跑出来的结果不能用。
4. **判分**：7 条和任务单逐条对得上，对着题目仓库的实际文件看过：`TODO.md` 是 `- [ ]` 格式，12 行；`package.json` 只有 `typescript` 一个 devDependency；`npm test` 是 `npm run build && node --test ...`，所以「最终测试条数」那个 `ℹ tests N` 行对得上；测试在 `tests/` 下，第 5 条只扫 `src`，测试里的字符串不会让它误判通过。第 2 条用 `rev-list --count` 加「没有一条主题不以 `ritual: ` 开头」，判的是「正好 12 个、都以 `ritual: ` 开头」。第 3 条取第 3～12 个提交最后一个非空行，和 `Task: i/12` 比。第 6 条比的是 dependencies 和 devDependencies。第 7 条只记数。没发现会把该过的判成不过、或把该不过的判成过（第 7 条那种写法上的个例除外）。护栏统计用的三条 warning 前缀和 `[Repeated call]`，在 `crates/canter-core/src/long_run.rs` 里原样都有。
