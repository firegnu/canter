### 建议改

1. **重放是平方级，大会话打开、列表都很慢**
   - 位置：`canter-protocol/src/reducer.rs` 的 `apply_event`；`canter-store/src/lib.rs` 的 `replay`、`SessionWriter::append`、`Store::list`。
   - 问题：`apply_event` 每条事件先复制整个快照，重放 n 条的代价约是 n × 快照大小。实测（每条增量 80 字节的命令输出）：5 万条、快照 4 MB，`open` 1.7 秒；20 万条、16 MB，24 秒；40 万条、32 MB，98 秒。`list` 对每个会话整条重放，和 `open` 一样慢，而 `GET /v1/info`、`GET /v1/sessions` 都要列表。一个字一条增量，一个用一整天的会话到几十万条不稀奇（推测）。终端客户端每收一条增量也要复制一次整个快照。
   - 改法：归并改成原地改，比如 `apply_event_mut(&mut SessionSnapshot, &Event) -> Result<()>`：先查完所有会报错的条件再动快照，报错时快照不变。`apply_event` 保留成「克隆 + 原地改」。存盘的 `replay` 用原地版；`append` 照旧先校验、写盘成功后再改内存。

2. **已知事件里出现新的枚举值，整条解析失败**
   - 位置：`types.rs` 的 `SessionStatus`、`TurnStatus`、`ItemStatus`、`PermissionMode`、`ApprovalDecision`、`ApprovalResolution`、`PatchChangeKind`、`UserInput`，以及 `ApprovalRequest`。
   - 问题：`#[serde(other)]` 只加在事件种类、项目种类、增量种类上。实测这些都让旧版本整条事件解析失败：`session.status` 带 `waiting_answer`（第二期提问框就要加）、`turn.started` 的输入里有图片、`request.opened` 多一种回答、`turn.completed` 多一种轮状态、`request.resolved` 多一种结果、新的权限模式。快照状态是 `waiting_answer` 时，`GET /v1/sessions/{id}` 的回复整个解析失败。待处理请求是没有种类字段的结构体，以后把提问请求（字段不同）放进 `pendingRequests`，旧客户端也是整个快照解析失败。存盘同样受影响：退回旧版 canter 后，用过新值的会话打不开。
   - 改法：这些枚举都加 `#[serde(other)] Unknown`（Codex `rust-v0.163.0` 也这么用，如 `account.rs` 的 `RateLimitResetCreditStatus`）。待处理请求把公共字段（`id`、`turnId`、`createdAt`）放外层，种类和内容放内层带 `type` 的枚举，内层加 `Unknown`，这样旧客户端还能按 id 移除。兼容测试补一条「已知事件里的未知枚举值」。

3. **`turn.completed` 整个替换一轮，和 Codex 的用法相反**
   - 位置：`reducer.rs` 的 `TurnCompleted` 分支（`*existing = turn.clone()`）；协议包 README「`turn.completed` 携带完整最终轮」。
   - 问题：Codex `rust-v0.163.0` 的 `turn/completed` 里 `items` 是空的，或只有最后一句（`app-server/src/bespoke_event_handling.rs` 的 `emit_turn_completed_with_status`，`TurnItemsView::NotLoaded` / `Summary`）。第 4 件要是照 Codex 发，这一轮的项目在快照里全没了：实测发一条 `items` 为空的 `turn.completed`，项目数从 1 变 0。要是照现在的约定发完整一轮，每轮全部内容（命令输出、diff）在存盘和事件流里多存一遍：增量一遍，`item.completed` 一遍，`turn.completed` 再一遍。
   - 改法：`turn.completed` 只更新状态、错误、用量，项目以 `item.*` 事件为准，README 跟着改。我建议这样改。不改的话，至少在协议包文档和第 4 件任务文件里写明「必须带全部项目」。

4. **第 4 件要「从存盘恢复后，模型收到的上下文和恢复前一样」，现在的项目装不下**
   - 位置：`types.rs` 的 `Item`。
   - 问题：Chat Completions 的上下文要有每次工具调用的 id、工具名、原样参数，以及回给模型的结果原文。现在这些都存不下：
     - 命令项目只有命令文字和完整输出，截断后给模型的那份不在。
     - 改文件只有 diff，edit 的旧段新段、write 的原参数都还原不出来。
     - 所有项目都没有调用 id。
     - 模型调了不存在的工具、或参数不是合法 JSON 时，没有项目种类可以记。
   - 改法：派第 3、4 件前二选一定下来：
     - (a) 工具类项目加 `callId`、原样 `arguments`、给模型的结果文字，另加一个通用的工具调用项目兜底；
     - (b) `canter-store` 另存一份不发给客户端的模型历史。Codex 就是这样：rollout 文件存模型层的条目，和 app-server 的通知分开。

     两种都是兼容的新增，但现在不定，第 4 件就得回头改第 1 件的两个包。

5. **第 5、6 件都要用、协议包还没定的约定**
   - 位置：`commands.rs`、协议包 README。
   - 问题：第 6 件对着假服务端做，第 5 件做真服务端，两边要用同一份约定，协议包里还缺：
     - HTTP 出错时的回复体，比如会话不存在、`turnId` 对不上、回答不在 `availableDecisions` 里。
     - SSE 帧的 `id:` 是不是序号，`Last-Event-ID` 和 `after` 谁优先，`event:` 写什么。
     - 送话排队时不发事件，所以 `SessionInputResponse.eventSeq` 指哪条不清楚，别的客户端也看不到排队的话。
   - 改法：加一个错误回复类型，比如 `{ code, message }`，`code` 用固定字符串；README 写明 SSE 帧格式；排队要么发一条事件（新增事件种类，兼容），要么写明 `eventSeq` 取当时的最后序号。

6. **存盘缺「从某个序号往后读事件」**
   - 位置：`canter-store/src/lib.rs`。
   - 问题：第 5 件「断线后从序号接着收」，以及服务端重启后续订，都要从盘上读第 N 条以后的事件。现在只有 `open`（给快照）和 `append`，服务端只能自己再解析一遍 JSONL，再写一遍跳过半行的逻辑。
   - 改法：加一个不拿写锁的读接口，比如 `Store::events_after(id, seq)`，和 `replay` 共用按行切、跳过半行的代码。

7. **每条事件刷一次盘，在 macOS 上是全盘刷写，约 4–5 毫秒**
   - 位置：`SessionWriter::append`。
   - 问题：Rust 标准库在 Apple 平台上把 `sync_data` 实现成 `fcntl(F_FULLFSYNC)`（工具链源码 `library/std/src/sys/fs/unix.rs` 的 `datasync`）。实测每条 4–5 毫秒，一个会话每秒最多写 200 多条。文字增量、命令输出都是一条一条写，`cargo build` 这类刷屏的输出会跟不上；几个会话同时写会互相拖慢（推测，没实测）。
   - 改法：加批量追加（几条事件一次写、一次刷盘），第 4、5 件把短时间内的增量合成一批。保持「回复成功的事件一定已落盘」，掉电后序号不会被重用，第 7 件重启续订靠的就是这一点。README 写明 `append` 会阻塞几毫秒，服务端要放到阻塞线程里调。

8. **列会话：一个坏会话，或一个名字不合规的目录，整个列表报错**（主控已记一半）
   - 位置：`Store::list`。
   - 问题：主控记的「一个会话坏了整个列表报错」，实测属实（`invalid stored JSON`）。另一个触发：根目录下任何名字不合会话 id 规则的子目录（实测用 `.tmp-backup`；`s1.bak` 这类也一样）都让 `self.session_dir(&id)?` 返回 `InvalidId`，整个列表失败。可非 UTF-8 的名字却是跳过的，两种处理不一致。
   - 改法：名字不合规的目录跳过；单个会话重放失败也跳过（或者在摘要里标成坏的），不让整个列表失败。

9. **建会话中途失败的残留**（主控已记）
   - 位置：`Store::create`、`Store::open`。
   - 问题：补充主控那条，实测有两种残留：
     - 只有空的 `events.jsonl`、没有 `private.json`：`open` 报找不到文件，`create` 报已存在，这个 id 卡死。
     - `private.json` 写好了、第一条事件没写进去：`open` 成功，拿到序号 0、模型为空字符串、状态 `starting` 的空快照，还能接着写，成了一个没有 `session.updated` 的会话。

     另外，第一条事件已落盘、最后同步目录失败时，`create` 报错，会话其实建成了，列表里看得到。
   - 改法：在根目录下用临时名字建好（私有配置和第一条事件都落盘），再改名成正式 id；失败就删掉临时目录。`open` 遇到没有任何已提交事件的会话，当作不存在。临时目录要靠第 8 条让列表跳过。

10. **批准边角用例的测试没测到要测的路径**
    - 位置：`canter-protocol/tests/approval.rs`。
    - 问题：测试把同一条事件（同一序号）归并两次，第二次在 `apply_event` 开头的序号去重就返回了，`RequestResolved` 分支根本没走到；把那个分支改坏，测试照样过。行为本身是对的：实测用新序号、不同回答再来一条 `request.resolved`，待处理请求不变，只推进序号和时间。
    - 改法：测试加一条新序号、不同回答的 `request.resolved`，断言除 `lastEventSeq`、`updatedAt` 外快照不变。

11. **工作目录给不给客户端，任务文件和需求单说得不一样**（主控定）
    - 位置：`SessionSettings`、`SessionSummary`、`Item::CommandExecution` 的 `cwd`。
    - 问题：需求单第 5 件只说「环境里的东西不进事件流」，任务文件把工作目录也划成不发给客户端。实现照任务文件做了，但命令项目按要求带 `cwd`，第一条命令就把会话的工作目录露出来了，藏起来得不到什么。反过来，第 7 件的 `--resume` 和会话列表要按当前目录挑会话、显示会话在哪个目录，以后接 corral 也要目录；现在的摘要里只有 id、名字、状态、时间、序号。
    - 改法：主控定工作目录是否公开。公开的话，放进公开设置，或放进快照和摘要；环境变量照旧只放 `private.json`。摘要里加首句预览也是兼容新增，可以等第 7 件。

### 可以不改

12. 快照不记已处理的请求：服务端重启后，迟到的回答拿不到原处理事件的序号，「本会话都允许」也无从还原。需要时在快照里加字段（兼容新增），留给第 3、5 件。
13. `snapshot.error` 只设不清，`willRetry: true` 的错误也一直留着。显示时以 `status` 为准即可。
14. 跨版本时，旧客户端经 `GET` 拿到的快照保留 `Item::Unknown` 占位，经事件归并的没有，两条路结果略有不同。同一版本内没有差别。
15. `private.json` 存的是客户端交来的全部环境变量，常常含令牌，一直留在盘上（0600）。只存必要的变量，还是续聊时让客户端重新交，第 5 件定。
16. `private.json` 解析失败时，serde_json 的错误信息在类型不对时会引用原字符串，可能带出变量值。只在文件格式变了时才会遇到；可以把这个错误换成不带内容的说明。
17. `append` 写进去了、刷盘失败时，事件可能已在盘上，重开后会出现，调用方不能直接重发同一件事。存盘 README 可以补一句。

### 建议改

1. **排队的话只能靠「开轮」移出队列**（这次新加的 `input.queued`）
   - 位置：`reducer.rs` 的 `TurnStarted` 分支；`EventPayload::TurnStarted.inputId`。
   - 问题：`queuedInputs` 只在 `turn.started.inputId` 等于某条的 id 时移出，一轮只能带一个 id。下面这些情况都会让排队的话一直留在快照里，所有客户端一直显示它在排队：
     - 打断后服务端丢掉队列；
     - 会话关闭；
     - 服务端重启后不再执行队列；
     - 排队的话后来插进了当前轮；
     - 几句排队的话合成一轮。

     另外，插话（steer）时回复的 `eventSeq`、`turnId` 指什么，README 没写。
   - 改法：加一条移出排队的事件，比如 `input.dequeued { inputId, reason }`，原因分开轮、插话、丢弃；或者把 `inputId` 改成 `inputIds`，另加丢弃事件。README 补上插话时的回复约定。新增事件种类是兼容的，也可以等第 4 件定排队语义时一起做，但要写进第 4 件的任务文件。

2. **建会话中途进程被杀或掉电，`.creating-*` 临时目录永远留着，里面有环境变量**
   - 位置：`Store::create_with_sync`。
   - 问题：失败时的清理靠 `TempDir` 的 drop，进程被杀或掉电时不会执行。残留目录的名字不合会话 id 规则，`list` 会跳过，也没有地方回收；里面的 `private.json` 是建会话时交来的全部环境变量，常含令牌。权限仍是 0700/0600，不算外泄，但会悄悄累积。出事的窗口只有几次刷盘的时间，很少碰到。
   - 改法：`Store::new` 或 `list` 顺手清理 `.creating-*`：能拿到其中 `events.jsonl` 的锁（说明没有进程正在建），就删掉。

3. **写明：重放出的 `PermissionMode::Unknown` 按「每次问」处理**
   - 位置：协议包 README「错误与 SSE」一节；第 3 件。
   - 问题：服务端自己不会写 Unknown。但退回旧版 canter 后，旧服务端重放新版写的 `session.updated`（带新的权限模式）会得到 `Unknown`。第 3 件的权限闸门要是用 `_ =>` 兜底放行，退回后这个会话就变成不问直接执行。
   - 改法：README 加一句「存盘重放出 Unknown 的权限模式按 alwaysAsk 处理」，第 3 件的任务文件照抄。

### 可以不改

4. 两个进程同时建同一个 id 时，输的一方报 `Directory not empty`（改名时撞上已经发布的目录），不是 `AlreadyExists`。服务端自己生成 id 就碰不到；要统一的话，把这个改名错误转成 `AlreadyExists`。
5. `Store::model_history::<T>` 任何一行解不成 `T` 就整个失败。第 4 件定条目类型时要能容忍以后新增的种类（用 `#[serde(other)]` 兜底，或者带版本），否则升级或退回后，这个会话的模型历史读不出来，接不着聊。
6. `events_after` 每次读整个文件，结果全放进内存；续传点很靠前时（比如从 0 开始）一次拿全部历史。第一期够用，量大了再改成迭代器。
7. 新增的 `readme_generation_command_uses_the_main_build_directory` 测的是 README 里的文字，价值不大，留着也无害。
