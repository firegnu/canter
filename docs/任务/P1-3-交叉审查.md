## 重点看

1. **权限闸门会不会放错**：该问的会不会没问就执行；批准时给人看的参数和真正执行的参数会不会不一致（准备和执行分两步）；「本会话都允许」的范围对不对；不认识的权限模式、不认识的回答。
2. **进程收不干净**：超时、取消、正常退出后，子进程、孙子进程有没有漏掉的；有没有办法让命令逃出进程组、留下孤儿（逃得掉的话，第一期能不能接受）。
3. **改文件出错**：edit 全改或全不改是不是真成立；write、edit 用临时文件再改名，会不会丢掉原文件的权限位、改坏符号链接、跨文件系统失败；准备之后文件被别人改了怎么办。
4. **隐私**：环境变量会不会进 Debug 输出、错误信息、回给模型的文字；起命令时是不是只带客户端交来的环境。
5. **够不够 P1-4 用**：照需求单第 4 件，流式输出、取消、批准、回给模型的文字和给客户端的 Item，接口有没有明显缺口。

### 必须改

**1. shell：有进程逃出进程组、又占着输出管道时，超时和取消都失效，工具不返回**

- 位置：`crates/canter-tools/src/shell.rs:97-129`（`capture` 的循环）；`src/executor.rs:22` 的注释。
- 问题：循环要等 stdout、stderr 都读到结尾才退出。shell 一退出（包括取消、超时后被杀），取消和超时两个分支的条件 `status.is_none()` 就不成立，这两个分支关掉了。命令里有进程换了进程组（`set -m` 之后起的命令、`setsid`、自己转后台但不关标准输出的程序，比如不带 `-l` 的 `pg_ctl start`、`ssh -f`），`killpg` 杀不到它，它又占着管道，循环就一直等到它退出为止；对常驻程序就是永远。取消也没用。到 P1-4，打断这一轮会卡住，会话一直停在 working，那个进程也留着。
- 试验（外面套 5 秒上限）：
  - `set -m; /bin/sleep 30 & echo $! > esc.pid; echo started`，正常退出：5 秒后还没返回；
  - 同样的命令后面再跟 `/bin/sleep 30`，500 ms 时取消：5 秒后还没返回；
  - 同上，`timeoutMs: 500`：5 秒后还没返回；
  - perl 里 `setsid()` 再 sleep，500 ms 时取消：5 秒后还没返回。
  - 对照：逃出的进程把输出重定向到 `/dev/null` 时，工具 7 ms 就返回，但那个进程还活着（见第 2 条）；同组的后台进程 `/bin/sleep 30 &` 在 shell 正常退出后被杀掉，和 README 一致。
- 改法：
  1. shell 退出（或被杀）之后，读管道只再等一个短的收尾时间，到时就丢掉读端返回，回给模型和客户端的文字里注明「有后台进程仍占着输出，已停止读取」。Codex `rust-v0.163.0` 的 `codex-rs/core/src/exec.rs` 就是这样做的（`IO_DRAIN_TIMEOUT_MS = 2000`）。
  2. 收尾期间取消和超时照样生效（Codex 同处注释：「Keep the original expiration active until draining finishes」）。
  3. 加测试：上面 `set -m` 的三种情形（正常退出、取消、超时）都在有限时间内返回；逃出的进程在测试里用写下的 PID 停掉。
  4. README 和 `CommandProcess::kill` 的注释改成实话：只杀原来那个进程组，换了进程组或会话的进程不在内（第 2 条）。

### 建议改

**2. 逃出进程组的进程会留下：第一期可以接受，但要写明**

- 位置：`crates/canter-tools/README.md`「shell」一段；`Tool::Shell` 的说明。
- 问题：第 1 条修好以后，工具能返回，但用 `set -m`、`setsid` 等换了进程组的进程还会留着。第一期没有系统沙箱，批准过的命令本来也能用 launchd、cron 等办法留下进程，进程组只能尽力清理，所以第一期可以接受。
- 改法：README 写明这个限制。第二期执行器拆成子进程时，Linux 可以用 `PR_SET_CHILD_SUBREAPER` 或 cgroup 收齐所有后代；macOS 没有对等办法，要靠沙箱。

**3. shell 的完整输出没有上限（要主控定）**

- 位置：`src/shell.rs:31`、`:118`、`:125`（`output` 一直往里加）。
- 问题：`yes`、`cat` 大日志、`find /` 这类命令在默认 120 秒里能产出几个 GB，全攒在服务端内存里，每一块还会变成 `item.delta` 事件写盘，服务端可能被撑死。Codex 同处给客户端的聚合输出上限 1 MiB（`EXEC_OUTPUT_MAX_BYTES`），增量事件每次调用最多 10000 条。
- 改法：给客户端的完整输出也设上限（比如头尾各留几 MiB、中间注明省略多少），增量到上限后不再发。这和原任务「给客户端显示的是完整输出」冲突，做的人照任务做没有错，要主控定（需要的话问用户），最好在 P1-4 开工前定。

**4. write 新建的文件权限是 0600**

- 位置：`src/executor.rs:120-123`。
- 问题：`NamedTempFile` 建的临时文件是 0600，原文件不存在时没有改权限，改名后新文件就是 0600。试验：write 新建的 `new.txt` 是 600，同目录用 `std::fs::write` 建的是 644。已有文件的权限位能保住（0755 的脚本 edit 后还是 755）。新文件给 web 服务、Docker 镜像（COPY 保留 0600，非 root 用户读不了）或别的用户用时会出问题。
- 改法：新文件用 `tempfile::Builder::new().permissions(Permissions::from_mode(0o666))` 建临时文件（受 umask 约束，和平常新建的文件一样）；加一条测试。

**5. 悬空的符号链接被换成普通文件；只读文件照样被改**

- 位置：`src/executor.rs:100-104`、`:130`。
- 问题：
  - 路径是一个指向不存在目标的符号链接时，`canonicalize` 失败后退回原路径，改名把链接本身换成了普通文件，批准时显示的是「新建」。试验：`dangling.txt -> missing/target.txt`，write 之后 `dangling.txt` 不再是链接，目标也没建。正常的符号链接没问题：试验 edit `link.txt -> real.txt`，链接还在，`real.txt` 改了。
  - 0444 的只读文件，改名不检查文件本身能不能写，照样改掉。试验：内容变了，权限还是 444。用 `>` 或普通编辑器写会报权限错误。在 askForExecution、allowAll 下，这是不问人就改了用户特意设成只读的文件。
- 改法：悬空链接报错（「路径是指向不存在目标的符号链接」），或者按链接目标新建；已有文件不可写时报错。各加一条测试。

**6. 批准请求里看不出实际要改哪个文件**

- 位置：`src/lib.rs:231-233`（批准参数只多加了 `diff`）。
- 问题：path 是符号链接或带 `..` 时，批准框里只有模型给的路径，比如 `notes`；实际改的是链接指向的 `~/.zshrc`。diff 内容是对的，路径看不出来。
- 改法：准备阶段算出实际路径（解析符号链接后的绝对路径），和模型给的不同时，在批准参数里另加一项（比如 `resolvedPath`），客户端显示出来。

**7. read 不问人就能读 canter 自己的私有文件，环境变量能经此进事件和模型（要主控定）**

- 位置：`src/permission.rs:42`（读在任何模式下都不问）；要和 P1-5 一起定。
- 问题：会话的环境变量存在会话目录的 `private.json`（0600，`serde_json::to_writer` 写的单行 JSON，read 能读）。任何权限模式下，包括 alwaysAsk，模型都能不经批准 read 它，内容会进 `fileRead` 项目（事件流、所有客户端、`events.jsonl`）和回给模型的文字。P1-5 的配置文件（DeepSeek key）也一样。这绕开了 DESIGN 第 8 条「环境变量不公开，只存私有文件」。原任务定的是「读不问」，所以不算没做到；但仓库里的文件只要带一段提示注入，就能让模型去读。
- 改法：服务端建执行器时交给它一份受保护的路径（canter 的状态目录、配置文件），read、write、edit 碰到就拒绝；或者 alwaysAsk 下读工作目录以外的文件也要问。最好在第 4、5 件开工前定。

**8. P1-4 要用的接口还有缺口**

- 位置：`src/lib.rs:166-185`（`PreparedCall`）、`:343-348`（`execute`）、`:528-566`（`tool_error`）。
- 问题：
  1. 没有对外给出「进行中」的项目和「被拒绝」的结果。协议有 `ItemStatus::InProgress`、`Declined`；P1-4 要先发 `item.started`，被拒绝后发状态为 `declined` 的 `item.completed`。但 `PreparedCall` 不给出 `FileUpdateChange`（新建还是修改、diff），`tool_error` 是私有的，P1-4 只能从 `approval_arguments()` 倒推，新建还是修改拿不到。
  2. 失败的项目信息不全：shell 准备失败时项目的 `cwd` 是空字符串；write、edit 失败时 `changes` 是空的，连路径都没有（包括执行时发现文件被改了的情况，批准过的 diff 也没了）；read 失败把错误文字放进 `content`，客户端会当成文件内容显示。
  3. 执行不要求先过闸门：`Tools::execute` 收任何 `PreparedCall`，会不会没问就执行，全靠 P1-4 自己守规矩。一个会话准备的调用也能交给另一个会话的 `Tools` 执行，相对路径换了解析目录，和批准时看到的 diff 对不上。
- 改法：
  1. 给 `PreparedCall` 加 `started_item()` 和 `declined_output()`（回给模型的文字加 `Declined` 项目），P1-4 直接用；
  2. 失败项目带上 cwd、path 和已经算好的 diff；read 失败时 `content` 留空，错误只进回给模型的文字（要在协议里另加字段的话得改 `canter-protocol`，交主控）；
  3. 闸门放行时给一个只有闸门能造的许可（比如 `PermissionCheck::Execute` 里带上 call），`execute` 只收许可；`PreparedCall` 记下是哪个执行器准备的，交错了就报错。
  这几处在 P1-4 开工前改最省事。

**9. write、edit 回给模型的 diff 没有上限；diff 在运行时线程上同步算，取消打断不了**

- 位置：`src/lib.rs:398`（`Wrote {path}.\n{diff}`）、`:506`（`TextDiff::from_lines`）。
- 问题：试验：把一个文件整个改写，2 万行（377 KiB）时 `prepare` 要 1 秒，5 万行（960 KiB）要 6.7 秒（release 构建，增长接近平方）。这段时间占住一个 tokio 工作线程，取消也打断不了。5 万行时 diff 有 2 MB，原样进批准请求、回给模型的文字和事件。模型刚写的内容又整份回给它，白占上下文，大文件能直接撑爆上下文。
- 改法：diff 放进 `spawn_blocking`，用 `similar` 的 `TextDiff::configure().timeout(...)` 限时；回给模型的文字只写摘要（新建还是修改、增删几行，edit 可以带一段有长度上限的 diff）；客户端那份 diff 和第 3 条一起定上限。

**10. 取消时直接 SIGKILL，不给命令清理的机会**

- 位置：`src/executor.rs:179`。
- 问题：git 被 SIGKILL 会留下 `.git/index.lock`，下一条 git 命令报「另一个 git 进程在跑」；cargo、npm 也有各自的锁文件。Codex `rust-v0.163.0` 在取消时先给进程组发 SIGTERM，宽限 50 ms 再 SIGKILL；超时则直接 SIGKILL（`core/src/exec.rs`，`CANCELLATION_TERMINATION_GRACE_PERIOD`）。
- 改法：取消时先发 SIGTERM，短暂等待后再 SIGKILL；超时可以维持现状。现有测试照样查子进程和孙子进程。

**11. 细节**

- `src/shell.rs:46`：回给模型的退出信息是 Rust 调试格式：正常是 `Exit code: Some(0)`，被信号杀掉是 `Exit code: None`。改成 `Exit code: 0`、`Killed by signal 9` 这类。
- `src/lib.rs:69`：shell 的工具说明没写默认超时 120 秒、上限 600 秒，也没写命令结束时同组的后台进程会被杀掉。不写的话，模型会先 `npm run dev &`，下一次调用再去 curl。写进说明。
- `src/lib.rs:425-484`：read 的起始行超过文件末尾时返回空文字，没有说文件一共几行。
- 根目录依赖表里 `tokio-util` 开了 `rt` 特性，本包用不上（`CancellationToken` 不需要特性）。P1-2 也用不上的话可以去掉，主控合并依赖表时顺手处理。

### 可以不改

**12. 原子替换的副作用**：改名会断开硬链接（试验：edit `a.txt` 后，硬链接 `b.txt` 还是旧内容），也会丢掉扩展属性、ACL，别人的文件改完会变成自己的。用临时文件加改名的编辑器都是这样，第一期可以接受，README 记一句就行。另外改名前没有 `sync_all`，断电时可能留下空文件；要更稳可以加。

**13. 「本会话都允许」的范围**：按会话和工具记，只在内存里，不跨会话，服务端重启后不保留，和主控定的一致，测试也覆盖了。要注意两点：对 shell 来说，它等于这个会话里所有命令都放行；用户之后把权限模式改回 alwaysAsk，已经给过的允许照样有效。P1-7 的批准框和 README 要把这两点写清楚。

**14. 参数里键名重复**：`{"command":"echo shown","command":"echo ran > dup.out"}` 解析后取后一个，批准框显示的和实际执行的都是后一个，两边一致。原样字符串里两个都在，客户端只要显示 `arguments`、不显示原样字符串，就不会被误导。

### 查过、没发现问题的

- 闸门：不认识的权限模式按 alwaysAsk；不认识的回答返回 `invalid_decision`；风险档来自内置的工具定义，模型改不了。
- 准备和执行：`PreparedCall` 的字段都是私有的，批准和执行用的是同一份；准备阶段不写文件、不起命令。执行前核对原文件没变：试验在准备之后改了文件，执行报「file changed since preparation」，文件保持用户改的内容。
- edit 全改或全不改成立；找不到、多处匹配、互相重叠都在准备阶段报错，而且指明是第几处。
- 临时文件建在目标文件（解析符号链接之后）的同一目录，不会跨文件系统；正常的符号链接保留；已有文件的权限位保留。
- 环境变量：先 `env_clear` 再只装客户端交来的环境（测试也查了 `CARGO_MANIFEST_DIR` 没混进来）；执行器、调用、命令句柄都没有实现 Debug；错误信息里没有环境变量。
- 进程：普通的子进程、孙子进程在超时、取消、正常退出后都被清干净（原测试，加上试验里同组的后台进程）。
- 给 P1-4：`prepare`、`execute` 返回的 future 可以交给 `tokio::spawn`（试验）；流式回调的合流顺序和跨块 UTF-8 解码都正确。
- read 一个没人写的 FIFO 会卡在打开文件那一步，但取消能马上返回；后台线程要等到有人写才结束，可以不管。
