## 要做的

1. **5090**：`ssh -R` 隧道做成 systemd 用户服务（`~/.config/systemd/user/`），`Restart=always`，带 `ExitOnForwardFailure`、`ServerAliveInterval`；用户没登录时也要跑（`loginctl enable-linger`，要不要开问用户）。5090 去中转机经代理（v2rayN / sing-box），代理没起来时服务要能等着重试，不刷爆日志。
2. **Mac**：`ssh -L` 隧道做成 launchd 用户代理（`~/Library/LaunchAgents/`），`KeepAlive`、登录时起；睡眠醒来、换网络、Shadowrocket 换节点后能自己连回去。
3. **中转机上旧转发占着端口**：5090 断线重连时，中转机上旧的 `-R` 可能还没超时，新的会因端口被占失败。看要不要在中转机 sshd 上设 `ClientAliveInterval` / `ClientAliveCountMax` 让旧连接早点断（改 VPS 配置先问用户），或者靠重试等它超时。
4. **`docs/remote.md`**：补一节「让隧道一直开着」，给 systemd 和 launchd 的示例，主机名、端口用占位（`gcp-relay`、`server.example.com`、`127.0.0.1`），不写真实 IP、用户名。
5. **验收时试**：重启 Mac 的 launchd 代理、断开再恢复代理、Mac 睡眠再醒、5090 上 `systemctl --user restart`，每种情况下多久能重新连上，`canter --server 5090` 的会话是否自己续上。

## 实际碰到：11-18 断线后 5090 的隧道几分钟挂不上（只记录，不开发）

来源：rein 主控转来，原文在 rein 仓库 `docs/canter需求.md` 第 1 条。用户 11-18：「只是写，不要让他开发」「把信息给canter主控，让他先更新一下对应的任务文件即可」。

- **现象**：11-18 约 17:53（北京时间），Mac 的 `local.canter-tunnel.5090` 和 5090 的 `canter-relay-tunnel.service` 几乎同时断。
  - Mac：那条进程还在但不通，本机 8791 上堆着一串 CLOSE_WAIT；`canter --server 5090` 报 `Server '5090' did not respond`。
  - 5090：`ssh -R` 退出后由 systemd 每十几秒重启一次，连续 34 次都报 `Error: remote port forwarding failed for listen port 8790`，18:00:21 那次才挂上，之后正常。`canter-server.service` 全程正常，没重启。
- **中转机日志**（`journalctl -u ssh`）：sshd 主进程一直在跑；5090 每次重连都登录成功（`Accepted publickey`），但转发挂不上（默认日志级别不记这条）；占着 8790 的旧连接，日志里没有任何超时断开或关闭的记录。
- **没查清的**：`canter-relay.conf` 的 `ClientAliveInterval 15`／`ClientAliveCountMax 3` 已生效，按理死连接 45 秒左右就该清掉，实际占了六七分钟。推测：旧连接经代理成了半死状态，代理那头替它应答，存活检测判断不出来。要查清得把中转机 sshd 日志级别调高，等下一次再断。
- **影响**：这几分钟里 Mac 终端和 rein 都用不了 5090；rein 显示 `Reconnecting`，恢复后自动连回，表现正确。
- 和上面第 5 条表里「断代理 / 换节点」「中转机上旧 `-R` 占端口」两项有关；这次算碰到了一次，但不是有意测的，表里先不改。
