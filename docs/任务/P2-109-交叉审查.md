### 意见

1. **必须改**：预算收尾的总结请求把工具定义整个去掉，请求前缀因此变了
   - 位置：`crates/canter-core/src/runner.rs:231`（`request.tools.clear()`）。测试在 `crates/canter-server/src/goal_tests.rs:336` 和 `:811` 断言总结请求里没有 `tools`。
   - 已查证：
     - 每个用完预算的目标都会发这一次请求，正常使用一定会碰到。
     - 请求开头的工具定义和前面每一轮都不一样了，违反 DESIGN 第 17 条「发给模型的内容只往后加，前面不改」。DESIGN 新写的目标续跑规矩没有把它列成例外，那里写的是「不执行新工具」，不是不带工具定义。
     - 旁路问答已经有现成做法：`btw.rs:227` 写着「Definitions stay in the prefix; side requests never execute tools」。完成记录自己也写了「工具定义固定放在会话前缀」。
   - 推测（没用真接口验证）：
     - DeepSeek 把工具说明放在对话消息前面拼进提示，去掉工具后整段历史都按没命中缓存计价。
     - 按 canter 自己的价格表（`crates/canter-core/src/usage.rs:27-28`），v4-pro 高峰时段命中 $0.044/M、没命中 $1.32/M，差 30 倍；flash 差 50 倍。
     - 上下文 50 万 token 时，这一次请求约 $0.66（命中缓存约 $0.02）。默认 $5 预算到 90% 时只剩 $0.50，所以会明显超预算，不只是 DESIGN 说的「略超」。
   - 未知：请求历史里有 `tool_calls` 和工具结果、请求本身却不带 `tools` 时，DeepSeek 会不会拒绝。如果拒绝，真用的时候收尾总结会一直失败。目标照样会停，但「让模型收尾」就落空了。
   - 改法：
     - 删掉 `request.tools.clear()`，保留 `max_retries = Some(0)`。
     - 不用担心工具被执行：总结分支（`runner.rs:309-319`）已经把这次返回的工具调用都补成「Not run」并结束本轮。
     - 两处测试改成：总结请求的 `tools` 和上一次请求相同，写文件的工具没有执行。
     - 想让模型更确定只写文字，可以另加 `tool_choice: "none"`。它会不会影响缓存也是推测，要加的话先在用户在场时真调一次确认。

2. **建议改**：没回用量的请求按 0 记进目标，不标「未知」
   - 位置：`runner.rs:513`。`model_response` 只在收到 usage 时调 `record_usage`；`compaction.rs`、`btw.rs` 也是这样。
   - 问题：请求结束了却没回 usage 时，目标花费按 0 记，也不标未知。比如流中途断开后重试的那次尝试，或者供应商不回 usage。任务要求「算不出价钱的时候宁可早停」。
   - 影响：DeepSeek 正常请求都会回 usage，所以只有断流重试时少算，不会因此一直跑下去。这个缺口是沿用现有会话花费统计带来的，不是本件新加的。
   - 改法，二选一，交主控定：
     - (a) 一次计进目标的请求尝试，已经收到模型输出、不是用户打断、却没有 usage 时，把目标的 `cost.unknown` 标上，目标随即进入收尾。注意用户 Esc 的情况不能算进去，否则恢复后会立刻进入收尾。
     - (b) 不改代码，在 DESIGN 目标续跑那条写明「没回用量的请求不计入」。

3. **可以不改**：每次打开会话都再补一条目标说明
   - 位置：`crates/canter-core/src/session.rs:452`。
   - 已查证：服务端每次启动后第一次打开某个会话，只要它有目标、或者以前有过目标说明，就往历史里再追加一条目标说明（清除过目标的会话追加「[Goal cleared]」），不看和上一条是不是一样。
   - 历史本来就从 journal 恢复，说明不会丢，这条是重复的。它只往后加，不破坏缓存，只多几十个 token。
   - 要改的话：打开会话时，只在最后一条目标说明和当前状态不一致时才补。

4. **可以不改**：看不出目标停了还是在跑
   - 服务端重启后，或者模型请求最终失败后，目标状态仍是 `active`，但已经不会自己续跑。状态栏 `goal $x/$5` 和 `/goal` 的显示和正在跑时一样。
   - 失败时对话里有报错，DESIGN 也写了要用户发消息或 resume 才会接着跑。
   - 以后做 GPUI 或网页客户端时，可以考虑在协议里给出「是否在续跑」。

5. **可以不改**：设目标请求还没返回时按 Esc，可能丢掉这次 Esc
   - 位置：`crates/canter-tui/src/app.rs:4362`。
   - `/goal <目标>` 或 `/goal resume` 的请求还没返回时按 Esc，终端只记下「请求回来后暂停」，不打断屏幕上正在跑的那一轮。
   - 这次请求要是失败了，这个 Esc 就丢了。中间只隔一次 HTTP 往返，很少碰到。

### 重点看的五项逐条核对

1. **该停就停**：没找到停不下来、一直花钱的路径。
   - 完成、卡住、预算用完、暂停、Esc 都会把 `goal_running` 设成 false，并清掉 `goal_deadline`（`goal.rs:134-137`、`session.rs:822-831`）。
   - 只有三个地方能把 `goal_running` 重新设成 true：状态为 active 时用户发消息、设目标、resume。
   - 请求最终失败时，`runner.rs:185-189` 不再排下一轮。
   - P2-101 叫醒轮结束后只走 `schedule_goal`，不会把已经停下的目标重新拉起来。
2. **钱算对**：除第 1、2 条外没发现问题。
   - 发模型请求的只有三个地方：正常对话、压缩、旁路问答。三处都在请求开始时用 `charge_goal` 定下这次记到哪个目标。用量回来后加进目标，再检查 90% 和未知金额。
   - 暂停时 `charge_goal` 为空，不计费。
   - 收尾请求带 `max_retries = 0`，也不会触发自动压缩。
3. **存盘和兼容**：没问题。
   - 快照里的 `goal` 可以没有；旧客户端把新事件读成 `Unknown`。
   - 服务端重启后 `goal_running` 初始为 false，不会自动续跑。
   - 目标说明的补法沿用计划模式的 `flush_plan_mode_notices`：有工具调用还没配上结果时会往后推，不会插在调用和结果之间。
   - 压缩时目标说明不进摘要原文，压缩完再补回。
4. **没人时提问**：没问题。
   - 只有 `start_goal` 开的轮会设 `goal_continuation`，也只有这些轮的提问有 5 分钟超时。用户消息开的轮照旧一直等，批准框不变。
   - 超时和用户回答在同一把锁下判断，晚到的回答不会被算两次。
5. **并发**：不会两轮同时跑。
   - 开新轮的四个地方（`next_goal`、`set_goal`、resume、`input`）都在同一把锁下先确认 `active.is_none()`。
   - Esc 正好落在两轮之间时，终端收到 `TurnMismatch`、或者看不到正在跑的轮，就改发 pause，有测试覆盖。
   - 设目标请求还没返回时按 Esc 的情况见第 5 条。
