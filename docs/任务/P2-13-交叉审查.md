## 审查意见

2026-10-26，canter/review-fetch。

结论：**改完再合并**。必须改 1 条，建议改 4 条，可以不改 4 条。权限、跳转、数据外带、超时、取消、下载上限、兼容都按任务书做到了；问题出在 HTML 转换：一个十几 KB 的网页就能让服务端进程崩溃。

### 必须改

1. **深层嵌套的 HTML 让服务端整个进程栈溢出崩溃**
   - 位置：`crates/canter-tools/src/web_fetch.rs:159`（`spawn_blocking` 里调 htmd）。根因是 htmd 0.5.6 的 `dom_walker.rs` 里 `walk_node` / `walk_children` 互相递归，tokio 阻塞线程默认 2 MiB 栈（markup5ever_rcdom 的释放是迭代的，不是它）。
   - 复现：本机 HTTP 服务回 `text/html`，正文 `"<div>".repeat(3000)`（约 15 KB），全都允许模式下调一次 `web_fetch`。release 编译下测试进程报 `thread 'tokio-rt-worker' has overflowed its stack`，SIGABRT 退出；2000 层不崩；debug 编译 1000 层就崩。放到服务端就是 `canter serve` 整个退出，所有会话在跑的轮都断。询问模式也挡不住：用户批准的是网址，页面内容由对方决定。
   - 为什么算必须改：违反「怎么算做完」里的「作为工具错误回给模型、这一轮继续」，也是「调用卡住这一轮」这类要害上的真实缺陷，而且比卡住更重。
   - 改法：转换前先限嵌套深度，超了就不转换，作为工具错误回给模型（或者退回纯文本，由开发者定）。htmd 公开了 `html_to_tree` / `tree_to_markdown`，但 html5ever 解析超深嵌套本身就是平方级的（见建议改 1），所以检查要放在解析之前：对原文做一遍线性扫描粗算深度（只数非空元素的开始和结束标签），上限取几百到一千，按实测栈用量留余量。另开一个指定栈大小的线程跑转换可以作为第二道保险，但不能只靠加大栈。补回归测试：几千层和接近 5 MiB 的深嵌套页面都回工具错误、这一轮继续、进程不崩。

### 建议改

1. **构造过的 HTML 在超时或 Esc 之后还长时间占满一个 CPU 核**
   - 位置：同上 `web_fetch.rs:159`；`crates/canter-tools/README.md:234` 写的「已开始的有界转换会自行结束」与实际不符。
   - 实测（release）：100 万层 `<div>`（约 5 MB，在下载上限内）时，这一轮在 30 秒准时超时结束、继续往下走，但后台解析 100% 占着一个核跑了近 10 分钟还没完（是我自己起的测试进程，按 PID 停掉了）；10 万层时解析约 16 秒后栈溢出崩溃。单个标签带大量属性时，html5ever 查重复属性是逐个比对：5 万、10 万、20 万个属性分别要 1.8、8.5、22.8 秒，按平方推到 5 MiB 约 4 分钟。阻塞线程停不下来，模型反复调用还会叠加。5 MiB 的普通 HTML 实测只要 0.18 秒，正常页面不受影响。这一轮本身不卡，所以算建议改。
   - 改法：在必须改 1 的扫描里顺带限制单个标签的长度或属性个数，超了同样不转换；README 那句改成实际的边界。

2. **批准框显示的是模型给的原字符串，不是实际请求的网址；授权范围也没写是哪个主机**
   - 位置：`crates/canter-tui/src/approval.rs:88`（`json_body` 原样显示参数）、`approval.rs:227`（`session_note` 只写 this host and port）；`crates/canter-tools/src/lib.rs:253` 和 execute 里 `Item::WebFetch.url` 用的也是原字符串。
   - 实测：模型给 `http://127.0.0.1:<端口>\@good.example/`，批准框显示的就是这串，看着像 good.example；实际请求发到 127.0.0.1，路径是 `/@good.example/`；选「本会话都允许」后放行的是 127.0.0.1:<端口>。同类情况：国际化域名显示原 Unicode，实际请求的是 punycode（形近字骗人）；网址里的 tab、换行会被解析器删掉。授权判断本身是准的（整数和十六进制 IP、大小写都规范到同一个主机），问题只在用户看到的和实际请求的不一致。网页里的提示注入可以借这一点骗用户选「本会话都允许」。
   - 改法：照 `resolvedPath` 的先例，规范化后和原串不同时，在批准参数里加上实际网址（比如 `resolvedUrl`，取 `Url::as_str()`），批准框和项目显示它；`session_note` 写出具体的「主机:端口」。也可以直接拒收含 `\`、空白或控制字符的网址。

3. **服务器不理会 `Accept-Encoding: identity`、照样回压缩正文时，压缩字节会当成文字交给模型**
   - 位置：`web_fetch.rs:88`、`:155`。reqwest 没开 gzip 等特性，不会解压。带 `Content-Encoding: gzip` 的 `text/html` 会被宽松解码成文字后送进 htmd，模型拿到最多 32 KiB 乱码。
   - 改法：响应带非 identity 的 `Content-Encoding` 时，回一行占位说明或工具错误，不交正文。

4. **只按 UTF-8 解码，不看 charset**
   - 位置：`web_fetch.rs:155`；README 第 226 行已写明。GBK/GB2312、Shift_JIS、latin-1 的页面会变成满屏替换符，中文老站点很常见。
   - 改法：按 `Content-Type` 的 charset（以及 HTML 的 meta charset）转码要用 encoding_rs（reqwest 的 `charset` 特性也是引它），属于新依赖，要用户定，可以另开一件。不加依赖的话，至少在结果里注明「按 UTF-8 解码，声明的编码是 xxx」，让模型知道内容可能是乱码。

### 可以不改

1. 「本会话都允许」不区分 http 和 https：`http://h:443` 的授权也覆盖 `https://h`，反过来一样；实测同主机、同端口换成 https 不会再问。这符合任务书说的「域名（含端口）」，同一个端口同时跑两种协议也很少见。
2. 主机名末尾带点（`localhost.`）算另一个主机、会再问，比要求更严，不用改。按主机名放行之后，DNS 可以改指本机或内网地址（DNS rebinding）；这和「本机、内网不另外拦」一致，可以在 README 补一句。
3. 审查轮里从闸门拒绝的那条路（`crates/canter-core/src/runner.rs:554`），webFetch 项目的 `result` 是空串；参数错误那条路的 `result` 是 `review is read-only`。只影响显示是否一致。
4. 连接失败、DNS 失败、证书错误都回同一句 `connection or TLS error`，模型分不清是证书问题还是域名不存在。可以带上 reqwest 的错误种类（不含敏感信息）。
