### 已查证、没有问题的地方

1. **订阅追赶不漏不重**（读代码加测试）。
   - `read_after` 的位置只推进到 seq ≤ through 的最后一条完整行。半行不推进。校验出错时 `?` 提前返回，`stamp`、`offset`、`seq` 都不改。`catch_up` 把 reader 克隆一份交给阻塞线程，成功后才把新 reader 和事件一起装回；future 被丢掉时旧位置原样保留，`cancelling_a_disk_read_does_not_advance_the_subscription` 覆盖了这种情况。
   - `committed` 在写盘并同步之后才更新，through 又在取文件标识之前读，所以位置不会超过当次的文件长度，`stamp.len < offset` 只会出现在截短时。退回从头读有四个条件：换了 inode、长度短于位置、长度没增加但标识变了、游标或 through 倒退。canter 自己会造成的情况都覆盖了，`truncate_tail` 只截掉不完整的尾行，碰不到位置之前的字节。
   - `recv` 的三条路径：只有 `pending` 为空时才会走到 Lagged 或 Closed；跳号只会出在广播上，从盘上补的事件是连续的、从 cursor+1 开始；`committed` 比广播先更新。新旧两种读法都返回 (cursor, through] 区间里的连续事件，逐条一样。
   - `read_jsonl_from` 先 `seek` 的问题：调用方 `open`、`list`、`events_after`、`model_history`、`read_after` 用的都是刚打开的句柄，seek(0) 和原来一样。写端是 O_APPEND，`truncate_tail` 用的是 `set_len`，都不靠读位置。`committed_bytes` 改成先累加再 visit，出错时返回值没人用，`open` 拿到的已提交长度和原来一样。
2. **摘要缓存不显示旧的**（读代码加测试）。
   - 文件标识在重放之前取，用的是同一个文件句柄的 `fstat`，重放期间有追加，下次长度一定不同。同长度改写靠 ctime 发现（测试覆盖了 mtime 被改回去的情况）。删掉的目录由 `retain` 清出缓存。坏会话缓存成「不列」，临时读错不缓存。跳过规则和排序和原来一字不差，`SessionSummary` 只取快照里的字段。
   - 每次 list 都重新 stat 全部文件，就算哪次补算没赶上旧服务端最后写的事件，下一次也会自己好，不会一直显示旧的。
   - 缓存锁只有 `list` 用。调用方有 `/v1/info`、`/v1/usage`、`/v1/stats`（`stats::list`），都在 `spawn_blocking` 里。会话写入、订阅、登记表锁都不碰它。
3. **启动预热**（读代码加测试）。
   - 预热和 `Lease::acquire` 并行，没有串到等锁之后。`replace.json` 在拿锁的任务里马上写出，不等预热；`replacement_warms_before_the_old_lock_is_released_and_refreshes_afterward` 用闸门挡住预热验证过这一点。

### 建议改 1：期限账的预热数字低估约 8 倍；普通启动时预热和 MCP 初始化串着跑

- **位置**：完成记录「返工 1」里的期限复核；`crates/canter-server/src/history_read_tests.rs:189-190`（生成器每条都是 900 个 `x` 的 warning）、`:359-374`（release 断言）；`crates/canter-server/src/startup.rs:52-66` 和 `crates/canter-server/src/lib.rs:77-96`（`initialize` 全部做完才开始 `LiveConfig::connect`）；`docs/DESIGN.md:412`（新进程的启动链路里没有这一步）。
- **问题**：
  - 已查证：同样约 800 MiB，按轮造的历史首次预热 5.5–5.7 秒，一个 52 MB 会话变了以后补算 0.34 秒；warning 造法在本机是 0.65–0.71 秒（完成记录里是 0.43 秒）。差别在每条事件的解析和重放开销：warning 每条接近 1 KB、全是 ASCII，也不用查找 turn 和 item。
  - 已查证：不带 `--replace` 的普通启动，拿锁马上就成，预热没有能重叠的等待；`initialize` 返回以后才初始化 MCP。所以新进程的耗时是「预热 + MCP（缺省最多 10 秒）」两段相加。
  - 推算：按 5.6 秒代入完成记录的算法，普通启动是 `max(2, 5.6) + 10 + 0.05 + 2 = 17.65 秒`，超过 15 秒；就绪探测实际只要几毫秒，这样算也有约 15.65 秒。替换按「全部会话都变了」算是 `90 + 5.6 + 12.05 = 107.65 秒`，超过 105 秒。按主控 11-01 量的用户真实历史速度（237 MB 约 0.9 秒）线性外推，800 MB 约 3 秒，两条分别是 15.05 秒和 105.05 秒，也都刚好超一点。把 release 基准换成按轮造的历史，三条断言里第一条和第三条会失败。
  - 实际影响（推测，没有起服务端实测）：历史到 800 MB 量级、同时 MCP 初始化接近 10 秒缺省超时，才会出事。第一个客户端会报 `timed out waiting for the server to start`，但服务端随后照样起来，下一次就能连上。替换要碰到 105 秒，得等锁期间有几百 MB 的长会话都在写；平时只有旧服务端里打开着的会话会变。这不是比 main 退步：同样的历史在 main 上，第一次 `/v1/info` 冷读要 3～5.6 秒，每次启动都会被 2 秒探活判失败。用户现在 237 MB，预热约 0.9 秒，各项期限都还有余量。

  1. 把拿锁后的补算（普通启动时就是首次预热）和 `LiveConfig::connect` 并行，在监听、发布登记之前等它做完。这样普通启动变成 `max(预热, MCP) + 0.05 + 探活`，替换变成 `等锁 + max(补算, MCP) + 0.05 + 探活`；预热在 10 秒以内都不增加期限。
  2. 基准生成器改成按轮造（turn、item、增量），按新数字重写完成记录的期限复核和 release 断言。
  3. DESIGN 第 412 行的新进程链路补上「预热 / 补算会话摘要」这一步，写清它在账里排在哪里。
  - 主控如果认为「800 MB 加上慢 MCP」可以先不管，至少做第 2、3 条，不要让文档和断言留着按 warning 算出来的余量。

### 建议改 2：拿锁失败时要等预热做完才退出

### 可以不改 1：摘要缓存锁中毒以后一直失败

- **位置**：`crates/canter-store/src/lib.rs:232`，`lock().expect("summary cache")`。
- **问题**：锁内 panic 一次，以后所有 `list`（`/v1/info`、`/v1/usage`、`/v1/stats`）都会 panic，直到重启。预热时 panic 会让 `spawn_blocking` 返回 JoinError，启动报 `initialization failed`。查证：锁内会走到的代码有读目录、fstat、`replay` 和 reducer、HashMap、排序；reducer 里的 `expect("validated turn")` 和 `unreachable!` 都排在 `validate_event` 之后，目前没有能触发的 panic。而且原来 list 里出同样的 panic，也会让 `/v1/info` 每次都失败、客户端探活失败，结果差不多。
- **改法**（如果要改）：换成 `lock().unwrap_or_else(PoisonError::into_inner)`。条目都是算完以后整条插入的，从中毒里恢复是安全的。

### 可以不改 2：`EventReader` 发现不了「同一个 inode 原地重写、而且变长了」

- **位置**：`crates/canter-store/src/lib.rs:90-96`。
- **问题**（读代码推断，没实测）：文件被截断后原地重写（inode 不变），新内容比上次长时，四个退回条件都不成立，reader 会从旧位置接着读，多半报 JSON 或序号错误。canter 自己只追加，`truncate_tail` 只截掉不完整的尾行，替换文件也会换 inode，都碰不到这种情况；只有手工改 `events.jsonl` 才会。摘要缓存比较的是整份文件标识，不受影响。
- **改法**（如果要改）：额外记下位置前最后一行的 seq 或末尾几个字节，读之前核对一下。
