## 要做的

1. **「只问执行」墙内命令不问**：沙箱开着时，`askForExecution` 下普通模型 shell（前台、后台）直接在墙里跑，不弹批准框。下面这些照旧先判断、照旧问或拒：`rules.json` 的 forbidden / prompt、P2-161 关键路径删除（强制单次批准）、计划模式和审查轮的只读限制。`alwaysAsk` 照原来问。沙箱关闭时三档一切照旧。
2. **申请越界**：shell 工具加可选参数，让模型为这一条命令申请：
   - 联网（这条命令及其子进程的全部 IP 网络，含本机和内网）；
   - 写墙外的普通路径（列出路径）。
   - 再加一句理由，显示在批准框里。
   - 参数名和结构你定，参考 Codex 的 `sandbox_permissions` / `justification`，写进完成记录；协议和 DESIGN 照 CLAUDE.md 写明和 Codex 哪里不同、为什么。
3. **批准**：带申请的命令在 `alwaysAsk`、`askForExecution` 下一律单次批准，批准框写明这次放开的是什么，没有「本会话放行」「以后都不问」；P2-108 的 allow 规则、会话前缀授权、只读白名单都不能免掉这次批准。批准后只这一条命令（含后台命令到退出为止）拿到放开的范围，其余墙照旧；拒绝就照现有的拒绝反馈。
4. **「全部允许」**：本来就能联网，联网申请直接放行；写墙外路径的申请直接拒绝，不弹框，给模型英文说明（「全部允许」不扩大写范围，用户真要做可以自己用 `!`）。
5. **硬边界**：申请的路径落在敏感目录、canter 状态目录里，或是它们的上级，或是 `.git` 的 config / hooks，批准也解不开，直接拒绝并说明。路径按 P2-118 的规范化办法算（`..`、符号链接、不存在的尾部）。
6. **给模型看的文字**（改提示词和工具说明，要用户定，见下面「要用户定的文字」）：沙箱开着时，shell 工具说明说明墙的范围和怎么申请；被墙挡住时附的说明在询问档里提示可以带申请重试。沙箱关闭时，给模型的请求和改动前逐字节一样（工具说明、参数都不出现）。
7. **协议和终端批准框**：批准请求带上申请的内容（联网、路径、理由），终端批准框照显示；旧客户端忽略新字段时不能把带申请的批准显示成普通批准，处理办法你定（例如 `GET /v1/info.features` 加能力标记，或批准请求里换一种类型），写进完成记录。界面文字用英文。
