### 意见

1. **建议改**：passwd 读不到可用账号时，服务端整个起不来。
   - 位置：`crates/canter-server/src/session_environment.rs:76-103`（`current_user`），`crates/canter-server/src/lib.rs:93`（`load(...).await?`）。
   - 问题：以下几种情况 `SessionEnvironment::load` 都返回错误，`serve` 直接退出：passwd 里查不到当前 uid；HOME 或 SHELL 不是 UTF-8；HOME 或 SHELL 不是绝对路径，包括 passwd 的 SHELL 字段为空（按 Linux 约定就是 /bin/sh）。改之前服务端不读 passwd，这类机器上旧客户端（照旧交 `env`）能用，改之后连服务端都起不来。用户现在的环境都不会碰到：Mac，5090 是本机账号、用 glibc 构建，Terminal-Bench 容器里是 root 或镜像里建好的用户。会碰到的有两种：`docker run --user <没登记的 uid>`；musl 静态版跑在 LDAP/SSSD 账号的 Linux 上（musl 只读 `/etc/passwd`）。
   - 改法：拿不到可用的 passwd 账号时不报错。HOME 取服务端进程环境里的绝对路径 HOME，跳过登录 shell 探测，退回进程环境，doctor 的 `session.environment` 给固定原因。SHELL 为空时按 /bin/sh 处理，或者也跳过探测。连可用的 HOME 都没有时，才拒绝启动，或者只让不交 `env` 的请求报错。补一个单元测试。
2. **可以不改**：登录脚本里起的后台进程如果一直占着 stdout，探测会白等满 5 秒。
   - 位置：`session_environment.rs:154-173`。
   - 问题：`read_to_end` 要等 stdout 的 EOF。比如登录脚本里写了 `nohup cmd &`：stdout 不是终端时 nohup 不重定向它，后台进程就一直占着管道。这种情况下 `env -0` 已经输出完，仍要等到 5 秒超时，报 `timed out`，然后回退。最多 5 秒，不会挂住；进程组照样清掉（后台进程自己 setsid 了的除外）。
   - 改法（如果要改）：读输出和等 shell 退出同时进行。shell 退出后只留很短的宽限期读完已到的输出，然后就解析，不再等 EOF。
3. **可以不改**：探测在装信号处理之前跑。
   - 位置：`lib.rs:93-98`。
   - 问题：在这最多 5 秒里，服务端如果被 SIGTERM/SIGINT/SIGHUP 按默认动作杀掉，`ProbeGroup` 的 Drop 不会执行，探测的进程组会留下来；登录脚本卡住的话，它会一直留着。启动早期本来就有这个窗口（`startup::initialize` 也在装信号之前），这次只是把窗口拉长了。程序内各条路径都清干净了：成功、非零退出、读失败、输出超限、超时，以及 future 被取消（`ProbeGroup` Drop 加 `kill_on_drop`）。
   - 改法（如果要改）：先装信号处理再探测，或者让探测和信号放进同一个 select。

### 重点各项的核对

1. **沙箱拿到的 HOME**
   - 服务端只有三处构建会话运行时：新建（`Session::create`）、恢复未打开的会话（`open_for_resume`）、fork（`ForkSnapshot::create`）。三处都经 `App::runtime` → `resolve`。

2. **隐私**
   - `SessionEnvironment` 和 `Config` 都没有 Debug/Serialize。探测的 stderr 直接丢掉，stdout 只在内存里解析。
   - passwd 错误、探测原因、doctor 文字、配置校验错误、重载警告都是固定字符串，不回显键和值。测试断言了校验错误里没有值。

   - 非法项会让整份 config.json 加载失败：重载时保留旧配置并发固定警告，启动时拒绝启动，和其他字段的处理一致。
