## 要做的

1. **服务端公布沙箱状态**：客户端能拿到沙箱开没开，以及这个会话的实际范围（可写的目录：cwd、新增目录、会话临时目录、缓存；当前权限档下联不联网；不能读写的目录）。放在哪里（`/v1/info`、会话设置或单独接口）、字段叫什么你定，照 CLAUDE.md 在 DESIGN 写明和 Codex（`sandboxPolicy`）哪里不同、为什么。旧服务端没有这些字段时，终端不显示沙箱状态，不能显示成「开」。
2. **状态栏**：在权限档旁边显示沙箱开还是关（文字见下）。关着时用醒目的颜色（和 `Allow all` 一样的红色）。切换权限档后，联网状态跟着变的地方要跟着刷新。自定义状态栏脚本拿到的 JSON 里也加上沙箱开关。
3. **`/sandbox` 命令**：只看不改，列出上面第 1 条的实际范围，Esc 关闭。沙箱关着时只说一句关着、怎么打开。不提供开关或修改。
4. **墙外的入口标出来**（只在沙箱开着时标）：
   - 用户 `!` 命令（含 `!cmd &`）的卡片标明不在沙箱里；
   - MCP 工具和 `web_fetch` 的卡片标明不在沙箱里。
5. 沙箱关着、或服务端是旧版时，界面和现在一样，只有状态栏多一个 `Sandbox off`（旧服务端连这个也不显示）。

## 完成记录

### 做了什么

- 协议：会话设置加可选 `sandboxEnabled`，打开、新建会话时按执行器实际开关写入，和存盘不同就追加 `session.updated`（做法同 `planEnabled`）。新增 `GET /v1/sessions/{id}/sandbox`，返回 `{enabled, writable, readOnly, noAccess, network}`，每次现算、不存盘。已重新生成协议类型文件；协议 README、DESIGN 第 8 条和「沙箱」一节写明了和 Codex `sandboxPolicy` 的不同和理由。
- 服务端：`Executor::sandbox_scope` 带默认实现（关）。`LocalExecutor` 从当前 shell 范围取 cwd、新增目录、联网；从 `Sandbox` 取会话临时目录（规范化后的路径）、两个缓存、原 `~/.cargo` / `~/.npm`，以及不能读写的目录（按原写法去重，已在列出目录里的不重复列，比如 `config.json`）。墙的规则、批准判断、文件工具边界都没改。
- 状态栏：`permission` 项后接 ` · Sandbox on`（灰）或 ` · Sandbox off`（红）；旧服务端不显示。放不下完整文字就整个拿掉；Shift+Tab 照旧只看权限档；计划模式下接在 `Plan (then …)` 后面。自定义状态栏脚本的 JSON 加 `sandbox`（`true` / `false` / 旧服务端 `null`）。
- `/sandbox`：只看，Esc 关闭，`/help` 一行用定好的文字。开着时列 Writable / Read-only / No access / Network / Not sandboxed，路径缩成 `~`，Network 按服务端当前权限档。关着时显示那一句。旧服务端提示 `This server does not support /sandbox; run canter serve --replace and retry`。
- 卡片：沙箱开着时，用户 `!`（含后台）、MCP、`web_fetch` 卡片右侧状态后接灰色 `not sandboxed`；模型命令和后台命令操作卡片不标；关着或旧服务端不标。
