## 重点看

1. **一台机器一个**：文件锁、登记文件、socket 的创建和清理；两个 `canter serve` 同时起、旧服务端崩溃后残留、`--replace` 交接时，会不会出现两个服务端同时写一个会话，或者谁都起不来。
2. **key 和环境不外泄**：API key、环境变量的值、请求体里的私有内容会不会进日志、错误回复、事件、SSE、登记文件；状态目录、配置文件、socket 的权限；受保护路径是否正确交给执行器；非本机 `http://` 的 base_url 是否拒绝。
3. **HTTP + SSE 和多客户端**：每条命令接得对不对、错误映射对不对；SSE 续传（`Last-Event-ID` 优先）不漏不重，包括会话还没接着聊时从盘上读、接着聊之后衔接到实时事件；几个客户端同看一个会话、批准先到先得；客户端中途断开会不会留下半截状态。
4. **接着聊**：没接着聊时改动命令一律被拒；接着聊时环境只放内存；已打开时不换环境；协议改动对旧客户端兼容。
5. **起服务端和升级**：「找服务端，没有就起」的竞态（两个客户端同时起）；`--replace` 等在跑的轮跑完、超时记成被打断；停服务时每个会话都 `close()` 了。

### 意见

1. **建议改**｜`crates/canter-server/src/discovery.rs:33-37、60-63`（`ensure_server` 经 `discover`）
   - 问题：判断服务端在不在只看登记的 PID 活不活。服务端崩溃或机器重启后，`server.json`、`server.sock` 留在状态目录里；这个 PID 一旦被别的进程用上（重启后很常见；回 EPERM 的系统进程也算「活」），探活连不上就报「无法连接已登记的服务端；未自动替换」，`ensure_server` 也不再去起新的。实测：登记 PID 写成 1 或本用户另一个活进程、socket 是残留文件，`ensure_server` 立刻返回这个错，这时 `server.lock` 是空闲的；只有用户手动跑一次 `canter serve` 才清得掉。这是「找服务端，没有就起」在崩溃残留下起不来的情况。
   - 改法：以服务端锁为准判活。探活失败时试一下非阻塞拿 `server.lock`（拿到立刻放掉）：拿得到说明没有服务端，按「没有」处理去起；拿不到才报现在的错。补一个测试：登记指向一个活的非 canter 进程时，`ensure_server` 应起出新服务端。

2. **建议改**｜`crates/canter-server/src/lib.rs:100-124`（退出流程）
   - 问题：旧服务端因 `--replace` 进入排空后，`select!` 已经选了升级分支，SIGTERM 和 Ctrl-C 不再有人收；tokio 注册过信号处理，默认动作也没了。于是排空的最长 60 秒和随后关会话期间，SIGTERM、SIGINT 都被吞掉，只有 SIGKILL 停得下。实测：排空中发 SIGTERM 等 10 秒、再发 SIGINT 等 3 秒，旧进程都还在。完成记录里「Ctrl-C / SIGTERM 直接关闭会话，不等待升级窗口」只在没有升级时成立。
   - 改法：排空等待里同时 select 退出信号，收到就跳过等待、直接并发 `close()`；README 和完成记录的说法按实际改。

3. **建议改**｜`crates/canter-server/src/http.rs:361-376`（`close`）
   - 问题：`session.close().await?` 出错就直接返回，会话留在登记表里。核心的 close 只在存盘失败（或轮的任务异常退出）时出错，出错前已经 `journal.release()` 放掉写锁、置了 `closing`。之后再 DELETE 仍回 500；`resume` 在登记表里找到它，只回旧快照、不重开；送话回 `session_closed` / `internal`。P1-4 定的「写失败后关掉再打开」恢复路径（`StoreError::WriteFailed` 的提示）在 HTTP 上走不通，只能重启服务端。读代码得出，没有做故障注入。
   - 改法：close 出错时也从登记表移除并 `notify_waiters()`（写锁已放，轮已结束），照常回错误；或者 resume 碰到已关闭、写失败的登记会话时先移除再 `Session::open`。

4. **建议改**｜`crates/canter-server/src/http.rs` 登记表锁：`App::session` 48-56、`read` 190-195、`resume` 210-225、`create` 254-290、`close` 362-371、`EventReader::new` 389-409、`EventReader::recv` 432-438
   - 问题：所有会话共用一把 `Mutex<HashMap>`，而这把锁在耗时的 await 期间一直拿着：打开会话（读整份事件和模型历史）、建会话加送话、关会话（等本轮停下、工具回收）、未打开会话的整份事件重放、SSE 订阅时从盘补历史。一个会话做这些时，所有会话的命令（包括批准）和新的 SSE 都排队等；每次登记变化还会叫醒所有在等的未打开会话订阅者，各自持锁重读整份文件。历史越大越明显。不影响正确性（未打开会话读盘和接着聊互斥靠的就是它），所以是建议。
   - 改法：登记表锁只管查、插、删；同一会话的打开、关闭、读盘用每个会话 id 一把的异步锁串行；已打开的会话克隆出 `Session` 后先放锁再 await 核心方法。

5. **建议改**｜`crates/canter-server/src/discovery.rs:118-143`
   - 问题：后台起的 `canter serve` 马上退出时（没有或写错 config.json 等），循环只看是否到期，客户端要干等满 15 秒才拿到笼统的「服务端未启动，请检查状态目录中的 server.log」。实测：没有 config.json 时 15.0 秒才返回。几个客户端同时起时，输的那几个往 server.log 里写「已经有一个服务端在运行；要升级请运行 canter serve --replace」，对用户是误导。
   - 改法：子进程已退出且 `server.lock` 空闲（没有别的服务端在起）就立刻返回错误，可以带上 server.log 最后一行（内容都是固定文字）；有人拿着锁才接着等。

6. **建议改**｜`crates/canter-server/src/discovery.rs:96-106`
   - 问题：后台起的服务端继承了起它的那个客户端的全部环境变量（包括那个终端里的令牌），并在整个生命周期里带着。现在没有代码用它（执行器 `env_clear`，核心不合并服务端环境，模型客户端不走代理），所以没有泄露；但以后哪里起子进程漏了 `env_clear`，终端 A 的环境就会进终端 B 的会话，和 DESIGN 第 14 条「用接着聊那个终端的环境」相反。
   - 改法：`command.env_clear().env("CANTER_HOME", home)`，确实需要时再加 HOME、TMPDIR。

7. **建议改**（文档）｜`crates/canter-protocol/README.md`
   - 问题：「建会话时 `model` 为空字符串就用配置里的默认模型」是客户端看得到的约定，现在只写在 `canter-server/README.md`；P1-7 和以后的网页客户端看的是协议 README。
   - 改法：在协议 README 建会话那段补一句。

8. **可以不改**｜`crates/canter-server/src/http.rs:167-178`、`discovery.rs:51-63`
   - 问题：`/v1/info` 每次都重放所有会话的完整事件，而客户端探活总共只等 2 秒。实测（release）：10 个会话各 2 万条事件（共 44 MB）0.11 秒；20 个各 5 万条（共 220 MB）0.55 秒。按线性估，历史到 800 MB 左右会超过 2 秒，客户端就报「已登记的服务端没有响应」。离得还远。

9. **可以不改**｜`crates/canter-server/src/lib.rs:112-124`

11. **可以不改**｜`crates/canter-server/src/lib.rs:86-109`
