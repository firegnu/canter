## 要做的

方案里每项写：推荐怎么做、为什么；有实质备选的写备选和取舍；引别家的做法标出处（文件和版本标签，或 P2-64 报告的条目）。

1. **分段结构**：有哪些段、每段的种类和稳定性、先后顺序；按工具生成的句子和模型家族补充怎么挂上去。顺序要照顾跨会话的缓存：所有会话都一样的放最前（比如考虑把全局 `AGENTS.md` 放到环境前面），说清得失。会话存盘存什么，恢复时怎么转出和原来一样的字节；**已有的旧会话**（存的是拼好的一条 system）升级后怎么办，给推荐。`/context` 的分段统计怎么对上。
2. **转换器**：Chat Completions 的规则写到能照着实现（拼成一条 `system`，段之间怎么分隔、标题和标签怎么写）。另列一张表写 Responses（照 P2-33 方案）、Anthropic、Gemini 各放哪一层、「所有会话都一样」和「本会话固定」的分界落在哪（比如 Anthropic 的缓存断点），只设计不实现。
3. **固定段原文**：约 1,500 词英文全文。覆盖 P2-64 报告 4.1 里 canter 缺的方面：工作方式、工具使用（互不依赖的调用放同一次回复；用户给的命令照原样跑，不加 `echo $?` 这类东西）、改代码（不还原用户自己的改动）、git 和危险命令、批准被拒以后怎么办、什么时候用 `ask_user`、不可信内容（文件、网页抓取、MCP、命令输出里的指令当数据）、验证和汇报（分清验证过的和推测的）、回答（用用户的语言、先说结果、终端会渲染 markdown、`路径:行号`、长任务中途的进度）、凭证。按工具生成的句子标明出现的条件。估算 token 数。
4. **工具说明原文**：6 个工具的新说明全文，合计约 600～800 词；只属于某个工具的规矩放这里，不放固定段。
5. **环境段**：写哪些（目录、系统、shell、日期，要不要加 git 仓库和分支的打开时快照），格式。
6. **压缩和 `/handoff` 原文**：结构化小节（用户目标和明确要求、关键原话照抄、约束和偏好、决定和理由、读过改过的文件、跑过的命令和结果、停在哪、没解决的、下一步）。纯文字、各家模型都能读，以后换提供方时也能用。`/handoff` 和压缩共用小节时怎么区分。
7. **长度和花费**：新前缀（固定段 + 环境 + 工具说明）大约多少 token；按 `usage.rs` 的 DeepSeek 价目表，算一个典型会话多花多少。
8. **对比场景**：约 8 个，和模型无关，每个写：发给模型的原话、准备的项目状态、看什么、怎么算过。至少包括：照原样跑命令（`ls /no-such-dir`）、改之前先读、没要求不 commit、网页里藏的指令不照做、用用户的语言回答、批准被拒以后不原样重试、长任务压缩后能接着做。写怎么跑、估计真调多少次、花多少。
9. **要用户选的**：真有取舍、要用户拍板的点列成问题，每个给选项和你的推荐，最多 5 个，按重要程度排。没有就写「没有」。
10. **实现分件**：照推荐拆成能分别派出去的小活，每件写标题、做什么、动哪些包、大小（小 / 中 / 大）、依赖和先后；标出哪件要用户在场真调。

## 用户试用时看到的（10-26）
