   - 问题：用户全局 git 配置里有 `filter.<名>.clean/smudge/process/required`（`git lfs install` 写的就是这一组）。新检查见到任何 filter 的 clean/smudge/process 就问，用户机器上的 `git status --short`、`git diff --stat`、`git log --oneline -15` 因此全部要问（用隔离 HOME 时放行，用真实 HOME 时要问，实测）。P1-8 四条里有三条带 git，会整条弹框；验收原话「`git diff` 这类不再弹批准框」没达到。测试用的是空 HOME，所以没发现。
   - 改法：对 `filter.lfs.*` 只认 `git lfs install` 写入的那几个固定值（clean/smudge/process 的标准命令，`required = true`），值完全一致就算安全，其他 filter 或其他值照旧问。这样即使模型自己写了同样的配置，也只会运行 git-lfs 本身。具体值请开发者按 git-lfs 文档核对。加两个用例：标准 lfs 配置放行，同名 filter 改了值就问。

### 建议改

1. **建议改｜`src/readonly/git.rs` 40 行｜没查系统级 git 配置，而这台机器上它是用户可写的。** 和这次改动无关，这次才注意到。PATH 上第一个 git 是 Homebrew 的 `/opt/homebrew/bin/git`，它的系统配置 `/opt/homebrew/etc/gitconfig` 属于用户、可写。「只问执行」下 write 工具能写这个文件，属于必须改 3 同一类问题，README 现在写成边界。改法：会话环境没设 `GIT_CONFIG_NOSYSTEM` 时，用同一个检查函数再读 `/etc/gitconfig`，以及 PATH 上 git 所在前缀下的 `etc/gitconfig`（例如 `/opt/homebrew/etc/gitconfig`、`/usr/local/etc/gitconfig`），不起进程。
2. **建议改｜`src/readonly/git.rs` 201–203 行｜`gpg` 判断过宽。** `key.contains("gpg")` 和 `signingkey` 会把 `commit.gpgsign`、`tag.gpgsign`、`user.signingkey` 也算成危险项（`gpgsign = false` 也会问）。签提交的用户很常见，他们的 git 命令就都会弹框。status/diff/log/show 只有在验签时才起 gpg，而验签已经由 `%G`、`log.showSignature` 和 `gpg.*` 这几条单独拦住了。改法：只拦 `gpg` 段和 `gpg.<格式>` 子段、`log.showsignature`、含 `%G` 的格式，放过 `*.gpgsign` 和 `user.signingkey`。这台机器上没有这几项，所以记为建议改。
3. **建议改｜`src/readonly.rs` cd 之后的相对路径检查｜改成字面 cwd 之后，路径里的 `..` 跟在目录符号链接后面时，检查结果和实际打开的文件可能不一致。** 按代码推断，没实测。原因：shell 的 `cd` 按字面处理，但后面命令里的相对路径由系统按真实目录解析。这次改法让 cd 本身的 `..` 算对了；`cd` 进链接目录之后，再在普通参数里写 `..`，又落回 README 已记的「一般符号链接限制」那一类。不经 cd、直接写在路径里时原来就有这个问题，所以不列必须改。改法：`path_allowed` 除了字面规范化，再按文件工具 `resolve_target` 的办法逐段解析已存在的前缀，两种结果都检查；这样 cd 前后和直接写的情况都能一起收窄。
