### 这次改动重点查的

1. **等交接被取消后**：select 走取消分支时，`acquire` 的 future 连同其中的租约一起丢掉；如果 `acquire` 已经返回、拿锁后才发现取消，配置在返回时丢掉；两种情况都不写进 `Active.configuration_lease`。runner 对已取消的轮直接走原有 Interrupted 收尾（`state.active = None`，丢弃队列）。在临时拷贝里加了一条探针：B 等交接时按 Esc，B 回到 Idle；A 的轮结束后旧 x 关、新 x 起；再改一次 x（此时没有轮在跑），B 的下一轮 3 秒内拿到完整工具，没有残留租约卡住交接；结束后三个版本的进程都退出。取消后会话的配置停在"未配置"，下一轮再补，不影响。
2. **revision 为 None 的会话第一轮**：所有开轮路径（输入、排队、自动唤醒、目标续跑、用户 shell、手动压缩）都起 `runner::run`，runner 每次循环先调 `prepare_turn`：只要有配置源、本轮还没有租约，就先 `acquire` 完整配置再干活；`apply_configuration` 从 None 到 Some 一定整体重建。所以第一轮一定补齐服务。`opening_sessions_and_listing_mcp_do_not_wait_for_service_handover` 验证了交接中新建、恢复的会话首轮都带 MCP 工具；上面探针里被取消过的会话，下一轮也补齐了。
3. **一轮之内配置不变**：轮的工作（模型请求、工具、压缩、用户 shell）都在 `prepare_turn` 之后。同一轮里 `prepare_turn` 只应用一次，之后租约非空直接返回（steering 的 `continue` 也一样）；轮登记后，只在空闲时调用的 `configure`（开轮、btw）不会再跑。等待期间的 btw 用就绪快照里的新模型和选项，不碰服务。
4. **锁**：等交接时只有 `acquire` 的 future 持有新版本槽的租约，不拿任何会话锁，跨会话没有环。新建、打开会话拿到的快照租约只在处理请求期间持有，`create` 发首轮输入之前已经丢掉。
5. **撤回**：没就绪的路径下，完整配置的前缀记录写在本轮开始之后。查了回放：前缀记录以最后一条为准，撤回只截消息，前缀不会退回旧工具。
