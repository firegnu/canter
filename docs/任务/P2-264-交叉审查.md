## 审查意见

改完再合并：2 条必须改，均已用本次分支编出的 CLI 和临时仓库复现。

1. **必须改：附加仓库路径与另一个 run 的主路径碰撞，旧 run 再次 clean 会强删新 run。**

   位置：`eval/src/paths.rs:299–309`（`other_worktree_path`）、`eval/src/prepare.rs:515–520`（`clean`）。

   问题：`<run>-<repo>` 不是各 run 独占的路径。临时例子中，同一轮次先 `prepare --run a --task two`（主仓库 rust、附加仓库 ts），再 `clean --run a`；随后 `prepare --run a-ts --task single`（主仓库 ts）会成功，主 worktree 正好占用原来的附加 worktree 路径。此时再次 `clean --run a`，旧 state 仍记着这个路径和 ts 仓库，`git worktree remove --force` 返回成功，把新 run 的 worktree 连同我放入的未提交文件一起删掉；新 run 的 state 仍在。根目录检查和 Git 的仓库归属检查都挡不住，因为两次确实使用同一仓库、同一个根下路径。这违反“只删这次跑建的”，是实际误删。

   改法：让附加 worktree 路径与所有合法 run 的主路径、其他 run 的附加路径都不重叠。例如用一个不能作为 run 标签的固定目录段隔开附加 worktree，再按 run 和仓库分层，主仓库路径保持原样；不要只换成另一种仍可能拼出合法 run 名的连接符。兼容已有 state 时也要保证已释放的旧路径不能被旧 clean 当成当前所有物。补上上述“clean A → prepare B → 再 clean A，B 的未提交文件仍在”的回归检查。

2. **必须改：多仓库 prepare 中途失败会留下没有 state 的 worktree，clean 无法收尾。**

   位置：`eval/src/prepare.rs:300–336`（逐个建 worktree、执行 setup）、`eval/src/prepare.rs:351–376`（全部成功后才保存 state）。

   问题：第二个仓库的路径检查、起点解析、worktree 创建或 setup 失败都会直接返回，之前创建的 worktree 没有持久记录，也没有回滚。已分别复现第二个仓库的 base 不存在、第二个仓库 `setup = ["exit 42"]`：前者留下第一个 worktree，后者留下两个；两者都没有 `state.json`。后续 `clean` 报 `cannot read .../state.json`，同名 `prepare` 又报 run 目录已存在，并提示用实际无法工作的 clean。这未达到任务要求的清理闭环。

   改法：先检查所有目标路径、解析所有起点，减少可预见的半途失败；仍须处理 setup 和 Git 操作失败。每成功创建一个 worktree 就记录它，失败时仅回滚本次已成功创建的 worktree，或持久保存可供 clean 使用的已创建清单。不能把尚未创建的目标或原先已存在的目录当作本次所有物。覆盖上述两个失败点，并验证预先存在的目录不动、遗留 worktree 可被清理。
