### 建议改

1. **跳过未知种类后，工具调用和工具结果会配不上对**
   - 位置：`crates/canter-model/src/wire.rs:9`（`filter_map(message)`）、`wire.rs:41-46`、`wire.rs:68`。
   - 问题：试验确认了两种情况。（a）助手消息里只有一种以后才有的工具调用（比如接 OpenAI 时 apply_patch 用的 `custom_tool_call`），整条被跳过，但对应的 `tool_result` 照发，请求里出现没有出处的 `role: tool`。（b）以后新加一种工具结果（比如带图片的），被跳过以后，助手的 `tool_calls` 后面没有结果。这两种请求 Chat Completions 都会以 400 拒绝，归为 `InvalidRequest`，不重试，这个会话退回旧版本后就接不着聊了。P1-4 打断「工具已经发出、结果还没写」的时候，也会留下同样配不上对的历史。
   - 改法：在 `request_body` 里转换完以后做一步配对整理：删掉在前面助手消息的 `tool_calls` 里找不到 id 的 `tool` 消息；助手的工具调用如果后面没有结果，紧跟着补一条占位的 `tool` 消息（比如「没有结果：被打断或本版本无法识别」）。可参考 Codex `rust-v0.163.0` 的 `codex-rs/core/src/context_manager/normalize.rs`（`ensure_call_outputs_present`、`remove_orphan_outputs`，补的是 `"aborted"`）。加一个测试，用上面两段历史，断言发出的请求能配上对。最迟在加任何新种类之前改；放进 P1-4 一起做也可以，但要写进 P1-4 的任务文件。
2. **`Retry-After` 没有上限**（主控已记，同意）
   - 位置：`chat_completions.rs:177-179`、`parse_retry_after`（`:201-211`）。
   - 问题：试验中 429 带 `Retry-After: 86400`，流不出任何东西，也不报错，一直等，只有取消能停下来。头里给一个很远的 HTTP 日期，结果一样。
   - 改法：设一个上限（比如 60 s）。服务端要求等得更久时不等，直接把带 `retry_after` 的错误交给调用方，由核心或界面显示「限流，N 秒后再试」。补一个测试。
3. **DeepSeek 的 `insufficient_system_resource`、`aborted` 被当成正常结束**
   - 位置：`chat_completions.rs:136-142`。
   - 问题：官方接口文档列的结束原因是 `stop`、`length`、`content_filter`、`tool_calls`、`insufficient_system_resource`（推理资源不够、请求被中断）、`aborted`（生成被中断）。代码把后两个归为 `Finished(Other)`，也就是「成功收完」。试验：一个字都没交出就收到 `insufficient_system_resource` 时，返回 `[Finished(Other)]`，不重试，已经拼好的工具调用也悄悄丢了；P1-4 如果把 `Other` 当成这一轮结束，用户看到的就是一条空回复，没有任何报错。代码里倒是对文档里没有的 `network_error` 做了处理。
   - 改法：`insufficient_system_resource` 和 `aborted` 照 `network_error` 处理，归为 `ErrorKind::Server`：还没交出东西就自动重试，交出过就报错。`content_filter` 维持 `Finished(Other)`。README 写明 `Finished(Length)`、`Finished(Other)` 都表示回复不完整，核心要给用户看到。补一个测试。
4. **工具调用的 id 和名字用 `push_str` 拼接**
   - 位置：`chat_completions.rs:129-131`。
   - 问题：DeepSeek 文档说只有第一段带 id 和名字，后面只带参数，所以对 DeepSeek 没问题。但 base_url 可以配置，有些兼容接口每段都重发 id 和名字。试验：每段都带 `"id":"call_1"`、`"name":"read"` 时，拼出来是 `call_1call_1`、`readread`，工具执行失败，工具结果也配不上 id。
   - 改法：id、名字取第一个非空值（pi 的 `openai-completions.ts` 就是 `if (!block.id && toolCall.id)`），参数照旧拼接。补一个测试。
5. **存盘类型以后怎么改的规矩没写下来；`Unknown` 写回会丢内容**
   - 位置：`crates/canter-model/README.md`「模型历史」；`types.rs:21-23`、`:36-37`。
   - 问题：试验：（a）已知种类多出字段，旧版本读得了；（b）已知种类的字段改了形状（比如 `tool_result` 的 `text` 换成 `parts`），这一行解析失败，而 `canter-store` 的 `model_history` 遇到任何一行失败整份都读不出来（`canter-store/src/lib.rs:289`）；（c）`Unknown` 再序列化成 `{"type":"unknown"}`，原内容没了。以后 P1-4 只要整份重写历史（复制会话、压缩后重写），旧版本读到的新内容就会悄悄丢掉。
   - 改法：README 写明三条规矩：新字段一律用 `Option` 或 `#[serde(default)]`；不改已有种类字段的形状和意思，要改就加新种类；读出来的 `Unknown` 不写回。在两个 `Unknown` 变体上加 `#[serde(skip_serializing)]`，误写回时直接报错，不会悄悄丢内容。

### 可以不改

1. **没有思考内容的助手消息不带 `reasoning_content` 字段**（`wire.rs:60-62`）：思考开关中途切换过，或者某条助手消息被打断时还没出思考内容，带工具的请求里这条消息就没有这个字段。文档只说「没正确回传会 400」，没说缺字段算不算。不调真接口没法确认，建议在最后真模型试用时测一次：思考关掉再打开以后，带工具接着聊。
2. **重试期间调用方什么也收不到**：最多重试 3 次。DeepSeek 排队时 10 分钟还没开始推理就会断开连接（限流页原文），每次断开都算 Network 错误，要重试，最坏要静默等大约 40 分钟。以后可以加一个「正在重试」的信号给界面，由 P1-4、P1-6 决定。
3. **`ContextLength` 靠报错文字识别**（`chat_completions.rs:228-246`）：错误码页没有列这种错误。公开问题报告里 DeepSeek 的原文是「This model's maximum context length is 131072 tokens. However, you requested 131329 tokens (123137 in the messages, 8192 in the completion)…」，现在的判断能认出来（来源：[claude-code-router#895](https://github.com/musistudio/claude-code-router/issues/895)、[zed#45456](https://github.com/zed-industries/zed/issues/45456)）。注意 requested 里算了 `max_tokens` 的预留（思考模式默认 64K），见下面给 P1-4 的提醒。真模型试用时最好确认一次。
