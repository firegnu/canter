### 意见

1. **建议改**：`crates/canter-server/src/doctor.rs:347-383`（`provider`）。
   - 问题：Chat Completions 这家查模型列表时只带 `Bearer api_key`，没带 provider 配置里的 `headers`（`Provider.headers`，真实请求会带）。靠自定义头鉴权或分流的网关（某些代理或企业网关）会因此回 401/403，doctor 就会误报「rejected its API key」，让用户去换一个其实没问题的 key。只在配了 headers 的家才会碰到。
   - 改法：`DoctorProvider::ChatCompletions` 带上这家的 `RequestHeaders`，请求时照真实请求的方式加上，值设 sensitive，原因里仍然只写家名。

2. **建议改**：`crates/canter-server/src/doctor.rs:519-541`（`mcp`）。
   - 问题：服务端刚启动或刚热重载、MCP 还在握手时，状态是 `Starting; waiting for service handover or initialization`，doctor 会把它报成 fail「is not connected」，修法写「Check … in config.json」。这时其实还判断不了，和「判断不了报 skip」不一致。只在启动或重载后几秒内跑 doctor 才会碰到。
   - 改法：把这个「还在启动」的状态报成 skip（原因写 still starting），其余没连上的照旧报 fail。最好在 `McpServerStatus` 或 slot 上用一个明确的标志判断，别靠匹配错误文字（现有的 `Login required` 判断同理，可以一起换）。

3. **可以不改**：`crates/canter-server/build.rs`、`crates/canter-server/src/lib.rs:43`（服务端版本改成带提交）。主控让表态的那条：
   - 影响可以接受。`discovery.rs:87` 比的是 server.json 里的版本和本机 `canter_server::VERSION`，两个都出自同一个 canter 可执行文件。以前包版本一直是 `0.1.0`，这个「still using the old server」提示几乎不会出现；现在升级后、旧服务端还在跑时会提示，这正是这条提示本来要说的事，算修正，不算回退。代价有两个：一是合并后第一次升级时，旧服务端登记的是 `0.1.0`，提示一次，`canter upgrade` / `serve --replace` 后就消失；二是 `/v1/info` 的 `serverVersion` 多了 ` · <sha>`。仓库里没有代码按 semver 解析这个字段（只有 discovery 拿它和 server.json 比相等），所以没有影响。
   - 有更小的做法：`canter_server::serve(replace, canter::VERSION)` 本来就在运行时拿到了 CLI 的完整版本（现在只用来打 ready 那一行）。把它存进 Registration / App，作为 server.json、`/v1/info` 和 doctor 的版本，就不用另写 build.rs、不用在 canter-server 里再跑 git，也免掉 canter-server 每次 git 暂存或提交都重编。对外看到的效果一样。现在的写法能用，不强求改。

4. **可以不改**：`crates/canter/src/doctor.rs:19-21`。`discover` 出错（协议不同、身份和登记对不上、不响应）时 CLI 丢掉了具体原因，只显示通用的「Could not connect to a running server」。协议不同还能从离线的版本那行看出来，其余情况用户要自己去翻。以后想改，可以把 `ServerError` 的文字（本来就是固定的英文、不带凭证）当成 `connection_reason` 传进去。

5. **可以不改**：`crates/canter-server/src/doctor.rs:893-895`（`log_errors`）。server.log 不轮转，离线 doctor 会把整份读进内存再取最后几行；文件里混进非 UTF-8 字节时整项报 skip。用量小，只影响离线那条路，结果也落在 skip 上，不会误报 ok。以后可以改成只读文件末尾一段、按有损 UTF-8 解码。
