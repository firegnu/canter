### 重点看的结论

1. 判定条件
   - 原来的 `state.non_interactive()` 读的就是当前轮的 `active.non_interactive`（`session.rs:165`），不是会话级。新条件判 exec 的结果和原来一样。
   - exec 每一轮都等：exec 只发一轮 `nonInteractive: true`（`crates/canter/src/exec.rs:288`）。这一轮在跑时，别的输入（包括插话、排队）都被拒（`session.rs:1401` 起）。轮开始时 `automatic_turns_paused` 置真，报告叫醒和 `/goal` 续跑都不会开新轮。所以 exec 会话里不会出现 `non_interactive = false` 的轮。`exec_wait_agent_still_waits_for_the_child` 覆盖了这种情况。
   - 子 agent 会话：`runner.rs:986-992` 在进 `agent_tools::execute` 之前，就用 `allows_agent_tool` 把 agent 工具拦掉了，走不到新判定，没有误伤。
2. 叫醒能不能保证结果送达
   - 用户开的轮：每次用户输入（直接、排队、插话）都会在 `session.rs:1440` 把叫醒计数清零。主会话的 `automatic_turns_paused` 只在轮开始时按是不是 exec 设，交互轮一开始就是 false。所以用户轮不等之后，至少还能叫醒一次。子 agent 在本轮结束前回来的，附到本轮下一次请求；在本轮结束后回来的，轮末 2 秒后叫醒。不会拖到用户下次输入。
   - 报告叫醒的轮：上限只可能在这里用完，即第 `auto_wake_limit` 次叫醒的那一轮（`background.rs:597`）。这时不等，剩下的报告要等用户下次输入才交给模型。但原来 P2-248 的 `WOKEN_WAIT` 也是直接返回，不算退步，界面上也有 Auto wake paused 提示。见意见 3。
3. `/goal`
   - 开发的读法对：`schedule_goal`（`goal.rs:118`）在轮末把下一轮定在 10 毫秒后；`next_goal`（`goal.rs:227`）只看有没有在跑的轮、排队、请求和目标状态，不看子 agent。续跑轮不等就会空转，保留等待是对的。
   - 有目标时用户开的轮：这轮不等，模型回复后结束；10 毫秒后开的续跑轮照旧等，不会空转。代价是续跑轮在等的时候，用户发的消息要排到等完，这是任务书定的取舍（见意见 5）。
4. 返回内容和交付标记
   - 不等时走的还是同一个 `wait_agents`，只在 `agent_sessions.rs:198` 的判断里加了 `no_wait ||`：取一次快照，格式还是同一个 `{"data":[...]}`（`agent_value`），卡片同样换成带结果的状态。唯一的区别是，有子 agent 还在跑时，末尾接一段英文提示。
   - 交付标记：只对已经结束的子 agent 调 `acknowledge_agent_result`，和真等时有一个结束或到时返回走的是同一段代码。还在跑的不标，之后照常发通知、叫醒。已排队、还没发给模型的通知会撤掉，也不再叫醒；已经发给模型的保持原样。没看到误标、漏标、重复叫醒或结果丢失。
   - 和原来报告叫醒那一轮比：原来不调宿主，也不返回状态；现在返回状态，已经结束的会标成已交付。叫醒这一轮的那份报告已经发给模型，再标一次只是记一笔，不会撤掉，结果不会丢。
5. 工具说明

### 意见

1. 建议改：`crates/canter-core/src/long_run.rs:28`（对应 DESIGN 第 707 行「等待类工具不计入重复」）
   - 问题：重复调用保护对 `wait_agent` 一律不提醒、不停，理由是「相同结果可能只是说明还在等」。现在交互轮里 `wait_agent` 立刻返回，这个理由不成立了。
   - 触发条件：在交互用户轮或报告叫醒轮里，模型没理会结果末尾的提示，接着用同样的 ids 再调 `wait_agent`。每次都立刻返回同样的结果，第 3 次不提醒，第 5 次也不停，就会一个接一个地发模型请求，直到模型自己停下。这会花钱，用户看到的是这一轮一直不结束。原来在用户轮里，子 agent 还在跑时，每次调用至少要等到有一个结束或超时，自带节流。报告叫醒那一轮从 P2-248 起就有同样的口子，目前没见过模型这样做。
   - 改法：只在这次 `wait_agent` 真的等了的时候才豁免；不等的那种照普通工具算重复（子 agent 跑完之前，结果逐字节相同，第 3 次会提醒，第 5 次之前会停）。这条规则是 11-08 用户补定的，要改先问用户。也可以先看主控真跑那次有没有连续调用，出现了再改。
2. 建议改：`crates/canter-core/src/agent_tools.rs:79`（`wait_agent` 说明）
   - 问题：(a) 「user-started and report-woken turns return at once」主语是轮次，字面意思成了轮次立刻返回。(b) 讲「会等」的那句只列了自动叫醒关闭和 goal 续跑，没列 exec；exec 只在最后一句「use this tool to receive results」里间接提到。行为没有错（exec 确实会等，exec 里 `spawn_agent` 的结果也会提示模型先调 wait_agent），只是措辞问题。
   - 改法：比如改成 `In an interactive session with auto wake enabled, it returns at once in user-started and report-woken turns. ... In canter exec, with auto wake disabled, or in an automatic goal continuation, it waits until ...`，最后那句 exec 不动。改了要同步三份请求快照和 `wait_description_explains_interactive_returns_and_blocking_exceptions` 的断言。
3. 可以不改：叫醒次数刚好到上限的那一轮（`background.rs:597`，`agent_tools.rs:226`）
   - 触发条件：用户一直不输入，连续叫醒到第 `auto_wake_limit` 次（默认第 10 次），这一轮模型调了 `wait_agent`，还有子 agent 在跑。
   - 问题：返回的提示说「报告回来会叫醒你」，其实不会再叫醒了，剩下的报告要等用户下次输入才交给模型。结果不会丢，界面上有 Auto wake paused 提示；和 P2-248 原来叫醒轮的行为一样，不是退步。
   - 改法：要更准，可以在这一轮（`active.auto_wake` 且计数已到上限）照旧等。代价是用户回来插话时，要等这次等待结束才有回复。
4. 可以不改：读上限的时机（`agent_tools.rs:316` 用的是 `runtime().options`，叫醒循环 `background.rs:570` 用的是 `next_options()`）
   - 触发条件：一轮进行中途改了配置，把 `auto_wake_limit` 改成 0，这一轮接着调 `wait_agent`。
   - 问题：这一轮按旧值不等，之后又按新值不叫醒（上限为 0 时连暂停提示都不出），结果要等用户下次输入。极少见。
   - 改法：改用 `next_options()`，和叫醒循环保持一致。
5. 可以不改：`/goal` 续跑轮里用户插话
   - 触发条件：目标在跑，用户在续跑轮里插话，模型接着调 `wait_agent`，子 agent 还在跑。
   - 问题：这一轮按续跑轮处理，照旧等，用户的插话要等这次等待结束才有回复。这是任务书「续跑轮次照旧要等」的直接结果，不用改。
   - 以后：如果用户在 /goal 里碰到了，再考虑「续跑轮收到插话就按用户轮处理」。下一次续跑照旧会等，不会空转。

### 对「拿主意的地方」逐条表态

- `/goal` 续跑轮保留等待：同意。读了 `goal.rs:118` 和 `goal.rs:227`，续跑确实在轮末 10 毫秒后就开下一轮，不看子 agent，不等会空转。
