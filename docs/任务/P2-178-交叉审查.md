### 建议改

1. **用 `wait_agent` 拿到结果后，完成通知还会把同一结果再交一次**

     - wait_agent 返回终态结果时，没有任何标记告诉转发任务「这条已经交过」；转发任务照样调 `agent_notice`，把同一份结果（最多 32 KiB）写进父会话历史，下一次模型请求时再交一次。用 wait_agent 拿结果时，同一结果通常紧接着又出现一次。已查证（代码）。
     - 交互会话还可能多叫醒一轮：如果通知在这一轮最后一次请求之后才写进去（两边抢父状态锁，先后不定），`wake_pending` 留着，轮结束时 `turn_finished` 按 2 秒窗口再开一轮。推测，没实测。exec 下同样情形，重复内容留到下一次输入。
     - explorer 的用处之一是省主上下文，重复交付把它抵消了一部分。

### 可以不改

1. **子 agent 停止出错时，父会话的 Esc、关闭会提前返回错误**
   - 位置：`crates/canter-core/src/session.rs:1417`、`1918`（`finish_agent_stops(children).await?` 在等父会话自己的轮之前）。

### 1. wait_agent 拿过的结果不再发完成通知：改对了

- 做法：wait_agent 返回时，对每个已停的子 agent，按「子会话 ID + 最近一轮普通工作的轮 ID」登记已交付（`Session::acknowledge_agent_result`，`agents.rs` 新增）；转发任务发通知前查这个集合，查到就不发（`background.rs` `agent_notice`）。通知已经写进去、还没发给模型的，从待发卡片、`plan_mode_notices` 或历史里撤掉；待发卡片清空时一并清掉 `wake_pending` 和截止时间，不再叫醒。已查证（代码，`wait_withdraws_queued_completion_without_waking_and_survives_reopen`）。
- 两种先后都对：wait 先登记、转发任务后到，会被集合挡住；转发任务先写、wait 后登记，会撤回。两边都在父状态锁里判断，没有漏的窗口。已查证（代码）。
- 重开：登记写进父会话私有历史 `AgentResultDelivered {noticeId, withdrawn}`，恢复时重建集合，撤回过的 `BackgroundNotice` 在重放时跳过，所以历史下标、回退边界和现场一致；重开不补发。已查证（代码、上面的测试）。
- 回退边界：从历史里删通知时，同步平移 LSP 诊断提示、恢复文件提示、上下文预算提示、压缩摘要的下标和回退边界的 `messages`（`rewind.rs` `remove_message`）。我逐个对了 `State` 里存历史下标的字段，就这几样；`user_messages`、`tool_images` 存的是消息本身，不受影响。回退掉 wait 所在那一轮时，结果和旧做法一样随那一轮一起退掉，没有新的丢失。压缩后重新补入的待发通知也是 `BackgroundNotice` 记录，撤回和重放规则同样适用。已查证（代码）；回退和压缩这两条没有专门的测试，属于读代码的结论。
- 其他子 agent：登记只针对具体的子会话和轮，其他子 agent 和同一子 agent 之后的轮照常通知；撤回只移除对应的那张卡片。已查证（`wait_only_acknowledges_terminal_results_and_keeps_already_sent_notices`、上面测试的后半段）。已经发给模型的通知只登记、不删，已发历史前缀不变。已查证（同一测试）。
- 锁：登记在服务端拿着父操作锁、再拿父状态锁，顺序不变。已查证（代码）。

### 建议改

1. **主会话撤回一轮时，这期间到达的子 agent 完成通知会丢**（复核时看到，`42d7724` 就有，和本次返工无关）
   - 位置：`crates/canter-core/src/runner.rs` 撤回分支（`state.restate_background_notices(removed)`）；`crates/canter-core/src/background.rs` `restate_background_notices` 只按 `notice_id`（后台命令编号）补回通知，`requeue_background_cards` 只保留还在历史里的卡片。
   - 问题：主会话一轮开始后、模型还没有任何输出前（`model_started` 为假，包括首个请求等第一个字的时间），如果某个子 agent 刚好做完，完成通知会写进这一轮之后的历史。用户此时按 Esc 撤回这一轮，历史从这一轮的边界截断，通知被删；补回逻辑只认后台命令通知，子 agent 通知不会补回，卡片也被丢掉，之后再也不会交给模型或叫醒（结果还留在子会话快照里，模型自己再调 wait_agent 能拿到）。窗口不大，但首个请求慢时有几秒。已查证（代码），没写测试复现。
   - 改法：撤回时对被删掉的子 agent 通知，同样按「还没交付、没登记」补回（比如 `restate_background_notices` 对带 `agent-result-` 事件 ID 且不在已交付集合里的通知重新 `background_notice`）。
