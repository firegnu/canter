### 意见

1. **建议改（已查证）**：`crates/canter-core/src/runner.rs:113`，撤回（P2-59）截断历史时没同步 `lsp_delivery.notices`。
   - 问题：回退（`rewind.rs:509`）和恢复（`context.rs:164`、`:173`）截断时都做了 `retain(< messages)`，在线撤回漏了。晚到诊断在新一轮第一次请求前追加，这时模型还没开口，撤回照样成功；通知随这一轮被截掉，索引却留着，之后落在这个位置的别的 `Message::User` 在压缩时被标成 `Tool diagnostics`。临时测试：上一轮留下晚到诊断 → 新一轮请求发出后马上撤回 → 跑一条 `!echo hi` → 用户发「REVIEW user words」→ 手动压缩。压缩请求里是 `Tool diagnostics: REVIEW user words`，应为 `User: REVIEW user words`；用户原话可能因此进不了「User's words」。重开会话后索引按存盘重算，会恢复正常。要同时满足「上一轮留下晚到诊断、60 秒内撤回、之后恰好有用户消息落在那个位置、重开前压缩」，算罕见组合。
   - 改法：在 `split_off(messages)` 后加 `state.lsp_delivery.notices.retain(|index| *index < messages);`，并按上面的流程补一条回归测试。

2. **建议改（回退已查证；撤回、压缩是读代码）**：`crates/canter-core/src/lsp.rs:19` 的已交付基线 `seen`（更新在 207–215 行），回退、撤回后不回滚。
   - 问题：`Delivery::rewind`（`lsp.rs:712`）只丢待发和到期记录。回退把交付过诊断的那段历史截掉后，`seen` 仍当模型看过。临时测试：写入 "bad"，快速结果列出 `main.fake:1:1: error fixture error` → 连对话带文件回退到这一轮之前 → 模型再写同样内容，这次工具结果是 `main.fake (fake). Only new or changed diagnostics are listed.` / `1 error, 0 warnings.` / `Resolved since last report: 0.`，不列错误本身；而这次请求的历史里已经没有第一次的报告，模型只知道有 1 个错误，不知道在哪里。「回退后重做」是正常用法。撤回同理（读代码）：被撤回通知里的条目已经记进 `seen`，对应票据也标了 `reported`，之后既不会再给，也不会报到期。压缩后摘要未必留下原条目，也可能少给。这是少给，不是重复或复活，不在「必须改」那几类里，所以记建议改。
   - 改法（交主控选）：最简单是回退、撤回（以及压缩）时清空 `seen`，保留 `batches`（防止同一批次再发一次），下一次报告重新标「First report for this file: pre-existing problems may be included.」，代价是可能重列仍在历史里的条目；精确做法是在每轮边界记下 `seen` 的快照，回退、撤回时恢复到那一轮。补一条回退后重做的回归测试。

3. **建议改（已查证；改的是发给模型的内容，要主控问用户）**：`crates/canter-core/src/lsp.rs:380–399`，LSP 开着时，改没有配置服务器的文件，每次都追加一段「unavailable」。
   - 问题：扩展名没有服务器支持、或文件在同步范围外时，票据立即以 `Unsupported` 失败，`inline` 照「快速不可用」处理。临时测试写 `notes.md`，工具结果末尾多了 `[LSP diagnostics]` / `The file change succeeded.    - 改法：`ErrorKind::Unsupported`（没有服务器、范围外、本轮不同步）时不附文字、不建项目，表现和 LSP 关着一样；配置了服务器但没装、起不来、出错的，照旧报 unavailable。用户停掉的订阅（`Stopped`）每次改文件也会报一遍，要不要也不报，一起问用户。

4. **建议改（推测，没能复现）**：`crates/canter-core/src/lsp.rs:486–497`、`:511`，晚到批次只要 id 更新就发，没有新内容也会发一条通知。
   - 问题：快速结果交付后 60 秒内，服务器对同一文件或同项目的文件再发一次同样的诊断，会生成一条只有文件头、计数和 `Resolved since last report: 0.` 的 `[LSP diagnostics update]`。读代码确认中间没有「没有新内容就跳过」的判断。临时测试用假服务器的 push+pull 模式跑了 5 次，两份结果都落在 500 ms 内，没有触发。真实服务器会不会经常这样重发（pyright 改一个文件后重算其它打开的文件，rust-analyzer 开了 checkOnSave 后再发一次），本轮不能装服务器，不知道。
