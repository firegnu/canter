## 现象

- 条件：canter-test-ts，压缩线 60000，deepseek-flash（思考 high）。
- 起因：试跑目录残留的 `dist/` 里有旧测试，模型拷去当参考答案。
- 每轮它要同时读源码、测试和这些旧测试，约 4 万 token。压缩后的起点是 2.2–3 万，读到一半就碰到压缩线；压缩删掉刚读的内容，摘要又让它去重读。
- 结果：10 分钟压缩 12 次，约 30 秒一次，一件没提交，工作区一行没改，花了 $0.14。
- canter 不会察觉，也不停、不提醒，只能人看出来按 Esc。

## 为什么会空转（11-02 主控查代码）

- 压缩后起点不是 0：系统提示词和工具说明约 1 万，加摘要、最近用户原话（最多 2 万，`compaction.rs` 的 `KEEP_USER_TOKENS`）、自动重读的最近 5 个文件（每个超过 5000 token 只给路径，`restore_files.rs`）。压缩线 6 万时只剩约 3～3.8 万，不够一轮要读的 4 万。
- 压缩在一轮中间发生（`runner.rs` 每次发请求前看占用），刚读进来的文件被压成摘要里的一两行，摘要「下一步」写「接着读 X、Y、Z」，模型就从头再读。
- 模型看不到离压缩线还有多远，不会改成边读边写。
- `runner.rs` 的 `compacted` 标记只防「压缩完没发请求又压缩」，每圈之间都发过读文件的请求，标记每次重置，压多少次都拦不住；canter 也不看压缩之间有没有改文件、有没有完成计划项。

## 要做的

### 一、告诉模型离压缩线还剩多少

1. **什么时候加**：每次发模型请求前，用和自动压缩判断同一个占用数，跟压缩线（`input_limit`）比。占用第一次跨过压缩线的 75%、90% 时，往对话里加一条提示。每段上下文（两次压缩之间）每个点只加一次；一次同时跨过两个点只加 90% 那条；压缩后重新算。没跨过就不加，不在每次请求都加。
2. **提示的样子**（主控草稿，意思不变的前提下可以改措辞，改了写进完成记录）：
   `[Context budget] 45000 of 60000 tokens used before automatic compaction; about 15000 left.`
   这里的数字只是示例，不能写死：「已用」取当时的占用，「压缩线」取当时的 `input_limit`（跟着模型窗口、`auto_compact_tokens` 走，换模型、改配置后用新的值），剩余是两者之差。75%、90% 也按当时的压缩线算。数字取整到千也行。
3. **怎么记**：照 `[LSP diagnostics update]` 这类内部提示的现有做法记进历史和会话存盘，加在对话末尾，前面的内容不动（缓存照常命中）；重开、分叉、回退后发给模型的内容和没重开时一样。界面上显不显示也照那类提示的现有做法。压缩时它算内部信息：加进 `PREFIX_SOURCES` 那份清单，不算用户原话，不进「最近用户原话」。
4. **系统提示词**：在 `core.txt` 里加几句（主控草稿，可改措辞、意思不变）：
   `- A [Context budget] note tells you how much room is left before automatic compaction. If what you still plan to read will not fit, read only what the next step needs, record findings in the plan or in files as you go, and start making changes instead of reading everything first. After a compaction, rely on the summary and reread only the files you are about to change.`
   `core_deepseek.txt` 等跟着更新。
5. 手动 `/compact`、`/btw`、审查轮、压缩请求自己不加这条提示。

### 二、连续压缩没进展时停下

6. **怎么数**：服务端每个会话记一个数：上次有进展之后自动压缩了几次。自动压缩包括占用过线触发的和服务商报上下文超长后触发的；手动 `/compact` 不算，也不清零。
7. **什么算进展**（数清零）：`write` 或 `edit` 成功改了文件；`update_plan` 里有一项从不是 completed 变成 completed；用户发了新消息（含插话）。目标续跑起的新一轮不清零。用 shell 改的文件、MCP 工具做的事不算进展。这个数只在内存里，服务端重启从 0 开始。
8. **停下**：数到 3（第 3 次自动压缩完成后、发下一个模型请求前）就停下这一轮，不再发请求：
   - 这一轮按「被停下」结束，用户在终端看到原因（英文，主控草稿，可改措辞）：
     `Stopped: context was compacted 3 times in a row with no file edits or completed plan steps. Send a message to continue, or narrow the task.`
   - 有目标在续跑，目标改成 Paused（照用户暂停目标的现有做法），不再自动起下一轮。
   - 轮结束时现有的做完提醒、钩子照常走现有轮结束的路径，不为停下另加。
   - `canter exec` 跑的轮同样停下，退出时能看出是因为这个停的。
   - 停下之后数清零；用户发消息就接着干。
9. 判断放在服务端核心，终端只显示服务端发来的原因。要加协议字段（比如轮结束原因）就照 DESIGN 第 8 条把和 Codex 结构不同的地方写进 DESIGN；能用现有的警告事件和轮结束状态表达就不加。
