### 必须改

1. **namespace 工具缺了必填的 `description`**
   - 位置：`crates/canter-model/src/responses/wire.rs:72`（`json!({"type":"namespace","name":group,"tools":functions})`）；测试 `responses.rs` 里 `request_preserves_prompt_images_and_tools_using_only_allowed_fields` 的期望值照着这个形状写的。
   - 问题：官方 SDK 按 OpenAPI 规范生成的类型里，NamespaceTool 的 `description` 是必填：Python SDK `namespace_tool_param.py` 写 `description: Required[str]`，Node SDK 写 `description: string`（不可省）。namespace 里的函数自己的 description 才是可选。Function calling 指南的 namespace 示例都带 description；Codex `tools/src/responses_api.rs` 的 `ResponsesApiNamespace.description: String` 每次都发（`default_namespace_description` 给 `Tools in the {name} namespace.`）。canter 不发这个字段，带工具的请求在真服务器上很可能直接 400。这样工具循环跑不起来，「要做成什么」第 2、6 条和「一轮对话加工具循环能用」都达不到。
   - 改法：两个 namespace 各加一句固定的英文 description（比如照 Codex 写 `Tools in the canter namespace.` / `Tools in the mcp namespace.`，措辞由主控定）。字符串固定，不随会话变，缓存前缀不受影响；这只是 GPT 适配器的外壳，工具列表的顺序和内容不变。测试期望值一起改。

2. **普通历史里的助手文字用了 `input_text`，真服务器会拒收**
   - 位置：`wire.rs:35-37`，`AssistantContent::Text` 走 `text_message("assistant", text)`，而 `text_message` 固定写 `{"type":"input_text"}`。
   - 问题：Responses 接口不接受 assistant 角色里的 `input_text`，会报 400 `Invalid value: 'input_text'. Supported values are: 'output_text' and 'refusal'.`。2025-10 起 OpenAI 社区有多帖报告，比如 <https://community.openai.com/t/responseinputtext-cannot-be-used-in-easyinputmessage-with-role-assistant/1402481>、<https://community.openai.com/t/input-message-doesnt-support-role-as-assistant/1364269>；Codex 历史里的助手消息一律用 `ContentItem::OutputText`。本件规定以下几种情况只发普通内容：更早轮次、重启之后、压缩（前缀摘要法会把原历史带上）、顺口问、交接、从别家用 `/model` 换到 GPT。这些请求都会带上之前的助手文字，所以一个 GPT 会话从第二条用户消息起就会失败。第 6 条「更早的轮次……只用普通内容」等于没做到；合并后用户真调的 2 次如果在同一个会话里，第二次也会挂。本轮之内的工具循环走 replay（服务器原样给的 `output_text`），不受影响，所以现有测试都过。
   - 改法：assistant 文字照 Codex 发成 `{"type":"message","role":"assistant","content":[{"type":"output_text","text":…}]}`（content 直接写字符串也行），developer 和 user 保持 `input_text`。补一个请求编码测试：历史里有上一轮的助手文字、工具调用和结果，逐字段断言 assistant 是 `output_text`、function_call / function_call_output 的形状对。

### 重点 1～5 逐条核对（除上面两条外没发现问题）

2. 状态机：工具调用的 `ItemCompleted` 只在 `response.completed` 整批校验通过后才发，和 `Finished` 同批；failed、顶层 error、incomplete、EOF 都返回错误；取消时 runner 走 `cancel.is_cancelled()` 直接返回，不执行；`interrupted_with_content` 那条路对 Responses 到不了（出错时不会有已完成的项）。`output_item.done` 不发文字；`ItemCompleted` 会覆盖增量累积的内容，不会重复显示。`observed` 覆盖了增量、`added` 带内容、`done` 和用量；额度错误不可重试；目标模式失败后不再自动续轮（runner 320 行）。

5. 后台同意：每次尝试（包括重试和排队的新轮）都在 `authorization()` 里等界面或同意，刷新令牌后再查一次；子 agent 用根会话的 `Clients` 和本轮账号绑定；等待中可以取消；工具照常跑完、结果存盘，测试覆盖了。`canter exec` 等客户端都以非 observe 方式连 SSE，算在界面里。
