### 重点 1～5 的查证结果

1. **数据**（已查证）：`Store::create_child` 把 `session.updated` 和 `session.parent` 两条事件都写进 `.creating-*` 暂存目录，再整体 `rename` 发布（`crates/canter-store/src/lib.rs:209-216`），所以子会话不会短暂出现在普通列表里。`parent`/`agent` 都是 `serde(default)` 的可选字段，旧存盘照普通会话读（`canter-protocol/tests/agents.rs` 有测试）。状态和结果只由 reducer 从事件推出（`reducer.rs:381-383`、`392-446`），运行时和重放走的是同一个 `apply_event_mut`，重开后一致（core 测试比较了重开前后的 `agent`）。
2. **并发**（已查证，推测部分见建议 5）：操作锁一律先父后子。`Family::lock` 每锁住一层，再 `list_all` 找下一层（`agent_sessions.rs:54-105`）；开子会话必须先拿父会话的操作锁（`agent_sessions.rs:22`），所以删、回退时不会漏掉刚开的子会话，也没找到操作锁成环的路径。所有可预见的拒绝条件（在跑、挂着终端、等批准、回收站目标已存在、回退序号过期）都在动任何东西之前查完；中途 I/O 失败的残留见可以不改 8。
3. **权限继承**（已查证）：模型、思考档位、工作目录、新增目录取父会话快照；权限档位取 `state.approval_policy()`（含当前轮的覆盖值）；`RuntimeContext` 整体复制，所以受限模式、环境变量、受保护路径和父会话一致；沙箱和放行规则文件取父会话的 `options`。之后配置热更新从子会话自己那份 context 出发（`configuration.rs` 里 `old.context.clone()`），不会把受限模式放宽。目前没找到能让子会话比父会话宽的路径；当前轮的「审查」限制没带过去，见建议 2（现在走不到）。
4. **重启**（已查证）：`recover_agent_sessions` 只处理 `parent` 不为空且状态是 running 的会话，处理后状态变 interrupted，第二次启动会跳过；普通会话不动（core 测试覆盖）。它在拿到服务端独占权之后才跑（`startup.rs:83-89`）。失败时的处理见建议 3。
5. **列表**（已查证）：`Store::list` 统一过滤子会话，`--resume`/info 列表、`canter stats` 列表、`-c`、`exec --last` 都经过它；按 ID 读取、恢复、SSE 照常可用（`crates/canter/tests/tui.rs` 新测试覆盖 `-c`、`exec --last` 和按 ID 恢复）。过滤也连带影响了花费统计，见建议 1。

### 建议改

1. **花费统计把子会话漏掉了**
   - 位置：`crates/canter-server/src/http.rs:675-677`（`usage`）。
   - 问题：`/v1/usage`（终端 `/usage` 用它）调用 `store.list()`，现在这个函数会过滤子会话。P2-178 能开子会话以后，子会话花的钱不会算进总额。这碰了「不改统计和花费的算法（P2-180）」这条边界。本件在正式运行时没有开子会话的入口（`App::spawn_agent` 标了 `expect(dead_code)`），所以目前没有实际影响。
   - 改法：`usage` 改用 `list_all()`，保持原来的花费口径；P2-180 再定子会话的花费怎么归到父会话下。最晚在 P2-178 合并前改。
2. **继承时没带上当前轮的限制**
   - 位置：`crates/canter-core/src/agents.rs:171-195`。
   - 问题：权限档位用的是当前轮的有效值，但当前轮的「审查」限制（`review`）没带给子会话。审查轮会拒掉 Write、Edit、非只读 Shell 等工具（`canter-tools/src/permission.rs:247-273`，`runner.rs:1295-1310`），子会话第一轮却是 `review: None`。如果 P2-178 允许在审查轮里开子 agent，子会话就能改文件，比父会话宽。`non_interactive` 也没带过去：`exec` 下子会话会一直等批准，而父会话那边是自动处理（这是卡住，不是放宽）。计划模式是随整份设置复制过去的：子会话的权限检查按计划模式收紧，但模型历史里没有「进入计划模式」的提示。这一条只收窄、不越权，任务的继承项里没列，完成记录里也没写。
   - 改法：P2-178 接工具时决定审查轮里能不能开子 agent，或者把这些限制带给子会话；计划模式要不要继承也一起写进 DESIGN。本件的代码可以先不动。
3. **任何一个子会话补记失败，服务端就起不来；每次启动都完整打开所有子会话**
   - 位置：`crates/canter-core/src/agents.rs:6-77`，`crates/canter-server/src/startup.rs:88-89`。
   - 问题：只要有一个子会话 `store.open` 或 `append` 失败（比如 `StoreError::Locked`，或磁盘满），整个服务端就会报 `cannot recover interrupted child sessions` 起不来。普通会话是打开时才补记中断，不会挡启动。另外，函数先对每个子会话做 `store.open`（重放全部事件，再整个读一遍 `model-history.jsonl`），然后才判断是不是 running。P2-178 以后子会话会越来越多，启动会变慢。
   - 改法：单个子会话失败时记日志跳过，等下次启动或按 ID 打开时再补；先用便宜的办法挑出 running 的（比如摘要里带上 agent 状态），再去 open。
4. **`/agents` 读不到其中一个子会话，就整个请求失败**
   - 位置：`crates/canter-server/src/http.rs:589`。
   - 问题：直接删某个子会话只拿那个子会话的操作锁，不拿父会话的锁。所以 `/agents` 先用 `list_all` 列出了它，等到 `read` 时它已经进了回收站，`?` 让父会话的 `/agents` 直接返回 404 `session not found`。另外，没打开的子会话每次都要从磁盘完整重放并计算花费，P2-179 如果轮询这个接口会比较重。
   - 改法：遇到 NotFound 就跳过这一条；P2-179 之前考虑改成轻量读取。
5. **回退时会话状态锁是先子后父，和删除的顺序相反**
   - 位置：`crates/canter-server/src/agent_sessions.rs:166-198`。
   - 问题：回退先拿各个子会话的 `maintenance()`（核心状态锁），再进 `session.rewind` 去拿父会话的状态锁；删除则是先父后子。现有代码里，只有核心 `spawn_agent` 会在持有父会话状态锁时去拿子会话的锁，而且那个子会话是新建的，不可能在回退的锁集合里，所以现在不会死锁（推测；没做并发实测）。如果 P2-178 加了「持有父会话状态锁时操作已有子会话」的路径（比如在父会话状态锁里实现 send_input、wait_agent 或叫醒父会话），就可能和回退互相等待。
   - 改法：让回退也先拿父会话的锁；做不到的话，在 `SessionMaintenance` 的注释和 P2-178 任务文件里写明这条锁顺序约束。
6. **状态和结果会被几种操作覆盖掉**
   - 位置：`crates/canter-protocol/src/reducer.rs:396-446`。
   - 问题：
     - 不管子会话当时有没有在跑，`session.status` 变成 closed（clientRequest）都会把状态改成 Closed；而结果只在状态是 Completed 时保留。所以一个已经做完、空闲的子会话，被 DELETE 或以后的 close_agent 关掉后，`/agents` 里的 result 就变成 null。
     - 「最近一轮」只排除了 `rewind`。在子会话里手动 `/compact`，或用户跑 `!命令`，各自也算一轮（`compact`、`userShell`），之后状态显示 completed、result 为 null。
     - 任务的说法是状态「跟着最近一轮变」，最终回复「作为交给父会话的结果」存盘。
   - 改法：只有关的时候确实有轮在跑，才记成 Closed，或者 Closed 时保留上一次的结果；`compact`、`userShell` 和 `rewind` 一样不参与计算。P2-178 定 close_agent 语义时一起定也可以。
7. **回退「对话和文件」不会还原子会话改过的文件**
   - 位置：`crates/canter-server/src/agent_sessions.rs:146-207`。
   - 问题：被回退掉的轮里开的子会话会进回收站，但文件只按父会话自己的备份还原。P2-178 起子会话可以在同一个工作目录里改文件，用户回退后这些改动还在。任务没要求还原，所以不算本件的缺陷。
   - 改法：在 DESIGN 的 P2-177 条里写明这一点，P2-178 讨论时决定要不要处理。

### 可以不改

8. **连带移走中途失败会留下一半状态**
   - 位置：`agent_sessions.rs:209-230`。
   - 情况：所有可预见的拒绝条件都在动手前检查完。过了这一步，只有 `close` 或 `rename` 的 I/O 失败才会留下残留：后代已经移走；失败的那个已关闭但没移走；祖先标了 `closing` 还留在登记表里，可以再关闭或恢复。因为按后代在前的顺序移动，不会出现父会话没了、子会话还孤零零留在 `sessions/` 里的情况。这和现有单会话删除失败时的残留是同一类。
9. **开子会话中途失败会留下一个「在跑」的子会话**
   - 位置：core `agents.rs:177-198`。
   - 情况：子会话已经落盘（状态 running）之后，如果 executor、前缀或 `child.input` 失败，函数返回错误，子会话不登记，但目录还在。`/agents` 会一直显示 running，直到下次重启被标成中断。普通会话创建中途失败也会留下目录，是同一类问题。P2-178 接工具时可以顺手关掉它，或者标成失败。
10. **存盘测试没走 `create_child`**
    - 位置：`canter-store/tests/agents.rs`。
    - 情况：这个测试用 `create` 加单独 `append` 来造子会话。`create_child` 的原子发布我只是读代码确认的（见重点 1），没有测试覆盖。
