# 任务：第二期 - 只读工具（读文件、结构搜索）一次多个并行跑

依据：P2-249 候选 #9。
执行：主控
结论：不做（11-08，统计后用户定）。

## 用户原话

- 11-08 主控建议 P2-251 之后先做「编辑更稳」（P2-252），再做「只读工具并行跑」，收益最大但碰并发。用户：「可以」
- 写好任务文件后用户定：范围 A（只并行 `read`、`ast_grep`、`mcp_search`）、先统计、同时最多 8 个、交给 Codex。
- 看了统计后问：「这个做起来难度大吗？爆炸半径有多大？omp或者pi之类的做了吗？」
- 用户：「好，不做，记一下然后推送」

## 原计划（没做）

一次回复里连在一起的只读调用同时跑，结果仍按模型发出的顺序记进历史；碰到写文件、命令、提问等调用就等前面的跑完再单独跑；批准一次一个、Esc 能停、P2-251 护栏、计划模式、钩子、子 agent 照旧。路由：重 / 交叉审查要 / 碰要害。

## 别家怎么做（只读参考）

- Codex（`codex-rs/core/src/tools/parallel.rs`）：一把 `RwLock`，标了「支持并行」的工具拿读锁同时跑，其余拿写锁单独跑；shell 命令（`exec_command`）也标成支持并行。
- pi（`packages/agent/src/agent-loop.ts`）：默认**所有工具并行**（包括命令、写、改），先按顺序做准备和检查，再同时执行；同一文件的改动用 `file-mutation-queue.ts` 排队；工具标了 `executionMode: "sequential"` 时整批退回一个一个跑。
- omp 基于 pi，没单独核对。

## 统计（11-08，主控用 `canter stats` 和会话记录只读统计，用户同意）

用户本机 246 个会话：

| 项目 | 数 |
|---|---|
| 等模型回复 | 9.6 小时（5159 次请求） |
| 工具执行 | 2.0 小时（其中命令 55 分钟） |
| `read`、`ast_grep`、`mcp_search` | 1961 次共 20 秒，平均约 10 毫秒 |
| 方案 A：连在一起的只读调用全并行能省 | 8.6 秒（445 组，多是 2～4 个一组，最大 13 个） |
| 命令也全并行（方案 C 上限）能省 | 45 秒，单组最多 4 秒 |

跑得久的命令（测试、编译）几乎都是模型单独发的；读文件本身只要几毫秒。

## 为什么不做

- 收益：A 只省 8.6 秒，连命令都并行也只省 45 秒，时间大头在等模型回复。
- 难度中偏难：`runner.rs` 的 `execute()` 约 300 行、十几处拿会话状态锁（批准、检查点、钩子、LSP、后台同步、记事件、P2-251 护栏），要拆成「按顺序检查和批准 → 同时执行 → 按顺序记结果」。
- 爆炸半径大：每次工具调用、所有会话和子 agent 都走这个循环；出错会让结果顺序乱、Esc 停不干净、锁卡死会话。
- 多个耗时任务同时做，canter 已经有子 agent（最多 4 个同时跑）。
- 以后如果真要提速，先看减少请求次数或让请求更快（P2-249 #5 压缩保留最近记录、#10 提前压缩）。
