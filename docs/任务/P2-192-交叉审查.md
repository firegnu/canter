### 1.（必须改）受管收尾会再关一次已经不在册的旧实例，打断后来重开实例的子 agent

- 位置：`crates/canter-server/src/managed.rs` 的 `close_sessions`（69 行）、`finish`（82 行）；牵涉 `crates/canter-core/src/session.rs:1981`（`close_inner` 里的 `interrupt_agents`）、`crates/canter-core/src/agents.rs:67`、`crates/canter-server/src/http.rs:88`（新实例打开时把仍开着的子 agent 挂上去）。
- 问题：owner 按会话 id 存的是认领时的实例句柄。实例被别人关掉、移出登记表后，句柄还留在 owner 里，owner 退出时照样对它调 `Session::close()`。核心的 close 对已关实例不会提前返回，会再遍历旧实例的 `agent_children`。这个列表关闭时不清空；子 agent 会话在父会话关掉后只是被打断、仍然开着；新实例打开时 `register_session` 又把同一个子 agent 挂到新实例上。所以旧实例的第二次 close 会：取消子 agent 正在跑的轮，并把这一轮记进 `suppressed_agent_turns`（结果不再通知父会话），暂停它的自动轮，停掉它的后台命令。这些都是新实例（别的终端）正在用的。原来的 HTTP DELETE 只关登记表里的当前实例，没有这条路。DESIGN 写的「关闭针对登记的会话实例，不误关后来重新恢复的实例」对子 agent 不成立。现有测试 `managed_owner_cannot_close_a_later_unmanaged_resume_of_the_same_id` 只看父会话状态，没覆盖子 agent。
- 怎么触发（两种都是设计里明确支持的用法）：
  - 两个受管终端 A、B 都打开了会话 S（S 有子 agent C）。A 退出，S 的实例 I1 关闭，C 被打断但仍开着。普通终端 N 恢复 S，得到 I2，C 挂到 I2 上，N 让 C 接着干活。之后 B 退出（或被杀、10 秒后），对 I1 再 close：C 在 I2 下的活被打断、后台命令被停、结果回不到 I2。
  - 受管终端 M 开过 S（带子 agent）后 `/new` 切走；别的客户端 `DELETE` 了 S；N 恢复 S 并继续用子 agent；之后 M 退出，结果同上。
- 改法：受管收尾只关「仍在登记表里的同一实例」，而且比对和关闭之间不能让新实例插进来。比如在 `session_locks` 里比对 `same_instance` 后再关，关完在同一把锁里移出登记表（照 HTTP `close` 的语义，不另写关闭逻辑）；或者让核心对已经 Closed 的实例再次 close 时直接返回、不再动子 agent（这要改核心，由主控定）。顺带在 `claim` 时把 owner 里已关的旧实例清掉。补一条测试：受管 owner 认领带子 agent 的 S → 普通 `DELETE` S → 普通恢复 S，让子 agent 跑一轮或起一个后台命令 → `DELETE` owner → 子 agent 那一轮和后台命令不受影响。

### 2.（建议改）旧服务端排空期间，受管终端正常退出发的 DELETE 不起作用

- 位置：`crates/canter-server/src/managed.rs:84`（`finish` 遇到 `draining` 直接返回）、`crates/canter-server/src/http.rs:97`。
- 问题：`disarm` 把宽限计时和显式 DELETE 一起停了。排空最长要等 UPGRADE_GRACE 60 秒再加关会话的时间；这期间受管终端正常退出，会话由排空按 `ServerShutdown` 关闭。普通终端重连时见到 `ServerShutdown` 会在新服务端自动恢复（`run.rs` 的 `reconnect`），于是另有普通终端连着的那些会话在新服务端照样开着，「照样收尾」没做到。原有的 HTTP `DELETE /v1/sessions/{id}` 在排空期间照常生效，受管的显式退出反而更严。窗口窄（升级期间退出，且另有普通终端连着），任务第 4 节只要求「断线」不误关，所以不列必须改。
- 改法：`disarm` 只停宽限计时（`finish(.., Some(generation))`），显式 DELETE（`finish(.., None)`）在排空期间照常走关闭。关闭是分离任务，和排空时来的 HTTP DELETE 一样，期限链不变。不改的话，在 DESIGN 受管理模式「升级」那条里写明这个边界。

### 3.（建议改）受管分支收到信号时整段丢掉界面，跳过了原来退出时做的几件事

- 位置：`crates/canter-tui/src/run.rs:427`（外层 `select!` 的 `shutdown.wait() => Ok(None)`）。
- 问题：不带选项时 TERM 走 `run_connected` 自己的退出：`leave_tab` 清掉标签页标题和进度标记，返回会话 id 并打出 `To resume: ...`。受管分支直接丢掉 future，于是标签页标题和进度标记（OSC 9;4）留在终端上，也不打恢复提示。另外，如果当时开着外部编辑器（`editor::open` 的子进程没设 `kill_on_drop`），canter 恢复终端后退出，编辑器还占着终端，它的临时目录已被删掉。HUP 时终端已经没了，影响不大；TERM（外部程序停 canter、终端还在）时看得到。
- 改法：外层收到信号后，先给 `operation` 一小段时间（比如 300 毫秒）走内部同一个信号的正常退出，过时再丢；`close` 的预算相应扣掉，总和仍在 5 秒内。最少也要在丢掉后补一次清标签页标题。

### 4.（建议改）owner 已被收尾而终端还活着时，终端无限重连，提示也含糊

- 位置：`crates/canter-tui/src/managed.rs:83`（`watch` 每 250 毫秒重连）、`run.rs` 的 `pump`（每 500 毫秒）；`crates/canter-server/src/managed.rs:24`。
- 问题：保活断开超过 10 秒（或别的原因让 owner 被封住）后，服务端对这个 ID 一律回 409。终端的 `watch` 和 `pump` 会一直重试，界面一直显示 `Reconnecting: managed client has exited`，直到用户自己退出。另外，未知 ID 和服务端排空也回同一句 `managed client has exited`：升级窗口里，新服务端还不认识这个 ID 时用户 `/new`，看到的是「已退出」，容易误解。

### 第 1 条修好没有

修好了。`close_sessions` 现在先拿 `session_locks(id)`，只有登记表里仍是认领时的同一实例（`same_instance`）、且这个实例不是 `Closed`，才放锁走原来的 `close_session`。上一轮的两条触发路径都被挡住了：
- 旧实例已移出登记表，新实例由别的终端重开：`same_instance` 不成立，跳过，不再碰挂到新实例上的子 agent。
- 已经 Closed、还没移出登记表：状态检查跳过。

新加的两条回归（`managed_stale_parent_does_not_interrupt_reopened_parents_child_work`、`managed_closed_parent_still_registered_does_not_interrupt_child_work`）正好覆盖这两种，断言子 agent 的新一轮仍在跑、后台命令仍在跑；它们用暂停点等实际收尾结束，不靠睡眠猜时间。剩下的窗口是：检查放锁之后、核心 close 开始之前，旧实例被别人关完、移出、又被重开，新实例的子 agent 也开了新活。这和两个客户端同时普通 DELETE 同一会话的窗口一样（普通 DELETE 连 Closed 检查都没有），主控已接受，同意。

### 这次改动有没有引入新问题

- **claim 新拿 `app.sessions` 后的锁顺序**：没问题。现在的顺序是 `session_locks(id)`（调用方持有）→ `app.sessions`（tokio）→ owner（std）。owner 锁只在不 await 的同步段里拿，也没有任何地方先拿 owner 再等 `app.sessions` 或 registry。服务端所有拿 `app.sessions` 的地方（`opened_session`、`opened_sessions`、`close_session` 的移除、`agent_sessions` 两处移除、trash）都是拿了马上放，持锁期间不再等别的锁。所以 sessions → owner 和 registry → owner 两条顺序不会成环。claim 里 owner 已关时调 `close_sessions` 只 spawn，派出去的检查要等调用方放掉 `session_locks(id)` 和 `app.sessions`，不会自锁。`owner` 为 `None` 时 claim 在拿锁前就返回，普通终端路径不变。
- **检查时 snapshot 会不会在持锁时等很久**：不会比现有路径更久。`&&` 短路，只有当前在册的同一实例才调 `snapshot()`。它只等核心状态锁，再克隆一份快照；`resume` 的已打开分支本来就是「拿 `session_locks` → `snapshot()`」，所以这里没有新的锁顺序，也没有新的等待上限。核心状态锁不会在等 `session_locks` 时被持有：否则现有的 resume 和子 agent 工具早就会互锁。专门的回归 `managed_close_finishes_when_an_agent_tool_waits_for_the_session_lock` 覆盖了上一版的死锁：子 agent 工具已过取消检查、卡在等父会话锁之前，收尾检查照样做完、放锁、关完。排空和停机不拿 `session_locks`，`--replace` 的 90 秒、105 秒不受影响。
- **其它**：`claim` 里按登记表清掉已移出的旧句柄，只会删「已关、已移出」的实例，不会误删在册实例，顺带解决了上一轮第 5 条的旧实例句柄部分（墓碑仍在，照旧可以不改）。新加的暂停点都在 `#[cfg(test)]` 下，生产路径不受影响。普通 HTTP DELETE 和共用的 `close_session` 没改。
