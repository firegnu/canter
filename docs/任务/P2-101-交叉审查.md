## 重点看

1. **叫醒和别的事撞在一起**：叫醒正好碰上用户发消息、按 Esc、批准框弹出、压缩、服务端关闭时，会不会抢掉用户的输入、开出两轮、或者卡住不再叫醒。
2. **事件不丢不重**：压缩、回退、重开会话之后，没送到模型的事件还在、只送一次；补记的事件不会再触发叫醒。

### 1. 必须改：干活时到的叫醒事件，这一轮结束后不叫醒，卡片也看不到

- 位置：`crates/canter-core/src/background.rs:91`（只在空闲时设叫醒时间）、`:309`（匹配第一次出现时记下当时忙不忙，忙就永远不叫醒这一批）；`crates/canter-core/src/runner.rs:155-162`（一轮结束、`active = None` 后没有补设叫醒）；用户 `!` 命令轮和手动压缩轮不走 `background_cards`，卡片不挂出来。
- 问题（已查证）：事件来时会话在干活，只进待送列表和模型历史，不设叫醒时间。如果这一轮之后不再发模型请求，轮结束后会话空闲、事件没送到模型，也不会再叫醒；卡片要等下一次模型请求才挂到那一轮上，用户在界面上也看不到。要等用户再说话才送到。临时测试结果：
  - 模型 `shell {background:true}` 起命令后，用户再说一句；模型这一轮唯一一次回复还在输出时命令结束（exit 7）→ 回复结束后再等 3 秒：仍是 2 轮、0 张事件卡片、没有叫醒；用户再说一句，第 3 轮请求里才有「Exit code: 7」。
  - 用户前台 `!` 命令在跑时、手动 `/compact` 进行中时，模型的后台命令结束 → 同样：2 轮、0 张卡片、没有叫醒。
  - 另外两种同一原因（读代码推出，未单独跑）：事件进 2 秒合并窗口后、叫醒前用户敲了 `!cmd`（`user_input()` 清掉叫醒时间）或 `/compact`（到点时不空闲，叫醒时间被清掉）；第一次叫醒之后 2 秒外到的第二个事件，正好落在叫醒轮最后一次回复期间。
- 为什么算必须改：这是主路径，不是罕见时机。模型起后台构建/测试后通常紧接着用一句话结束本轮，命令在这句回复输出期间结束很常见；叫醒轮自己也一样会漏掉紧跟着的下一个事件。对没人在场的会话，这次叫醒等于丢了，正是重点看第 1 条问的「撞上压缩……卡住不再叫醒」，也不符合「怎么算做完」第一条「模型空闲就被叫醒开一轮」。任务文件「正在干活……附在下一次请求前，不另开一轮」，我理解是干活时不插一轮，没有说这一轮已经没有下一次请求时怎么办；Claude Code 忙时到的后台通知是排着、空闲后再处理（据我了解，本轮没查证）。主控如果认为原文就是要等用户说话，这条改成问用户，不算实现错。
- 改法：在 `PendingEvents` 记一个「有该叫醒、还没送到的事件」标记。忙时到的叫醒事件置上：命令结束看 `wake`；匹配看 `allowed`，不再看第一次出现时忙不忙（`output_wakes`）。事件随请求送出（`consume_background_notices`）、用户输入时清掉。一轮结束时（runner 里 `active = None` 之后、队列为空、没被 Esc 打断、没在关闭或排空），标记还在就设叫醒时间（now+2s，沿用合并），上限、`auto_wake_limit`、排空仍由 watch 那段检查。回退、压缩补记的卡片不置标记，保持「补记不触发叫醒」。补测试：最后一次回复期间命令结束 → 回复结束后开叫醒轮；同样情况按 Esc 打断的 → 不开；用户 `!` 命令轮、手动压缩轮期间结束 → 轮结束后开叫醒轮。

### 2. 建议改：不能叫醒时，频繁匹配每 2 秒存一条新通知，不封顶

- 位置：`background.rs:321-333`（每到点就取走匹配，每批变成一张可见卡片、一条模型历史、一条存盘记录）；`PendingEvents.all`（`background.rs:13`）留着会话里所有可见事件，打开会话时全部恢复。
- 问题（已查证）：`auto_wake_limit: 1`，盯着的命令每 0.25 秒出一行 `error`，11 秒里：叫醒 1 次后暂停，之后每 2 秒一批各成一条，用户再说话时那次请求带了 5 条「output matched」通知，5 张卡片一起挂在用户那一轮。每条最多 4 KiB 多，总量没有上限。叫醒次数确实被 2 秒合并和上限挡住了（重点看第 3 条这部分没问题）；但没人在时（到了上限、`auto_wake_limit` 为 0、叫醒轮在等批准或提问没人答），开发服务器一直报错的话，几十分钟能攒出几 MiB 文字，用户回来第一句话的请求很大，可能直接超窗口、触发压缩。要「一直匹配的命令 + 没人在」才出现，记建议改。
- 改法：不能叫醒时不急着取走匹配，让它留在每条命令自己的有界缓冲里（本来就只留最近 20 行、4 KiB，并记跳过数），等下一次请求（runner 的 `sync_background(true)` 本来就会取）或下一次叫醒再一次取成一条；或者把同一条命令还没送出的批次合成一张卡片。

### 3. 可以不改

- `background.rs:171`：`auto_wake_limit` 为 0 时，每次用户说话后第一个空闲事件都会在最后一轮追加一张「Auto wake paused」卡片。用户自己关的叫醒，每次都提示有点吵；可以只在第一次提示，或 0 时不提示。
- 第 10 次叫醒时，暂停卡片在那一轮开头就出现（模型还在跑）。文字是「已到上限」，意思对，不影响使用。
- 卡片正文是给模型看的英文原文（`[Background command 1 finished: … Use shell_output …]`），任务文件举例是「后台 #1 结束（exit 1）」。卡片标题已经有「Event Background #1」，能分辨，不影响验收。
- 回答批准、提问不清零连续叫醒次数，只有发消息和 `!` 命令清零。这样更保守，最多提前暂停。

### 重点看逐条

1. 叫醒和别的事撞在一起：抢输入、开两轮没有找到问题。开轮都在同一把锁下检查 `active`、队列、待答请求；runner 收尾时在同一把锁里接排队的输入，中间没有空档；`input_waiters` 让正在进来的 `/input` 先走；`!cmd` 撞上叫醒轮会被拒，终端把草稿放回输入框，不丢；Esc 只停叫醒轮、不撤回、不立刻再叫醒；排空和关闭不再开轮。卡住不叫醒见第 1 条。
2. 事件不丢不重：压缩（压缩前排着的、压缩中新到的都补回，按内容去重）、回退和撤回（按原命令卡片是否还在补记，同一事件标识，`background_notice` 按内容去重）、重开会话（从存盘的 `visible` 恢复卡片，没挂出来的重新排上）都对，补记不设叫醒时间。没有发现重复送。
3. 不会一直花钱：计数只在叫醒开轮时加，`/input` 和 `!` 命令清零，到上限、上限为 0 都不开轮；频繁匹配时叫醒被 2 秒合并和上限挡住。通知堆积见第 2 条。
4. 谁的命令叫醒谁：来源存在后台条目上，Ctrl+B 转后台不变；用户命令只看结束时是否还挂着 monitor；`shell_stop`、`/ps`、`/stop`、服务端关闭都会先取消 stop 令牌或关闭令牌，`wakes_on_exit` 和匹配的 `allowed` 都检查。符合任务文件。
