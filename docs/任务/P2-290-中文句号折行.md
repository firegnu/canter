## 看到的

`crates/canter-tui/tests/expected/replay.txt`（提交 `f358fa1` 起）里，80 列宽的屏幕上一段折起来的思考画成：

```
∴ 用户想把 README 的安装步骤换成 cargo install。先读 README 看现在怎么写的，再改
  。
```

句号单独一行。折行在 `crates/canter-tui/src/text.rs` 的 `break_row`：英文在空格处断，宽字（中文）前后哪里都能断，所以「。」前面也能断。回答、思考、用户的话、卡片里折行的文字都走它，不是 11-13 那次改动带进来的。

## 要的结果

1. 收尾的标点不出现在行首：放不下时，把它前面那个字一起挪到下一行，这一行少一个字。
2. 连着的几个收尾标点（`。」`、`……`、`？！`）算一块，一起挪。
3. 开头的括号、引号不留在行尾，跟后面的字一起到下一行。
4. 不管怎么挪，一行都不超过屏幕宽度。挪不动的时候（比如这一行除了标点没有别的字可挪），照现在的样子断。
5. 英文照旧在空格处断；别的折法、复制出来的文字都不变。

## 定下的（主控建议，用户 11-13：「都按你的建议，开始做吧」）

- 哪些算收尾标点。建议：中文的 `。，、；：？！…—）」』】》〉”’`，全角的 `）］｝`；还有紧跟在中文后面的英文标点 `, . ; : ! ? ) ] }`（比如「中文,」的逗号）。
- 哪些算开头的括号、引号（第 3 条）。建议：`（「『【《〈“‘` 和全角的 `［｛`。这次一起做。
- 第 4 条挪不动时：建议照现在断（标点在行首），保证不超宽、不丢字；不选「让标点伸出行尾」，终端里伸不出去。

## 完成记录

- 做了什么：`crates/canter-tui/src/text.rs` 的 `break_row` 在中文字旁边找断点时，跳过两种位置：收尾标点前（`closes`）、开头括号引号后（`opens`）。于是放不下时退到上一个能断的地方，标点带着旁边那个字一起换行；连着的标点之间都不能断，自然成一块。一行里没有能断的地方时照旧在放满处断（原来的兜底），不超宽、不丢字。英文在空格处断的规矩没碰。`crates/canter-tui/README.md`「空行和状态行」下补一条「折行」。
- 验证了什么：先在 `text.rs` 加四条单元测试，跑了确认两条因为旧折法失败（`["一二三四", "。"]`、`["一二三「", "四」"]`），另两条（挪不动时不超宽、英文照旧）是守住现状的回归；改完四条都过。回放金样本用 `CANTER_UPDATE_EXPECTED=1` 重写，差别只有那段思考：`……再改` / `。` 变成 `……再` / `改。`。canter-tui 全部 729 个测试通过，`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`、`git diff --check` 干净。
- 拿主意的地方：都照「定下的」三条。英文标点只在它挨着中文、本来就能断的地方才管，空格处的断法不变，所以英文句子不受影响。
- 没做的事：没在真终端里看；改动在客户端，canter-desktop 二期做 P2-6 期间不装，等 P2-6 收尾、看完遥测后用户再 `canter upgrade`。
