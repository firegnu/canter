## 重点看

1. **5 条规矩照样成立**：
   - 读盘时不能被打开写入，包括读请求被取消、读盘任务还在跑的情况；
   - 同一个会话只打开一份；
   - 删除和恢复、挂接、事件流挂接不撞车；
   - 关会话只移除自己那一份；
   - 停机不漏关：停机前已接受的新建、恢复都收进来，之后来的被拒。

   逐条找有没有绕过 id 锁、直接查登记表再做慢事的路径，比如 `App::session` 的各个调用方、`ledger`、`EventReader::recv` 的重新挂接、`registry_changed` 的等待。
2. **死锁和锁顺序**：
   - 有没有拿着登记表锁去等 id 锁、同时等两把 id 锁，或者从 Core 反过来拿登记表；
   - `/v1/usage` 逐个会话拿 id 锁时，会不会和某个会话的长操作互相等；
   - SessionEnd 钩子回调 canter 的接口时会怎样；
   - `draining` 读锁和 id 锁的先后顺序。
3. **`session_locks.rs` 的回收**：弱引用索引在「旧条目正在析构、新条目刚插入」时不会删错，也不会让两个调用方拿到不同的锁；被取消的等待者不留下条目；不会无限长大。
4. **停机期限**：完成记录里的期限账（85.4 / 97.45 / 102.05 秒）有没有漏掉串着等的步骤。新的写法下，停机会不会去等某个 id 锁后面排着的长读盘。
5. **范围**：没改协议和返回内容、终端、盘上格式；P2-105 的读法、P2-32 的删除判定没动，只改了怎么拿锁；测试用的暂停点（`pauses`）只在测试构建里有。

### 可以不改（记下，供主控决定是否进 HANDOFF）

**1. 删除等 SessionEnd 钩子时，钩子回调同一会话或 `/v1/usage`，会卡到 10 秒被杀**

- 位置：`crates/canter-server/src/http.rs:1103-1136`（`trash` 全程持该 ID 的锁）→ Core `close_inner` → `hooks::drain`（`crates/canter-core/src/hooks.rs:235`，10 秒超时后杀掉钩子）。
- 已查证（实测）：在临时拷贝里加探查用例，SessionEnd 钩子用 `curl --unix-socket` 回调 canter，再删会话：
  - 钩子读**另一个**会话：删除 29 ms 完成，钩子正常跑完；
  - 钩子读**同一个**会话：删除 10,009 ms 后返回 204，钩子没跑完（被杀）；
  - 钩子调 `/v1/usage`：10,008 ms 后返回 204，钩子被杀。
  之后服务端照常响应。不会永久死锁，删除结果也对。
- 不改的理由：有 10 秒上限，原实现下钩子回调**任何**要登记表锁的接口都会这样卡，现在只剩同一会话和全局用量；P2-32 交叉审查第 3 条的影响面也随之缩到同一会话。

**2. 全局 `/v1/usage` 会等任何一个会话的长操作**

- 位置：`http.rs:600-629` 逐个会话调 `ledger`，`ledger` 先拿该会话的锁（`http.rs:541`）。
- 已查证（读代码）：某个会话在恢复长历史（开发量的 52 MB 约 6.4 秒）或删除等钩子（最长 10 秒）时，`/v1/usage` 读到它就要等。等的时候自己不持任何锁，对方也不等它，不会互相等。README 已写明这个边界。
- 不改的理由：全局用量本来就要读那个会话；只有命令行 `canter usage` 用它（`crates/canter/src/lib.rs:256`），终端的 `/usage` 走单会话用量（`crates/canter-tui/src/run.rs:691`），不受影响。

**3. 同一会话里，挂事件流时从文件开头扫一遍，期间这个会话的命令要排队**

- 位置：`EventReader::new`／`recv` 在该会话的锁里调 `session.subscribe`（`http.rs:1153-1164`、`1207-1213`）；Core 新建的读取器从偏移 0 开始（`crates/canter-store/src/lib.rs:307-315`），`read_after` 从头解析到 cursor（同文件 `87-117`），即使 cursor 是最新的。
- 已查证（读代码）：长会话上新挂一个终端或事件流时，这个会话的发消息、打断、批准要等这一遍扫完。别的会话不受影响（开发的 `events_new/subscribe`、`events_recv/subscribe` 两组测试覆盖）。
- 不改的理由：原实现下是所有会话一起等（P2-32 把挂接放进登记表锁），现在只挡同一会话，符合任务「同一个会话照样排队」。要再快，是订阅读法的事（P2-105 那条线），不在本件范围。

### 查过没问题的

**1. 5 条规矩**

- 规矩 1（读盘时不被打开写入）：main 上 10 处 `sessions.lock()` 全部换掉了；从盘上读没开着会话的路径（`App::session`、`read`、`ledger`、`EventReader::new`／`recv`、`trash`、`resume`）都在该 ID 的锁里读。读盘的 `spawn_blocking` 闭包自己持有一份 guard（`http.rs:179-183`、`202-206`），请求被取消也要等读完才放锁。从盘上打开会话只有 `resume` 一处（`http.rs:780`），在锁里。开发的取消测试覆盖快照、用量、事件三条路径。
- 规矩 2（只打开一份）：`resume` 放锁取配置后重新拿锁、复查登记、再打开并插入（`http.rs:754-799`）；往登记表插入只有 `resume` 和 `create`（新 ID，`http.rs:839` 起就持锁）两处。
- 规矩 3（删除不和恢复、挂接撞车）：`trash` 从检查到移走目录一直持锁（`http.rs:1103-1136`）；恢复、事件流订阅和挂接都要同一把锁。`trash` 里的 `remove(&id)` 不查 `same_instance` 也安全，因为所有能改这个 ID 登记的路径都要先拿这把锁。已经拿到 `Session` 引用的命令照旧靠 Core 的 `closing`／`available()` 挡迟到写入，这部分没动。
- 规矩 4（关会话只移除自己那份）：`close` 在 Core 关完之后重新拿锁，再在登记表锁里查 `same_instance`（`http.rs:1078-1085`）。
- 规矩 5（停机不漏关）：`begin_drain`（`http.rs:60-67`）和原来三行等价；`resume`、`create` 的整个后台任务持 `draining` 读锁，一直到插入之后，所以拿到写锁时已经接受的都已登记，之后来的看到排空标记被拒。
- `registry_changed`：`recv` 先 `enable` 再拿锁检查（`http.rs:1203-1207`），`resume` 插入后在锁里通知；读完先放锁再等通知，不会漏掉恢复的通知，也不会持锁空等。

**2. 死锁和锁顺序**

- 登记表锁只在同步片段里用：查、克隆、插入、移除；`close` 持着它时只调同步的 `same_instance` 和 `notify_waiters`。没有持登记表锁去等 ID 锁的路径。
- 没有同时等两把 ID 锁：`/v1/usage` 逐个调 `ledger`，每次的锁在读盘闭包结束时放掉，再拿下一个；`create` 只锁新 ID。
- 持 ID 锁时调用的东西（`disk_snapshot`／`disk_events` 把锁传进去、`configure_session`、`opening_warning`、Core 的方法）都不会再拿同一把 ID 锁，也不碰 `App`；Core 不反向拿登记表。
- `draining` 读锁 → ID 锁：所有要准入检查的接口都是先 `draining` 后 `app.session()`；不拿 `draining` 的路径（`close`、`read`、`ledger`、事件流）也不会持 ID 锁去拿 `draining`。
- SessionEnd 钩子回调：见可以不改 1，实测有 10 秒上限。

**3. `session_locks.rs` 的回收**

- 只在旧条目的强引用已经归零（`Weak::upgrade` 失败）时才新建锁；持锁的和排队的都握着 `Arc<Entry>`，所以有人持锁或排队时不会出现第二把锁。
- 析构时用 `std::ptr::eq` 只删自己；旧条目析构时，它的内存还被 Arc 自带的弱引用占着，新条目不会落在同一个地址，所以不会删错。持索引锁期间不 await，也不会在持锁时析构条目（被替换掉的只是 `Weak`）。`SessionGuard` 先放锁再放条目。
- 被取消的等待者会放掉自己的 `Arc<Entry>`，最后一个离开时删掉条目，不会越积越多。开发的单元测试覆盖了取消和重用。
- 已查证（实测）：在临时拷贝里加压测，8 个工作线程、64 个任务在 3 个 ID 上随机加锁、取消等待、把 guard 交给 `spawn_blocking` 释放，共加锁 19,278 次：同一个 ID 从没出现两个持有者，结束时索引为空。

**4. 停机期限**

- 按 `lib.rs` 的执行顺序对过：替换检测 0.2 秒 → 停热加载 → `begin_drain`（取 `draining` 写锁、短取登记、逐个 `drain()`，`drain()` 只设标记）→ 等轮 60 秒 → 并行关会话 2.05 + 2.05 + 10 秒 → LSP 6 秒 → HTTP 5 秒 → 0.1 秒。和 DESIGN 的 85.4 秒一致，没有新串进来的等待；`close_for_shutdown` 不拿 ID 锁。97.45／102.05 秒是新进程那一半，本件没动。
- 停机本身不拿任何 ID 锁。`draining` 写锁仍要等已经接受、正在排同一 ID 锁的命令（比如没开着的会话上的 input，排在同一会话的读盘后面，然后自己再重放一遍）。这部分没有固定上限，DESIGN 已写明不按零算。原来这些命令排在任何会话的读盘后面，现在只排同一会话的，只会更少。
- 原实现拿到写锁后的 `sessions.lock()` 还要等不持 `draining` 的读盘（没开着会话的快照、事件读取），新实现没有这段等待了（`shutdown_does_not_wait_for_an_unopened_disk_reader` 覆盖）。停机时还在 ID 锁上排队的 HTTP 请求，仍由原来的 5 秒上限兜住。
