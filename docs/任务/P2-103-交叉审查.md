   - 问题：
     - 排队：模型还在写方案时（或从另一个终端）发一条排队消息，然后选第 2 项、框里选 Allow all。原会话这一轮结束后马上用这条消息开下一轮，这时已出计划模式、档位是 Allow all；临时测试里模型接着调的 `write` 真的写出了文件。作答的终端已经切到新会话照方案做，两个会话在同一个目录同时改东西，原会话那一轮用户看不到。没达到「怎么算做完」第 2 项的「原会话这一轮结束」，也是并发出错。

### 建议改

1. **作答终端等原轮结束时没有超时，等不到或出错时方案也不开工**
   - 位置：`crates/canter-tui/src/run.rs` `resolve_plan` 和 `plan_withdrawn_inputs`。这是这次新加的代码。
   - 问题：
     - 主循环是在处理按键动作时直接 await 的（`run.rs` 510 行起），等待期间不重画、不收按键，Ctrl+C 也不起作用。
     - 推断（读代码）：原轮收尾写盘失败时（`journal.rs` 只把 `failed` 置上，不关闭事件广播），事件流一直开着，却永远等不到 `TurnCompleted`，终端会卡死。磁盘满这类情况才会碰上。
     - 订阅失败，或者事件流在 `TurnCompleted` 之前断了，就走 `Err` 分支：只提示「Could not recover the original session's withdrawn input」，然后直接返回。新会话没建，撤回的文字也没放回草稿。原会话这时已经出了计划模式、这一轮也结束了，提示却没说方案没开工。
   - 改法：等待加个超时（几秒）。超时或出错时照常建新会话、切过去，再提示撤回的输入没取回、可到原会话去看；或者至少在提示里写明方案没开工、请到原会话的方案卡片里拿全文。
2. **和这次改动无关，复核时才看到**：`resolve_plan` 里，`create_session` 成功、但 `show` 订阅新会话失败时，提示写「Could not start the plan in a new session」。其实新会话已经建好，第一条消息也发了，正在照方案干活；终端却留在原会话，用户可能再选一次，结果两个会话同时做同一份方案。这种情况很少见（刚建完会话就订阅失败）。改法：这种失败的提示写明新会话已经在跑，给出它的名字或 id，让用户用 `/resume` 切过去。

### 可以不改

3. `/rewind` 截掉了退出说明、进入说明还留着，而计划模式已经关了：模型会以为自己还在计划模式。主控定的范围是「计划模式开着时补说明」，这种情况没管；模型调 `submit_plan` 会收到「not in Plan mode」，能自己纠正。
4. 计划模式里 `/rewind` 时，如果进入说明本来就没被截掉，也会再补一条，历史里多一条重复的说明，没有害处。
5. 原会话里排队的 `/review` 也会被撤掉，但终端不会把它放回草稿（`Drafts` 本来就跳过 review）。和 P2-99 按 Esc 中断时一样。
