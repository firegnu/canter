### 必须改

1. **回收站里「父会话不在回收站」的子会话永远不清**
   - 位置：`crates/canter-server/src/cleanup.rs:116`（`cleanup_trash` 只从 `parent.is_none()` 的会话开始找一族）；`cleanup.rs:37` 同样的写法。
   - 问题：回退（`Family::rewind` → `move_to_trash(&removed)`，`agent_sessions.rs`）只把被回退掉的子会话移进 `trash/`，父会话留在 `sessions/`。这些子会话在回收站里 `parent` 不为空，又不是回收站里任何根会话的后代，所以永远不会到期删除。回退一轮里开过子 agent 是正常用法，「回收站里的照同一个天数清」没做到。另外，`cleanup.rs:81-85` 删一族时先删子会话再删父会话，子会话删失败也照删父会话，留下的子会话在 `sessions/` 里同样变成没父会话的，以后也清不掉。
   - 改法：两处都把「`parent` 为空，或父会话不在同一个目录（`by_id` 里没有）」的会话当一族的根；删一族时某个成员删失败就停下，不再删它的上级。加一条测试：回退掉一个带子会话的轮后，子会话在回收站里到期能被清掉。

### 建议改

1. **加锁后没有重读最后使用时间**（重点 1）
   - 位置：`cleanup.rs:44-53`。
   - 问题：到没到期用的是开头 `list_all` 拿到的 `updated_at`，加锁后只查了「现在是否打开」。如果一个过期会话在列出之后、轮到它加锁之前被打开、跑了一轮、又关掉（终端退出时 managed 会关它），这一轮会按旧时间把它删掉。归档的 rows 是加锁后现读的，用量不丢，但会话本身丢了。窗口只有一次清理遍历那么长（每天一次，一般 1 秒内），人手几乎碰不到，所以记建议改；但这是删错，改起来也小。
   - 改法：`Family::lock` 之后对各成员重读摘要（或再 `list_all` 一次），用新的 `updated_at` 和 `last_event_seq` 判断和归档；或者 `guards()` 里 `disk_snapshot` 的结果别丢，拿它的时间判断。

2. **回收站会话删前不算、删后算进 `/v1/usage`**（主控提的那条，我同意记建议改）
   - 位置：`http.rs` `usage`（`live` 只来自 `sessions/`）、`cleanup.rs:149-163`。
   - 问题：会话进回收站后 `/v1/usage` 就不算它；被自动清掉后摘要又把它算回来，当天看到的历史总数会变大。没有重复计算，只是前后对不上。
   - 改法（要用户定）：甲、`/v1/usage` 把回收站里的会话也当「还在的」算进去（花过的钱本来就是花了，删前删后都一致，但改了 P2-7 现有口径）；乙、回收站会话清掉时不写摘要（和现在口径一致，但这部分用量永远看不到）。我倾向甲，要问用户。

3. **摘要文件坏一行就整个用量查询失败、以后也不再清理**
   - 位置：`cleanup.rs:257-269`（`read_archive` 遇到解析不了的行直接返回错误），`cleanup.rs:243-254`（追加不检查文件是否以换行结尾）。
   - 问题：写到一半断电或磁盘满，最后一行不完整；之后 `/v1/usage` 一直返回 internal 错误，`archive()` 也一直失败，清理就停了。下一次追加还会接在那半行后面，把新记录也弄坏。
   - 改法：读的时候跳过解析不了的行并写一行日志；追加前若文件不以 `\n` 结尾先补一个换行。

4. **摘要文件的字段名和 DESIGN 写的不一样**
   - 位置：`cleanup.rs:7-12` `ArchiveRecord` 没有 `#[serde(rename_all = "camelCase")]`，实际写出来是 `session_id`、`event_seq`；DESIGN 第 8 条写的是 `sessionId`、`eventSeq`（`rows` 里是 camelCase）。
   - 改法：合并前统一，建议给 `ArchiveRecord` 加 `rename_all = "camelCase"`；这是存盘格式，上线后再改要兼容旧文件。

5. **清理时在异步线程上做阻塞的文件操作**
   - 位置：`cleanup.rs` 里 `archive()`、`remove_dir_all`，`cleanup_trash` 里的 `Store::new`、`list_all` 都直接在 async 函数里同步调用。
   - 问题：大会话（带图片副本）读事件、删目录可能要几秒，期间占住一个运行时线程，还拿着这一族的会话锁；不出错，但会拖慢同时到来的请求。
   - 改法：整族的「归档 + 删除」放进一个 `spawn_blocking`，`cleanup_trash` 的列目录也一样。

### 可以不改

1. **「每天一次」在笔记本睡眠时会拉长**：`cleanup.rs:178` 用 `tokio::time::interval(86_400s)`，macOS 上单调时钟睡眠时不走，机器每晚睡的话实际两三天才跑一次。启动和升级重启也会跑一次，会话只是晚几天删，不影响数据。真要按墙上时间，可以每小时醒一次、比较墙上时间够不够 24 小时。
2. **`remove_dir_all` 删到一半失败留下的目录**：如果 `events.jsonl` 已删、目录里还剩别的文件，`list_all` 不再列它，以后也清不掉，只占点空间；用量按摘要算，不会错。日志里有记录，用户能手动删。
3. **每个会话都整份重读摘要文件**：`archive()` 每次调 `read_archive`，文件越长越慢；按每天几个到几十个会话，几年内都无所谓。

### 重点逐条

- 重点 1（删到正在用的）：打开的会话（含空闲）、有打开子会话的一族都跳过；新建子会话要父会话打开，清理期间建的子会话不在开头的列表里，会让整族跳过；手动进回收站、打开/续接和清理都走同一把会话锁，测试也覆盖了。缺口是加锁后没重读时间（建议改 1）。没有服务端「从回收站恢复」接口，只能手动挪目录，`cleanup_trash` 加锁后查目录还在不在，挪走了就跳过，没问题。
- 重点 2（用量不丢不重）：先写摘要并 `sync_all` 再删；`/v1/usage` 先读各会话实时账本、最后读摘要，摘要只算不在 `sessions/` 的，和清理的先后顺序无论怎么交错都不重复不漏；删一半失败、重启后再跑，同 ID 同事件序号不重复追加，读取时最后一行为准。子会话各自一行；分叉会话没有父子关系，分叉时不复制用量事件，各算各的。问题在回收站口径（建议改 2）和坏行（建议改 3）。
- 重点 3（删除范围）：所有 id 都来自 `Store::list_all`，它只收经过 `session_dir` 校验的 id（字母数字、`-`、`_`，≤128）且跳过符号链接，`unwrap()` 不会 panic，路径只会落在 `sessions/<id>`、`trash/<id>`；`remove_dir_all` 不跟随里面的符号链接。没碰别的状态目录项。
- 重点 4（配置和定时）：`session_retention_days` 为 0 直接返回，有测试；每次执行时从 `LiveConfig` 现读，热重载后下一次清理用新值；等待时 `select` 着 `app.stopped`，服务端停时退出。正在跑的一次清理不看停止信号，会被运行时关掉时打断，打断点在写摘要之后、删除之前也不会算错。

### 对 Kimi「拿主意的地方」表态

1. 配置名用 `session_retention_days`：同意，和 `auto_compact_tokens` 等现有写法一致。
2. 最后使用时间取会话摘要的 `updatedAt`，回收站也用它、不另记移入时间：同意。用户选的是「按最后一次用的时间」，回收站本来也没记移入时间。副作用是 29 天没用的会话进回收站后一两天就会被清，DESIGN 已写明，可以接受。
3. 装载在服务端的会话即使空闲也不删，其余照 P2-32 的拒绝条件：同意，比任务要求更保守，没有坏处。
4. 摘要每个会话一行、带会话 ID 和事件序号、同 ID 同序号不重复、读取时最后一行为准：同意这个格式；但文件里实际的字段名和 DESIGN 不一致，见建议改 4。

### 这次改动有没有引入新问题

- **加锁后重读**：`Family::lock` 之后重新 `list_all`，用新的 `updatedAt` 判断是否到期，归档也用新的 `lastEventSeq`；成员在新列表里找不到时整族保留，和原来一样保守。回收站在加锁、确认目录还在之后也重读一次。没有发现新问题。
- **`/v1/usage` 的回收站账本**：读完 `sessions/` 的实时账本后读 `trash/`（`live.insert` 返回 false 的跳过），最后读摘要（`live` 里已有的跳过）。和手动移进回收站、自动清理任意交错时，同一个会话最多被算一次：移动发生在读 `sessions/` 之后，账本读不到就不进 `live`，读回收站时补上；已经读到的，读回收站时会被去重跳过。清理是先写摘要再删除，删除前读到的算实时账本，删除后读到的算摘要。读回收站不加会话锁，但回收站的会话不会再被写，`remove_dir_all` 中途读到 `NotFound` 的会跳过、由摘要接上，不会算错。
- **摘要坏行和补换行**：读的时候跳过坏行并写日志，追加前末尾不是换行就先补一个换行。`O_APPEND` 保证写在文件末尾，前面的 `seek`/`read` 不影响写入位置。字段名已改成 camelCase，和 DESIGN 一致；旧的 snake_case 格式没发布过，不用兼容。

### 可以不改

1. `http.rs` `trash_ledgers` 每次查询都新建一个 `Store`，摘要缓存是空的，回收站会话每次都要回放两遍（`list_all` 一遍、`events_after` 一遍）。`/v1/usage` 只在 `canter usage`、`/usage` 时才调用，回收站又有 30 天清理，影响不大。
2. `cleanup.rs` `read_archive` 每次调用都会对同一坏行写一条日志，清理每归档一个会话都要读一次，坏行一直留着时日志会重复出现。只是服务端日志里多几行。
