## 重点看

1. **丢不丢用户文件**：退回后每个文件是不是那一轮之前的内容（同一文件多轮改动取最早的原内容）；那时不存在的文件才删；超过 1 MiB 没存的、恢复中途失败的怎么报告、会不会把文件留成半截；「只退文件」后再「对话和文件一起退」会不会重复恢复或恢复错版本；外部修改的判断准不准，确认前列出的是不是全了。

### 必须改

1. **确认没有和预览绑定，预览之后才在外面被改的文件会被直接覆盖（会丢用户文件）**
   - 位置：`crates/canter-tui/src/rewind.rs:93`（`params.confirmed_external_changes = Some(true)`，不管预览里有没有外部修改都填 true）；`crates/canter-core/src/rewind.rs:387-394`；`crates/canter-core/README.md:167`。
   - 问题：终端拿到预览后，确认请求总是带 `confirmedExternalChanges: true`。服务端执行时虽然会重新算一遍外部修改，但只看这个开关，不看用户确认的是哪些文件。用户看预览、犹豫的那段时间里（几秒到几分钟），编辑器自动保存、用户自己改了一个文件、或者之前留下的后台进程写了一个已跟踪的文件，这个文件预览里写的是 "will restore" 或根本没标外部修改，确认后会被直接退回，外面那次修改就丢了，也没有备份。这违反任务书「确认前列出来、标明『之后在 canter 以外被改过』，用户确认后照样退回」，README 里「执行时再比较一次……返回 conflict」对终端这条路也不成立。
   - 改法：把确认的内容带上。比如把 `confirmedExternalChanges` 改成路径列表，终端只填预览里标了外部修改的那些路径；服务端执行时算出的外部修改文件只要有一个不在列表里，就返回 conflict、什么都不改；终端收到 conflict 后重新预览、重新确认。协议是本分支新加的，还没有旧客户端，可以直接改，同步改 DESIGN 第 8 条、protocol README 和生成的 Schema/TS。补一个回归测试：预览时没有外部修改，之后测试自己改一个已跟踪的文件（模拟用户编辑，这是任务书里的验收场景，不是绕过测试），再用终端会发的参数确认，结果应该是 conflict、文件不动。

### 建议改

1. **重启后的轮边界和恢复出来的模型历史用两套规则数消息**
   - 位置：`crates/canter-core/src/rewind.rs:68-93`（`Checkpoints::restore`）和 `crates/canter-core/src/context.rs:72-123`（`restore`）。
   - 问题：`context::restore` 用 `known()` 滤掉 `Message::Unknown`、只剩未知内容的 assistant 消息，用户消息也只数 `User`/`UserParts`；`Checkpoints::restore` 每条 `Message` 都 `messages += 1`、`users += user_input`，压缩那里也是直接取 `kept.len()`、`user_inputs.len()`。现在 canter 写出的数据两边数出来一样，但模型历史里一旦有新版写的未知消息（升级后再降级），重启后的一次回退会按偏大的下标 `history.truncate`，被退掉那一轮的消息留在内存里接着发给模型；再重启一次，回放用的是 `context::restore` 自己的下标，两次发出去的前缀就不一样了。
   - 改法：只在一处算边界。比如让 `context::restore` 顺带返回 `(turn_id, history.len(), users.len())` 列表，`Checkpoints::restore` 直接用这份；或者 `Checkpoints::restore` 用和 `context::restore` 一样的过滤规则。
2. **写入后的内容超过 1 MiB 时，原内容也不存，这种文件退不回去**
   - 位置：`crates/canter-core/src/rewind.rs:170-196`、`:281`。
   - 问题：原内容或写入内容只要有一个超过 1 MiB，整次改动就记成 unavailable，两份都不存。「模型把一个小文件写成很大的生成内容」或「模型新建了一个大文件」正是 `/rewind` 最该管的情况，但现在小的原文件恢复不了，新建的大文件也删不掉。
   - 改法：原内容不超过 1 MiB 时照样存（新建文件时原内容就是「不存在」）。写入内容超限时只记长度，执行时一律当作「无法确认有没有外部修改」，要用户确认，不要整件标成 unavailable。另外，每次改动的写入内容一般和下一次改动的原内容一样，可以复用同一份副本，省一半盘。
3. **预览里「要删的」也写成 "will restore"**
   - 位置：`crates/canter-tui/src/rewind.rs:75-81`；协议 `RewindFile`。
   - 问题：退回到那一轮之前时会被删掉的新建文件，预览里写的是 "will restore"，用户确认前看不出哪些文件会被删。
   - 改法：`RewindFile` 加一个字段说明是删还是恢复（比如 `delete: bool`），终端显示成 "will delete"。
4. **确认时会话已经变了也照样执行**
   - 位置：`crates/canter-core/src/rewind.rs:376-394`。
   - 问题：预览之后，另一个终端跑完了一轮新的、又改了文件，这时确认，新那一轮也会被退掉，它改的文件也会被退回，但这些都不在用户刚看的预览里。这不算外部修改，也符合「那一轮及以后」，只是用户确认的不是他看到的那份。
   - 改法：预览回复带上当时的 `lastEventSeq`，确认时传回去，不一致就返回 conflict、重新预览。可以和必须改第 1 条一起做。
5. **缓存前缀只在重启后测了，回退后马上发的那次没测**
   - 位置：`crates/canter-server/src/rewind_tests.rs:416-428`。
   - 问题：逐字节比较放在服务端重启、重新打开之后，测的是回放出来的历史；用户最常走的「回退后马上在同一个服务端里接着发」这条路（`rewind_inner` 里的 `history.truncate`），没有断言管着。
   - 改法：回退之后、重启之前先发一句，同样比较 `messages[..len-1]`；重启后那次比较留着。

### 可以不改

1. **只退文件时，模型不知道文件已经退回去了**（`rewind.rs:446-472`，记录轮不进模型历史）。保前缀没问题，但下一轮模型还以为文件是改过之后的样子。要不要在下一条用户消息前追加一句说明（只往后加，不影响缓存），是产品上的事，交主控或用户定。
2. **退对话后，快照里的 `token_usage` 没清掉**，终端显示的上下文用量要到下一次请求后才对。
3. **记录轮的文字写的是内部轮 id**（"Rewind before turn-…"），换成所选那句话的开头会更好认。
4. **删文件时，`write` 当初建的上级目录不删**，会留下空目录。任务书只说删文件，可以不管。
5. **写盘失败时的报告**：文件已经退回，但写模型历史或事件失败时，客户端只收到 internal 错误，逐文件的结果没有传回来。这时会话已经不能再写了，下次打开、预览会照实际内容报差异，可以接受。
6. **跨重开的前缀**：退到会话重开之前的一轮时，用的是这次打开时定下的系统提示词（日期、AGENTS.md），和那一轮当初的请求不是逐字节相同，但和重开以后的请求前缀一致，符合 DESIGN 第 17 条「只在打开会话时定下来」。建议在 core README 写一句。

### 重点逐项结论

1. **丢不丢文件**：退回的版本对，同一文件改了好几轮时取最早的原内容（`files()` 取范围里第一条还有效的改动）；只有那时原内容为「不存在」的才删；工具失败的改动记了 `file_aborted`，不算进去。写文件用执行器原有的「临时文件 + 改名」，不会留下半截文件。超限、副本丢了、路径变了、权限错误都会逐个文件写进预览和记录。我推了「只退文件之后再一起退」的几种顺序：已退的改动标了失效，不会重复恢复；之后再往前退，按还有效的最早改动恢复，版本对。外部修改按「现在的内容和 canter 最后一次写入的不一样」判断，和任务书的定义一致，预览那一刻列出来的也全；问题出在预览和确认之间（必须改第 1 条）。
2. **写到哪里**：恢复走 `Executor::write_file`，删除先 `resolve_path`（会查保护路径和符号链接），解析出来的路径和当初记下的不一致就拒绝；能写到的只有 `write`/`edit` 当初批准并写过的路径，不会多出新的地方。副本是 0600，放在 0700 的会话目录里，副本名只出现在模型历史里；事件、协议回复和记录轮里只有路径和出错原因，没有文件内容。预览读当前文件用的是 `std::fs`，没走执行器，但只拿来比较、不返回内容；真正写回时还会再查一遍。
3. **存盘和恢复**：两份 JSONL 都只往后追加（测试也比了旧内容是新文件的开头）。先写模型历史、再写事件，事件写失败时日志就标记坏了、不再写，下次打开时补发事件，序号对得上；服务端启动时不往会话里写东西，所以补发不会重复，也不会漏。压缩成功后清掉以前的边界，回放时也一样；压缩前的轮不列，在那一轮中途自动压缩的那一轮也不列，README 写了。
4. **缓存前缀**：轮边界、检查点、回退条目都不进内存里的消息，回放时也跳过；回退只把消息截到边界，前面的不动。测试在重启后逐字节比过。
5. **并发**：列表、预览、回退都要拿会话的锁，并且在跑的轮、旁问、排队的输入都会拒绝；新一轮开始也要拿同一把锁，所以两者不会交叉。两个终端同时回退会排队执行，第二个要么因为边界没了被拒绝，要么只剩还有效的改动可退；回退放在 `owned` 里，客户端断开也会做完；停机前要等回退做完（持有 `draining` 读锁）。剩下的是预览和确认之间会话或文件变了的问题（必须改第 1 条、建议改第 4 条）。
