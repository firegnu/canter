## 重点看

1. **进程收得干净吗**：
   - 这几种情况下，整个进程组（包括子进程、孙进程）都不留孤儿：`shell_stop`、`/stop`、命令自己结束、领导进程先退出、服务端停（包括 `canter serve --replace`）、会话关闭。
   - 停掉和自己结束同时发生时，退出码和状态对不对。
   - Ctrl+B 转后台和命令恰好结束同时发生时，会不会一条命令被记两次、或丢掉。
2. **并发和上限**：
   - 8 条上限在并发起命令时守得住吗。
   - 1 MiB 环形保留和 32 KiB 末尾截断，在多字节字符、没有换行的大块输出处会不会切坏或出错。
   - 模型的增量游标和终端读取互不影响。
   - 过期的 `shellBackground` 请求不会把后来的命令转到后台。
3. **模型历史**：
   - 完成说明延后追加（等工具结果收齐），是否总能保持工具调用和结果相邻、只往后加。
   - 回退（`/rewind`）、压缩、服务端重启后重建是否一致。
   - 重启后残留的「运行中」恢复成退出码未知，编号继续往上走。
4. **批准和计划模式**：
   - 放后台（模型的 `background:true`、用户的 `!cmd &`、Ctrl+B）不绕过批准，拒绝了不起进程。

5. **新旧版本互相读**：

### 意见

1. **必须改**：后台命令在压缩期间结束，完成说明会丢，模型一直不知道。
   - 位置：
     - `crates/canter-core/src/compaction.rs:164`：summarize 先拷一份历史。
     - `compaction.rs:122`：`state.history = messages` 整个替换历史。
     - `crates/canter-core/src/background.rs:31`：watch 任务随时会把说明 flush 进 history。
   - 问题：
     - 压缩在等模型时不持锁。后台命令这时结束，watch 任务把 `BackgroundNotice` 记进模型历史，并 flush 进 `state.history`。压缩回来，用旧拷贝做出的 messages 替换历史，说明被冲掉。
     - 重放时 `BackgroundNotice` 排在 `Compaction` 前面，也被替换掉。所以 live 和重放一致，但两边都丢了，不满足「后台命令结束时模型下一次请求能知道」。
     - 临时测试复现：在压缩的模型请求里放行命令，并延迟 1.5 秒回答。命令 exit 0，快照已经是结束，但压缩后第一次请求、关闭重开后的请求里都没有 `[Background command 1 finished`。
     - 自动压缩也走这条路。上下文接近上限的长会话里，后台常有长测试在跑，这个时间窗口不算小。
   - 改法：
     - 照 `restate_plan_mode` 的做法，在 `Compaction` 记录之后，给压缩期间新到的说明重记一条 `BackgroundNotice` 并入队。比如 summarize 时记下 history 长度，回来后把 `history[len..]` 里的后台说明在 `Compaction` 之后重记。这样重放自然一致。
     - 加回归测试：命令在压缩中结束，压缩后第一次请求和重开后都看得到说明。

2. **必须改**：同一条前台命令的两个 `shellBackground` 请求同时到，第二个会一直挂到命令结束。
   - 位置：
     - `crates/canter-tools/src/background.rs:145`：`promote`。
     - `crates/canter-tools/src/shell.rs:308`：promotions 分支在转后台之后就关掉。
     - `crates/canter-tui/src/run.rs:620`：终端在主循环里直接 await 这个请求。
   - 问题：
     - 两个请求都在 `detach` 清掉 `foreground` 之前拿到了 sender。第一个处理完，`background_id` 有了值，promotions 分支不再接收；第二个的回复一直留在通道里，要等命令结束、`Control` 丢弃，才回 `null`。
     - 临时测试复现（current_thread，两个 `promote` 同时发）：第一个回 `Ok(Some(1))`，第二个 3 秒内没返回，`stop_all` 之后才回 `Ok(None)`。
     - 两个终端开着同一个会话、几乎同时按 Ctrl+B，或者别的客户端重试，就会触发。终端在主循环里等这个请求，整个界面会卡到后台命令结束；开发服务器可能跑几个小时。
     - 推测：单个终端按住 Ctrl+B 连发不会触发，因为它是一个请求等完再发下一个。窗口只在两个请求都还在路上、服务端还没处理第一个的那几毫秒。不过这是重点看的 Ctrl+B 并发里的缺陷。
   - 改法：
     - promotions 分支 `detach` 成功后调 `control.promotions.close()`，再用 `try_recv` 取出已排队的请求，回 `Ok(Some(id))` 或 `Ok(None)`。
     - 或者 `promote` 改用 `try_send`，通道满了就当已经有人在转。
     - 加回归测试：两个 `promote` 同时发，都很快返回。

3. **建议改**：`/rewind` 和撤回把完成说明截掉之后，不再补。
   - 位置：`crates/canter-core/src/rewind.rs:499`，`crates/canter-core/src/runner.rs:84`。
   - 问题：
     - 第 1 轮起的后台命令在第 2 轮期间结束，说明落在第 2 轮。回退第 2 轮之后，历史里只剩第 1 轮那条「running」的工具结果；命令其实已经结束，模型不知道。临时测试复现了。
     - 撤回窗口里（模型还没开始）结束的命令也一样。
     - live 和重放一致，不坏存盘。
   - 改法：二选一，交主控定。
     - 截断之后照 `restate_plan_mode` 补记：对「开始那条还在保留的历史里、说明被截掉」的已结束命令，重记一条 `BackgroundNotice`。
     - 或者在 DESIGN 第 22 条写明：回退会连带丢掉那一段里的完成说明。

4. **建议改**：后台命令卡片的 `ItemCompleted` 带着 `status: inProgress`，旧版终端和 `/export` 一直把它当成在跑。
   - 位置：
     - `crates/canter-tools/src/shell.rs:222`。
     - 新终端靠 `crates/canter-tui/src/app.rs:4277` 特判。
     - 旧版（main）`crates/canter-tui/src/app.rs` 的 `item_done`，对 CommandExecution 只看 status。
     - `crates/canter-tui/src/export.rs:190`。
   - 问题：（读代码查证，没有跑旧版。）
     - 旧版 `item_done` 对 InProgress 返回 false，`finished_part` 卡在这张卡片上，后面的内容都留在实时区、进不了历史，这张卡片永远显示在跑。

     - 不丢数据，是显示变差。以后 GPUI 和网页客户端也都得照新终端做同样的特判。
   - 改法：
     - `ItemCompleted` 用完成态（比如 Completed、exitCode null，表示「这次工具调用结束了」）；跑没跑、退出码只看 `backgroundCommands`。新终端本来就按 itemId 叠加后台状态。

   - 位置：

   - 改法：
     - `shell_output`、`shell_stop` 在内存表里查不到时退回快照里的条目，回「已退出、退出码未知、重启后输出不可用」。

     - lsof 看到一个看护进程拿着 fd 33（一根管道）。命令自己早已关掉了 3 以上的描述符，所以拖住它的是看护进程。
   - **读代码**：macOS 上 std 的 `pipe()` 是先 `pipe()`，再分别设 CLOEXEC。
     - 服务端里不经过这把锁、会碰上同一个窗口的地方：
       - MCP stdio 起子进程（`crates/canter-tools/src/mcp.rs:353`，rmcp 内部用 tokio 起进程、建管道）；
       - HTTP 服务接受客户端连接；
       - 模型和 web_fetch 的 TCP 连接。
     - 套接字也是分两步设 CLOEXEC，这一点没在本仓库实测，是推测。
   - **影响有多大**：
     - 这个竞态同样会把描述符漏给命令自己。P2-28 之前就有这类问题。
     - 看护进程在杀掉进程组之后马上解除，所以它拿着的时间不超过命令本身的寿命。命令不关继承来的描述符时（大多数命令都这样），看护进程不会把 EOF 拖得比命令更久。
     - 只有命令自己关掉了继承来的描述符时，看护进程才是唯一拿着的那个。
     - 和上一版比是一点退步：f991d8f 的看护进程会把描述符全关掉，不会拿着。
   - **建议**：看护脚本在 exec 之后、`read` 之前，遍历 `/dev/fd`，除 0 以外全部关掉。
     - 代价只和打开的描述符数量有关。exec 之后做，不涉及 fork 后的安全问题。
     - 这样看护进程就回到 f991d8f「什么都不拿」的状态。
     - 命令那一侧的同类问题（要把所有起进程的地方收到一处，或者在领导进程里关掉多余描述符），另开任务。

2. **没查完：反方向，锁外起的子进程（MCP 这类）继承看护进程的管道**
   - **读代码**：这是可能的。
     - std 在 macOS 上用 posix_spawn 时，没有设 `POSIX_SPAWN_CLOEXEC_DEFAULT`。
     - 锁里建的管道也是分两步设 CLOEXEC，而 MCP 起进程不拿这把锁。
   - **实测没抓到**：
     - 锁外起的 400 个 `sleep`，lsof 看没有多拿的管道。
     - 509 次受看护命令启动期间，锁外 fork 了 5035 次，在子进程里检查不带 CLOEXEC 的描述符，0 次。
     - 检测方法本身有效：配一个不停建管道的线程，2821 次 fork 里抓到 405 次。
     - 结论是窗口很小，没复现出来。
   - **万一发生**：MCP 服务进程拿着某个看护管道的写端时，服务端被 kill -9，那个看护进程收不到 EOF，对应命令的进程组会一直活到那个 MCP 进程退出。
     - MCP 进程一般在 stdin 收到 EOF 后就会退出，所以实际影响多半不大。这一点是推测。
   - **修法**：让 MCP 等起进程的地方也拿同一把锁，或者第 1 条里说的整体收口。

3. **建议改：命令启动时阻塞异步运行时的工作线程（这次改动带来的）**
   - **读代码**：`spawn()` 在工作线程上同步阻塞约 4.7 ms，期间一直拿着 std 的 `Mutex`。
     - 原因是领导进程在 pre_exec 里要等中间进程退出，而中间进程要等看护进程 exec 完 sh、报就绪。
     - 并发启动时，等锁的工作线程也会被卡住。
   - **已查证**：4 个工作线程上同时启动 32 条命令，用时 142 ms，期间整个运行时最长停顿 129 ms（1 ms 定时任务测得的最大间隔）。
   - **影响有多大**：实际同时启动的命令很少，影响不大。
   - **建议**：把拿锁加 spawn 这段放进 `spawn_blocking`。

4. **建议改：看护进程用 `execv` 继承了服务端的整套环境变量（推测，没测）**
   - **读代码**：
     - std 在 pre_exec 之后才切换子进程的环境，所以 pre_exec 里 `execv` 起的 `/bin/sh` 拿到的是服务端自己的环境，不是 `env_clear` 后的那套。
     - 服务端环境里如果有会影响 sh 行为的变量（比如导出的 shell 函数覆盖了 `read`、`kill`），看护脚本可能失效。
   - **建议**：改用 `execve`，传空环境（或只给最小的 PATH）。改动只有一行。

5. **建议改（和这次改动无关）**：
   - **macOS 上进程组只剩僵尸进程时，`killpg` 返回 EPERM**
     - **已查证**：用最小的例子实测，回收前 KILL、TERM 都是 EPERM，回收后才是 ESRCH。
     - **读代码**：`kill_group` 和 `terminate` 只把 ESRCH 当作「组已经没了」。
       - 如果领导进程刚退出、还没被 tokio 回收时，正好碰上取消或超时，`crates/canter-tools/src/shell.rs:276` 和 `:289` 会以 IO 错误（Operation not permitted）收场，而不是「已取消」或「超时」。
       - 这时也不会解除看护。看护进程要等 drop 时管道关闭才退出，退出前对一个已经没了的组发一次 kill。组号刚好被重用的概率可以忽略。
     - **来源**：P2-28 之前的 main 上就是这套判断。
   - **`cancellation_interrupts_retry_after_and_local_backoff` 偶发失败**
     - **读代码**：测试先 sleep 50 ms，再断言只收到一个请求，靠时间窗口判断，并行负载高时会偶发失败。
     - **来源**：P2-2 时写的。

### 对 R1 到 R4 的判断

R1 到 R4 都改好了。上面第 1 到 4 条都不属于「怎么算做完」没满足，也不属于关键处的实际缺陷：
- 第 1、2 条是命令侧早就有的同类问题，看护进程只是多了一个持有者，时间不超过命令本身的寿命；
- 第 3 条是性能问题；
- 第 4 条是推测，没测。

所以记「建议改」，不挡合并。
