## 调研（11-12 主控）

## 边界（11-13 用户定）

- 助理是 canter 之外的另一个程序，canter 只当执行者。
- canter 不为助理写特例。助理只用 canter 的公开接口：HTTP + SSE 协议、`canter exec`。这和 DESIGN 第 1 条对 corral 的要求一样（corral 去适配 canter 的公开接口）。
- 公开接口缺通用的东西时，按「终端、桌面版、corral 是否也用得上」判断：用得上，就当普通 canter 需求做；只有助理用，就留在助理那边。
- 11-12 主控建议的「把助理这一层放进 canter 服务端」作废。

## 按这个边界的思路（11-13 主控）

### 谁管什么

- **助理管**：
  - 记提醒、到点触发。
  - 通知出口：Slack、系统通知、推送。
  - 用户生活上的记忆，比如报销、约会。
  - 手机、iPad、Mac 连进来的远程访问和登录。
  - 和用户的对话。
- **canter 管**：要 agent 干活的事。例如「到点去查一下某个东西再告诉我」，由助理开一个 canter 会话、发任务、等结果。

### 第一版大概率不用改 canter

现有公开接口已经够用：

- 开会话、发任务：协议和 `canter exec` 都有。
- 知道活干完了：SSE 有 `turn.completed`。
- 要批准的操作：协议里本来就有批准请求和应答，终端就是这么用的。助理当一个协议客户端，就能把批准转到手机上。

单纯的提醒（「明天 9 点提醒我交报销」）完全不经过 canter。

### 因此跟着变的事

- **另开一个仓库**：助理不放在 canter 仓库里。用户同意建仓库后，本任务在 canter 这边按「收尾: P2-285 不做：挪到助理仓库」处理。canter 的 CLAUDE.md 开头「coding agent」这个定位不变。
- **原生 iOS App 不再和「只用 Rust」冲突**：那条规矩只管 canter 仓库，助理仓库自己定。
- **手机连的是助理，不是 canter**：远程访问和鉴权是助理的事，canter 服务端照旧只在本机监听。
- **还没变的**：
  - 助理要常驻，而且和 canter 在同一台机器上，因为它走本机连接调 canter。
  - Mac 合盖睡着时提醒不准的问题还在。

### 助理自己要不要直接调模型

听懂「明天 9 点提醒我」、陪用户聊几句，需要用模型。

- **(a) 主控推荐**：助理自己直接调一次模型，不带工具，轻、快、便宜；要干活时交给 canter。
  - 代价：DeepSeek key 这类凭证要在助理那边也存一份。
  - 助理仓库要照搬 canter 的凭证规矩：只放本机，不进仓库、日志和提交。
- **(b)**：所有模型调用都走 canter，助理里没有模型代码。
  - 代价：canter 的提示词是为写代码设计的，每句闲聊都要开一个带沙箱和工具的 coding 会话，又重又慢。

## 设计（11-13 主控提，用户：「明白了，把这个设计写进P2-285吧」）

### 整体

```
 iPhone / iPad / Mac
        │  (第一版：Slack；以后：网页，再以后：原生 App)
        ▼
 ┌─────────────── 助理服务（新仓库，常驻）───────────────┐
 │ 对话：直接调模型，听懂“明天 9 点提醒我…”               │
 │ 提醒库 + 定时器：记下、到点触发、错过补发              │
 │ 通知：发出去，带“完成 / 推迟”                          │
 │ 个人记忆：生活上的事，和 canter 的记忆分开             │
 └───────────────────────┬───────────────────────────────┘
                         │ 本机 unix socket（HTTP + SSE）或 canter exec
                         ▼
                 canter 服务端（不改）
```

canter 服务端只听 `~/.canter/server.sock`，不开 TCP（DESIGN 第 15 条），所以助理要和 canter 跑在同一台机器上、用同一个用户。canter 已经支持 Linux，放到 5090 那台也行。

### 第一版：只做提醒，用 Slack 收发

不写客户端。用户在 Slack 私有频道里对助理说话，提醒也发回同一个频道。

- 好处：iPhone、iPad、Mac 马上都能用。助理只主动往外连 Slack，不开端口，所以第一版不用做远程访问和登录鉴权。
- 代价：提醒内容经过 Slack。如果不接受，第一版改用 macOS 系统通知，但手机收不到。

**记一条提醒**：
1. 用户说「明天 9 点提醒我交报销」。
2. 助理调模型，让模型通过一个 `create_reminder` 工具交出结构化的结果：内容和带时区的绝对时间。
3. 助理回一句「好，11-14（周五）09:00 提醒你：交报销」，把它理解的时间写出来。模型把「下周一」这类说法算错了，用户能马上看到。

**到点**：
- 助理发通知，带「完成」「推迟 10 分钟 / 1 小时 / 明天」。
- 没点「完成」的提醒一直留着。

**错过**：机器睡眠或助理没在跑时到了点，助理起来后补发，并标上「晚了 N 分钟」，不悄悄丢掉。

**存储**：
- 提醒和模型 key 存在助理自己的状态目录（例如 `~/.<助理名>/`）。
- 目录 0700、文件 0600，照搬 canter 的凭证规矩，不进仓库和日志。

**第一版完全不经过 canter**：
- 记提醒、到点通知这两件事只用到 Slack、模型接口和助理自己的定时器、存储。
- 不开 canter 会话，不调 `canter exec`，不连 canter 的 socket。canter 服务端没在跑，提醒也照样能用。
- 因此第一版不验证「助理调 canter 干活」这条链路，这条链路要到第二版才第一次走通。

### 第二版：到点让 canter 干活

例子：「每天 8 点看一下 canter 仓库的 CI 有没有挂，挂了告诉我」。

1. 这类提醒多带两样东西：交给 canter 的任务，以及在哪个目录做。
2. 到点后，助理作为协议客户端，通过 unix socket 开一个 canter 会话并发任务。
3. canter 要求批准时（执行命令、改文件），助理把批准请求转到 Slack，带「同意 / 拒绝」；用户点了之后，助理再回给 canter。这对应 Duet 的「先等用户同意」，用的是 canter 已有的批准机制。
4. 收到 `turn.completed` 后，助理取最后的回答，总结成一两句发给用户，附上会话 ID，用户可以用 `canter -r` 打开看全过程。

不用 `canter exec --yolo`：它会跳过所有批准，等于让定时任务在机器上随便执行命令。

重复提醒（每天、每周）和早报也放这一版。

### 第三版起：自己的客户端

- 网页客户端：一份代码，三个设备都能用；iPhone、iPad 加到主屏幕后能收推送。这时才做远程访问（比如 Tailscale）和登录。
- 原生 iOS App 放最后，要 Apple 开发者账号和推送转发服务。

### 语言

主控推荐助理服务用 Rust：
- 可以通过 git 引用依赖 canter 的 `canter-protocol` 包，拿到现成的协议类型。依赖方向是助理依赖 canter，canter 不知道助理的存在，符合边界。
- 用户和这套工具链都熟。

Swift 只在做原生 iOS App 时才用。
