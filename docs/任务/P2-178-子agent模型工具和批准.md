## 主控记下的

- 拆分时的设想（待讨论）：`spawn_agent` / `wait_agent` / `send_input` / `close_agent`；只读查找、通用两种，嵌套 1 层，同时最多 4 个；继承主会话的权限、放行规则和沙箱；子 agent 的批准请求发到主会话客户端并标明来源；做完叫醒主 agent；只读的模型可自己开，会改文件的要用户明说。权限和批准，碰要害，要交叉审查。
- P2-177 交叉审查留下的建议（详见 `P2-177-交叉审查.md`「建议改」1～7），本件接上开子会话后都会碰到，讨论本件时和用户一起定：
  1. `/v1/usage` 用 `store.list()`，把子会话的花费漏掉了；最晚本件合并前改成 `list_all()`，子会话花费怎么归到父会话下留给 P2-180。
  2. 继承时没带当前轮的审查限制（`review`）和 `non_interactive`；计划模式随设置整体继承。要定：审查轮里能不能开子 agent、计划模式继不继承。
  3. 启动时补记中断，任何一个子会话打开失败整个服务端就起不来，而且每次启动都完整打开所有子会话；改成失败跳过、先便宜地挑出在跑的。
  4. `/agents` 读不到其中一个子会话（刚被删）就整个 404；没打开的子会话每次完整重放。
  5. 回退时状态锁是先子后父，和删除相反；本件若在持有父会话状态锁时操作已有子会话（send_input、wait_agent、叫醒），可能和回退互相等待。
  6. 关掉一个已做完、空闲的子会话会清掉它的结果；子会话里手动压缩或 `!命令` 也算「最近一轮」，之后结果变空。和 close_agent 的语义一起定。
  7. 回退父会话不会还原子会话改过的文件。
