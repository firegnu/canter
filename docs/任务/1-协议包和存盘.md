### `canter-protocol`

服务端和客户端之间的协议类型。传输是 HTTP 下命令、SSE 推事件（DESIGN 第 8 条），本包只放类型和纯逻辑，不起服务。

- **命令**：报告 §5.5 命令表里的每一条，都有请求体和回复体的类型；路径用常量写在包里（比如 `/v1/sessions/{id}/input`），服务端和客户端共用。第一期不要提问框，待处理请求只有「批准」一种。
  - 建会话带：工作目录、环境变量、模型、权限模式、可选的首句、名字。
  - 回答批准的选项四个：允许这一次、本会话都允许、拒绝、拒绝并停下；带上回答的客户端名。
  - 送一句话：空闲就开新一轮；在干活时可选排队或插话。
  - 命令的回复里带上这条命令对应的事件序号，客户端拿它和事件流对齐（报告 §5.2）。
- **事件**：报告 §5.5 事件表里的每一种。每条事件有：序号（每个会话从 1 起递增）、会话 id、时间、内容。
  - 项目种类第一期要：用户的话、模型的话、思考内容、命令（完整命令、目录、输出增量、退出码、用时）、改文件（每个文件的 diff）、读文件、压缩（摘要）。
  - 会话状态照 §5.5：`starting`、`idle`、`working`、`waiting_approval`、`error`、`closed`；第一期没有提问框，`waiting_answer` 不要。
- **会话的完整样子（快照）**：状态、各轮、各项目、还没处理的批准请求、最后的事件序号。
- **事件归并成快照**：给一个快照和一条事件，算出新快照。服务端从盘恢复、客户端显示都用它，所以放在本包里。
- **协议版本**：有一个协议版本号，`GET /v1/info` 的回复里带上。
- **兼容**：以后只做兼容的新增。旧客户端遇到不认识的字段要能忽略；遇到不认识的事件种类、项目种类，要能跳过，不能整条解析失败。
- **字段名**：结构和字段名尽量照 Codex app-server v2（thread → 会话、turn → 一轮、item → 项目），JSON 里的大小写也照 Codex。和 Codex 不一样的地方，在完成记录里列出来，主控再写进 DESIGN。
- **导出**：从这些类型生成 JSON Schema 和 TypeScript 类型文件，放进仓库；有一条命令能重新生成（用 Rust 写，不用 Python）。

### `canter-store`

会话存盘。本包不决定状态目录放哪：调用方传一个根目录进来（服务端那一件再定 canter 的状态目录）。

- 每个会话一个只追加的 JSONL 文件，一行一条事件，就是 `canter-protocol` 里的事件本身，带序号。
- 建会话时的工作目录、环境变量这类不发给客户端的东西，不进事件文件；要存盘的话单独存，文件权限 0600，目录 0700。
- 每个会话一把文件锁：同一个会话同一时刻只能被一处打开写。
- 打开一个已有会话：按顺序读事件，用 `canter-protocol` 的归并逻辑还原成快照；之后写的事件序号接着编。
- 写到一半崩了，最后一行可能不完整：打开时跳过这半行，不能因此打不开整个会话。
- 列出根目录下的所有会话（id、名字、状态、最后更新时间这类够列表用的）。
