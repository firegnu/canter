### 重点看的五项

1. **隔离**：`set_sandbox`（`crates/canter-core/src/configuration.rs:118`）只换本会话 `shared.runtime` 里的 `context.sandbox_override`，不碰 `config.json`、别的会话和存盘。已在跑的子 agent 有自己的 `RuntimeContext` 副本，`apply_configuration` 对子会话又固定 `options.sandbox = old.options.sandbox`，父会话切换碰不到它；新子 agent 在 `create_inner` 拿父会话当时的 `runtime.context.clone()`，跟新选择走（`agents.rs:665`），`open_agent`（`agents.rs:403`）同理。没发现隔离失效。
2. **生效时机**：所有开轮入口（普通输入、排队输入 `runner.rs:353`、后台唤醒 `background.rs:590`、目标续跑 `goal.rs:207`、手动压缩、`!` 命令）都经 `start_input → configure → apply_configuration(.., true)`，在登记新轮之前应用。同一轮里晚到的 steering 走 `continue 'turn`，`prepare_turn` 见租约已在就直接返回，不换执行器；等服务时 `prepare_turn` 传 `false`，保持登记时的执行器。轮进行中 `set_sandbox` 不动 `runtime.tools`，当前轮剩下的工具调用仍用原执行器；执行器只在 `sandbox_tools` 和建会话、开会话时造，加目录、改权限档、信任重查都不重建。后台命令留在 `retired_tools` 的旧执行器里，测试实测了旧后台命令照原范围写出。btw/handoff 空闲时也会应用，见意见 2。
3. **确认**：服务端只要 `!enabled && !confirmed` 就拒绝（`confirmed` 缺省 false；传 `null` 或字符串解析失败，也是 400）。终端只有确认框里那一项能产生 `SetSandbox { enabled: false }`；按 Enter 要满足 `seen && !send_guarded`，提前敲的回车确认不了还没画出来的框；Esc、Ctrl+C 关框不做事。旧服务端没有 `sessionSandboxSwitch` 时，报替换提示，不发请求。不经确认能强制关的只有打开参数 `sandboxDisabled`（`--yolo`，P2-198 原有），不算绕过。
4. **重开和存盘**：`/resume`、`-c`、`-r` 都走 POST resume → `set_sandbox_disabled(params.sandbox_disabled, 当前配置)`。普通重开把选择清回 None，`--yolo` 仍是 Some(false)；会话开着时重开、关了再重开，都有测试。选择和 `sandboxPending` 只在内存里，事件只经 `ephemeral` 广播，不进 `journal.append`；存储靠重放事件，测试也查了 events.jsonl。落盘的只有 P2-166 原有的实际状态 `sandboxEnabled`，下次打开按配置重写，不算把切换结果存进会话。
   - 和原语义有一处差别：以前重开时，如果会话正在跑一轮，`set_sandbox_disabled` 当场换执行器；现在要等这轮结束（`set_sandbox_override` 里的 `if state.active.is_none()`）。`--yolo` 和普通重开都这样，符合主控定的①，DESIGN P2-289 段「切换时不换执行器，下一轮边界应用」也写到了。
   - 用户试用时可能碰到：第二个终端用 `-r` 打开同一个会话，也算重开，会把第一个终端的 `/sandbox off` 清掉（P2-198「最后一次打开为准」，加上本任务第 4 条）。两边都会收到状态变化，显示一致。
5. **显示一致**：临时事件的 seq 是 0，SSE 不带 id；`recv` 在检查游标之前就返回它，不推进游标，也不插进持久事件序列。从没切换过的会话不补任何通知，原有事件顺序不变。补读时把内存里最新一条接在磁盘事件后面；`recv` 收到旧的沙箱通知，一律换成最新值，并按订阅去重，所以积压或重连之后，最后的值和服务端一致。我能想到的偏差，只有 `session.updated` 和紧跟着的「清掉 pending」之间可能多一帧过渡（比如瞬间显示 `▲ Sandbox off → off next turn`），下一条事件一到就收敛，不会停在错的状态。弹框刷新有保护：取回的结果和本地快照对不上就丢弃，等后续事件再取。
