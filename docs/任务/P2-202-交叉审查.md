## 重点看

1. **令牌不外流**：access、refresh、ID token、授权 `code`、`state`、完整授权网址，会不会经 `Debug`/`Display`/`Serialize`、错误链、日志、回调网页、HTTP 跳转、panic 信息漏出去；带令牌的请求头是不是 sensitive、会不会被发到 OpenAI 以外的地址（discovery 给的地址怎么校验）。
2. **ID token 校验对不对**：签名算法有没有限死（不接受 `none`、不能拿公钥当 HMAC 密钥这类混淆），issuer、audience、过期、`nonce` 都查了；再登录时 client id 和 `sub` 不一致确实拒绝、不覆盖旧记录；缺 `chatgpt.tokens.use.direct` 时取不到推理令牌。
3. **刷新和退出的并发**：同一条记录同时要令牌只刷一次、失败共享；刷新回来整组原子保存，中途崩了不会丢掉新的 refresh token 或留下半新半旧；退出和刷新同时发生时令牌不会复活、撤销的是最新的 refresh token；调用方放弃等待不会弄丢正在轮换的令牌。
4. **本机存储**：目录 0700、文件创建时就是 0600（不是先写后 chmod）；临时文件同目录、原子替换、落盘顺序对；拒绝符号链接和所有者不对；锁能挡住同一状态目录的第二个服务端；同邮箱两条记录不串。
5. **登录事务**：先监听再生成 state/nonce/PKCE；`state` 不对、用户拒绝时不换令牌；取消、超时后监听关掉；首次用 `dynamic_agent_client`、换令牌用签下来的 client id，绝不用 `dynamic_agent_client` 换令牌；没有借 Codex 的 client id 和接口。

### 必须改

1. **刷新成功后，新 ID token 校验没过就把已经轮换的新 refresh token 扔了**（重点 3，丢令牌）
   - 位置：`chatgpt_auth/manager.rs:137-160`（`identity_result?`）；`chatgpt_auth/http.rs:205-210`（每次校验都联网取 discovery 和 JWKS）。
   - 问题：token 端点回了 200、服务器已经轮换 refresh token 之后，代码还要再发 discovery 和 JWKS 两个请求去校验新 ID token。这两个请求只要有一个出网络错、超过 10 秒、回 503，或者本机时钟比服务器慢 5 秒以上让 `iat` 不过，`identity_result?` 就直接返回，`fresh` 被丢掉。内存和盘上留下的是服务器已经作废的旧 refresh token，状态还是 `logged_in`。下一次取令牌一定拿旧 refresh token 去刷，得到 `refresh_token_reused`，结果是清令牌、要重新登录。调用方这次看到的是 `Network`（“暂时连不上”），其实凭证已经坏了。官方文档没说刷新响应带不带 `id_token`（token-reference 只列了字段），假服务器每次都带；真实响应如果也带，每次刷新都会走这条路。
   - 改法：拿到 200 刷新响应以后，后面的校验步骤不能把新 refresh token 悄悄扔掉。建议：取 discovery 或 JWKS 时出网络错，照样把新的 access、refresh、过期时间、scopes 整组落盘，ID token 先留上一个验过的，下次刷新再验；ID token 确实无效（签名、claims 不对或 `sub` 不一致）时，不发令牌，尽力拿新 refresh token 去远程作废，再清令牌、标 `needs_login` 落盘，不能把已经作废的旧令牌组当成 `logged_in` 留着。补回归测试：刷新时让假 JWKS 回 503（或停掉），断言盘上已经是新 refresh token，再刷新一次发出去的也是新的。

2. **退出在远程作废完成前没有落盘，这段时间服务端一停，重启后令牌又能用了**（重点 3，作废的令牌复活）
   - 位置：`chatgpt_auth/manager.rs:8-28`。
   - 问题：`blocked` 只记在内存里。盘上的记录要等远程作废结束才改成 `signed_out`；作废最多 3 次，每次 discovery 加 revoke，每个请求 10 秒超时，网络卡住时要三十秒以上，前面还要先等在途的刷新。这段时间里服务端被停掉、重启、升级或者崩溃，重新打开时 `Entry::new` 看到的是 `logged_in`，不会封住，`access_token` 照常发旧 access token，需要时还拿 refresh token 去刷新：用户已经退出的账号又能用了。第 26 行 `save_record(...)?` 失败也一样：内存清了，盘上还是 `logged_in`，重启就回来。
   - 改法：远程作废请求发出之前，先把“已退出”落盘。比如先存成 `signed_out`，清掉 access token 和 ID token，refresh token 作为“待作废”单独留着（读盘时 `signed_out` 的记录一律不发令牌，`load_records` 的校验要放行这种组合）；作废有了结果，再清掉 refresh token 落盘。官方写的是先尝试作废、再清本地令牌，这样做也符合。落盘失败时 `logout` 要报错，不能当作已经退出。补测试：让假 revoke 卡住，断言这时盘上记录已经是 `signed_out`、没有 access token；放行以后 refresh token 也清掉了。

### 建议改

1. **`iat`、`nbf` 只容 5 秒误差，太紧**（`http.rs:245-246`）。本机时钟慢 5 秒以上，登录就一直报 `InvalidIdToken`，用户看不出为什么；必须改 1 也会变成每次刷新都中。改成 60 秒（jsonwebtoken 默认就容 60 秒）。
2. **刷新响应的字段要求太死**（`http.rs:34-42`、`manager.rs:133-136`）。`scope` 是必填，刷新响应不带 `scope` 时整个 200 响应解析失败，这时服务器已经轮换过了，后果和必须改 1 一样。RFC 6749 §5.1 允许 scope 没变时不返回，官方文档没写刷新一定带。建议刷新没给 `scope` 就沿用原来的；没给新 refresh token（RFC 6749 §6 允许）就沿用旧的，不要每次都报 `InvalidResponse`。
3. **不外流的测试只管到刷新阶段**（`tests.rs:941-947`：日志在登录完成之后才开始抓）。登录阶段（回调、换令牌）的 TRACE 日志没抓，换令牌出错时把 `code` 回显出来的情况也没测。非测试代码里没有任何日志或打印调用，问题不在代码，在于测试没证明。建议子进程一开始就装好日志订阅，再加一次换令牌失败（假服务器回 400，正文里带 `code` 和 `state`）。

### 可以不改

1. 回调地址收到的第一个请求就定了这次登录的结果（`login.rs:79-89`）：本机任何进程抢先请求一次 `/auth/callback`（`state` 不对），这次登录就失败。不会泄露，只是本机进程能打断登录；Codex 的做法是回 400、接着等。
2. 没有 refresh token 的记录（比如 `needs_login`）退出时，`remote_revoked` 是 false，P2-203 会提示“远程没确认”，其实没有东西可作废。P2-203 可以按退出前的状态区分。
3. `CANTER_HOME` 本身是符号链接时，GPT 登录整个打不开（`storage.rs:133` 用 `symlink_metadata` 查 home），canter 其他部分却能用；`auth/chatgpt/` 里有一个不认识的文件（比如 Finder 生成的 `.DS_Store`），整个凭证目录也打不开。都是从严处理，P2-203 真登录时留意一下。
4. HTTP 客户端写了 `no_proxy`（`http.rs:59`），和现有 DeepSeek、web_fetch 客户端一致；可是用户如果要靠 HTTP 代理环境变量才能连 OpenAI，P2-203 那次真登录会连不上，到时再定。
5. 崩溃留下的 `.tmp*` 临时文件（0600，里面有令牌）不会被清掉。

### 五个重点逐项核对（上面两条必须改之外没发现问题）

1. **令牌不外流**：`Secret`、`TokenSet`、`AccessToken`、`LoginAttempt`、回调参数和 token 响应的结构都没有 Debug、Display、Serialize；`AuthError` 只有枚举、状态码、认得的错误码，`source` 为空；非测试代码没有日志和打印；回调页是固定文字，带 `default-src 'none'`、`no-store`、`no-referrer`；Authorization 头标了 sensitive；不跟随跳转；authorize 和 token 地址写死在 `http.rs`，只有 `cfg(test)` 能换成 `127.0.0.1`；discovery 的 `issuer` 必须等于写死的 issuer，`jwks_uri`、`revocation_endpoint` 必须和它同源、不带用户名口令，生产环境就是 `https://auth.openai.com`。
2. **ID token**：只接受 RS、PS、ES、EdDSA 几类算法，`none` 连头都解析不了；JWK 的 `use`、`key_ops`、`alg` 对不上就拒；jsonwebtoken 11.1.0 按 `header.alg` 限定算法，并检查密钥族（`crypto/aws_lc/*.rs`），公钥没法当 HMAC 密钥用；`iss`、`aud`（签下来的 client id）、`sub`、`exp`、`iat` 都必须有；登录时比对 `nonce`；复登 `sub` 不一样报 `IdentityMismatch`、不覆盖，测试里旧令牌还能用；缺 `chatgpt.tokens.use.direct` 时记成 `plan_not_authorized`，取令牌报 `PlanNotAuthorized`。
3. **并发**：每条记录一把 tokio 锁串行；刷新代次加 `refresh_error`，同一批等着的请求共享这次的成功或失败；成功时先落盘再换内存；取令牌放在 spawn 里跑，调用方放弃不会打断轮换；退出在 publish 锁下设 `blocked`、`epoch` 加 1，在途的刷新回来看到 `blocked`，新令牌组只留给退出去作废，不落盘也不发出去；旧 `AccessToken` 因为 `blocked`、`epoch` 失效，复登以后也不会复活；复登按开始时的 `epoch` 比对，退出之后才完成的旧登录会被拒。
4. **存储**：home、`auth`、`auth/chatgpt` 都是 0700 并且都查过；tempfile 在同一目录以 0600 新建后才写，顺序是同步文件、rename、同步目录，然后才换内存；读文件用 `O_NOFOLLOW` 打开后再 fstat 校验；拒绝符号链接、非本用户所有、组或其他用户有权限、硬链接；`auth.lock` 用 flock 挡住同一目录的第二个管理器，同一进程里也挡；记录文件名是随机 UUIDv4，按 client id 去重，同邮箱两条记录不串，测试里重启后各取各的令牌。
5. **登录**：先 bind `127.0.0.1:0`，再生成 `state`、`nonce`、verifier（各 32 字节随机，S256）；首次用 `dynamic_agent_client` 加 `agent_name_hint=canter`，复登用存下的 client id、不带 hint；先核对 `state`，`access_denied` 不换令牌；首次回调没有 client id 或者给的是 `dynamic_agent_client` 就拒绝，复登回调的 client id 不一样也拒绝；换令牌用签下来的 client id、同一个 `redirect_uri`、verifier 和 `resource`；取消、超时、完成都会关监听（1 秒后强制 abort）并清掉事务；代码里搜不到 Codex 的 client id、`backend-api` 和 Codex 的请求头，User-Agent 是 `canter/<版本>`。

### 对「拿主意的地方」逐条表态

1. **`expires_in`、提前 60 秒、`earliest_refresh_at`（主控已定）**：实现和主控的决定一致（`manager.rs:93-107`）：整数按 Unix 秒，只在令牌还没过期时挡，过期了照刷，缺失或解析不了就忽略，测试都覆盖了。同意。即使真实值是毫秒，最坏也只是到过期才刷新、401 恢复报 `RefreshTooEarly` 直到过期，不会清凭证，可以留到 P2-203 真登录时核对。

- `manager.rs:159-178`：ID token 确实无效（签名、issuer、audience、过期、`sub` 不一致）时，不发令牌，拿新 refresh token 去作废（有限次重试），然后 `invalidate` 清令牌、盘上落 `needs_login`，`epoch` 加 1，旧 `AccessToken` 也随之失效。这时如果退出正在进行，就把新 refresh token 存成待作废，交给退出去作废。测试覆盖了五类无效和作废失败。

### 必须改 2：退出在远程作废前就落盘 —— 已修好

- `manager.rs:8-13` 加 `storage.rs` 的 `begin_logout`：在 publish 锁下设 `blocked`，同时从盘上读出记录，改成 `signed_out`，清掉 access 和 ID token，refresh token 单独存成 `pending_revocation`，然后才去等在途刷新、发远程作废。盘上的内容不会比内存旧：每次发布都是先落盘再换内存，而且都在 publish 锁下，所以从盘上读是安全的。
- 在途刷新回来看到 `blocked`（`manager.rs:179-187`，ID token 无效时走 `159-167`），只把最新的 refresh token 写成 `pending_revocation` 落盘；退出作废的是最新那个（原有测试仍然断言作废的是 `fake-refresh-2`）。
- 读盘：`pending_revocation` 只允许和 `signed_out` 一起出现，`signed_out` 又不允许带令牌组，所以内存里令牌组和待作废令牌不会同时存在，`Record::sign_out` 不会丢掉哪一个。`signed_out` 的记录打开时 `Entry::new` 直接封住，任何路径都不发令牌。`logout_is_durable_before_revocation...` 在作废卡住时把盘上的文件拷出来另外打开，断言取不到令牌、也不会触发刷新；`logout_is_durable_while_waiting_for_inflight_refresh` 断言等在途刷新期间盘上已经是 `signed_out`。
- 落盘失败：两次写盘的失败都返回 `Storage`，不再当成已经退出；有测试。

### 建议改（复核时看到，不挡合并）

1. **只有 `Network` 被当成暂时失败，其他“取不到校验材料”的情况都按“ID token 无效”处理**（`manager.rs:150-158`）。discovery 或 JWKS 回 403、404（比如网关或 CDN 的拦截页）、回 200 但正文不是合法 JSON、超过 1 MiB、discovery 的 issuer 对不上，`identity()` 返回的都是 `InvalidResponse`，于是走进 `159-178` 的分支：刚轮换好的、本来能用的 refresh token 被主动作废，记录标成 `needs_login`，用户只能重新登录。这比改前好（改前是悄悄丢掉、下次刷新才报 reused），不算回退；但和返工说明、DESIGN 里写的“签名、claims 或 subject 确实不符时才作废”对不上。改法：只有 `InvalidIdToken`、`IdentityMismatch` 走作废分支，取 discovery、JWKS 的其他失败都按 `Network` 那样处理（整组落盘，保留旧 ID token）。
2. **退出作废中途服务端停掉以后，留下的待作废令牌没人管**。盘上会留下 `signed_out` 加 `pending_revocation`：之后没有地方自动重试；`RecordInfo` 也看不出有待作废的令牌，P2-203 没法照官方要求告诉用户“远程作废没确认”；复登会直接把它覆盖掉（`login.rs:189` 写的是 `pending_revocation: None`），不去作废。再调一次 `logout` 会重试，这条路是通的。改法：`RecordInfo` 加一个“有待作废”的标记，给 P2-203 用来提示或再调一次 `logout`；或者复登覆盖之前先尽力作废一次。也可以留到 P2-203 一起做。
