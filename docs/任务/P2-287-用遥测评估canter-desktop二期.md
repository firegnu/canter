## 要做的

canter-desktop 二期（P2-1～P2-9，功能和终端版对齐）全部由 `canter-desktop/main`（deepseek-flash）一个人做。每件做完、用户叫主控看时：

- 取那件活的时间段：从用户说开始做那句话，到 canter-desktop 那件的「收尾:」提交。数据是 `canter stats <n> --json` 和那个会话的 `model-history.jsonl`（工具失败的原文在 tool_result 里）。
- 先看核心用量（用户最关心的）：
  - 时间：总时长拆成模型时间、一回合内跑工具的时间、等用户的时间；首字时间。
  - 花费和 token：按用途（对话、压缩、建议）分；输入里缓存命中多少，哪几次请求命中掉下来、为什么。
  - 上下文：平均和最大多大，最大时系统提示、工具定义、对话、工具结果各占多少。
  - 压缩：几次、什么时候触发、压缩前后多大、压缩后重读了哪些文件、压完多久又涨回去。
  - 空转：一样的调用重复、同一文件反复读、轮询和等待、一次请求只做一件事的比例（每多一轮都要把整个上下文再发一遍）、重试。
- 再看工具失败率和失败原文、用户发现的 bug 和返工。
- 找出 canter 能改的地方，报给用户；用户同意的，小改主控直接在 main 上修（先写测试），大的写任务单。
- 每次修了什么写清提交号，下一件活看遥测时对照有没有起效。

主控提、用户同意的四条：
1. 二期期间不换模型，一直用 deepseek-flash，前后可比的只有 canter 的改动。
2. canter 只在两件活之间升级；一件活中间换了版本，那段遥测分开算。
3. 二期做完、换 Opus 当主控之前，让 Opus 把二期的代码整体看一遍。
4. 换主控时改 canter-desktop 的 AGENTS.md：每件活开独立的 worktree 和分支（顺带解决看板上活不进 In progress 的问题）。
