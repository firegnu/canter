### 重点逐条

以下除注明「推测」的，都是读代码或跑测试查证的。

1. **Esc 行为和 main 一样**：
   - 模型历史：`runner.rs` 的 `model_response` 在 `cancel.is_cancelled()` 时取 `response.items` 的全部内容（半截回答、思考和已收到的工具调用），和 main 的 `content` 相同。项目按 ID 合并、main 按相邻合并，在回答和思考交替出现时条数会不同，但 `wire.rs` 发请求时会把同一条里的回答、思考各自拼起来，所以发给模型的请求一样（DeepSeek 也不会交替）。没执行的工具调用仍由收尾的 `complete_missing_tools("No result: interrupted, ...")` 补占位结果，这段没改。
   - 界面、存盘、导出：Esc 时 `finish_items(..., !interrupted)` 传 false，回答和思考不带 `status`；`cells.rs`、`export.rs` 只在 `status == Interrupted` 时加标记，所以显示和 main 一样。`interrupt_during_model_stream_repairs_history_and_discards_queued_input` 只改了事件的写法，断言和 main 一致；新测试 `user_interrupt_preserves_partial_history_and_normal_item_status_after_reopen` 覆盖了历史、没有 `status` 字段和重开会话。存盘的事件有两处写法变化，见意见 2，不影响显示。
   - 用量估算：main 是无条件 `Some(estimated)`，现在是 `(reason.is_some() || interrupted).then_some(estimated)`。Esc（`interrupted`）和正常收完（`reason`）都是 `Some`，和 main 一样；只有不按 Esc、出错结束时变成 `None`。那时这次的输出已经丢了，不按它更新上下文占用更合理。
   - 等重试时按 Esc：模型层等待和核心读流都用 `select!` 优先看取消。`interruption_cancels_a_long_retry_wait_without_another_request`（`Retry-After: 60`，1 秒内停下、只发 1 次请求）通过。
2. **工具不跑两次、半截不进模型历史**：
   - 重发：`RetryPolicy::stream` 只在这次尝试没收到 `ItemCompleted`/`Finished` 时重发；核心收到 `Retrying` 就清空 `Response`，上次收到的工具调用不保留。Chat Completions 在 `[DONE]` 后才交出工具调用、紧接着发 `Finished`，核心收到 `Finished` 就不再读，所以拿到工具调用后不会再重发。
   - 保留收完整的接着做：只有标了完整的项进 `content`、写进历史、执行一次；`conversation` 里的 `interrupted_with_content` 跳过出错和结束原因检查，执行完整的工具调用后发下一次请求。
   - 次数用完或不能重试的错误：`response.completed()` 为空，半截不写进历史（main 会写进去，这是本件要的改变）。
   - 只往后加：重发用同一个请求体；接着做只在历史末尾加完整项和工具结果；`completed_items_survive_disconnect_and_tools_run_once` 用 `assert_request_extension` 查了。
3. **不写死 DeepSeek**：重试规矩在 `canter-model/src/retry.rs`，`ChatCompletions::stream` 只调它。核心的 `response.rs`、`runner.rs`、`compaction.rs`、`btw.rs` 只认 `ItemCompleted`、`Finished`；在核心的改动里搜了，没有 DeepSeek 或 Chat Completions 的特例。Chat Completions 不发 `ItemCompleted`，只在收到 `[DONE]` 且有结束原因时发 `Finished`，所以 DeepSeek 只会走「一项都没收完整」的重发。
4. **重试和次数**：`is_retryable` 没改（限流、5xx、网络、超时重试；认证、请求不合法、上下文超长不重试）。退避 0.5 秒起翻倍、32 秒封顶、向下最多 10% 抖动；`Retry-After` 截到 60 秒；`max_retries` 为 0 只发一次；用完时 `retries` 等于上限，错误文字写 `retried N times`。`model_max_retries` 0～100 在启动时读，101、负数、小数、字符串都报错。压缩走 `shared.model.stream`，用同一套重试，`Retrying` 记成本轮的 `modelRetry`，出错时直接报带次数的错误。每条都有测试。

### 意见

1. **建议改**：重试那一行的原因里带了 `retried N times`，和「第几次」对不上。
   - 位置：`crates/canter-model/src/retry.rs` 在交出 `Retrying` 前就执行 `error.retries = retry;`；`crates/canter-core/src/runner.rs` 的 `record_retry` 和 `crates/canter-core/src/btw.rs` 用 `error.to_string()` 当原因。
   - 问题：实测第一次重试显示 `Retrying in 0.5s (1/10): model request failed: Server (HTTP status: Some(503)); retried 0 times`，第三次是 `(3/10) ... retried 2 times`。「第几次」和「已重试几次」并排出现，读起来像自相矛盾。这只是显示问题，重试本身没错；验收要的「第几次、几秒后再试、为什么」都有。
   - 改法：重试那一行的原因不带次数。比如 `retry.rs` 只在最后交出错误前写 `retries`，`ModelError` 在 `retries == 0` 时不显示 `; retried 0 times`；或者给 `ModelError` 加一个不带次数的原因文字，给 `record_retry` 和 `/btw` 用。
2. **可以不改**：每条回复存盘的事件和 main 有两处写法不同。
   - 位置：`crates/canter-core/src/response.rs`（`id("model")`）、`runner.rs` 的 `finish_items`。
   - 问题：回答、思考项目的 ID 前缀从 `message-`、`reasoning-` 变成了 `model-`；回复结束时的 `item.completed` 按收到的先后发（先思考后回答），main 是先回答后思考。reducer 按 ID 原地替换，界面按快照里项目开始的先后排，也搜了没有代码按 ID 前缀判断，所以快照、界面、重开、导出都一样。Esc 和正常回复都受影响，不算 Esc 行为的变化。
   - 改法：不用改，记一笔。
3. **可以不改**：以后会提前确认单项的接口，在「保留收完整的接着做」那条路上没有提示。
   - 位置：`crates/canter-core/src/runner.rs` 的 `conversation`，`interrupted_with_content` 那条路。DeepSeek 走不到。
   - 问题：断开后接着做时不出 `modelRetry` 那一行，也不算进 `model_max_retries`。界面上只有半截标 `[Interrupted]`；如果正好断在两项之间，就什么都看不出来。每次接着做之前都得多收完整一项，所以不会原地空转（推测：以后的接口按这个约定发 `ItemCompleted`）。
   - 改法：等 P2-80 接 Responses 时再看要不要加一行提示。
