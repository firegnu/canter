## 重点看

1. **钩子不能放宽限制**：PreToolUse 只在 canter 自己判成「要问」或「直接执行」时才跑，跑完重新判权限；JSON 里的 `allow` / `ask` 确实被忽略。计划模式、审查轮、敏感路径、`fileRules`、沙箱的判断都没被绕开。受限会话从哪条路都不跑钩子。
2. **进程和并发**：钩子在锁外跑，一个会话的钩子慢或卡住不会拖住别的会话、界面和服务端。超时、打断、会话关闭、服务端停机时，整组进程都杀干净，钩子自己再起的子进程也算在内。只通知的事件不让这一轮等它。输出限长，不会撑爆内存。
3. **UserPromptSubmit 的空轮流程**：被拦的话不进模型历史、不发给模型，重开会话也不会回放；空轮在 Esc、关闭、撤回、配置交接、`canter exec` 下都能正常结束。被拦的插话不会多发一次模型请求。改了 reducer 的回填规则和终端撤回草稿，旧客户端和旧存盘照样能读。
4. **九个事件触发得对**：各条开始一轮的路都算上，包括你送的话、排队输入、后台叫醒、目标续跑、计划批准后开的新会话、`/new`、`/handoff`、`exec`；结束分完成、出错、打断。不该触发的时候不触发：比如自动叫醒的那一轮不触发 UserPromptSubmit，`ask_user` 不额外弹批准框。标准输入的字段名对。热加载后下一轮才生效。
5. **坏钩子不挡路**：起不来、超时、退出码不是 0 也不是 2、JSON 坏了，都放行并给一行提示。钩子配置写错时照 P2-154 沿用旧配置。

### 五个重点逐条核对

1. **钩子不能放宽限制**（已查证）。PreToolUse 只在 `permission()` 判出 `Ask` 或 `Execute` 时跑（`runner.rs:1260-1287`），准备阶段被拒（敏感路径、计划模式拦写、审查轮拦写改）走 `Err(output)` 分支，根本不进 `permission()`；`Forbidden`、`Deny` 不跑钩子。钩子放行后 `continue` 回循环顶，重新取锁、重新判审查轮／计划模式／`fileRules`／沙箱／档位，判成什么就是什么；批准后还有原来的计划模式复查和 `resolve_with_prefixes`。钩子结果只有 `Some(reason)`（拦）或 `None`，`allow`、`ask` 和别的字段在 `execute()` 里根本不读（`hooks.rs:420-448`）。测试 `permissions_are_rechecked_after_waiting_for_pre_tool_hooks`、`restricted_sessions_and_hard_denials_never_run_hooks`、`lifecycle_notifications_and_permission_cannot_approve_or_continue_a_turn` 都过。受限会话：所有钩子只经 `hooks::run` 和 `hooks::notify` 两个口子，两处都先查 `runtime.context.restricted_mode`；`start()` 算 `check_prompt` 也查了；热加载 `apply_configuration` 沿用旧 `context`，不会改掉受限标记；`set_folder_trust` 改受限时立刻换 runtime。
2. **进程和并发**（已查证）。会阻塞这一轮的钩子（UserPromptSubmit、PreToolUse、PostToolUse、goal 工具）调用时都不持状态锁（`check_prompt`、`consume_steering`、`permission()` 里先 `drop(state)`、`goal::execute` 先 `drop(state)`；`runner::execute` 的调用方也不持锁）；`hooks::run` 只为拼输入和追加 warning 短暂取锁。通知事件 `tokio::spawn`，不让这一轮等。每条命令 `process_group(0)` + `kill_on_drop`；`ProcessGroup` 的 Drop 对整组发 SIGKILL，超时（`timeout` 丢掉 `work`）、取消（`select!` 丢掉 `work`）、领导进程正常退出（`drop(group)`）三条路都会触发；钩子用 `setsid` 自己脱组的不在内（没法管，可接受）。stdout、stderr 各留 32 KiB，超出的继续读、丢掉；stdin 写不进时其它三路照样并行，不死锁。测试里 `sleep 30 &` 的孙进程在超时和打断两种情况都确认被杀。关会话、停服务端的等待见建议改 2。
3. **UserPromptSubmit 空轮流程**（已查证）。`start()` 在有 UPS 钩子时不调 `user_input`、不发 `UserMessage`，`TurnStarted.input` 为空，原话放在 `pending_prompt`；放行才写历史和 `UserMessage`；拦下只发 warning（只含原因，不含原话）。重开：模型历史只从私有历史重建，被拦的原话从没写进去；排队输入在 `TurnStarted{input_id}` 时就从 `queued_inputs` 去掉，被拦插话用 `InputRemoved{blocked}` 去掉，重开不回放（测试 `prompt_block_never_reaches_the_model_even_after_resume` 过）。各种结束：Esc／撤回时 `model_started` 为假，撤回成立，回退点在 `user_input` 之前登记，撤回能完成；关闭会取消 token、杀钩子；配置交接在 `prepare_turn` 里锁外等，取消照常；`exec` 拦下后正常收到 `TurnCompleted`。被拦插话：`consume_steering` 只在真消费了输入时返回 true，轮末只在 true 时 `continue 'turn`，不会多发请求（测试 `blocked_late_steering_does_not_restart_the_model` 过）；主提示被拦时插话挪回队首，下一轮各自再查。兼容：reducer 只在原 input 为空时回填，旧存盘的 `TurnStarted`、`TurnCompleted` 都带原输入，不变；`InputRemovalReason` 有 `#[serde(other)] Unknown`，旧客户端能读 `blocked`。终端：轮进行中 `turn.input` 为空时 `echo_index` 为空，`UserMessage` 项照常画出来；完成回填后改由轮标题画、跳过回声项，不重复也不丢。

### 建议改

1. **到期用 `abort` 取消通知任务，可能打断正在写日志的任务，让这次关会话失败**（推测，读代码推出，没复现；只在时间正好撞上时出现）
   - 位置：`crates/canter-core/src/hooks.rs:240`（`task.abort()`）；`hooks.rs:204`（通知任务结束前在状态锁下 `journal.append(warnings)`）；`crates/canter-core/src/journal.rs:134-152`；`crates/canter-store/src/lib.rs` 的 `append_batch`。
   - 问题：`journal.append` 不能中途取消。它在 `spawn_blocking` 里由写入器给事件编号并写盘，回来后才把事件应用到内存快照、广播给客户端。通知任务里某条命令失败（退出码非 0 非 2、自身超时、输出坏），任务要写 warning。如果这一刻正好碰上 3 秒到期，`abort` 会在等写盘结果时丢掉这个任务：盘上已经写了这条 warning，内存快照没跟上。之后 `close_inner` 写 `SessionStatus Closed` 时，写入器给的编号比内存快照期望的大 1，`validate_event` 报序号错，`append` 返回错误（`failed` 不置位）。结果是这次关会话返回错误，HTTP 处理重试一次还是错；停机时最后报 `some sessions failed to close; resume them to recover`，进程退出码非 0。盘上的事件是连续的，恢复能好。窗口只有一次写盘的时长，正常使用里要「通知钩子正好在第 3 秒左右失败」才会碰上。比如 Stop 钩子里 `curl` 连不上，3 秒左右超时退出非 0。所以只算建议改。被卡住的钩子还在跑、不在写日志，不受影响。
   - 改法：到期不要 `abort`，改为取消通知任务的令牌。比如 `Shared` 上加一个停钩子用的令牌，`notify` 里和原来的令牌合起来交给 `run_input`。`execute` 里现有的取消分支会丢掉 `work`、整组杀进程、返回 `Ok(None)`，任务自己把已有的 warning 写完，`drain` 再等它们结束。补一条回归：通知命令在接近上限时以非 0 退出，关会话仍成功。
