### 必须改

1. **必须改：一个补丁同时碰到「询问」和「禁止」两种文件规则时，禁止规则被跳过**
   - 位置：`crates/canter-tools/src/permission.rs` `file_rules`（分支里 199–231 行的循环）。
   - 问题（读代码确认）：循环按 `prepared_paths()` 的顺序逐个判断，遇到第一个 `Prompt` 就 `return Some(self.ask(call, false))`，后面路径的 `Forbidden` 根本没查到。`resolve_with_prefixes` 批准时又用同一个 `file_rules(call, AlwaysAsk)` 复查，得到的还是 `Ask`、不是 `Forbidden`，于是 `Accept` 直接给了执行许可。举例：rules.json 里 `*.md` 是 prompt、`secrets/**` 是 forbidden，在询问模式下模型发一个补丁，先 `Update File: README.md`，再 `Add File: secrets/x`，会弹批准框，用户点同意后 `secrets/x` 就写进去了。write/edit 只有一个路径，单个文件取的是所有规则里最严的（`rules.rs` 的 `decision.max`），禁止规则不能靠批准绕过。apply_patch 这里跟 write/edit 不一致，属于任务里说的「越过权限」。Allow all 模式下 `Prompt` 落到 `_` 分支、会继续往下查，所以不受影响；只有询问模式有这个问题。
   - 改法：先把所有路径（含删除、改名两端和新文件父目录）的决定都算出来，有任何一个 `Forbidden`（或在 Allow all 下规则读不了）就返回禁止；全部查完后，有 `Prompt` 或规则读不了才返回 `ask`。补一条回归测试：询问模式下，一个补丁里前一个路径是 prompt、后一个是 forbidden，结果是禁止、不弹框、一个文件都不写，`resolve(Accept)` 也返回禁止。
