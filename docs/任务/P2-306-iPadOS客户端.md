# 任务：iPadOS 客户端，iPad 加妙控键盘连服务端干活

依据：从 P2-300 第 3 条拆出。用户嫌 Mac 重，想拿 iPad + Magic Keyboard 工作，连 5090（或别的机器）上的 canter 服务端。优先级比 canter-desktop 连远程（P2-308）高。
依赖：P2-299（远程连接已齐）；推送见 P2-149；连接安全见 P2-305
执行：派出（先出方案给用户定，再派实现）
待用户：开工前定下面「开工时要定的」
优先：高（在 P2-149 之后）

## 用户原话

- 11-17（主控列 P2-300 剩下的 4 条后）：「这里面的拆出来写成任务。然后我理解接下来就是 推送（纯用canter客户端，不牵涉corral，padock之类的，理解我意思吧？）。嗨哟一个就是ipados的客户端任务，这个比canter-desktop优先级还要高（因为mac太重了，我想拿ipados+magic keyboard来工作）」

## 要的结果

- 在 iPad 上，用 Magic Keyboard，像现在 Mac 上的 canter 终端一样干活：开新会话、接回会话、聊天、批准、看输出、贴图。
- 只靠 canter 自己，不经 corral、paddock。

## 开工时要定的（主控先出方案，用户定）

- **做成什么**：iPadOS 原生 App（Swift，单独的仓库，像 canter-desktop），还是网页客户端在 Safari 里用（一个客户端 iPad、手机、任何浏览器都能用，和 P2-307 合成一件），还是先用 iPad 上的 SSH 终端 App 登服务端机器跑现成的 canter 终端（不用开发，今天就能用，但就是用户嫌慢的 SSH 那条路）。
- **怎么连到服务端**：iPad 上开不了常驻的 `ssh -L` 隧道（App 进后台会被挂起）。可选：VPS 上开 HTTPS（Caddy，P2-300 原计划），那 VPS 能看到令牌，要一并做 P2-305 的第 2 条；或者别的办法，方案里比。
- **后台和推送**：App 进后台 SSE 会断，回来要续接（canter 已经支持按事件编号续接）；等批准、做完的提醒走 P2-149。
- 令牌：iPad 单独一个令牌；要不要限权限看 P2-309。

## 不要做

- 不改「一台服务端只服务一个人」。
- 不写 canter 的特例给某个客户端；客户端只用公开协议，缺的接口在 canter 这边另开任务、写进 DESIGN。
- 文档和测试里不写真实的 IP、主机名、用户名。
