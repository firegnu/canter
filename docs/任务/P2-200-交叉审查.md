### 必须改

1. **纯旧单家配置下，带 `/` 又不在当前列表里的存盘模型发不出去**
   - 位置：`crates/canter-server/src/config.rs:262`（`legacy_models`）、`:377`（Router 的旧客户端分支）。
   - 问题：改前 `model_client` 把所有模型都交给那一个客户端。改后，`providers` 为空时 Router 也要求带 `/` 的模型名在 `config.models` 里，否则不发请求，直接回无状态码的 `InvalidRequest`。用户看到 "invalid request"，这一轮失败。恢复会话和分叉不检查模型（`http.rs` 的 resume/fork 不调 `validate_model`，DESIGN 第 8 条写「已存的旧模型仍可恢复」），所以这条路径真的会走到。例子：旧配置接 OpenRouter，默认模型从 `deepseek/deepseek-chat-v3.1` 改成了 `deepseek/deepseek-v3.2`，没写 `models`，用旧模型的存盘会话升级后就跑不了，而改前照常发给旧地址。这违反第 5 条「用户不改 `config.json` 就能升级，行为和现在一样」。按用户定的第 2 条，前缀不是已配置家名的名字也该按旧单家认。
   - 改法：`providers` 为空时，Router 跳过 `legacy_models` 判断，全部交给旧客户端，和改前逐字节相同。配了 `providers` 时保留现在「认不出的家名报错」，所以混用配置删掉其中一家时，它的会话仍不会回落到旧地址。`removing_a_provider_does_not_send_its_sessions_to_the_legacy_provider`（`reload_tests/providers.rs:464`）改成删掉 `one`、留下 `two`，仍验证不回落。再补一条：纯旧配置下，列表外带 `/` 的存盘模型照发旧地址，请求字节不变。代价是 `providers` 全删光时，那几家的会话会发到旧地址；改前单家时换 `base_url`，旧会话也是一律发到新地址，这和改前一致。这会推翻开发「踩过的坑」里的一个有意选择，也要改它的测试断言，请主控确认。如果主控要保留「全删光也不回落」，就得明确接受第 5 条的这个例外，并写进 DESIGN。

### 建议改

1. **混用写法时，旧 `models` 列表里的名字可能和家名撞上**
   - 位置：`config.rs:207-214` 只检查了默认模型。
   - 问题：例如旧顶层接 OpenRouter，`models` 里有 `deepseek/deepseek-v3.2`，又加了一家叫 `deepseek` 的官方。`/v1/models` 把这条显示成旧单家的：没有 `provider`，窗口和看图都是旧的全局值。选它以后，Router 却按第一个 `/` 把它发给 DeepSeek 官方，带 DeepSeek 的 key，模型名是 `deepseek-v3.2`。这符合第 2 条的拆分规则，但模型目录和实际路由对不上，用户会以为发给了 OpenRouter。
   - 改法：`load` 里对旧 `models` 的每一项做和默认模型一样的检查：第一个 `/` 前是已配置的家名、那家 `models` 里却没登记后半段，就报错并说明是哪一家（沿用 P2-154 整份保留旧配置）。存盘会话里的旧名字查不到，在 DESIGN 第 6 条补一句「家名和旧模型名的前缀撞上时按家名走」。

2. **空闲时换模型，状态栏的窗口数字不立即变**
   - 位置：`crates/canter-core/src/session.rs:1790` 只改了 `runtime.limits`；状态栏读快照里最后一次 `TokenUsage.model_context_window`（`canter-tui/src/app.rs:6128`），而 `runner.rs:845` 在轮外沿用旧值。
   - 问题：换模型以后，`/context` 马上是对的，但状态栏的窗口和百分比要等下一轮第一个回复记完用量才变，比如从 1M 换到 100k 时，中间这段百分比是错的。审查任务第 5 条「状态栏的上下文数字跟着变」没做到。原任务「怎么算做完」没有这一项，状态栏又归 P2-201，所以算建议改。
   - 改法：换模型时用现有事件追加一条 `TokenUsage`，只把 `model_context_window` 和 `auto_compact_tokens` 换成新模型的值，其余照旧；或者记到 P2-201 一起做。

3. **子 agent 还在跑时，父会话可以换模型**
   - 位置：`session.rs:1716-1726` 只拦了活动轮和顺口问。
   - 问题：交互会话里，父轮结束后子 agent 还能继续跑（`agents.rs` 的 `running_agents`）。这时父会话换模型会被放行，跑着的子 agent 和之后 `send_input` 都继续用派出时的模型和那一家。key 和地址是配对的，不会串，但和审查任务第 5 条「子 agent 在跑时换模型被拒」不一致。
   - 改法：二选一。换模型时按 `running_agents` 的条件拒绝；或者在 DESIGN 写明「子 agent 一直用派出时父会话的模型」。

4. **路由失败时，用户只看到 "invalid request"**
   - 位置：`config.rs` Router 末尾。
   - 问题：认不出家名时（比如删掉一家以后打开它的旧会话）回的是无状态码的 `InvalidRequest`，和上游 400 分不出来，用户不知道该去改配置。
   - 改法：给一句明确的英文提示，比如 "model X is not configured"。可以在 core 发请求前按当前配置查，也可以让模型层错误带说明。不急，可以记 HANDOFF。

### 可以不改

1. 配置刚重读、会话还没开新一轮时，换到新加进来的模型：会话手里的 `runtime.options` 还是旧版本，`limits` 会退回全局窗口，`/context` 暂时显示不对。下一轮开始时 `apply_configuration` 按新版本重算，压缩判断用的是对的值；顺口问开始前也会先刷新配置。只影响显示。
2. 换模型时取消正在生成的提示建议（`session.rs` 新加的 `state.suggestions.cancel()`）：旧单家换模型时也会触发，算一点行为变化。但它只取消还没出来的建议，免得拿旧模型的结果，合理。
3. `/v1/models` 对旧单家也加了 `contextWindow`（全局窗口）：只是加字段，旧客户端不受影响。

### 重点 1～5 逐条核对（除上面几条外没发现问题）

1. **请求发对家、key 不串**：所有模型请求都经 `telemetry::stream`，取 `shared.runtime().model`（Router），`request.model` 来自会话的 `settings.model`。普通轮、压缩（`compaction.rs:378`）、顺口问和交接（`btw.rs`，空闲时先刷新配置再冻结）、提示建议、审查轮都一样。子 agent 复制父会话的设置，用父会话的 Router 和配置。Router 和 `options` 来自同一个配置版本，每轮开始应用一次，轮内不换；换模型在有活动轮或顺口问时被拒，所以一轮里不会前后用两家。旧单家里带 `/` 的模型名在列表内时，走旧客户端是对的。例外见必须改 1、建议改 1。
2. **凭证不漏**：`Config`、`Provider`、`Router` 都没有 `Debug`/`Serialize`。`providers` 下的解析错误只报字段路径和家名，不报值；其余错误仍只报行列。重读失败的提示、`/v1/models`、事件、遥测里只有家名、模型名和窗口。相关测试覆盖了 key 和请求头的值。
3. **旧配置照旧**：旧客户端的构造和改前完全一样；`providers` 为空时价格、看图、搜网页、窗口和压缩线（`CoreOptions::limits` 退回全局值）、模型列表顺序都没变；`config.rs` 的逐字节测试比较了改前的直连客户端和 Router。例外见必须改 1。
4. **没碰不该碰的**：core 的 `compaction.rs`、`context.rs`、`runner.rs` 只把 `options.context_window` 和 `options.auto_compact_tokens` 换成 `limits`。系统提示词、上下文拼接、工具列表、压缩提示词和摘要、P2-142 带回文件、P2-176 待办都没动。换到小窗口用的是 runner 里原有的占用判断和压缩流程。core 里没有按厂商名字或地址分支，认 DeepSeek 官方地址只在 `config.rs` 的 `options()` 一处。
