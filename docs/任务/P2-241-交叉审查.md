### 必须改

1. **必须改：逐文件规则判断的目标与实际打开的目标没有绑定。**
   - 位置：`crates/canter-tools/src/ast_grep.rs:273–289`；对照 `executor.rs:450–452`、`lib.rs:1491–1501,1683`。
   - 问题（源码已确认）：先把目录项 `path` 解析成 `resolved`，以二者判断文件规则，随后却调用 `open_file(&path)`。`LocalExecutor::open_file` 又解析一次原路径，而且只复查执行器保护，不复查 `rules.json`。若文件符号链接在这两次解析间改变目标，第一次允许的目标与真正读到的目标可以不同；第二个目标即使命中文件规则的 forbidden/prompt，也没有再过该规则。`read` 至少会把已检查的规范路径传给读取函数，本次新增的目录内读取没有沿用这一点。根目录在 `execute_with_images` 的复查不能保护每个子文件。这是文件规则越权窗口，不是对静态私有文件检查失效的指控；私有文件仍会被第二次 `resolve_path` 检查。未构造竞态输入运行。
   - 改法：逐文件保留 requested/resolved 做规则判断，读取至少像 `read` 一样使用已经检查的 `resolved`，不要再通过原符号链接选择另一个目标；若要覆盖规范路径自身被替换的竞态，再将检查与打开的文件句柄绑定。不要仅多解析一次却不比较目标。

2. **必须改：把 `Pattern::try_new` 成功误当成模式语法正确。**
   - 位置：`crates/canter-tools/src/ast_grep.rs:133–134,199–203`；依赖 `ast-grep-core-0.40.0/src/matcher/pattern.rs:27–49,188–200,547–553`。
   - 问题（源码已确认）：`StrDoc::try_new` 能为有语法错误的输入生成恢复后的语法树，`PatternBuilder::single` 只检查根节点个数，并不拒绝 ERROR 节点。依赖自己的 `test_error_kind` 明确使用 `Pattern::new("123+", Tsx)` 并断言 `has_error()`；它使用的 TSX 语法包版本也是 0.23.2，语言构造方式与本实现一致。因此至少这类 TSX 错误模式会进入 `compiled`，随后作为正常搜索返回没有匹配，而不是让模型修正模式。现有错误模式测试只覆盖多根节点、空白和额外参数，不能证明语法错误被拒绝。违反验收中的「模式写错」行为。
   - 改法：在语言适配的模式构建处检查预处理后语法树的错误及缺失节点，返回带语言和可定位原因的模式错误；至少不能接受 `Pattern::has_error()` 为真的结果。保持按语言分别判定，不能因为 tree-sitter 恢复出一棵树就称该语言编译成功。

3. **必须改：显式单文件调用的 prompt 批准被执行阶段抹掉。**
   - 位置：`crates/canter-tools/src/ast_grep.rs:280–285,520–525`；对照 `permission.rs:237–245,377–379`。
   - 问题（源码已确认）：`walk` 会把显式指定的单文件也放进同一逐文件循环，而循环把所有 `Some(FileRuleDecision)` 无条件跳过。因此 `path` 指向命中 prompt 规则的文件时，即使询问档已经单次批准，或者 Allow all 已按 `read` 的规则放行，仍只得到 skipped / no matches。`run` 没有收到批准范围，无法区分已批准的根文件和未获批准的目录成员。这是核心文件权限语义算错；任务的「目录内 prompt 文件跳过」不能扩展成「单文件已批准也不读」。
   - 改法：区分显式单文件与目录扫描，将已通过闸门的单文件许可用于同一个已检查目标；目录成员仍按本任务明确要求跳过 prompt，不把批准一个根路径扩大成批准所有成员。forbidden 和不可读取规则文件继续拒绝。

### 建议改

4. **建议改：Esc 只停止等待，已经开始的解析和匹配还会继续。**
   - 位置：`crates/canter-tools/src/ast_grep.rs:315–325,475–495`；`tests/ast_grep.rs:436–463`。
   - 问题（源码已确认）：取消分支会及时返回，但 `spawn_blocking` 的闭包没有取消令牌；丢弃其句柄不会停止已经启动的工作，解析、匹配、复制全部命中仍会做到末尾。本地 Tokio 依赖的 `src/task/blocking.rs` 也明确说明运行中的 blocking 任务不能被 abort。现有取消测试在调用 execute 前就取消了，没有覆盖解析中的 Esc。普通小文件不一定能观察到影响；大生成文件上取消后继续耗用 CPU/内存是风险，未实测耗时或压力。
   - 改法：把取消传入解析与匹配阶段，遍历命中时定期检查，并给解析本身接入取消机制或明确的有界处理。保留当前快速返回，不将它描述成已停止后台解析。

5. **建议改：50 条和文字截断没有限制扫描内存及协议结果体积。**
   - 位置：`crates/canter-tools/src/ast_grep.rs:296–318,328–335,364–370,450–463,475–495`；依赖 `ast-grep-core-0.40.0/src/tree_sitter/mod.rs` 的 `StrDoc::try_new`。
   - 问题（源码已确认）：先无上限读完整文件，`StrDoc` 再复制一份源文；`find` 把该文件所有匹配的完整文本复制并排序，之后才做 offset 和 50 条选择。前三行预览没有字节上限，最终只截断给模型的 `text`，`Item::AstGrep.matches[].text` 仍保留未按字节截断的预览。正常仓库中提交的压缩 JS、大型生成 TS/Rust 文件就可能触发这条路径，并不需要异常目录或特制输入。能否导致本机 OOM 未测，不能断言必崩，但现有输出上限不能作为资源有界的依据。
   - 改法：限制实际读入字节数并报告因大小跳过的文件；计总数时只保留当前页需要的有界预览，避免为页外命中复制正文；给每条预览和整页协议字段也设字节预算。不要为了限内存把总数改成不说明的近似值。

6. **建议改：补默认 path 前先验证参数是对象，并统一处理 null。**
   - 位置：`crates/canter-tools/src/lib.rs:1151–1164,1170–1182`；`ast_grep.rs:150–157`。
   - 问题（源码已确认）：JSON 解码为 `Value` 后就执行 `arguments["path"] = ...`。合法 JSON 但类型错误的参数（如数组）会在 serde_json 的字符串索引赋值处 panic，来不及走 `Args` 的正常错误返回；依赖 `serde_json-1.0.154/src/value/index.rs:96–103` 明确是这个行为。另外，`path: null` 被 `Option<String>` 接受，却因字段已存在而不补默认值，`resolved_path` 为空，默认根目录不会进入 `prepared_paths` 的根路径规则检查；这与省略 path 的准备过程不同。逐文件检查仍存在，不把此处单独称为已证实的内容泄露。
   - 改法：先要求参数为对象并解析类型；按 schema 拒绝 null，或将其规范化成与省略完全一致的默认路径，然后统一准备、批准和执行。错误输入返回 Failed，不 panic。

7. **建议改：把未完整搜索的说明和总数传到卡片、导出。**
   - 位置：`crates/canter-tools/src/ast_grep.rs:342–370`、`crates/canter-protocol/src/types.rs:733–744`、`crates/canter-tui/src/cells.rs:1867–1928`、`export.rs:366–396`。
   - 问题（源码已确认）：跳过、文件语法错误、某语言模式失败的说明只存在模型结果 `text`，成功的协议项目 `error` 为 None，且没有保存这些说明。卡片和导出只显示本页 `matches.len()`，也不使用已有的 `total_matches`。所以所有文件都没解析成功时，人看到的仍是成功的 `0 matches`；有 55 条而本页 50 条时，人只看到 50。模型文字结果有说明，问题限定在人可见的卡片和导出。
   - 改法：用有界的可选说明或计数字段保留未完整搜索原因，并在展开卡片和导出显示；分页时区分本页数量与总数。保持旧客户端可忽略新增字段。

8. **建议改：修正新测试对临时目录路径写法的依赖。**
