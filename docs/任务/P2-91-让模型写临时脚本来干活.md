# 任务：让模型写临时脚本来干活

依据：用户 10-27 问 canter 能不能根据任务写代码来做事（不是改仓库的代码）。现在靠 `write` 加 `shell` 能做到，但没有专门的支持。本件先记下，范围等用户定了再补全、给用户看过再派。
待用户：定做哪几样
执行：派出

## 用户原话

- 10-27 用户：「还有一个事情，现在canter能根据任务写代码来做某些工作吗？（不是修改repo的代码），理解我意思吗？」
- 10-27 主控答：懂，指模型为完成一件事临时写段脚本跑一下拿结果（统计文件、转换数据格式、批量改名、算数），类似「代码解释器」；现在能用 `write` 写脚本、`shell` 跑，但批准多、没有放临时脚本的地方、没有隔离。用户：「对，记成一件待定任务吧。开一个新任务」。

## 现在的情况（主控 10-27 查的）

- 模型可以用 `write` 写脚本文件再用 `shell` 跑，或直接在 `shell` 里跑 `python3 -c '…'` 这类；跑在用户本机的真实环境里。
- 「每次问」模式下，写一次、跑一次都要批准；只读白名单（`readonly.rs`，`rg`、`ls` 等）免批准。切到「全部允许」就不问，但别的操作也不问了。
- 没有专门的临时目录：模型可能把脚本写进当前项目、用完不删。系统提示词（DESIGN 第 20 条）里没有讲临时脚本放哪、用完清掉。
- 没有沙箱，脚本能读写用户的文件。
- 和 P2-88 报告里的 code mode（Codex `exec`、pi `codemode`、opencode `execute`：模型写 JavaScript 组合调用 agent 自己的工具）不是一回事，那个报告建议不做。

## 待定

1. 给每个会话一个临时目录（比如放在 `~/.canter/` 下或系统临时目录），系统提示词里告诉模型临时脚本放那里、用完清掉。改系统提示词照 DESIGN 第 20 条要用户点头。
2. 写进这个临时目录、在这个目录里跑的脚本，要不要少问几次批准；少问到什么程度（只免写、还是写和跑都免）。这碰批准规则，算碰要害。
3. 沙箱（限制脚本能读写的路径、能不能联网）：现在做还是以后再说。报告第 7 节「Codex 沙箱怎么定免批准」还没查清，真做前要先调研。（10-27 并进 P2-104 沙箱。）
4. 要不要先调研别家（Codex、Claude Code、pi、opencode）有没有专门的临时目录或脚本执行的做法，再定上面几处。
