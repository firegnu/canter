### 重点逐条

1. **SessionStart 什么时候等、谁不跑**：`Session::create` 和 `open_inner`（含 fresh fork 的 startup）走新的 `hooks::session_start`，它照旧检查受限会话和 `parent`（子会话不跑）。`clients.rs` 重连那条仍是 `hooks::notify`，不碰 `session_start_hook`，有重连 3 次的测试。等待在 `check_prompt`，不拿状态锁；最长就是钩子自己的 timeout（`execute` 的超时）；取消时不取走 receiver，留给下一轮。`/new`、`/handoff`、计划清空后实施、`canter exec` 都走 HTTP 的 `Session::create`，路径相同（没有逐个入口的测试，结构上覆盖到了）。
2. **只往后加、下标一致**：注入只在轮边界之后 `history.push`（`check_prompt`、`consume_steering`、`conversation` 每次请求前），不往中间插。`hook_contexts` 在 restore 的回退、撤回、压缩，运行中的 rewind、retract、压缩，以及 `acknowledge_agent_result` 删背景通知后的平移里都跟着处理了；`history` 别的改动点（`grep history.remove/split_off/truncate/=`）都覆盖到了。分叉复制 `HookContext` 记录，不复制没完成的轮。前缀逐字节比对有测试。
3. **`defer_prompt` 那条路**：`pending_prompt` 只在 `check_prompt` 里 `take` 一次；`start_input` 在 defer 时不写用户输入，所以不会记两次。终端按 Esc 对非审查轮总是请求撤回，没出模型输出就撤回，草稿照 P2-153 的办法回到输入框。别的客户端不带撤回的打断，会丢掉这条还没放行的输入（不进模型历史），和原来 UserPromptSubmit 预检被打断一样。`/stop` 只停后台命令，跟轮无关。exec 最多多等钩子的 timeout。排队的输入开新轮时 receiver 已经取走，不再等；插话在首轮放行之后才消费，顺序对。没发现卡住。
4. **拦截和压缩**：`run_input` 先收齐所有命令再出结果，有 `reason` 就整条不注入（首轮和插话都是）；SessionStart 的注入留到下一条放行的输入，有测试。前缀压缩的说明里加了 `[Hook context: ...]`，转写那条路标成 `Internal hook context`；注入不进 `user_messages`，不算最近原话。
5. **`input()` 里的两个 `expect`**：服务端走不到。`state_directory` 拒绝相对路径的 CANTER_HOME（`crates/canter-server/src/lib.rs:57`），存储根目录是 `home.join("sessions")`，是绝对路径；`std::path::absolute` 收到非空的绝对路径时不读当前目录，不会出错。会话 ID 在 create、open 时已经过同一个 `session_dir` 校验（`crates/canter-store/src/lib.rs:178`、`:227`），`expect("valid session id")` 也走不到。只有别人把 canter-core 当库用、给相对路径的存储根目录、当前目录又被删掉时才会出错。见可以不改第 1 条。

### 建议改

1. **配了 SessionStart 后，新会话可能起不了名**（`crates/canter-tui/src/run.rs:1638`，`AutoName::sent`）。
   - 问题：现在只要有 SessionStart 钩子，首轮就走延后写输入的路，`TurnStarted.input` 是空的，轮结束才补上。如果终端先应用了事件流里的 `turn.started`，后处理 HTTP 回复，`first` 是 `None`，并且 `seq <= last_event_seq`，这一轮就被当成「已撤回」，不起名。之后几轮的 `first` 又不等于当前轮，这个会话一直不会自动起名。两种到达顺序都会发生（`first_message_after_user_shell_becomes_the_session_name` 就测了 `event_first` 两种情况，只是用的是带输入的 TurnStarted）。这个问题原来只碰得到配了 UserPromptSubmit 的用户，本件让所有配了 SessionStart 的会话都会碰到，正好是接 cairn 以后的常态。
   - 改法：判断这一轮还在不在时按轮 ID 找，比如 `find(|t| !t.input.is_empty() || t.id == turn)`；在上面那条测试里加「空输入的 TurnStarted 先到」的情况。不在验收里、不算要害，交主控定是本件里顺手修，还是另开一件小活或记进 HANDOFF。
2. **撤回首轮会让这一段的 SessionStart 注入整个丢掉**（`crates/canter-core/src/hooks.rs:316` 的 `session_start_context` 取走 receiver；`crates/canter-core/src/runner.rs:208` 撤回时去掉那一轮）。
   - 问题：终端 Esc 对普通轮总是请求撤回，模型还没出输出就能撤回。钩子早就跑完时（这是常态），用户发完消息马上按 Esc 改错字，注入就随这一轮去掉了，receiver 也已经取走，下一条输入没有 SessionStart 上下文。这一段里模型从来没收到过它，cairn 的「上次做到哪」就没送到。这符合验收原文（「回退、撤回掉的那一轮的注入跟着去掉」），所以不算必须改。

### 逐条

1. **下一条输入的请求里有且只有一份**：撤回时，`runner.rs` 先用 `retracted_start_contexts` 取出被撤回那一轮里的 SessionStart 注入，再截掉历史。取的时候只看 `hook_contexts` 里登记过的下标，再认 `[Hook context: SessionStart]` 开头，所以 UserPromptSubmit 的注入和用户自己打的同样字样都不会被取走。原来的 receiver 在首轮已经取走，所以下一轮只有队列里这一份。`defer_prompt` 在队列不空时也会延后写输入，`session_start_context` 先把队列里的补发出去，再放 UserPromptSubmit 注入和用户输入，补发的那份紧挨在用户输入前面。回退（`rewind.rs`）没改，不补发。测试断言补发后请求里只有一份、位置在用户输入前面、显示项只有一条、没有 UserPromptSubmit 注入。
2. **重开不重复也不丢**：restore 碰到 `Retract` 时，用当时的历史和下标重建待补发队列；碰到 `SessionStart` 的 `HookContext`、而且正文等于队首时，就算这次补发已经做过，把队首弹掉。按文字匹配不会认错：运行时 `session_start_context` 总是先把队列补发完，才注入 receiver 的新内容，所以 Retract 之后最先出现的那几条 SessionStart 记录一定是补发，顺序和队列一致。新内容和旧内容文字完全相同时，也只弹掉第一条。补发前重开、补发后重开两种情况都有测试，测试在重开前停用钩子，证明补发的内容来自历史。崩溃在记下 Retract、还没写 `turn.retracted` 时，`open_inner` 会补写这个事件，restore 也照样能重建队列。
3. **多次撤回**：补发的那一轮又被撤回时，补发那条也在 `hook_contexts` 里，会再次进队列；restore 里先弹掉，到这次 Retract 再放回去，和运行时一致。没有单独的测试，但走的是同一段代码，读下来没有问题。
4. **和 resume 新的一份同时存在**：撤回后还没补发就重开（钩子仍配着），下一次请求会有两份 SessionStart：先是欠的那份，再是 resume 新拿到的。没有撤回时，历史里本来也会有这两份，模型看到的份数一样，restore 也能分清（见第 2 条）。见可以不改第 1 条。
5. **其它**：撤回后如果先跑了一个自动轮（比如后台命令叫醒），补发会落在那个自动轮的请求里，不在下一条用户输入里。这和 DESIGN 写的「下一次模型请求前补发」一致。原建议改 1（自动起名）的范围跟着变大：撤回首轮后，下一条输入也会延后写，起名照样可能被跳过；改法不变。开发者记录里写了交主控在合并后处理，这里不另算一条。

### 可以不改

1. 第 4 条那种「欠的那份 + resume 新的那份」同时出现的情况没有测试，现有测试在重开前把钩子停了。行为是对的，想补就在 `retracted_session_start_is_reinjected_once_even_after_reopening` 里加一种「重开时钩子还在」的情况，断言请求里两份、顺序是欠的在前。
2. `hooks.rs` 的 `retracted_start_contexts` 用 `history[index]` 取值。现在 `hook_contexts` 在每个改动历史的地方都同步维护，走不到越界；换成 `history.get(index)` 更稳，不必为此返工。
3. 分叉不带走「撤回了、还没补发」的那份：`fork.rs` 不复制 Retract 记录，所以新会话里没有这个待补发队列。新分叉有自己的一份 startup 注入；已经补发过的那份会原样重放。不影响「分叉原样重放」。
