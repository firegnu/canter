## 要做的

1. **规则怎么写**：按词前缀匹配（`cargo test` 匹配 `cargo test --release`，不匹配 `cargo testx`），每条规则是放行 / 要问 / 禁止之一；一条命令命中几条时取最严的（禁止 > 要问 > 放行）。第一版不做中间的通配。
2. **存在哪**：只有全局一个文件 `~/.canter/rules.json`（设了 `CANTER_HOME` 时放该目录，0600），不和存 API key 的 `config.json` 混；没有文件当作没有规则。文件写坏了（读不了、格式不对）时不能当成「没有规则」悄悄放行：禁止规则读不出来就是没生效，要在界面上提示一次文件有问题、照现在的规矩问。规则文件改了要不要重启服务端才生效，照你的判断定，在完成记录里写。
3. **批准框上一键放行**：shell 命令的批准框加一项「以后 `<前缀>` 开头的都不问」，前缀取程序加子命令（`cargo test`、`git commit`；没有子命令的就是程序名），批准框上把要写进去的前缀原样显示出来；选了就写进 `rules.json` 一条放行规则，这次也照常执行，在对话里提示一句写进了哪个文件。组合命令按每一段需要批准的各写一条。太宽的前缀不给这一项：照 Codex 的 `BANNED_PREFIX_SUGGESTIONS` 那一类（`bash`/`sh`/`zsh -c`、`python`、`node`、`env`、`sudo`、单独的 `git` 等解释器和包一层的命令），清单定好写进完成记录。
4. **会话放行改窄**：shell 批准框上现在的「本会话都放行」改成只放行这个前缀（本会话内），不再一下放开所有命令。别的工具（改文件、网页、MCP）的「本会话都放行」不变。
5. **组合命令**：拆成一段段判断（`&&`、`||`、`;`、`|`、换行等，沿用 `readonly.rs` 现有的拆法，能复用就复用）：每一段都被放行（规则放行或只读白名单）才不问；有一段命中禁止就拒绝，命中要问就问；遇到 `$(...)`、反引号、变量这类判断不了的写法，放行规则不管用、照旧问，禁止规则仍要尽量管（能认出来的段命中禁止就拒绝）。
6. **和现有规矩怎么接**：
   - 禁止规则在三种权限模式下都管，包括「全部允许」；被禁止时模型收到原因，不弹批准框。
   - 放行、要问规则在「总是问」和「只问执行」下都管；「全部允许」下只看禁止规则。
   - 要问规则能让只读白名单里的命令也问。
   - 受保护路径、计划模式、审查轮只读照旧优先；用户自己的 `!` 命令不受规则管；只管模型的 shell 命令（含放后台的），MCP 和 `web_fetch` 不管。
7. **协议和文档**：一键放行这个新选项怎么在协议里表达，照 Codex app-server 的结构定（Codex 在批准请求里带 `proposed_execpolicy_amendment`、回答里带 `execpolicy_amendment`），比 Codex 多的、和 Codex 不同的写进 DESIGN 第 8 条；DESIGN 写一条命令规则的规矩（上面这些和用户 10-29 的选择）；`crates/canter-tools/README.md` 跟着改。旧客户端不认识新选项照旧能用（没有这一项），旧会话照旧能打开。
