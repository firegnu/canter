## 要做的

1. **规则写在哪、怎么写**：`rules.json` 加一段文件规则，和现有命令规则并列，每条是一个文件模式加 `forbidden` 或 `prompt`。模式写法照 Claude Code 的 Read 规则和 gitignore 的习惯：不带 `/` 的（如 `.env`、`.env.*`、`*.pem`）在任何目录下按文件名匹配；带 `/` 的按路径匹配，支持 `~/` 开头和 `**`。具体语法由你定，写进 DESIGN。没有这一段或这一段为空，行为和现在完全一样。
2. **管哪些工具**：只管模型的 read、write、edit（包括 read 读图片）。路径按工具现有的方式解析后再匹配，符号链接指向受管文件的也算。shell、用户 `!`、MCP、`web_fetch` 不管。
3. **命中以后**：
   - `forbidden`：三种权限模式下都拒绝，不弹框，告诉模型这个文件被用户的规则挡住、不要换办法去读。
   - `prompt`：「总是问」「只问执行」下单次弹框问用户；批准框不提供「本会话都放行」，已有的文件工具会话授权也免不掉。「全部允许」下直接放行。
   - 一个文件同时命中两种，取 `forbidden`。
   - 计划模式和审查轮里 read 现在直接放行，也要守这两条。
   - 受保护路径和沙箱的敏感路径照旧优先。
4. **`/permissions`**：现有列表里增加一组文件规则，能看、能删，删除方式和命令规则一致。服务端接口照现有 `commandRules` 的做法扩展，改了什么写进 DESIGN，旧客户端不受影响。不在界面里新增、修改规则；空列表的提示里说明可以在 `rules.json` 里加文件规则。
5. **坏文件**：`rules.json` 读不了或格式错时，现有命令规则怎么退回，文件规则就和它一致；不能因为文件坏了让 `forbidden` 的文件在「全部允许」下被读到。具体怎么退由你定，写进 DESIGN。
6. **文档**：DESIGN「按命令放行」后补一小节写文件规则；改了协议的，在 DESIGN 开头协议差异处补一条。界面上的文字一律英文。
