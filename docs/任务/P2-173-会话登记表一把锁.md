## 现在哪些地方拿着这把锁做慢事（11-01 主控读 `crates/canter-server/src/http.rs`）

| 路径 | 拿着锁做什么 |
|---|---|
| `resume`（没开着的会话） | `disk_snapshot` 整份重放 → 查文件夹信任 → `Session::open`（再读一遍历史和 model history）→ `configure_session` |
| `resume`（开着的会话，P2-32 加的） | 查文件夹信任、`set_folder_trust`、取快照 |
| `create` | `Session::create`（建目录、写盘同步）→ `configure_session` |
| `read`（没开着） | `disk_snapshot` 整份重放 |
| `App::session`（几乎所有按会话的命令都先走它；会话没开着时） | 只为了决定报「没恢复」还是「不存在」，做一次 `disk_snapshot` 整份重放 |
| `ledger`（`/v1/sessions/{id}/usage`；`/v1/usage` 对每个会话各调一次） | 没开着的会话整份读事件文件 |
| `EventReader::new` / `recv`（`GET /v1/events`） | 没开着：整份读事件文件；开着：订阅、挂接客户端（P2-32 加的） |
| `trash`（P2-32） | 没开着：`disk_snapshot`；开着：`close_for_trash`（最长约 10 秒等 SessionEnd 钩子）；建回收站目录、移目录 |
| `close`、停机（`lib.rs`）、热加载提示（`reload.rs`） | 只取出或移除登记表条目，快 |

这把锁现在顺带保住的规矩（改完必须照样成立）：
1. 读一个没开着的会话（重放、读事件）时，不能有别的请求把它打开、开始写（注释：「resume cannot start a writer mid-read」）。
2. 两个请求同时打开同一个会话，只建出一份 `Session`，第二个拿到第一个建好的。
3. 删会话（P2-32）和恢复、挂接、事件流挂接同时发生时只有一边成功，不半删、不删完又被建出来或写进去；检查「能不能删」到移走目录之间，同一个会话不能被打开或挂上。
4. 关会话只移除自己那一份（`same_instance`）。
5. 停机：拿到 `draining` 写锁之后取出的会话就是全部，不会有停机后才打开的会话漏关。

## 完成记录

2026-11-01，`p2-173-registry-lock`。

**做了什么**：`App.sessions` 改为只在查找、克隆、插入、移除时短暂持锁。新增按 ID 的 `SessionLocks`，恢复、新建、未打开会话的快照／命令查找／用量／事件读取、事件流挂接和删除改在各自会话的锁内执行；同 ID 复查登记、打开、关闭删除和挂接仍互斥。索引保存弱引用，最后一个持有者或等待者离开即回收，不积累访问过或不存在的 ID。关闭仍在 Core 关闭后检查 `same_instance`，不移除后来的新实例。停机的原有屏障与收集流程提取为 `begin_drain`，热加载用同一快速登记枚举方法，未新增等待阶段。

读请求取消也纳入第 1 条规矩：原实现取消 handler 后会释放登记表锁，但 `spawn_blocking` 读盘仍在继续；这时恢复能开始写。现在实际读盘任务共同持有该 ID 的 guard，直到读取／重放结束才放行。快照、用量、事件三条取消路径都有测试，没有让只读请求取得 `draining` 读锁。

**新的锁顺序**：需要准入检查的命令先持 `draining.read()`；短持锁索引的同步锁取得 ID 锁引用，放开索引锁后才等待该 ID 的操作锁；持操作锁时短暂访问登记表，放开登记表后才进 Core 或做 I/O。Core 仍为状态锁 → clients。没有持登记表等 ID 锁、同时等两把 ID 锁、或从 Core 反向取登记表的路径。`registry_changed` 保留先登记等待再检查、读完放锁再等待的顺序。README 已写清这些规则、取消读取的 guard 生命周期、关闭的实例检查，以及全局用量读到同 ID 时仍排队的边界。

**验证了什么**：先加受控读盘测试，在原实现上得到“另一会话快照超过 300 ms”的有效 RED；随后 16 个慢路径组合均复现跨会话阻塞。补齐创建配置和回收站准备后，将原锁实现连同同样的测试暂停点临时恢复复核：18 个组合全部阻塞，另复现真实 SessionEnd 钩子、同时打开两个 ID、打开与删除、停机收集被无关读盘挡住，以及取消读请求过早释放互斥；原实现下本组 4 项通过、7 项按预期失败，手动基准忽略，随后已恢复修复实现。
