### 意见

1. **建议改**　`crates/canter-model/src/wire.rs:122`、`:135`
   - 问题：GPT 消息只有思考摘要时（最常见是 GPT 还在思考、摘要已流出时按 Esc，存成 `[Reasoning]` 加来源标记），去掉摘要后会发出 `{"role":"assistant","content":""}`，既没有 `reasoning_content` 也没有 `tool_calls`。main 里不会出现这种消息（别家只有思考时带 `reasoning_content`，什么都没有的不记）。有的 Chat Completions 服务端会拒收空的 assistant 消息（印象里 Moonshot 有「role 'assistant' must not be empty」这类报错，**未查证**）。
   - 改法：只在本条因为来源是 Responses 去掉了思考、而且没有文字和调用时返回 `None`，其余情况不变，单家请求字节不受影响。不改也可以：合并后试用时留意「GPT 思考中按 Esc → 切到 Kimi」这一条，被拒再修。
2. **建议改**（或记 HANDOFF）　`crates/canter-model/src/wire.rs:127`、`crates/canter-model/src/history.rs:18`
   - 问题：Chat 拼装只按名字判断补丁调用。只用 DeepSeek/Kimi 的会话里，模型如果调了没提供给它的 `apply_patch`（canter 会照样记下调用和「找不到工具」一类结果），新版会把这条调用转成「Historical apply_patch call…earlier turn」文字、结果转成 user 消息，请求字节和 main 不同；要是发生在当前这一轮里，下一次请求还会把模型刚做的调用说成「之前的轮次」。前提是模型调用了工具列表里没有的工具，平常碰不到，不会被拒。
   - 改法：补丁转文字只认确定来自 GPT 的消息有难处（被拒后 `replay` 已清空，旧 GPT 消息也没有 `replay`），所以不建议为这条改判断规则；可以在完成记录或 HANDOFF 里记一句「别家自己调出的 `apply_patch` 也会转成文字」。
3. **可以不改**　`crates/canter-model/src/responses/wire.rs:32`、`:139`
   - 问题：切到目录里不是 freeform 的 GPT、又碰到「补丁 + 普通函数」混在一批时，Responses 请求按原位置放，补丁结果（user 消息）可能夹在 `function_call` 和它的 `function_call_output` 之间。Responses 一般按 `call_id` 配对、不要求紧挨着，但 ChatGPT 订阅接口会不会拒**未查证**；DESIGN 已写明「Responses 保持各项原位置」，是有意的取舍。
   - 改法：不改；试用时如果切到非 freeform GPT 被拒，再照 Chat 的做法把补丁结果挪到本批普通结果后面。
4. **可以不改**　`crates/canter-core/src/context.rs:336`
   - 问题：只用 GPT 的会话碰到 replay 被拒以后，内存里那些消息的思考摘要被去掉，`/context` 里助手部分和自动压缩前的估算会比 main 小一点。发给 GPT 的请求字节不变（Responses 本来不发摘要），存盘不变，重开后同样处理，结果一致。
   - 改法：不改；这是主控决定一的直接结果，估算反而更接近实际发出去的内容。
