### 具体意见

1. **必须改：macOS 的目录分支会启动应用包。** 位置：`crates/canter-tui/src/links.rs:213–215、265–271`，入口包括 `cells.rs:371–377、496–510`。`metadata` 跟随符号链接，只要目标是目录就选 `Kind::Directory`，随后不带 `-t` 地执行 `open <路径>`。`.app` 包在文件系统上也是目录，因此读文件卡片（包括读取失败的卡片）、改名后的新路径或指向应用包的符号链接，都可能把“点路径查看”变成启动应用。参数是一个且不经过 shell，并不能阻止 Launch Services 的这种行为。本机 Apple `open(1)` 手册说明其行为相当于双击文件图标；[Apple Launch Services 文档](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCTasks/LSCTasks.html)也明确说明打开应用项目会启动或激活应用。**改法：** 目录交给明确的 Finder 展示动作，例如 `open -R <路径>` 在 Finder 中定位，或明确指定 Finder；不要依靠 `.app` 后缀黑名单保证安全。普通文件继续明确交给文本编辑器，目录展示方式由主控定并同步文档。本条是代码和系统语义确认，未真的启动应用。

2. **必须改：Linux 的文件分支没有实现“路径用默认文本编辑器开”，且可转为执行启动器。** 位置：`crates/canter-tui/src/links.rs:265–271`；测试 `tests/links.rs:309–315` 也直接把 `xdg-open <文件>` 当作编辑器行为验收。[xdg-open 官方文档](https://portland.freedesktop.org/doc/xdg-open.html)说明文件按其类型的默认程序打开，不能保证文本编辑器。进一步读源码：[xdg-open 的 `open_xfce`](https://gitlab.freedesktop.org/xdg/xdg-utils/-/blob/master/scripts/xdg-open.in)会在没有 `xfce-open`、有 `exo-open` 时调用后者；[Xfce 的 `exo-open/main.c`](https://github.com/xfce-mirror/exo/blob/master/exo-open/main.c)在参数以 `.desktop` 结尾时进入 `exo_open_launch_desktop_file`，对本地 Application 类型调用 `g_app_info_launch`。因此在这类桌面环境中，点击模型新建或修改的 `.desktop` 卡片可以启动其中的程序，并非只是选错查看器。本条依据静态代码链，未运行 Linux 桌面程序。任务正文虽指定 `xdg-open`，但同时与「怎么算做完」和「不要做」冲突，完成记录不能自行解除这个约束。**改法：** 主控先定 Linux 的显式文本编辑器启动方案；找不到编辑器时提示失败或采用明确批准的复制方案，文件不能回退到通用 `xdg-open`。测试应验证实际选择的是文本编辑器，而非仅复述当前命令。

3. **必须改：命中检测用最新数据重新排版，可能打开用户没有看到的目标。** 位置：新增的 `crates/canter-tui/src/app.rs:1339、1439、1475–1492`；调用关系见 `app.rs:2063–2068`、`run.rs:336–340、579–580`。运行循环先归并服务器消息，再处理已排队的鼠标事件；鼠标事件原本带有屏幕帧号，但这里丢掉了它。`link_at` 调用 `laid_out`，按最新快照构造链接，而不是查询事件发生时已画出的那一帧。普通流式场景即可出现：屏幕还显示一个尚在增长的网址，新增路径片段先被归并，随后同一批处理按下、松开；两次命中都得到更新后的完整网址，比较相等，最终打开未曾显示给用户的目标。表格重排、滚轮事件与点击同批处理也有同类风险。现有 `tests/links.rs:802` 只测按下以后在末尾追加行，覆盖不到这条路径。**改法：** 绘制时保存实际显示的链接区域、目标、视口和帧号，鼠标按事件帧号查询，按下和松开都核对已显示的映射；旧帧不可用或位置含义改变时取消打开。补普通流式更新尚未重绘、滚动和改宽度的假 opener 回归测试，不需要构造任何安全绕过输入。

4. **建议改：取消交互没有清掉已经松开的待打开链接。** 位置：`crates/canter-tui/src/app.rs:724–740、1459–1470、1600–1617、2128–2135`。单击松开后选区已清除，但 `mouse.link` 还在；随后按 Esc 或 Ctrl+F 均不清它，`open_link` 也不检查搜索状态。因此点击后立即进入搜索，仍会在搜索打开、链接下划线消失后启动外部程序；Esc 也无法取消这次等待。**改法：** Esc、打开搜索以及明确切换会话/内容的操作取消待打开点击，并在执行前确认当前仍允许打开。增加点击后、计时到期前按键的普通交互测试。本条属于交互补强，不把完成记录里的搜索选择追加成用户的新硬性验收点。

5. **建议改：回收子进程的线程创建失败被吞掉。** 位置：`crates/canter-tui/src/links.rs:279–302`。子进程已经启动后才创建等待线程，`thread::Builder::spawn` 的结果被 `let _` 丢弃；线程创建失败时持有 `Child` 的闭包被丢弃，没人负责 `wait`，却仍返回成功并显示 `Opened`。正常路径的 `wait_with_output` 会等待并排空 stderr；非零退出时第一条非空 stderr 经过 `visible` 转义，未发现把 ESC、C1 或双向控制字符原样画进状态行的问题。**改法：** 先成功创建工作线程，再在线程里启动并等待子进程，通过 channel 回报启动和退出结果；处理线程创建失败，避免先生成无回收者的子进程。可将返回结果的格式化抽出做纯数据测试，不必真开浏览器或编辑器。

6. **建议改：路径检查仍在 UI 线程，且把所有非目录对象都当普通文件。** 位置：`crates/canter-tui/src/links.rs:213–226`，由 `app.rs:2135` 的绘制过程调用。等待子进程已移出 UI 线程，但 `std::fs::metadata` 和进程启动仍同步执行；网络卷或自动挂载目录上的 metadata 可能阻塞界面。`Ok(_) => Kind::File` 也会把 FIFO、设备、socket 等交给编辑器，而不只是普通文件。普通文件的符号链接会按预期走 `open -t`；指向目录的链接受第 1 条影响。**改法：** 将文件检查和启动一起移入工作线程，跟随符号链接后的对象只接受普通文件或按第 1 条处理的目录，其余提示不支持。未对网络卷和特殊文件做真实打开试验，故本条作为建议，不以未经实测的卡顿判定必须改。
