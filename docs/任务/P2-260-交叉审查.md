### 必须改

**必须改 1：超时以后、或主 agent 不等子 agent 就结束时，canter 继续在容器里干活，和判分同时进行**

- 位置：`bench/terminal-bench/canter_agent.py:119-135`（`run()`）、`:137-173`（`_collect`）、`:69-81`（`_exec_private`）。
- 问题：
  - Harbor 0.25.0 `SingleStepTrial._run_agent`（`trial/single_step.py:74-86`）把 `AgentTimeoutError` 记下后照常往下走：采集日志和 artifacts，然后 `_run_verifier`。TB 2.1 的 89 题都没有设 verifier 模式，按 `resolve_task_verifier_mode` 默认 SHARED：测试上传到**同一个容器**里跑（`single_step.py:37-54`），判分完才 `docker compose down`。
  - 超时由 `asyncio.wait_for` 取消 `run()`。`_exec_private` 不传 `on_output`，走 `_collect_buffered_output`，它只在自己的 `TimeoutError` 时结束子进程，被取消时什么都不做；就算宿主机上的 `docker compose exec` 客户端被杀，容器里的进程也不会因此停。
  - 更根本的是 canter 的结构：`canter exec` 只是客户端，回合跑在 `ensure_server` 用 `setsid` 拉起的常驻服务端里（`crates/canter-server/src/discovery.rs:199-202`）；只有 exec 收到 INT/TERM/HUP 才会向服务端发 `interrupt`（`crates/canter/src/exec.rs:148-161, 306-313`）。适配器的 finally 只做了 `_collect` 和 `_remove_config`；删掉 `config.json` 后服务端重读失败，按 `crates/canter-server/src/reload.rs:298` 「Keeping the previous configuration」继续用内存里的配置和 key。
  - 后果：超时的题，canter 在 Harbor 上传 `/tests`、跑测试的同时继续调模型、改文件、跑命令，可能在判分途中改出结果或改坏结果，也可能读到刚上传的 `/tests`。这等于放宽了超时（用户「不放宽超时」）；对比的 Terminus-2 的循环在 Harbor 进程里，超时就停，两边不对等。stats 是超时那一刻取的，之后的花费不记。全套里超时不会少（48 题只有 900 秒）。Harbor 自带的 installed 外壳也没有专门的超时清理，但 canter 的回合在脱离出去的服务端里，靠客户端怎么都停不下来，必须由适配器自己停。
  - 正常结束也有同类缺口：P2-178 定 `canter exec` 单轮、不自动等子 agent，只在 `spawn_agent` 结果里提示模型先 `wait_agent`。模型没等就结束本轮时，`canter exec` 退出，在跑的子 agent 留在服务端继续跑（P2-172：客户端离开不打断工作）。explorer 只读，主要影响用量；general 能改文件。
- 改法（具体写法由开发定）：
  - 容器里记下 exec 的 PID，比如 `echo $$ > /tmp/canter-harbor/exec.pid; exec /usr/local/bin/canter exec --yolo -- ...`。
  - `run()` 被取消或出错时，先对这个 PID 发 TERM（exec 会向服务端发 interrupt 并等回合结束），限时等（比如 30 秒），还在就 KILL。
  - 不管正常结束还是中断，取 stats 之前停掉容器里的 canter 服务端，让还在跑的子 agent 也停下：按 `$HOME/.canter/server.json` 里登记的 `pid` 发 TERM，限时后 KILL。不按名字批量杀，也不碰题目要求留着的服务进程。之后再 `canter stats --last --json`（会重新拉起服务端，开发时确认它不会续跑被打断的回合）、采集、删配置，最后再停一次服务端。
  - 取消路径里的清理不能把 `CancelledError` 换成别的异常，否则 Harbor 不再判分（见建议改 1）。
  - 验证不一定要调真实模型：把 `endpoint` 指向一个不应答的地址，让请求挂住，加 `--agent-timeout-multiplier` 把超时调短，跑 1 题（这是适配器测试，不算成绩）。核对判分开始前容器里已经没有 canter 进程，会话最后一条事件早于 `verifier.started_at`。也可以由主控在用户同意下用真模型跑一次。用哪种交主控定。

**必须改 2：子 agent 合计为空时，回退成只算主会话的用量**

- 位置：`bench/terminal-bench/canter_agent.py:177-180`。
- 问题：canter 算 `usageWithSubAgents` 用的是 `Option::zip`（`crates/canter-core/src/stats.rs:129-142`）：只要有一个直接子 agent 的 `usage` 为空，合计就成了 `null`。子 agent 有事件但没有一条记账的请求时就是空，比如刚开就被打断（必须改 1 修好后，超时时正好会出现）、第一次请求就失败。这时适配器回退到 `overview.usage.total`，**所有**子 agent 的用量都丢了，没有任何提示。canter 的系统提示会主动让模型并行开 explorer（P2-248），这种情况在全套里能碰到。试跑三题都没开子 agent，这条路径没跑到过。（子 agent 不能再开子 agent，`report()` 只算直接子 agent 是对的。）
- 改法：`subAgents` 不为空时，适配器自己把 `overview.usage.total` 加上每个 `subAgents[].usage` 不为空的那些。空的就是没记过账，算 0 是对的；任何一项 `cost.unknown` 为真则美元记 `null`。在 `metadata` 里记子 agent 个数和用量为空的个数。canter 这边 `zip` 让合计变空的写法（终端界面的合计也会因此不显示）记进完成记录，另开任务，不在本件改 canter。

### 建议改

**建议改 1：采集或用量解析失败会让 Harbor 跳过判分，按 0 分算**

- 位置：`canter_agent.py:148-149, 172-173, 175-187`。
- 问题：`_run_agent` 只接住 `AgentTimeoutError` 和 `NonZeroAgentExitCodeError`。`_collect` 抛的 `RuntimeError`（stats 失败、tar/base64 失败）和 `populate_context_post_run` 的 `TypeError`（canter 一次请求都没成功时 `overview.usage` 为 `null`，`None["total"]`）都会冒到 `Trial.run`，整个 trial 不判分，`report.py` 按 0 记。也就是说，canter 已经做对的题可能因为适配器自己的记账出错拿 0 分。另外，Harbor 把 compose 的 stderr 并进了 stdout（`stderr=STDOUT`），适配器直接对整段做 base64 解码，混进来的警告会把归档弄坏。试跑没出现，89 题也没有自带 compose 文件，风险低。
- 改法：记账出问题只记进 `metadata` 和单独的文件（用量记成未知），不抛会让判分取消的异常；`overview.usage` 为空时 token 记 0、美元记 `null`。容器里的 tar 写成文件，stderr 单独重定向，或者用 Harbor 的 `download_file` 取回。删配置失败仍然抛，这一处是有意的。

**建议改 2：偷看答案规则漏了几种明显的取法，有两类文件没扫却标了 complete**

- 问题：

**建议改 3：`report.py` 不检查缺题和重复题；oracle 和 canter 的题目版本靠人眼比**

- 改法：exec 需要 KILL，或者退出码不在 {0, 2, 3, 4, 130}（这几个都表示 exec 已经收到 `TurnCompleted`，或者回合还没开始）时，也停服务端，在 metadata 里另写一个原因。有空的话用 README 里的 TEST-NET 探针再跑一次超时路径（不花钱），在结果文件里注明用的是哪一版适配器。
