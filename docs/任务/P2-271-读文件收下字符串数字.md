# 任务：读文件收下写成字符串的行号

执行：主控
依据：11-10 查遥测，读文件有一次 `"limit":"220"` 因类型不对被拒（P2-265 当时定了不收字符串）。pi、omp 会先把 `"42"` 转成数字再校验，Codex 不转。本轮只改读文件这一个工具，不像 pi 那样所有工具统一转。

## 用户原话

- 「那limit字符串这个也像pi一样转一下这个难度和爆炸半径如何？」
- 「我觉得影响不大的话做了吧？」

## 要做的

- 读文件的 `startLine`、`lineCount`、`offset`、`limit` 收下纯数字字符串（`"220"`），结果和写数字一样。
- 不是数字的字符串（`"abc"`、`"-1"`、`""`）照旧报错；`startLine: "0"` 和 `startLine: 0` 一样报错；同一个意思写两遍照旧报错。
- 推翻 P2-265 第 3 条（「数字写成字符串这次不收」）。
- 发给模型的参数定义和工具说明不改。

## 不要做

- 不改别的工具，不加统一转类型那一层。`page`（PDF 页码）不动。

## 完成记录

- 做了什么：`crates/canter-tools/src/lib.rs` 读文件参数的 4 个行号字段改用自定义解析：数字照收，纯数字字符串转成数字，其他字符串报 `expected a non-negative integer`。转完后照旧走 P2-265 的别名换算和 `startLine` 必须为正的检查。
- 验证：先写测试，确认它因字符串被拒而失败；改完后通过。`tests/files.rs` 新增「字符串写的行号和数字结果逐字一样」，原来的报错测试把字符串那条换成 `"abc"`、`"-1"`、`""`、`"0"`、字符串重复写这几条。`cargo nextest run -p canter-tools` 244 条全过（工具说明快照没变），clippy、fmt、`git diff --check` 通过。
- 拿主意的地方：`page` 不动，用户只同意改这次碰到的那一类。
- 没做的事：别的工具不转。
- 踩过的坑：没有。
