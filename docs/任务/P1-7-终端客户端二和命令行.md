### 拿主意的地方

- **会话名**：用首句的前 80 个字。带首句的话建会话时直接写进去；不带的话，第一次送话成功后用 PATCH 补上，前提是会话还没名字、没有对话也没有排队的输入。
- **客户端名**：取终端设备名，比如 `canter-tui ttys003`，没有终端时用 `pid N`。这样两个终端能分清是谁送的、谁答的。来源只标在别人送的话上，自己送的不标。
- **重连**：只用 `discover`，不起服务端（服务端是谁停的，谁负责再起）。每次重连都发 resume，所以服务端那边被删掉的会话也会被重新打开。
- **`--resume` 和其他参数**：带 `-m` 或 `--yolo` 时，接上以后用 PATCH 改模型或权限；同时带首句会报错（「接上以后再说」）。
- **晚答**：服务端回 `alreadyResolved` 时，显示「你的回答晚了一步，没有生效」。
- **退出**：打印接着聊的命令。不带参数敲 `canter` 现在进对话界面，不再打印只有 serve 的用法。
- **依赖**：新加了 `chrono =0.4.45`（只开 `clock`），会话列表要用它显示本地时间。`canter` 用到了 nix 的 `term` 功能，用来读终端名。
- **对外接口**：`canter-tui` 新导出了 `Launch`、`Open`、`Connector`、`FrameSync`、`run_on`，`canter` 的测试直接用它们。

   - 测试 `a_small_window_never_hides_an_answer_it_accepts`：80 列、高 6 到 30 行，短命令和 30 行的长命令各试一遍。每种都只能是两种结果之一：四个选项和命令第一行都在屏幕上；或者显示「窗口太小」，并且不收回答。
   - 80 列时，高 14 行起放得下。

拿主意的地方：

- Unicode 双向控制字符（U+202A–202E、U+2066–2069、U+200E、U+200F、U+061C）也画成转义。它们会让终端把命令显示成另一个顺序。
- 窗口太小时 Esc 照样能打断这一轮。打断等于拒绝并停下，是安全的方向。
- 批准到达但还没画出来时，之前敲的按键照旧进输入框，不丢；Enter 会把输入框里的字送出去，不会答批准。
- 会话关着时，输入框里还能送话：服务端回 `session_not_resumed`，界面照旧显示「没送出去：…」，没有另外拦。

踩过的坑：

- 关会话测试一开始在旁观终端的状态行上留下「端结束了事件流」这样的残字。原因在测试用的 TestBackend，跟真终端不一样：
  - 真终端写一个宽字符会盖住后一格；ratatui 只重画变了的格子，靠的就是这一点。
  - TestBackend 不盖。状态行在几段中文提示之间切换、宽字符错开一格时，旧字就留下了。
  - 客户端本身没问题：旁观终端其实已经空闲，等插入新的历史行、整屏重画以后就干净了。
  - 改法：`tests/tui.rs` 里测试屏幕的 `draw` 写宽字符时把后一格清掉，跟真终端一样。
- macOS 的 `head` 不认 `-n -1`。看画面的临时测试改成追加到测试文件里，看完还原。

验证：

- 新测试 7 个（canter-tui 5 个，真服务端 2 个），在原代码上都先失败，改后通过。
- 通过的：`cargo test -p canter-tui --all-targets`；`cargo test -p canter --test tui`（7 个，连跑 3 次）；`cargo clippy --all-targets -- -D warnings`；`cargo fmt --check`。
- 照这次的要求只跑了直接相关的测试，没有跑全量的 `cargo test --all-targets`。
- 跑完没有残留的 canter 进程。真实模型接口调用 0 次。

还没解决、要主控定的：

- 有一种情形还会重开：别的客户端关了会话，旁观终端还开着，之后服务端又重启了（比如升级）。
  - 旁观终端连上新服务端时，分不清这个会话是之前被人关的，还是服务端退出时一起关的：两种情况都只有一条 `session.status: closed`，盘上也一样。按现在的规则它会 resume，把会话重新打开。
  - 要彻底分开，得让服务端关会话时记下原因，比如关闭事件里带上 `clientName`，或者注明「请求关闭 / 服务端退出」。这要改协议和服务端，所以没做。
  - 可选：
    - (a) 接受这个情形，写进已知问题；
    - (b) 另开一件改协议，客户端随后跟上。
  - 建议 (b)，不急。

## 审查后修改（复核第 1 轮）

2026-10-24，照 `P1-7-交叉审查.md` 末尾「主控判断（复核第 1 轮）」改第 2 条的残留。先写了走实际 `run_on` 的复现测试，在 36d49c5 上确认它因为这条缺陷失败，再改。

- **问题**：上一轮在布局时就记下了「画面上是什么」。可在真终端里，新的一帧要到 `end_frame`（结束同步刷新）之后才显示出来。所以画批准框这一帧的时候进队列的 Enter，等画完被处理时，会按新记下的批准框来处理，结果批准了 B。
- **改法**：按键带上「来的时候屏幕上是第几帧」，按那一帧显示的东西判断。
  - `run_on` 的终端输入改成新加的 `Input` / `InputSender`（用 `canter_tui::input()` 建）。读终端的线程每收到一个事件，就记下当时屏幕上的帧号。
  - 帧号只在 `end_frame` 之后才加一。画一帧期间进来的按键，带的还是上一帧的号。
  - 界面记下最近几次画面变化：每一帧上是哪个批准框、选项放不放得下、哪一轮在跑。按键按它带的帧号找到当时的画面再处理：
    - 那一帧是输入框，键就进输入框（Enter 有字就送出去）；
    - 那一帧是某个批准框，只答那个请求，而且那个请求还得在等回答；
    - Esc 只打断那一帧上在跑、现在也还在跑的那一轮。
  - 不在乎帧的地方（`Ui::draw` 配 TestBackend 的界面测试）照旧：画完就算显示了，`App::handle_key` 按最新一帧处理。
  - 会话列表的内容只随它自己的按键变，所以不看帧号；它每画一帧照样计数。
- **测试**：新加 `a_key_that_comes_in_while_the_box_is_drawn_does_not_answer_it`（真服务端、假模型、实际 `run_on`）。
  - 测试屏幕在批准框第一帧的 `end_frame` 里往按键队列放一个 Enter。之后多等两帧和 1 秒：请求 B 还在等回答，`second-proof.txt` 没有写出来。
  - 批准框显示以后再按 Enter，B 照常执行，写出 `B`。
  - 在 36d49c5 上这个测试失败：Enter 答了 B。
  - 反向检查：改成按最新一帧处理按键，或者在 `end_frame` 之前就加帧号，这个测试都失败。
- **测试屏幕跟着改了两处**，让它像开了同步刷新的终端：
  - 测试只看得到 `end_frame` 之后的画面；
  - 按键前先等客户端把测试看到的那一帧算作已显示（像人看到了才按）。这一步通常只有微秒，不放宽任何断言。
  - 原来的 7 个真服务端测试照旧通过，按键处只是改成了异步调用。
- **验证**：
  - `cargo test -p canter-tui --all-targets` 通过；
  - `cargo test -p canter --test tui`：8 个，连跑 3 次都通过；
  - `cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 通过；
  - 没有残留的 canter 进程，真实模型接口调用 0 次。
- **剩下的**：帧号是读终端的线程收到按键时记的。终端已经送出、但它自己还没画完新一帧时按下的键，如果正好在我们记下新帧号之后才被读到，就会算在新的一帧上。这个窗口是终端处理输出的那几毫秒，人来不及对新画面作出反应。终端不给按键带时间戳，程序这边没法再分。

## 审查后修改（复核第 2 轮：用户决定加保护期）

2026-10-24。第 2 轮复核还剩一条：终端把批准框那一帧写出去之后、真正显示出来之前按下的 Enter，带的已经是新帧号，仍会批准新请求（审查者用真实 PTY 复现）。复核满两轮后主控问了用户，**加保护期是用户的决定**（见 `P1-7-交叉审查.md`「用户决定（复核第 2 轮后）」）。先写复现测试、确认它因为这条缺陷失败，再改。

- **规则**（常量 `ANSWER_GUARD_MS = 300`）：
  - 批准框的选项出现在屏幕上，就开始保护期：从输入框换成批准框、从一个请求换成另一个、窗口拉高后选项第一次放得下，都算；同一个框重画不算。
  - 保护期内收到的回答键（数字 1–9、Enter、↑↓）丢掉，不留到之后执行。
  - 保护期内还有按键进来（任何键），就从这个键起再算 300 ms。
  - 保护期过后新按的键照常回答。
  - Esc（打断这一轮）、Ctrl+C / Ctrl+D（退出）、PgUp / PgDn（翻看命令）不是回答键，保护期内照常。
  - 帧号保护保留：按键先按它来时屏幕上的那一帧判断，再看保护期。
- **提示**：保护期内选项那几行画暗，文字不变；过后在下一次重画（最多 100 ms）恢复。框出现的第一帧就是暗的，不会先亮一下再暗。「本会话都允许」下面那行说明不变暗。
- **实现**：
  - `InputSender::send` 除了帧号，还记下按键来的时间（Unix ms），`run_on` 一路传给 `App::handle_key_on`。
  - `App::frame_on_screen` 多收一个时间，选项新出现时定下保护期到什么时候；处理按键时判断、顺延。
  - 公开接口：`App::handle_key` 多一个 `now_ms` 参数（和 `apply_event`、`Ui::draw` 一样由调用方给时间）；导出常量 `canter_tui::ANSWER_GUARD_MS`。
- **测试**：
  - 新加 `enter_right_after_the_box_appears_does_not_answer_it`（真服务端、假模型、实际 `run_on`）。
    - 批准框一显示就按 Enter。这个键带的是批准框那一帧的号，帧号保护拦不住。
    - 再等 1 秒：请求还在等回答，`second-proof.txt` 没写出来，框还在。
    - 之后再按 Enter，B 照常执行，写出 `B`。
    - 在 2887cea 上这个测试失败：Enter 答了 B。
  - 新加 `answer_keys_right_after_the_box_appears_are_dropped`（TestBackend，时间由测试给）。
    - A 被别的终端答了，B 出现。保护期内 ↓、2、Enter 都不生效，每个键都顺延。
    - 顺延后的保护期快结束时，Enter 仍不生效，选项仍是暗的。
    - 过后 Enter 答的是选项 1：↓ 被丢掉了，没留着。
    - 选项在保护期内暗，过后不暗。
    - 改之前这个测试失败：保护期内按 2 选了「本会话都允许」。
  - 反向检查：去掉按键顺延、A 换成 B 时不开始保护期、↑↓ 不算回答键，这三种改法这个测试都失败。
  - 原有测试里批准框一出来就回答的地方，改成先等保护期过去（像人先看清再答）。真服务端测试 4 处先等 500 ms（`read_the_box`），界面测试 3 处把测试时钟往后拨 300 ms。没有删测试，没有放宽断言。
- **验证**：
  - `cargo test -p canter-tui --all-targets` 通过；
  - `cargo test -p canter --test tui`：9 个，连跑 3 次都通过；
  - `cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 通过；
  - 没有残留的 canter 进程，真实模型接口调用 0 次；没改 canter-server 和协议，DESIGN 不涉及批准框按键，没改。
- **代价和剩下的**：
  - 框刚出来就按的回答键要再按一次。一直按着键会一直顺延，停手 300 ms 后才能答。
  - 保护期挡的是「写出到显示」这几毫秒到几十毫秒。终端卡顿超过 300 ms 时仍然挡不住。
  - 用的是系统时钟。时钟往回拨时，保护期跟着变长（选项一直暗，Esc 照常），直到时钟追上。
  - 反方向没加保护：批准框被别的终端答掉、换回输入框的一瞬间按的 Enter，如果输入框里有草稿，会把草稿发出去。这次用户定的是回答键，这里没动。
