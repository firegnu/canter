## 对核心稳定性的影响（主控评估，11-08）

三件都改「一轮什么时候结束」，是对话循环的核心，所以每件都只在条件很窄时才动手，并且有次数上限。

| 方面 | 影响 | 怎么守住 |
|---|---|---|
| 正常的回合（模型正常停、没有没做完的待办、没有重复、没被截断） | 一个字节都不变：不加消息、不多发请求，事件、遥测、Stop 钩子都照旧 | 测试锁住：普通回合的请求和事件和现在一样 |
| 误判打转（比如等后台命令时反复查输出、反复 `sleep; tail log`） | 只认「同一个工具、参数一字不差、结果也一字不差」连续出现；等后台命令时输出会变，不算 | 第 1 件按这个定，测试覆盖「调用相同、结果不同」不算打转 |
| 误判该停（模型停下是要问用户、或卡住了） | 提醒里明说：卡住了或需要用户决定，就说明原因再停；每轮最多提醒 3 次，提醒完还停就真停 | 次数上限，测试锁住第 4 次不再提醒 |
| 多花钱 | 每次提醒、每次接着写都多一次请求 | 每轮各最多 3 次 |
| 缓存命中 | 提醒和「接着写」都是新追加的消息，不改已有历史 | 不改已有历史；测试锁住之前的请求前缀不变 |
| 用户按 Esc、用户插话 | Esc 照旧立刻停，不再提醒、不再接着写；用户插了话先处理用户的话 | 测试覆盖 Esc 后不再发请求 |
| `/goal` | `/goal` 自己会接着开新一轮，再加待办提醒会重复 | 目标是 Active 时不发待办提醒 |
| 计划模式、`/review`、目标收尾总结那一次请求 | 这些回合本来就不该接着做 | 都不提醒、不接着写 |
| 压缩 | 计数只在这一轮里算，和压缩无关；压缩后待办清单本来就会带回 | 不动压缩 |

结论：三件都是「本来要结束这一轮的地方，在窄条件下再给模型一次机会，或者在明显卡死时提前结束」。最坏的情况是多发 3 次请求，或者误把一次正常的重复调用当成打转停下。后者要求结果也一字不差才算，所以概率很低。

### 核心稳定性评估与实现取舍

- 正常回合不追加任何消息、warning 或请求。只在末端触发条件成立时改变控制流；工具结果在持有会话状态锁、落历史前比较和追加，遥测仍统计实际交付文本。只保留最后一个调用、原始参数和结果，不扫描完整历史。
- 第五次不执行，因此判断依据只能是前四次完全相同的结果和第五次完全相同的工具/参数；已在设计中明确。这符合用户选定的“第五次不执行”。第三次追加的提醒不参与下一次比较。
- 两类追加请求各有三次上限，因此同轮两种都触发最多增加六次请求，不能把任务单的“最多三次”理解成共享额度。用户新输入后按要求重置。合法但输出连续不变的轮询仍可能被停止；发新消息可继续。
- 正常请求与新一轮续写仍走原有压缩检查；没有修改压缩模块、压缩计数和重试策略。没有需要主控重新选择的本任务内实现方案。
