## 现状（主控查过的，main `e0ccf73`）

一轮对话的循环在 `crates/canter-core/src/runner.rs` 的 `conversation()`（约 358～585 行）：请求模型 → 有工具调用就逐个执行 → 再请求；模型正常停（没有工具调用）就结束这一轮。

### 1. 原地打转

- 只有系统提示词里一句（`crates/canter-core/src/prompt/core.txt` 第 25 行）：`never repeat an identical failed call`。代码里没有任何检测。
- 别家：omp 同一个调用连续重复 5 次就打断。
- P2-81 两次长程试跑（11-03 DeepSeek、11-07 GPT，各 12 件）都没出现原地打转。

### 2. 停下时还有待办没做完

- 待办是 `update_plan` 写的清单，`journal.snapshot.current_plan()` 取当前清单，步骤状态有 Pending / InProgress / Completed。配置 `plan_enabled` 为 false 时不用待办。
- 已有一个提醒：`crates/canter-core/src/session.rs` 的 `tool_result()`（约 549～570 行），清单里有没做完的步骤时，每 10 次非 `update_plan` 的工具调用，在那次工具结果末尾加一句 `[Plan reminder] If any plan steps are complete, call update_plan ...`。它只提醒「记得更新清单」，不管「停下时还有没做完的」。
- 模型正常停时（`reason == Stop`、没有工具调用）`conversation()` 直接返回，这一轮结束，不看清单。
- `/goal`（`crates/canter-core/src/goal.rs`）打开且目标是 Active 时，这一轮结束后会自动开下一轮接着做（`schedule_goal`），每轮开头重述目标。
- P2-81 两次试跑都没有「待办没做完就停」。

### 3. 回复被截断（写到输出上限）

- `conversation()` 约 529～558 行：结束原因是 `Length` 时，没执行的工具调用补一条 `No result: the model reply was incomplete, so the tool was not run`，发一条警告 `The model reply was incomplete; its tool calls were not run.`，**这一轮直接结束**，要用户再说一句才会接着做。
- 已经写出来的文字照常进历史（`model_response()` 约 700～725 行）。
- 网络出错、服务端出错时自动重试，重试用完后保留半截内容接着做，这些已经有了（P2-110、P2-120、P2-121），本件不动。
- 别家：pi、omp 截断后自动让模型接着写。

## 对核心稳定性的影响（主控评估，11-08）

三件都改「一轮什么时候结束」，是对话循环的核心，所以每件都只在条件很窄时才动手，并且有次数上限。

| 方面 | 影响 | 怎么守住 |
|---|---|---|
| 正常的回合（模型正常停、没有没做完的待办、没有重复、没被截断） | 一个字节都不变：不加消息、不多发请求，事件、遥测、Stop 钩子都照旧 | 测试锁住：普通回合的请求和事件和现在一样 |
| 误判打转（比如等后台命令时反复查输出、反复 `sleep; tail log`） | 只认「同一个工具、参数一字不差、结果也一字不差」连续出现；等后台命令时输出会变，不算 | 第 1 件按这个定，测试覆盖「调用相同、结果不同」不算打转 |
| 误判该停（模型停下是要问用户、或卡住了） | 提醒里明说：卡住了或需要用户决定，就说明原因再停；每轮最多提醒 3 次，提醒完还停就真停 | 次数上限，测试锁住第 4 次不再提醒 |
| 多花钱 | 每次提醒、每次接着写都多一次请求 | 每轮各最多 3 次 |
| 缓存命中 | 提醒和「接着写」都是新追加的消息，不改已有历史 | 不改已有历史；测试锁住之前的请求前缀不变 |
| 用户按 Esc、用户插话 | Esc 照旧立刻停，不再提醒、不再接着写；用户插了话先处理用户的话 | 测试覆盖 Esc 后不再发请求 |
| `/goal` | `/goal` 自己会接着开新一轮，再加待办提醒会重复 | 目标是 Active 时不发待办提醒 |
| 计划模式、`/review`、目标收尾总结那一次请求 | 这些回合本来就不该接着做 | 都不提醒、不接着写 |
| 压缩 | 计数只在这一轮里算，和压缩无关；压缩后待办清单本来就会带回 | 不动压缩 |

结论：三件都是「本来要结束这一轮的地方，在窄条件下再给模型一次机会，或者在明显卡死时提前结束」。最坏的情况是多发 3 次请求，或者误把一次正常的重复调用当成打转停下。后者要求结果也一字不差才算，所以概率很低。

## 用户定的（11-08，四件都选主控推荐的 A）

1. **打转怎么算、怎么处理**：
   - **A（用户选定）**：同一个工具、参数一字不差、结果也一字不差，连续出现算一次重复。第 3 次时在那次结果末尾加一句英文提醒：「这个调用和结果已经连续 3 次一样，换个办法」。第 5 次时不执行这个调用，这一轮结束，终端里给一行英文说明；有 `/goal` 时目标暂停，不自动开下一轮。
   - B（没选）：只提醒，从不打断。
2. **待办提醒**：
   - **A（用户选定）**：模型正常停下、清单里还有 Pending 或 InProgress 的步骤，并且没开 `/goal`、不在计划模式、不是 `/review` 时，追加一条英文提醒：「清单里还有 N 步没做完：…；接着做；如果卡住了或需要用户决定，就说明原因再停；做完了的先用 update_plan 标上」。每轮最多 3 次。终端里给一行英文说明，让用户知道模型是被提醒才接着做的。子 agent 也适用。

3. **截断后接着写**：
