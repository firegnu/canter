P2-151 · agent eval 是怎么做的，canter 该怎么做

给用户看的讲解页（11-09）。先讲一般做法，再对上 canter 已有的东西，最后是主控建议的第一版和要你定的事。数字来自本机会话统计和 P2-81 / P2-176 / P2-248 的记录。

一句话版
  1. eval 就是：一批固定的题，每题从同一个起点开始，没人插手地跑完，用 agent 看不到的检查脚本判分，每题跑几次，再和上一版或别家比。
  2. canter 已经有一半零件：遥测和 canter stats 能记下过程（上下文、压缩、缓存、工具、花费），P2-81 的长程试跑就是一次手工 eval。缺的是：题目写成文件、判分写成脚本、跑法固定下来、结果自动出表。
  3. 你提的「Opus 主控用 corral 派题给 canter」可行，而且比 canter exec 更合适跑长程：能按时插话、多轮对话、能 attach 上去看。判分仍要交给脚本，不靠主控的感觉。
  4. 建议第一版只做三组题（长程、子 agent 调研、记忆），每题跑 3 次，DeepSeek 一轮全跑完约 1～2 美元、约 3 小时。

1. eval 要回答什么

agent 的表现 = 模型 × 外壳（canter：提示词、工具、压缩、护栏、子 agent……）。canter 能改的只有外壳，所以 canter 的 eval 主要回答两个问题：

A. 回归：这一版比上一版变好还是变坏？
同一批题、同一个模型，换 canter 版本跑。改了提示词、压缩、工具说明之后，靠它知道是不是真的变好了，而不是「感觉好了」。这是最该先有的。
B. 水平：canter 和 Codex、Claude Code 比怎么样？
同一批题换 agent 跑。差距大多来自模型，要比外壳就得用同一个模型——但别家不一定能接 DeepSeek。偶尔做一次就够。

P2-252、P2-253 那次的教训也算 eval 的一种：拿本机已有会话做统计，能回答「这个改动有没有收益」。eval 是在这之上再加「固定的题 + 判分」，用来回答「改完之后是不是更好了」。

2. 一次 eval 的七个零件

① 任务集真实的活，写成文件：提示词、起点、判分方法
② 固定起点同一个提交、空的记忆、一次性的拷贝，跑完就扔
③ 无人值守地跑不弹批准框；要插话就按预定时间插
④ 判分agent 看不到的检查：测试、类型检查、git 记录、文件内容
⑤ 记录过程每次请求的上下文、压缩、缓存、工具、花费
⑥ 重复每题 3～5 次，看通过率和波动
⑦ 对照和上一版、别的模型比；失败分「模型的」「canter 的」

几个容易做错的地方

  • 判分要 agent 看不到。检查脚本放在拷贝外面，跑完再拷进去执行。agent 看得到就可能「对着答案做」，或者改测试让它过（SpecBench 专门测这个）。
  • 只跑一次说明不了什么。同一题同一版本，模型每次走的路都不一样。P2-248 测子 agent 时，第三次 13 分半，第九次从派出到合并约 6 分 40 秒，提示词改动和运气都混在里面。3 次是最少，看「3 次都过」比看「过了 1 次」更说明可靠。
  • 起点要干净。P2-81 已经踩过：dist/ 里旧的编译结果被模型抄了；记忆里留着上一轮的东西会帮它作弊。
  • 花费和时间也是成绩。两版都做对了，便宜一半、快一半的那版更好。
  • 要能看回放。分数掉了，得能打开那次会话看是哪一步出的事——canter 会话本来就留盘，canter -r <id> 就能打开。

4. 公开 benchmark 能测什么

名字测什么对 canter 的用处
SWE-bench Verified / Pro真实 GitHub issue，改代码让隐藏测试通过。Python 仓库为主。业界最常引用的分数，能和别家比；但成绩主要看模型，每题都是短活，不测压缩、插话、缓存。
Terminal-Bench 2.0终端里的各种活（编译、配环境、数据处理……），Docker 里跑，官方框架 Harbor，用 --agent-import-path 接自己的 agent。排行榜上有 Codex、Claude Code。最适合拿来和别家比「整体水平」。接 canter 要写一小段适配器（Python），主控倾向放 canter 仓库外的单独 eval 仓库。
LongCLI-Bench、SWE-EVO、RoadmapBench、NL2Repo-Bench长程：一件活要几十上百步。方向对，但多是预印本、没有公认标准；一件可能一小时，真调模型很花时间。
SpecBenchagent 会不会钻空子骗过测试。提醒判分要防作弊，不必跑。
CL-Bench（Anthropic 记忆文章用的）连续很多题，看 agent 能不能用记忆越做越好。记忆 eval 的思路可以照搬（见第 8 节）。
结论：公开 bench 只回答「做没做完」，而且分数大多由模型决定；canter 自己改的东西（压缩、插话、子 agent、缓存、护栏）它们测不到。所以主力是 canter 自己的小题集，每版都跑；公开 bench（首选 Terminal-Bench 2.0）偶尔跑一次，看和别家的差距。

6. 怎么跑：canter exec 还是 corral 派 canter

你提的做法：Opus 主控（就是现在这个 Claude Code）用 corral 开 canter --yolo，一题一个，跑完收结果。和 canter exec 比：

corral 派 canter（你提的）canter exec
走的路和你日常用的完全一样（终端界面、批准、子 agent 叫醒）略有不同：exec 下子 agent 要 wait_agent 等，不靠叫醒
中途插话能：corral send 按预定时间插不能：只跑一轮
多轮对话（记忆题、子 agent 题要）能要用 --resume 一轮一轮接
跑的时候能看能：corral attach，或在 paddock 里看只能看输出
知道跑完了corral wait 等到 idle；要防「模型停下来问问题」也算 idle进程退出，有退出码
拿会话 ID--session-fileJSONL 结果里有
谁来编排Opus 主控照一份写好的流程做；基本不用写代码一段脚本（canter 规矩：不用 Python，写 Rust 或 shell）
可重复要靠流程写死：插话时间、判分命令都写进题目文件，主控只照做天然可重复
额外花费主控用的是你的 Claude 订阅（编排和归因，不是被测的模型）无
主控建议：用 corral 当主路。长程题要插话、子 agent 题和记忆题要多轮，这些 exec 都做不了，而且 corral 跑的就是你平时用的那条路。为了可重复，把「做什么」全写进题目文件（提示词、起点提交、插话的时间点和原文、判分命令），主控只负责照着派、照着插、跑判分、填表；主控不打分，只在失败时看回放，判断是「模型的」还是「canter 的」问题。
exec 先不用，等以后要接 Terminal-Bench 再说（它的框架是一条命令一个任务）。

一题跑一次的样子

# 1. 固定起点：eval 仓库里开一个新 worktree（共用信任，不弹框）
git -C ~/evals/canter-test-ts worktree add /tmp/eval/long-1 8e19ca8
# 2. 开 canter，记下会话 ID
corral start eval/long-1 --cwd /tmp/eval/long-1 --prompt "<题目文件里的提示词>" \
  -- canter --yolo --tag eval=2026-11-xx --session-file /tmp/eval/long-1.session.json
# 3. 按题目文件里的时间点插话（比如：第 2 件提交后）
corral send eval/long-1 "<插话原文>"
# 4. 等它停下，判分（脚本在 worktree 外面，agent 看不到）
corral wait eval/long-1 ... ; ~/evals/checks/long.sh /tmp/eval/long-1
# 5. 取过程数据，写一行结果；关掉、删 worktree
canter stats <会话ID> --json > results/long-1.json
corral stop eval/long-1; git worktree remove /tmp/eval/long-1

「第 2 件提交后」这种时间点，主控靠看 git log 判断；也可以简化成固定的几分钟后插。具体放进方案里定。

7. 把子 agent 那几次测试变成 eval

P2-248 里同一个调研问题（「对比 /tmp/codex 和 /tmp/pi-mono 怎么处理工具调用超时」）测了 9 次，每次都是你手工跑、我手工翻记录。下面这些当时人工看的东西，全能写成自动检查：

当时看的自动检查数据从哪来
派出后能不能接着聊开子 agent 那一轮在 N 秒内结束（第九次是 15 秒）stats：轮的开始、结束时间
闲聊时会不会干等你插话的那几轮里没有 wait_agent会话事件
会不会谎称报告到了回复里说「报告到了」之前，那个子 agent 的结果确实已经送到事件先后（这一条最难写，可以先人工看）
子 agent 命令被拦被拦 0 次会话事件 blocked
子 agent 有没有扩大范围、主会话有没有自己重查子 agent 请求次数、主会话在等待期间的读文件次数不超过上限stats 的 subAgents、tools
花费、用时和上一版比没有明显变差stats
最后答得好不好答案里提到了几个必须有的点（文件名、默认超时数值）判分脚本对答案做关键词检查

当时你在中间发的 4 句话（「谢谢」之类），写进题目文件，按时间点用 corral send 发，就能每版都重放一遍。

8. 记忆的 eval（P2-256 并进来的）

照 Anthropic 文章的做法：同一个仓库连着做几件相关的活，每件开一个新会话，比「记忆开」和「记忆清空」两种。

  • 题目例子：canter-test-ts 上连着做 4 件，后面的活要用到前面踩过的坑（比如「提交末行写 Task: N/12」这种只在对话里说过、代码里看不出来的约定）。
  • 看：后面几件是不是更快、更少犯同样的错；模型有没有去读记忆；写下的记忆有没有重复、有没有错。
  • 本机现在的数据：模型一共只写过 6 次记忆，3 条重复，从没读过细节——量太少，eval 正好能补上。
