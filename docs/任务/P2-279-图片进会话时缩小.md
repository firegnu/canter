# 任务：图片进会话时缩小

依据：11-11 canter-desktop 开发 GPUI 界面时截了 14 张 Retina 截图（每张 1～2 MB 的 PNG，共约 20 MiB），都在 40 MiB 的近期图片预算内，每次请求都整批重发（base64 约 27 MB）。同一模型（deepseek-flash，high）在上下文 15～30 万时，没有图的 P2-278 会话平均 2.7 秒开始回话，canter-desktop 要 12 秒，图多了以后 27～35 秒；文字缓存命中 99.9%，慢在图片上。本轮只在图片存进会话时缩小一次，不改保留预算、单张上限和 token 估算。
待用户：先别派；等 canter-desktop 做完手上的任务、用户关掉它，再开新会话之前派

## 用户原话

- 11-11（主控查出慢在图片上）：「我理解你的意思，我不需要马上见效，我可能会关了canter-desktop的主控，等你修复这个问题之后再开新session来做」
- 11-11：「不开新会话。也不改agents.md。我觉得就是正常跑。我不能workaround问题。」
- 11-11：「都按你的建议来。」「先别派，我要等canter-desktop把现在的任务做完，我会关掉它。再开新的canter session来做接下来的任务。」

## 要做的

1. 图片存成会话副本（`image-<随机名>.<格式>`）之前，长边超过 1568 像素的，等比缩到长边 1568。三条来源都算：用户附的图（P2-5）、`read` 和 MCP 返回的图（P2-130）、PDF 按页转出的图（P2-226）。
2. 缩小只在存副本时做一次。之后每次请求发的都是这份副本，请求字节不再变（DESIGN 第 17 条）。
3. 格式不变，PNG 还是 PNG，JPEG 还是 JPEG。缩完反而比原文件大、或者解不开的，存原图，照旧能用。动图（GIF、动画 WebP）不缩，存原图。
4. 单张 8 MiB 的上限照旧按原图算，40 MiB 预算、每张 1024 token 的估算、不收图模型的占位、卡片和导出都不变；卡片上显示的大小是副本的大小。
5. 解码和缩放不卡住服务端，别的会话照常收发。
6. 各家模型一样处理，不按模型或服务商分支（DESIGN 第 23 条）。

## 用户定的（11-11：「都按你的建议来」）

1. **已经存在的会话里的旧图**（选 B，DESIGN 第 17 条的例外由做的人补一句）（比如 canter-desktop 现在那个会话的 14 张）：
   - A：不动。旧会话里的旧图照旧发原图，只有新进来的图缩小。缓存不受影响，但 canter-desktop 那个会话要等那些图被压缩挤出去才会变快，照常用下去就一直慢。
   - **选 B**（主控建议）：旧会话里超过 1568 的旧图，第一次发请求前另存一份缩小的副本，以后请求都用缩小的那份；原图留在会话目录里不删。那个会话立刻变快，照常用下去就行。代价是请求前面的内容变一次，缓存冷一次（同压缩、换模型那类例外，DESIGN 第 17 条要加一句）；按 canter-desktop 那个会话最近一次请求约 30.7 万输入 token、deepseek-flash 未命中价每百万 $0.30 算，多花约 $0.09（白天高峰价翻倍，约 $0.18），只发生一次。
2. **1568 这个数**：取自 Anthropic 的看图文档，长边超过 1568 像素的图，服务端会先缩小再看；界面文字在这个尺寸下看得清。要更清楚可以放到 2048，代价是图大一些。**定 1568**，固定写死，不做配置项。

## 不要做

- 不改 40 MiB 预算、单张 8 MiB 上限和 token 估算，不改成「只留最近几张」。
- 不改别的格式（比如 PNG 转 JPEG）。
- 不改 P2-5、P2-130、P2-226 以外的图片行为，不加配置项。
- 不按模型或服务商分支。
