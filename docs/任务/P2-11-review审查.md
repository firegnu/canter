## 要做的

- **审什么**：
  - `/review`：会话目录里还没提交的改动，包括已暂存、未暂存的 diff，加上未跟踪文件的列表。不在 git 仓库里、没有改动时提示一句，不发。
  - `/review <PR 号>` 或 `/review <PR 网址>`：用 `gh pr view`（标题、说明、目标分支）和 `gh pr diff` 取 PR 的改动。不 checkout，不动工作区。没装 `gh`、没登录、PR 不存在、不是 GitHub 仓库时提示一句（带 gh 的报错原文），不发。
  - 取改动的命令照 P2-8 的办法跑：不拿锁、有超时、隔离全局 git 配置、关掉会起程序的设置。diff 太大（超过一个固定上限，你定，比如 256 KiB）时只带 `--stat` 和前面一段，并在消息里写明「已截断，需要时用读文件工具看」。
- **怎么发**：把「审查要求 + 审查对象说明 + 改动内容」拼成一条用户消息，在当前会话里开一轮，模型的回答就是审查结果，留在会话历史里（之后可以接着说「改第 2 条」）。对话区不显示整段拼好的消息，只显示一行 `Review: uncommitted changes` 或 `Review: PR #123 <标题>`。
  - 审查要求用英文自己写，短一些：只报这次改动引入的、有实际影响的问题（正确性、安全、性能、可维护性）；每条写严重程度、文件和行、问题、为什么、怎么改；按严重程度排；最后一句总结能不能合并；没有问题就直说。可以参考 Codex `review_prompt.md` 的结构，但不整段搬；如果搬了原文，按 `CLAUDE.md` 注明来源并保留许可证。
  - 审 PR 时在消息里说明：本地工作区可能不是 PR 的代码，读本地文件只作参考。
- **只读**：这一轮里改文件的工具（写文件、改补丁）和白名单以外的 shell 命令一律直接拒绝，不弹批准框；「本会话都允许」也不放行。拒绝时给模型的结果写明「review is read-only」。白名单里的 shell 命令和读文件照常可用。这一轮结束后恢复原来的权限。这一轮在协议里要能看出是审查轮（比如输入或 turn 上加一个可选字段，你定），旧客户端照常。
- **其它**：主线一轮正在跑时，`/review` 和普通消息一样排队。加进 `/` 命令列表和 `/help`。
