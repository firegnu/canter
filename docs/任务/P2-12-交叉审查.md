### 意见

1. **必须改（泄露凭证）——MCP 的 HTTP 客户端走环境代理，本机明文地址的请求头会明文交给代理**
   - 位置：`crates/canter-tools/src/mcp.rs:323-327`
   - 问题：reqwest 默认读 `HTTP_PROXY` / `http_proxy` / `ALL_PROXY`，不会自动绕过 127.0.0.1 / localhost。服务端从终端直接起时（DESIGN 第 16 条的升级办法 `canter serve --replace`，或手动 `canter serve`）继承终端环境；终端里 export 了 http_proxy 时（常见），发往 `http://127.0.0.1:…/mcp` 的 initialize、tools/call 连同 `headers` 里的 key 一起明文发给代理。代理在别的机器（公司代理，或本机代理全局模式转发出去）时，key 以明文离开本机，「仅本机允许明文」这条规矩失效。客户端后台起的服务端会 `env_clear`，不受影响，所以同一份配置在两种启动方式下行为不同（经代理时本机服务往往还连不上）。实测：临时测试把 `HTTP_PROXY` 指向本机一个监听端口，`Registry::connect` 连 `http://127.0.0.1:9/mcp`，监听端收到 `POST http://127.0.0.1:9/mcp`，请求头里有 `authorization: Bearer test-only-review-secret`。模型客户端（`crates/canter-model/src/chat_completions.rs:71-72`）和 discovery（`discovery.rs:36`）都写了 `.no_proxy()`；任务书写的「照模型地址的规矩」应包括这一条。
   - 改法：builder 加 `.no_proxy()`，和模型客户端一致（后台起的服务端本来就没有代理环境，常用路径不受影响）。补一个测试：服务端环境带 `HTTP_PROXY` 指向测试自己起的监听端口，本机 HTTP MCP 照常连上，监听端收不到连接。README「MCP」一节写一句不走代理。

2. **建议改（最好这次一起改）——所有 env 值都当密钥替换，普通短值会弄乱结果；`Bearer <token>` 只回显 token 时又替换不到**
   - 位置：`mcp.rs:131-137`（收集要替换的值）、`mcp.rs:239-245`（`public`）、`mcp.rs:441`（结果文字）
   - 问题：`env` 里每个非空值都参与替换。实测配置 `"env":{"DEBUG":"t"}` 时，假服务返回的 `stdio result` 到模型那里成了 `s[redacted]dio resul[redacted]`。后台起的服务端环境里只有 CANTER_HOME（见第 3 条），用户多半要在 `env` 里写 PATH、HOME；写了 `"HOME":"/Users/<用户名>"`，文件类 MCP 返回的每个路径都会变成 `[redacted]/…`，模型拿这种路径再调用就会出错。反过来，请求头最常见的写法 `Authorization: Bearer <token>` 只替换整串 `Bearer <token>`；服务回显里只有 token 时（比如「invalid token xxx」）不会替换，照样进模型请求和事件文件。
   - 改法：对每个配置值和它按空白切开的每一段，只替换长度到下限的（比如 ≥ 8 字节），短值不替换。补两个测试：短 env 值不改结果；`Bearer <token>` 里的 token 单独回显时会被替换。

3. **建议改——stdio 子进程拿到什么环境，取决于服务端是怎么起的；README 没写**
   - 位置：`crates/canter-server/src/discovery.rs:135-136`（后台起服务端时 `env_clear`，只留 CANTER_HOME）、`mcp.rs:295-300`、`crates/canter-server/README.md:209`
   - 问题：客户端后台起的服务端，MCP 子进程只有 `CANTER_HOME` 和配置里的 env，没有 PATH、HOME：`"command":"npx"`、`#!/usr/bin/env node` 这类脚本起不来，只报「could not start MCP process」或「MCP initialization failed」，stderr 又被丢掉，用户很难查。终端里 `canter serve --replace` 起的服务端则把整个终端环境（含终端里的各种令牌）交给每个 MCP 子进程。同一份配置在升级前后表现不同；CANTER_HOME 也传给了子进程。
   - 改法：最少在 README 写清楚：后台起的服务端环境是空的，`command` 写绝对路径，需要的 PATH、HOME 写进 `env`。更好的办法是子进程用固定环境：`env_clear()` 后只放一小组基础变量（参考 Codex 的 MCP 默认白名单：HOME、PATH、USER、LOGNAME、SHELL、TMPDIR、LANG 等，服务端环境里没有的就不放），再加配置里的 env，不传 CANTER_HOME。这样改会让行为和现在不同，由主控定。

4. **建议改——一次 HTTP 请求失败就把服务永久标成断开，连接其实还活着**
   - 位置：`mcp.rs:415-418`
   - 问题：调用返回 `TransportSend` / `TransportClosed` 时调 `disconnected()`，peer 置空，之后再也不恢复；监视任务和 rmcp 连接并没有停。实测：假 HTTP 服务对一次 tools/call 回 503，之后恢复正常；`/v1/mcp` 一直显示 `connected:false`、`error:"MCP connection failed"`，SSE 订阅却还挂着（receiver_count = 1），之后新建的会话请求里没有这个服务的工具，要重启服务端才回来。远端偶尔一次 5xx（重启、网关抖动）就让这个服务对所有新会话下线，状态和实际不一致，也和完成记录里「断开不自动重建」说的「断开」不是一回事。
   - 改法：单次调用失败只作为工具错误返回，不改连接状态；「断开」只在监视任务看到 `waiting` 结束（或 `is_transport_closed()`）时设。如果坚持失败一次就下线，至少同时 cancel 这条连接，让状态和资源一致。现在用 503 模拟「断开」的测试（`crates/canter/tests/support/mcp.rs:491-522`）改成真的断开：比如杀掉 stdio 假服务进程后再调用，断言回「MCP service disconnected」、这一轮正常结束。

5. **可以不改——超时测试真等 120 秒**
   - 位置：`crates/canter/tests/support/mcp.rs:588-637`
   - 问题：`canter` 的 server 测试从几秒变成约 130 秒，全套测试每次多等两分钟。
   - 改法：要缩短就得给调用超时开个口子（配置项或环境变量），任务书没要这类配置，这次可以不动；以后嫌慢再单独做。

6. **可以不改——每次建会话、开会话都对重名工具再写一行日志**
   - 位置：`mcp.rs:178-183`
   - 问题：`update()` 在连接和刷新时已经记过；`snapshot()` 每开一个会话再记一遍跨服务重名，server.log 随会话数增长。
   - 改法：跨服务重名在 `update()` 或 `status()` 里只记一次，`snapshot()` 里不打印。

7. **可以不改（提醒 P2-29）——启动时等 MCP 拉长了「持有 server.lock 但还没登记」的窗口**
   - 位置：`crates/canter-server/src/lib.rs:74-84`
   - 问题：MCP 连接夹在拿到 server.lock 和发布登记之间，最长 10 秒（以前是毫秒级）。这期间别的客户端调 `ensure_server` 会多起一个 `canter serve`，它报「a server is already running」后退出，客户端照常等到登记出现，功能没问题，只是 server.log 多一行。
   - 改法：本分支不用改；P2-29 改锁检查时把这个窗口考虑进去。

### 重点各条的结论

1. **权限**：没有绕过闸门的路径。参数不是 JSON 对象时，`prepare_named` 在闸门前就返回失败，不执行；`Tool::Mcp` 不在 `Tool::ALL` 里，模型叫 `mcp` 会按未知工具处理；内置名字先匹配，MCP 名字都以 `mcp__` 开头，碰不到内置名；会话内快照已去重，一个完整名字只对应一个服务的一个工具。闸门里 `Tool::Mcp` 风险是 Execute：一直问、问执行两种模式弹框，全都允许直接跑，只读 shell 那条豁免只认 `Action::Shell`。会话授权的键是完整工具名，内置工具的键是 `read` / `shell` 等，互相借用不了。审查轮 `evaluate_review` 对 MCP 一律 Deny，参数错误也改写成 `review is read-only`、Declined，不开批准请求；测试覆盖了这几种情况。批准框显示「Allow MCP 服务 / 工具?」加参数。
2. **凭证**：配置解析错误统一是「config.json is not valid」，校验、连接、协议错误都是固定文字；stdio 子进程的 stderr 丢弃；`/v1/mcp` 只有名字、状态、工具名和固定的警告文字；配置类型没有 Debug / Serialize；SDK 日志没有出口；测试里用的都是 test-only 占位值。问题只在第 1 条（代理）和第 2 条（服务回显的脱敏）。
3. **工具列表固定**：只有 `create` 和未打开时的 `resume` 调 `App::runtime()` 取快照；`State.tool_definitions` 在 `from_state` 时定下，普通请求、/btw、/context 估算都用它，压缩请求本来就不带工具；通知只更新服务目录，断开也只影响调用结果，列表和顺序不变（内置五个在前，MCP 按完整名排序）。重新打开才更新，有测试。断开时调用立即回错误：peer 为空时直接返回；调用中途传输关闭由 SDK 立刻失败；服务卡住时最多等 120 秒超时。
4. **子进程和启动**：正常退出、`--replace`、启动握手中收到信号、握手失败或超时、列工具失败，都会关闭 rmcp 连接并 `killpg` 原进程组（测试覆盖了前三种，后两种看代码）；旧服务端在放掉 server.lock 之前就收完了 MCP 子进程，新旧两批不会同时在跑。服务端在 `serve` 中途报错返回时，靠运行时退出时丢弃任务、触发 `ProcessGroup` 的 drop 和 `kill_on_drop` 回收。启动时各服务并行连接，共用 10 秒截止，几个慢服务不叠加，在客户端 15 秒的等待以内；终端断线后每 0.5 秒重连、不设上限，`--replace` 期间的 10 秒窗口不会让终端掉线。
5. **调用和兼容**：Esc 和超时都会让 SDK 发取消通知（HTTP 测试断言了）；文字照 32 KiB 头尾 / 客户端 1 MiB 截断，非文字给占位行，`isError` 和协议错误都按失败返回，这一轮继续。`mcpToolCall` 是新加的变体，旧客户端按 `#[serde(other)] Unknown` 忽略；旧会话没有这种项，打开不受影响；重启后没完成的调用由 `complete_missing_tools` 补上结果，项状态改成 Failed、这一轮记为 Interrupted。依赖只新增 rmcp 及它带进来的包，没有升级已有依赖。
