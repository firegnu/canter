### 核对了什么

- **crossterm 0.29.0 的死循环属实。** `src/event/source/unix/mio.rs` 95–120 行的内层 `loop`：`read` 返回 `Ok(0)`（EOF）时没有事件，接着读；返回的错误不是 `WouldBlock` / `Interrupted`（比如 EIO）时也不 break，接着读。149 行的超时检查在内层循环外面，所以 `poll(Duration::ZERO)` 也出不来。Codex 留的采样 `/tmp/p2-87-stuck.sample` 里，读线程 575/575 个样本都在 `poll_internal → try_read → FileDesc::read → read`，而且落在不同指令上，是忙等空转（占满一个核），不是阻塞在一次 `read` 上。竞态窗口在读线程原生 `poll` 返回、crossterm 的 mio `kevent` 开始之间，机器忙时线程被抢占，窗口变大，和「只有全套并行时才失败」对得上。
- **本机 macOS 实测**（scratchpad 里的小 Rust 程序，在 `script` 开的 PTY 里跑，零等待 `poll(POLLIN)`）：活着的 PTY 从端空闲时 revents=0，有一个没读的字节时也是 0（规范模式）；关掉主端后是 0x11（POLLIN|POLLHUP）；`/dev/tty` 和它 dup 出来的描述符一律 0x20（POLLNVAL）。
- **跑过的验证**（编译目录 `.target/review-p2-87-picker-exit`）：新单元测试、12 条状态栏和信号退出测试、`/exit` 测试，共 14 条全过；全套 `cargo nextest run --all-targets` 一轮 704 条全过（两条目标测试 0.544 s / 0.555 s）；`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 都过。Codex 的红测日志 `/tmp/p2-87-red.log` 里，新测试在没加检查的代码上 2.012 s FAIL。

### 重点 1：会不会误退出

不会多出新的误退出。

- stdin 是终端时（Ghostty、iTerm2、tmux、screen、SSH 里直接跑）：监视用的描述符是 stdin 的 dup，和读线程 poll 的是同一个打开的文件，revents 取决于终端本身，跟哪个描述符无关。`POLLHUP` / `POLLERR` 只在主端全关时出现：终端窗口关掉、tmux pane 被杀、sshd 断开。tmux / screen 脱离时，服务端还开着主端，不会报。`POLLNVAL` 在 Input 自己持有、一直开着的描述符上不会出现。
- 已装的 main `8c29af9` 里，读线程从 P2-60 起就对同一个文件用同一个判断（`terminal_input_open`，三种标志都算挂断，报错也算），判成挂断就结束线程、关掉通道、canter 退出。正常终端要是会误报，用户早就碰到了。新检查调的是同一个函数，判断条件没变，只是调得更频繁。
- stdin 不是终端时（HANDOFF 那条）：`/dev/tty` 在 macOS 上一律报 `POLLNVAL`（实测）。改之前，读线程第一次 poll 就结束、关掉通道，`recv` 收到 None 后退出；改之后，`Input::recv` 第一次检查就返回 None，结果一样。现在仍然先卡在 `supports_keyboard_enhancement`，到不了这里；前面那个问题修好以后，改前改后都是一启动就退。这个改动没有把原来「碰不到」的情况变成新的启动即退出，但给 HANDOFF 里的修法多加了一处要改的地方，见建议改 1。

### 重点 2–4 的核对

- **读线程怎么收场**：修法只是让外面绕过了卡住的读线程，读线程本身救不回来（除非改 crossterm，任务不许）。从挂断开始，读线程一直空转：最多 50 ms 后被发现，接着是收尾、`stop` 的 100 ms 上限、main 写一行 `To resume`、运行时退出，然后进程结束，线程随之消失。`run` 返回后 main 一定退出，所以空转线程不会活过进程。这个线程拿着 crossterm 的事件读锁，但收尾时恢复终端、清标题只写不读，不会死锁。
- **并发**：`Input::recv` 里的 `select!` 在 `events.recv()` 和 50 ms 定时之间选，`mpsc::recv` 取消安全，不会丢事件。外层 `biased` 的先后没变：信号、输入、消息、定时。外层每轮都重建 recv 的 future，第一次 poll 就同步查一次挂断，所以连续来消息时查得更勤，不会饿死。50 ms 定时到点只在 recv 里面转一圈，外层 select 不会因此结束，不会多画帧。帧号是读线程发事件时打的，recv 原样交出。
- **清理**：对话主循环收到 None 后 `quit` → 跳出循环 → `pump.abort`、`cancel_btw`、`stop_status_line`、`leave_tab`；启动时的列表 → `Pick::Exit` → `leave_tab`；`/resume` 列表 → `ControlFlow::Break` → 同一段收尾；之后 `reader.stop`，`TerminalSession` 析构时恢复终端。都和 SIGHUP 那条路一样。监视描述符用 `try_clone`（`F_DUPFD_CLOEXEC`）得到，不会漏进状态栏脚本的子进程。
- **新测试**：它复现的是竞态的后果（真实 PTY 挂断，发送端一直活着），不是竞态本身。不往代码里植入延时，没法稳定复现竞态，这样做合理。没加检查时 `recv` 就是 `events.recv()`，测试手里拿着发送端，recv 永远不返回，一定超时，所以不是「一定会过」的路，红测日志也证实了。原来那两条集成测试仍然覆盖真实路径。

### 意见

1. **建议改**：HANDOFF 那条「已知没修的问题」（stdin 重定向、`POLLNVAL`），主控合并后改 HANDOFF 时补一句。位置：`run.rs:198`（`Input::recv`）、`run.rs:1555`（`terminal_input_open`）。问题：HANDOFF 写的修法是「让读线程在 POLLNVAL 时退回原读法」，但现在 `Input::recv` 也调 `terminal_input_open`，`/dev/tty` 上第一次就返回 None。只改读线程的话，canter 照样一启动就退。改法：在 HANDOFF 那条注明两处都要改，比如 `Input::recv` 碰到 `POLLNVAL` 或 poll 报错时设 `self.tty = None`，退回只等通道。读线程卡住只会发生在真挂断之后，那时监视描述符报的是 `POLLHUP`，所以这样改不会漏掉挂断。现在这条路碰不到，这次代码可以不动。顺带一提：XNU 的 `poll` 是用临时 kqueue 实现的，内核分配失败时会报 EAGAIN，`unwrap_or(false)` 会把它当成挂断，让 canter 退出。读线程原来就是这样，新检查只是调得更频繁，概率很低，可以和上面那条一起处理。
2. **建议改**：`run.rs:1561` 的 SAFETY 注释。问题：「`tty` remains owned by the reader for the duration of this call.」现在 `Input::recv` 也拿 Input 自己的描述符调这个函数，「owned by the reader」不对了。改法：改成「the caller keeps `tty` open for the duration of this call.」，一行。
3. **可以不改**：挂断时，通道里已经排着的按键会被丢掉。位置：`run.rs:198`，先查挂断，后读通道。问题：主循环在 await（换会话、调接口）期间攒下的按键，如果下次 recv 之前终端挂断了，会直接返回 None，这些键不再处理。改之前，读线程没卡住的话，会先把它们交给主循环，再关掉通道。不过 SIGHUP 那条路（`biased` 先看信号）本来就丢这些键，真实终端关窗口大多走 SIGHUP，现在两条路一致了。真要改：循环开头先 `try_recv`，没有排着的事件再查挂断。
4. **可以不改**：挂断后读线程空转到进程退出，大约 150–200 ms，占一个核。位置：`TerminalReader::stop`（`run.rs:1537`）。不改 crossterm 就收不了，进程随即退出，不算留下空转线程。
5. **可以不改**：同一个 crossterm 死循环在启动时也可能撞上，不在本件范围内。`supports_keyboard_enhancement` 走 `poll_internal`，最多等 2 秒，用的是同一个 `try_read`。启动查询那一下要是正好碰上挂断，主线程会卡在里面，新检查管不到（那时还没进 `recv`）。窗口只有一次终端往返。HANDOFF 里「stdin 重定向时卡在查询键盘增强、CPU 100%」的现象，也和这个循环对得上（我没核实）。主控可以考虑在 HANDOFF 那条里记一笔。
6. **可以不改**：新测试只覆盖会话列表 `pick`，对话主循环那一处 `input.recv()`（`run.rs:406`）没有单独的测试。两处调的是同一个方法，改动只有一行，任务也只要求一条针对原因的测试。

### 对完成记录里取舍的表态

- **每 50 ms 轮询：同意。** crossterm 的死循环从外面打断不了，只能另外检查。读线程原本就每 50 ms 醒一次，空闲时唤醒从每秒约 20 次变成约 40 次，开销可以忽略；最多 50 ms 才发现挂断，用户感觉不到，离测试的 2 秒也很远。别的办法更差：用 tokio `AsyncFd`（kqueue）的话，macOS 上 `/dev/tty` 注册不了，而且有没读的输入时会一直报可读；另开一个线程阻塞 poll 的话，macOS 上没法只等挂断，有没读的输入时会空转。
- **`POLLNVAL` 也算挂断：现在可以接受，但含义不对。** 走 stdin 时不会出现；走 `/dev/tty` 时 macOS 一律报它，意思是「这个描述符没法 poll」，不是「终端挂了」。目前和读线程的判断一致，这条路也碰不到，所以这次不用动；HANDOFF 要补一句，见建议改 1。
